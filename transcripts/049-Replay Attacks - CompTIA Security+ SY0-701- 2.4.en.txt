A replay attack occurs when an attacker captures valid authentication data, session tokens, or other credentials transmitted over a network and later retransmits that same data to gain unauthorized access. The defining characteristic of a replay attack is that the captured data itself is legitimate and cryptographically valid. The attacker does not need to break the underlying encryption or forge credentials. The data was correct when it was originally transmitted, and it remains correct when replayed. The attacker's advantage is simply that they possess this valid data and can reuse it outside of its intended context or time window.

To perform a replay attack, an attacker first needs a method to capture the relevant authentication exchange. Common capture techniques include placing a physical network tap on the wire, using ARP poisoning to redirect traffic through the attacker's machine, or installing malware on the victim's system that captures credentials or session data before or after encryption. Once the attacker has the captured material, they replay it to the server at a time of their choosing, and the server, seeing perfectly valid authentication data, grants access as if the legitimate user were connecting. The replay attack itself does not require the attacker to be positioned on the network path during the attack; they can capture material once and replay it many times from anywhere.

Pass-the-hash is one of the most operationally significant forms of replay attack, particularly in Microsoft Windows environments. When Windows authenticates users to network resources using NTLM, the NT LAN Manager authentication protocol, the user's password hash is used directly as the authentication credential in the challenge-response exchange. The client proves knowledge of the password hash without transmitting the hash in cleartext, but the hash itself is functionally equivalent to the password for authentication purposes. An attacker who obtains a user's NTLM hash does not need to know the plaintext password. They can authenticate to any system that accepts NTLM using the hash directly. This technique, called pass-the-hash, is widely used for lateral movement in Windows domain environments. An attacker who compromises a workstation can extract NTLM hashes from the LSASS process memory using tools such as Mimikatz, then use those hashes to authenticate to other workstations, servers, and services across the domain, progressively expanding their access without ever cracking a single password. The hashdump module in Metasploit provides similar functionality for extracting hashes from a compromised system.

Pass-the-ticket applies the same conceptual approach to Kerberos environments. Kerberos authenticates users by issuing tickets, which are cryptographically signed tokens that the client presents to services to prove authentication. The Ticket Granting Ticket, or TGT, is issued by the Key Distribution Center after initial authentication and allows the client to request service tickets without re-entering credentials. An attacker who extracts a TGT or service ticket from memory on a compromised machine can import that ticket into their own session on a different machine and use it to authenticate to any service the original user could access, for as long as the ticket remains valid. The Golden Ticket attack is a particularly severe variant. If an attacker obtains the NTLM hash of the KRBTGT account, the special Kerberos account whose key is used to sign all TGTs in the domain, they can forge arbitrary TGTs for any user, including domain administrators, with any desired validity period. Golden Tickets provide persistent, domain-wide administrative access and are extremely difficult to eliminate because the KRBTGT password hash must be changed twice in succession to invalidate all outstanding forged tickets. Silver Ticket attacks forge service tickets for specific services using the service account's hash, providing access to that specific service without interaction with the domain controller.

Kerberos incorporates anti-replay mechanisms through its use of timestamps and authenticator tracking. Every Kerberos authentication request includes a timestamp, and the KDC requires that this timestamp fall within a configurable clock skew window, by default five minutes. A replay of an authenticator from more than five minutes ago will be rejected. Within the clock skew window, the KDC maintains a list of recently seen authenticators and rejects any that have already been used, preventing immediate replay of a captured ticket.

The broader category of anti-replay mechanisms includes several distinct approaches. Nonces are numbers used once: a random value generated by the server and included in the authentication challenge. The client must incorporate the nonce into its response, and the server rejects any response that does not include the current nonce, making previously captured responses useless. Timestamps require that authentication requests include a current time value within an acceptable window, making old captures invalid. Sequence numbers assign a monotonically increasing number to each packet in a protocol session; the receiver accepts packets only in order and rejects duplicates or out-of-sequence packets. Challenge-response protocols require the server to issue a fresh random challenge each time authentication is performed, so a captured response is only valid for the specific challenge that generated it. Short-lived session tokens with expiration times require clients to re-authenticate frequently, limiting the window during which a captured token can be used.

TLS version 1.3 includes anti-replay protection for zero-round-trip resumption. When a client attempts to reconnect using a pre-shared session ticket, TLS 1.3 includes mechanisms to detect and reject replayed connection attempts. Older versions of TLS and some DTLS implementations have had vulnerabilities related to replay protection gaps. WPA2 TKIP, the Temporal Key Integrity Protocol that served as the initial replacement for WEP, had known replay vulnerabilities that contributed to its deprecation. WPA2 using CCMP, the Counter Mode with Cipher Block Chaining Message Authentication Code Protocol based on AES, includes per-packet sequence numbers that provide replay protection.

OAuth access tokens and JSON Web Tokens are common replay targets in web and API authentication. Bearer tokens, named for the fact that any bearer of the token is granted access, provide no inherent binding to the legitimate client. An attacker who captures a Bearer token from an Authorization header can use it to call any API endpoint accessible to that token until it expires. Defenses include short token expiration times that minimize the window for replay, token binding that cryptographically binds tokens to a specific TLS connection so they cannot be used from a different connection, and the PKCE extension to OAuth flows that prevents authorization code interception and replay. JWT attacks include the algorithm confusion attack, where a token signed with RS256 is accepted when resubmitted with the algorithm changed to HS256 and the public key used as the HMAC secret, effectively forging tokens if the server accepts the attacker's specified algorithm.

Defending against replay attacks requires using protocols with built-in anti-replay mechanisms throughout the environment. Kerberos, TLS 1.2 and 1.3, and IPsec all include sequence numbers or nonces that prevent replay of captured authentication material. Short-lived session tokens transmitted only over HTTPS with the Secure and HttpOnly flags set are the correct model for web application authentication. Multi-factor authentication provides protection against pass-the-hash attacks because even if the attacker replays the hash to authenticate, they cannot satisfy a physical token or biometric requirement. Network segmentation limits an attacker's ability to reach systems where captured credentials can be replayed. Endpoint Detection and Response tools monitor for behavioral patterns characteristic of pass-the-hash and pass-the-ticket, including anomalous LSASS memory access consistent with Mimikatz activity. Windows Credential Guard stores credentials in an isolated Hyper-V container inaccessible to the main OS kernel, preventing Mimikatz from reading NTLM hashes from LSASS memory. Placing sensitive accounts in the Protected Users security group in Active Directory disables NTLM authentication entirely for those accounts and limits Kerberos ticket lifetimes, substantially reducing the risk of credential-based lateral movement.
