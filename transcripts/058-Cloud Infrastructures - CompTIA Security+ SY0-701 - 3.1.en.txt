Cloud computing has transformed how organizations deploy and consume technology, and with that transformation comes an equally significant shift in how security responsibilities are allocated. To understand cloud security, a professional must first understand the foundational service models that define what the cloud provider manages versus what the customer must manage, and then understand the deployment models that determine who shares the underlying infrastructure.

Infrastructure as a Service, universally abbreviated as IaaS, is the most fundamental cloud service model. In IaaS, the cloud provider supplies the raw compute, storage, and networking resources — the physical data centers, the server hardware, the storage arrays, the physical network switches and routers, and the hypervisor layer that allows virtualization. The customer, however, is responsible for everything above the hypervisor: the operating system, middleware, runtime environments, application code, and the data itself. When a company provisions a virtual machine on Amazon Web Services EC2, Microsoft Azure Virtual Machines, or Google Compute Engine, that is IaaS. The customer must apply operating system patches, configure firewalls within the instance, harden the OS, manage identity and access at the OS level, and secure application code. IaaS gives customers the greatest degree of control and customization, but also places the greatest security burden on the customer. Organizations using IaaS effectively need skilled administrators who understand OS hardening, patch management, and network security configuration within the cloud environment.

Platform as a Service, or PaaS, removes the operating system and runtime management burden from the customer. The cloud provider supplies the compute infrastructure, the hypervisor, the operating system, the runtime environment, middleware, and the networking infrastructure. The customer is responsible only for the application code they write and the data that application processes. AWS Elastic Beanstalk, Azure App Service, and Google App Engine are classic PaaS examples. A developer can deploy a web application to Elastic Beanstalk without ever patching an OS or configuring a web server binary. The platform manages all of that. PaaS is particularly attractive for development teams that want to focus on application features rather than infrastructure management. From a security perspective, PaaS reduces the customer's attack surface at the infrastructure level, but the customer remains fully responsible for writing secure application code, implementing proper authentication and authorization within the application, and securing the data the application handles.

Software as a Service, or SaaS, is the most abstracted service model. The cloud provider manages everything from the physical infrastructure through the application itself. The customer's responsibility is limited to managing their own data, configuring user access, and administering the application within the provider's predefined settings. Microsoft 365, Salesforce, Dropbox, and Google Workspace are archetypal SaaS products. A company using Microsoft 365 does not patch Exchange servers, does not configure TLS certificates on mail servers, and does not manage the underlying compute infrastructure. Microsoft handles all of that. However, the customer is entirely responsible for decisions like which users have access to which mailboxes, how data is classified and labeled, whether multi-factor authentication is enforced, and what data retention policies are configured. Losing sensitive data through poor SaaS configuration — for example, leaving SharePoint sites publicly accessible — is the customer's problem, not the provider's.

Function as a Service, often called FaaS or serverless computing, represents the most granular cloud consumption model. Rather than provisioning a server or a platform, customers provide only discrete functions — individual units of code that execute in response to specific events. AWS Lambda, Azure Functions, and Google Cloud Functions are the leading FaaS platforms. A function might run when a file is uploaded to cloud storage, when a message arrives in a queue, or when an HTTP request is received. The underlying infrastructure, including the operating system, server patching, scaling, and capacity management, is entirely invisible to the customer. Serverless architectures offer dramatic operational simplicity and cost efficiency because compute is billed only when functions actually execute. Security considerations shift accordingly: customers must secure function code, manage function permissions carefully using least privilege IAM roles, protect environment variables that may contain secrets, and ensure that event triggers are authenticated and authorized.

Understanding which deployment model an organization uses is equally important as knowing the service model. In a public cloud deployment, infrastructure is owned and operated by a cloud service provider and shared across multiple customers, each logically isolated from the others. AWS, Microsoft Azure, and Google Cloud Platform are the defining public cloud providers. Public cloud offers nearly unlimited scalability, economies of scale that reduce cost, and a global footprint that enables geographic distribution of services. The tradeoff is reduced control over physical infrastructure and, for some organizations, regulatory concerns about multi-tenant environments.

A private cloud consists of cloud infrastructure dedicated exclusively to a single organization. The infrastructure may be hosted on-premises in the organization's own data center, or it may be hosted by a third-party provider that maintains dedicated hardware. VMware vSphere, Microsoft Azure Stack, and OpenStack are common technologies for building private clouds. Private cloud provides the greatest degree of control, customization, and data sovereignty. Organizations subject to strict regulatory requirements — defense contractors with classified data, healthcare organizations with sensitive patient records — may require private cloud or even fully on-premises infrastructure.

Hybrid cloud architectures combine public and private cloud, allowing data and applications to move between environments based on requirements. A company might run sensitive workloads in a private cloud while using public cloud for burst capacity during peak demand. Hybrid cloud provides flexibility but significantly increases complexity. Each cloud environment may have different authentication mechanisms, different logging formats, different network configurations, and different security tooling. Connecting these environments requires encrypted tunnels — typically VPNs or dedicated private connections like AWS Direct Connect or Azure ExpressRoute — and a unified security management strategy that spans both environments.

Community cloud is a niche deployment model where infrastructure is shared among organizations with common requirements, such as government agencies operating under the same regulatory framework or healthcare systems sharing HIPAA compliance requirements. FedRAMP-authorized cloud services serving multiple federal agencies represent a community cloud model.

Multi-cloud describes using services from multiple cloud providers simultaneously. An organization might use AWS for compute workloads, Azure for Active Directory integration, and Google Cloud for machine learning capabilities. Multi-cloud strategies reduce dependence on a single vendor, enable organizations to select best-of-breed services, and provide geographic or provider redundancy. The security challenge is that each provider has its own identity and access management system, logging format, security tooling, and compliance posture, requiring deliberate effort to achieve unified visibility and consistent security controls across all providers.

The shared responsibility model is the defining framework for understanding cloud security accountability. Cloud providers describe security as two distinct domains. Security of the cloud refers to the provider's responsibility: the physical security of data centers, the hardware infrastructure, the hypervisor and virtualization layer, the global network connecting facilities, and the services the provider builds on top of that infrastructure. The customer never touches any of this. Security in the cloud refers to the customer's responsibility: the data they store, the identities and access controls they configure, the network security groups and firewall rules they apply, the operating system patches they apply in IaaS, the application code they write, and the encryption configurations they choose. The boundary of responsibility shifts depending on the service model. In IaaS, the customer patches the OS and manages everything above the hypervisor. In PaaS, the provider manages the OS and runtime, but the customer is still responsible for application code security and data protection. In SaaS, the provider handles almost everything, but the customer retains full accountability for identity configuration, data classification, and user access management. The shared responsibility model also applies to specific security controls: regardless of service model, identity and access management, data classification, and client-side encryption are nearly always the customer's responsibility.

Cloud providers offer a rich set of built-in security constructs. Security groups function as virtual stateful firewalls operating at the instance or network interface level in environments like AWS and Azure. Security groups evaluate whether to allow or deny traffic based on rules that specify source and destination IP ranges, protocols, and ports. Because they are stateful, return traffic for an allowed connection is automatically permitted without a corresponding outbound rule. Network Access Control Lists, or NACLs, operate at the subnet level and are stateless, meaning each direction of traffic must have an explicit rule. They provide a coarser, subnet-level control layer that complements the instance-level security groups.

Virtual Private Cloud, or VPC, is a logically isolated network within a public cloud environment. Organizations configure their IP address ranges, subnets, route tables, and internet gateways within a VPC. This creates an isolated network environment that resembles a traditional on-premises network while running on shared physical infrastructure. VPCs can be connected to each other through VPC peering, which allows traffic to flow between VPCs without traversing the public internet. More complex connectivity between many VPCs is managed through services like AWS Transit Gateway, which acts as a central hub for inter-VPC routing. AWS PrivateLink allows services to be accessed privately without exposing traffic to the public internet, using interface endpoints within the VPC.

Cloud Access Security Brokers, or CASBs, address the challenge of SaaS application visibility and control. A CASB sits between users and cloud services, providing visibility into which cloud applications are being used, enforcing data loss prevention policies, applying access controls, and ensuring compliance with regulations. CASBs can detect shadow IT — the use of unsanctioned cloud services — and enforce security policies on approved services. CASBs can be deployed in-line to inspect traffic or in API mode to integrate directly with SaaS providers' management APIs.

Secure Access Service Edge, or SASE, is an architectural framework that converges network security functions with wide area networking capabilities, delivered as a cloud service. SASE brings together functions like secure web gateways, CASB, zero trust network access, firewall-as-a-service, and SD-WAN into a unified cloud-delivered security platform. Rather than routing traffic through a central data center for security inspection, SASE moves the security stack to the cloud, close to where users and applications actually are. This eliminates the backhauling inefficiency of traditional hub-and-spoke network designs and enables consistent security policy enforcement regardless of where a user is located or what device they are using.

Cloud-native security services provided by major cloud platforms offer deep integration with the underlying infrastructure. AWS Security Hub aggregates findings from across the AWS environment, integrating with services like Amazon GuardDuty for threat detection, AWS Config for configuration compliance, and AWS Macie for sensitive data discovery in S3. Azure Security Center provides unified security management and advanced threat protection across Azure and hybrid workloads. Google Cloud Security Command Center offers centralized visibility across GCP assets and identifies misconfigurations, vulnerabilities, and threats.

Major cloud providers maintain extensive compliance programs that make it easier for customers to meet regulatory requirements. FedRAMP is the US federal government's authorization framework for cloud services used by federal agencies. SOC 2 Type II reports demonstrate that a provider's security controls operate effectively over time. ISO 27001 certification shows a provider's information security management system meets international standards. PCI DSS compliance is critical for organizations processing payment card data. These certifications do not automatically make a customer compliant — customers still must implement appropriate controls on their side of the shared responsibility model.

Data residency and data sovereignty are increasingly important considerations. Data residency refers to the physical location where data is stored. Data sovereignty refers to the legal jurisdiction that governs data based on where it is physically located. A company operating in the European Union must ensure that data about EU residents is stored and processed in compliance with GDPR, which may require data to remain within EU borders. Cloud providers offer regional and availability zone configurations that allow customers to specify where their data is physically stored, and customers must configure these settings intentionally to meet applicable legal requirements.

Infrastructure as Code is fundamental to cloud security at scale. Rather than manually configuring cloud resources through a console, IaC tools like Terraform, AWS CloudFormation, and Ansible define infrastructure in version-controlled code files. This enables consistent, repeatable deployments with security controls baked into the template. Security misconfigurations — a common cause of cloud breaches — are easier to detect when infrastructure is defined in code that can be scanned with static analysis tools. GitOps workflows allow security teams to review infrastructure changes through pull requests before deployment, and secrets management tools like AWS Secrets Manager and HashiCorp Vault ensure credentials are never hardcoded in templates. The ability to destroy and recreate entire environments from code also simplifies disaster recovery and supports security incident response by enabling rapid replacement of potentially compromised infrastructure.

Elasticity and on-demand provisioning are defining characteristics of cloud computing. Organizations can scale compute capacity up or down in minutes based on actual demand, rather than purchasing hardware for peak load. Content Delivery Networks, or CDNs, distribute static content to edge locations geographically close to users, reducing latency and providing resilience against distributed denial of service attacks by absorbing attack traffic at the edge before it reaches origin infrastructure. Managed services — databases, message queues, container orchestration, machine learning platforms — reduce the attack surface customers must manage directly, shifting responsibility for those layers to the provider while allowing customers to focus security efforts on configuration and data protection.
