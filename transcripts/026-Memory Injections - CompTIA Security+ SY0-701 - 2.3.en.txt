Every program that executes on a computer must first be loaded into RAM — random access memory — before the CPU can process its instructions. This fundamental requirement of computing means that malware, like any other software, must reside in memory to operate. The memory space of a running system contains operating system kernel code, device drivers, system services, application processes, dynamic link libraries shared between applications, thread stacks, heap allocations, and many other components. Understanding how memory works is prerequisite to understanding how memory injection attacks exploit its structure.

The simplest approach for malware is to execute as its own independent process. However, running as a standalone process has significant disadvantages from the attacker's perspective. Security products monitor process lists for suspicious entries, new process creation events generate log entries that threat hunters review, and a malicious process runs only with the privileges of the user account that launched it. Memory injection addresses all three of these problems by placing malicious code inside an existing, legitimate, already-running process rather than creating a new one.

Process injection is the umbrella term for techniques that insert malicious code into a legitimate running process's memory space and execute it there. When malicious code runs inside a legitimate process, it inherits that process's security context, including its privilege level, its access tokens, and the permissions granted to it. A process running as a SYSTEM-level service — one of the highest privilege levels on Windows — that is targeted for injection will grant the injected code SYSTEM-level privileges even if the attacker's initial foothold was an unprivileged user account. The injected code is also much harder to detect because it appears to be part of the legitimate process when observed in process lists, security monitoring tools, and task managers.

DLL injection is the most widely used form of process injection and exploits the Windows Dynamic Link Library mechanism. DLLs are shared executable files that multiple processes can load and use simultaneously, containing reusable functions and code. In DLL injection, the attacker first places a malicious DLL file in a location accessible to the target system. The attacker then uses a sequence of Windows API calls to force the target process to load the malicious DLL. Specifically, VirtualAllocEx allocates a region of memory inside the target process's address space, WriteProcessMemory writes the path to the malicious DLL into that allocated memory, and CreateRemoteThread creates a new thread in the target process that calls LoadLibrary with the path to the malicious DLL as its argument. When LoadLibrary executes, the Windows loader maps the DLL into the target process's memory, and the DLL's initialization code runs inside the target process with all of its privileges. The malicious DLL is now resident in a legitimate process, executing attacker-controlled code with elevated permissions.

Reflective DLL injection is an advanced variant that eliminates the requirement for the DLL to be written to disk at all. In traditional DLL injection, the malicious DLL file must exist on the file system for the Windows loader to find it when LoadLibrary is called. This means antivirus software scanning the file system may detect the malicious DLL before injection occurs. Reflective DLL injection works differently: the DLL contains its own loader code that can map the DLL from memory rather than from disk. The injected DLL is loaded into the target process's memory as raw bytes — bypassing the standard Windows DLL loader entirely — and the DLL's embedded loader code resolves its own imports, applies relocations, and makes the DLL fully functional without ever existing as a file on disk. Because no file is written and the Windows loader is not involved, traditional file-based antivirus has nothing to scan. Reflective DLL injection is implemented in widely used offensive security frameworks including Cobalt Strike and Metasploit's Meterpreter payload, making it a well-known technique that security defenders must understand and detect through behavioral monitoring rather than file scanning.

Process hollowing, also called process replacement, is a memory injection technique that creates a legitimate process and then replaces its content with malicious code. The attacker first spawns a legitimate process — often a trusted Windows binary such as svchost.exe, explorer.exe, or notepad.exe — in a suspended state, meaning the process has been created by the operating system and is allocated memory but has not begun executing its code. The attacker then unmaps the process's original executable image from its memory, removing the legitimate code entirely, and writes malicious code into the now-empty memory space. When the process is resumed, it executes the attacker's code under the identity and security context of the legitimate process. To an observer examining the process list, the entry shows a legitimate system binary with a legitimate process ID, but the code executing inside it belongs entirely to the attacker. Process hollowing is particularly effective for evading process-based security monitoring.

Thread hijacking involves compromising an existing thread within a legitimate process rather than creating a new one. The attacker suspends an existing thread, modifies its instruction pointer — the register that holds the address of the next instruction to execute — to point to malicious code, and then resumes the thread. The thread then executes the attacker's code as if it were a natural continuation of the legitimate thread's work.

APC injection, where APC stands for Asynchronous Procedure Call, exploits a Windows mechanism that allows code to be queued for execution in the context of a specific thread when that thread enters an alertable wait state. An attacker can queue a malicious APC to a thread in a legitimate process, and when that thread calls certain wait functions (SleepEx, WaitForSingleObjectEx, or similar alertable wait APIs), the queued APC function executes in the thread's context.

Process Doppelganging is a more sophisticated technique that abuses the NTFS transaction mechanism — a file system feature designed to allow atomic, rollback-capable file operations. The attacker creates a transaction, writes a malicious executable into the transaction (so the file appears on disk temporarily but within a transaction context), creates a process from the transacted file, and then rolls back the transaction so the malicious file disappears from disk. The process created during the transaction remains running with the malicious code it was initialized from, but no file on disk corresponds to it, making forensic recovery of the malicious executable very difficult.

Several defensive technologies address memory injection. Data Execution Prevention, or DEP, is a hardware-enforced security feature implemented using the NX bit (No-Execute bit) in the processor. DEP marks certain memory regions — such as the heap and the stack — as non-executable, meaning the processor will raise an exception if code attempts to execute instructions stored in those regions. Even if an attacker successfully injects shellcode into a data buffer, DEP prevents that shellcode from executing because data pages are marked as non-executable. DEP is effective against the simplest forms of code injection but can be bypassed by Return-Oriented Programming, or ROP, which chains together small sequences of existing legitimate code rather than injecting new code.

Address Space Layout Randomization, or ASLR, randomizes the base addresses at which the executable, the stack, the heap, and shared libraries are loaded into memory each time the system starts or a process launches. Without ASLR, the memory layout of a process is predictable, allowing an attacker to hard-code addresses for jumping to shellcode or for finding useful code gadgets. With ASLR enabled, the attacker must first discover the actual addresses through an information leak vulnerability before reliable exploitation is possible, significantly raising the difficulty of exploitation.

Control Flow Integrity, or CFI, is a security mechanism that validates that a program's execution follows only anticipated control flow paths — the function calls, returns, and branches that the compiler determined were valid at compile time. CFI blocks Return-Oriented Programming attacks by detecting when execution is attempting to flow to an unexpected location.

Endpoint Detection and Response, or EDR, products monitor API call sequences in real time to detect patterns associated with injection techniques. The sequence of OpenProcess followed by VirtualAllocEx followed by WriteProcessMemory followed by CreateRemoteThread is a well-known indicator of DLL injection, and EDR products generate alerts when this pattern is observed. EDR products can also perform continuous memory scanning of running processes looking for patterns associated with known malicious shellcode or injected code regions that lack corresponding files on disk. The Anti-Malware Scan Interface, or AMSI, is a Windows API that allows security products to inspect scripts and other code before they execute, including PowerShell scripts that might attempt to invoke injection techniques, providing an additional detection layer before malicious code reaches the process injection stage.
