Encryption technologies encompass not just algorithms and key exchange protocols but also the specialized hardware and software systems that implement cryptographic functions securely at scale. For the Security Plus exam, understanding where cryptographic operations are performed, how keys are protected in hardware, and how encryption is applied at the device, disk, file, database, cloud, and transport levels is essential.

The Trusted Platform Module, commonly called TPM, is a standardized security chip embedded directly on a computer's motherboard. It can also be implemented as a firmware TPM, sometimes called fTPM, which runs in a protected processor mode rather than on dedicated silicon. The TPM was designed with a specific and narrow purpose: providing cryptographic functions for a single computer in a way that is tightly bound to that specific device. The TPM generates random numbers and cryptographic keys, stores those keys in persistent protected memory that cannot be read from outside the chip, and performs cryptographic operations internally so key material never leaves the device unprotected.

One of the most important functions of the TPM is measured boot, also called measured launch or trusted boot. During the boot process, each component of the boot chain, including the firmware, bootloader, and operating system kernel, is measured by computing a cryptographic hash of its code. These hash values are extended into a set of Platform Configuration Registers inside the TPM. The TPM accumulates these measurements throughout the boot process, creating a complete record of everything that executed during startup. This record can be compared against a known-good baseline to detect unauthorized changes, such as a bootkit that has modified the bootloader, or a rootkit that has tampered with the kernel. If the measurements do not match the expected values, the system can be configured to refuse to release encryption keys or to refuse to boot entirely.

The TPM also enables attestation, which is the ability of a device to cryptographically prove its configuration to a remote server. A remote attestation server can request a quote from the TPM, which is a signed report of the current PCR values. Because the quote is signed with a key that only the TPM has, the server can verify both the authenticity of the report and whether the device is in an expected, trusted configuration. This is used in enterprise environments and cloud computing to verify the integrity of client devices before granting access to sensitive resources.

BitLocker, the full disk encryption feature of Windows, integrates tightly with the TPM. When BitLocker is enabled with TPM protection, the encryption key for the disk is sealed to the TPM, which means the TPM will only release the key if the boot measurements match the expected values. This ensures that the disk cannot be decrypted on a different machine or after tampering with the boot environment. TPM 2.0 is required for Windows 11 and supports a broader and more modern set of cryptographic algorithms than the older TPM 1.2 standard, including support for SHA-256, ECC, and additional hash algorithms.

While the TPM serves a single device, the Hardware Security Module, HSM, serves an entire enterprise environment. An HSM is a dedicated hardware appliance designed exclusively for cryptographic operations at scale. HSMs are certified to FIPS 140-2 or the newer FIPS 140-3 standard, which defines four security levels. Level 1 requires only the use of approved cryptographic algorithms. Level 2 adds tamper-evidence requirements such as physical seals. Level 3 requires tamper-resistant physical enclosures and identity-based authentication before the HSM will perform operations. Level 4 requires active tamper response, meaning the HSM will automatically destroy its keys if it detects that its physical enclosure is being breached.

HSMs are used wherever the compromise of cryptographic keys would be catastrophic. Certificate Authorities use HSMs to protect their root and intermediate CA private keys, ensuring that even if the CA's servers are compromised, the private key material cannot be extracted. Payment processing systems use HSMs for PIN encryption and key management, as required by the Payment Card Industry Data Security Standard. In large data centers with hundreds or thousands of servers, a clustered HSM deployment with redundant power supplies and network interfaces provides centralized key storage and cryptographic acceleration for all servers. Cloud providers offer HSM services including AWS CloudHSM and Azure Dedicated HSM for organizations that need FIPS-certified hardware protection without managing physical hardware.

The Secure Enclave is an isolated coprocessor region physically separate from the main CPU, used for the most sensitive security operations on personal and mobile devices. Apple's Secure Enclave Processor, SEP, is built into every Apple device including iPhones, iPads, and Apple Silicon Macs. The Secure Enclave runs its own dedicated operating system, stores Touch ID and Face ID biometric templates and device encryption keys, and performs all biometric matching and key derivation operations internally. The main processor never has access to the biometric templates or the raw key material stored in the Secure Enclave, because the Secure Enclave never exposes these values to the main OS. This ensures that even if the main operating system is fully compromised by malware, the biometric data and encryption keys remain protected.

Intel Software Guard Extensions, SGX, provides a similar concept for x86 servers and workstations. SGX allows an application to create an encrypted memory region called an enclave, which is protected by hardware such that even the operating system, hypervisor, or BIOS cannot read or modify the contents. Sensitive code and data loaded into an SGX enclave is encrypted and integrity-protected by the CPU itself. This is used for confidential computing workloads where cloud tenants need assurance that even the cloud provider's administrative staff cannot access their data while it is being processed.

Key management systems, KMS, provide centralized lifecycle management for cryptographic keys across an organization. An enterprise KMS tracks every key's creation date, expiration date, associated user or service, usage logs, and rotation schedule. IT administrators can view at a glance which keys are about to expire, which keys have been rotated recently, and which services depend on each key. The KMS enforces separation of duties: key administrators who can manage keys may not have access to the data protected by those keys. Automated key rotation policies can be configured to replace keys on a schedule, reducing the risk of long-term key compromise. KMS solutions may be on-premises appliances, software running on internal servers, or cloud services like AWS KMS, Azure Key Vault, and Google Cloud KMS.

Cloud key management introduces additional considerations about trust. In a standard cloud service, the cloud provider manages the encryption keys and could theoretically access your data. Bring Your Own Key, BYOK, allows a customer to generate their own encryption keys and import them into the cloud provider's KMS, giving the customer visibility and control over key generation while still using the provider's infrastructure for key management. Hold Your Own Key, HYOK, goes further by keeping the encryption keys entirely on the customer's own on-premises infrastructure. Data is encrypted client-side before it is uploaded to the cloud, and the cloud provider never has access to the keys, ensuring that even a legally compelled disclosure from the provider cannot expose plaintext customer data.

Full disk encryption, FDE, encrypts the entire storage volume at the block level so that every file, every directory, and the entire file system structure are protected. BitLocker on Windows supports TPM-only authentication, TPM plus PIN, TPM plus USB key, and USB key alone, with TPM plus PIN providing the strongest protection against both theft and cold boot attacks. FileVault on macOS encrypts the entire startup disk using the user's login password for key derivation or the Secure Enclave on Apple Silicon systems. LUKS, the Linux Unified Key Setup, is the standard framework for disk encryption on Linux, typically used with the dm-crypt kernel module. LUKS stores multiple encrypted key slots, allowing multiple passphrases or recovery keys to unlock the same volume and supporting key rotation without re-encrypting all the data.

Self-encrypting drives, SEDs, implement AES-256 encryption directly in the drive's firmware and controller hardware, making encryption completely transparent to the operating system. All data written to the drive is automatically encrypted, and all data read from the drive is automatically decrypted, with zero performance impact compared to unencrypted drives. SEDs follow the Opal standard from the Trusted Computing Group, which defines management interfaces for configuring the drive's encryption. One major advantage of SEDs is cryptographic erasure: because all user data is encrypted with an internal media encryption key, securely erasing an SED is instantaneous. Discarding the media encryption key renders all data on the drive permanently unrecoverable without any need to overwrite the data, which can take hours or days on large drives.

File-level encryption provides granular protection for individual files and folders rather than entire volumes. Windows Encrypting File System, EFS, is integrated into the NTFS file system and allows individual files and directories to be marked for encryption. EFS is transparent to authorized users because the operating system handles encryption and decryption automatically when files are accessed. PGP and its open-source equivalent GPG provide file encryption, email encryption, and digital signing for individual documents and messages, using a combination of symmetric and asymmetric cryptography.

Database encryption protects sensitive data in database management systems. Transparent Data Encryption, TDE, encrypts the database files at the storage layer so that the data is protected on disk but appears unencrypted to authorized database connections. TDE is available in Microsoft SQL Server, Oracle Database, and PostgreSQL, among others. An alternative to TDE is column-level encryption, where specific sensitive columns such as Social Security numbers or credit card numbers are encrypted individually while less sensitive data remains in plaintext, allowing efficient searching and sorting on non-sensitive fields while protecting the most sensitive information.

Transport encryption protects data as it moves across networks. TLS, Transport Layer Security, operates at the application layer and is used by HTTPS, SMTP with STARTTLS, and many other application protocols. IPsec operates at the network layer and can encrypt all IP traffic between two endpoints regardless of application. In TLS, the server is authenticated using a digital certificate, and the session key is established via ECDHE before any application data is exchanged. Application-layer end-to-end encryption, as used in Signal and WhatsApp, means that even the service provider's servers see only encrypted ciphertext and cannot read message content.

Looking toward the future of encryption technology, quantum computing presents an existential threat to RSA and ECC. A quantum computer running Shor's algorithm can factor the large integers underlying RSA and solve the elliptic curve discrete logarithm problem, breaking both in polynomial time. This would render essentially all current asymmetric cryptography obsolete. Grover's algorithm provides a quadratic speedup for symmetric key search, effectively halving the security strength of symmetric algorithms, meaning AES-128 would provide only 64-bit post-quantum security while AES-256 would retain 128-bit effective security.

In response to this threat, NIST finalized its first post-quantum cryptographic standards. CRYSTALS-Kyber, standardized as ML-KEM in FIPS 203, is a key encapsulation mechanism based on the module lattice problem and is designed to replace RSA and ECDH for key exchange. CRYSTALS-Dilithium, standardized as ML-DSA in FIPS 204, and FALCON, standardized as SLH-DSA, are digital signature algorithms also based on lattice problems. SPHINCS-plus, standardized as SLH-DSA, is a stateless hash-based signature scheme providing security based solely on the properties of the underlying hash function.

Cryptographic agility refers to the design principle of building systems such that the specific algorithms and key sizes used can be updated without requiring a complete redesign of the system. Organizations that design for cryptographic agility will be able to swap in post-quantum algorithms as they become standardized and tested, rather than facing a complete infrastructure overhaul when existing algorithms are deprecated. This is considered a best practice for any long-lived system that handles sensitive cryptographic operations.
