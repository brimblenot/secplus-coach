Cryptographic hash functions and digital signatures are foundational tools in information security. They provide data integrity, authentication, and non-repudiation across a vast range of applications including file verification, password storage, digital certificates, code signing, and secure communications. Understanding exactly how these mechanisms work, which algorithms are considered secure, and what security properties each provides is essential for the Security Plus exam.

A cryptographic hash function takes an input of arbitrary length, whether a single character or a multi-gigabyte file, and produces a fixed-length output called a hash, message digest, or fingerprint. Hash functions are designed to satisfy several specific properties. First, they must be one-way: given a hash output, it must be computationally infeasible to find any input that produces that hash. This is also called preimage resistance. Second, they must be deterministic: the same input always produces the same output. Third, the output length is fixed regardless of input length, so a one-byte file and a one-terabyte file both produce a hash of the same size. Fourth, hash functions must exhibit the avalanche effect: a tiny change in the input, even a single bit flip, produces a completely different output. In practice, changing one character in a sentence produces a hash that bears no resemblance to the hash of the original sentence. Fifth, hash functions must be collision-resistant: it must be computationally infeasible to find two different inputs that produce the same hash output.

Critically, hashing is not encryption. You cannot reverse a hash to recover the original input the way you can decrypt ciphertext with the right key. A hash destroys information: it maps an infinite set of possible inputs to a finite fixed-length output, so by the pigeonhole principle, collisions must theoretically exist, but finding them must be computationally impossible for a secure hash function.

MD5, the Message Digest 5 algorithm, produces a 128-bit hash represented as 32 hexadecimal characters. MD5 was widely used through the 1990s for file integrity verification and password hashing. In 1996, researchers discovered weaknesses in MD5's internal structure, and by 2004 researchers demonstrated practical collision attacks, finding two different inputs that produce the same MD5 hash. This is a fundamental violation of the collision resistance property and means MD5 cannot be used for any security-critical purpose where an adversary might construct inputs. MD5 is still sometimes used for non-adversarial integrity checks where the goal is to detect accidental corruption rather than deliberate tampering, and it remains common in legacy systems, but it must never be used for digital signatures, certificate signing, or password hashing.

SHA-1, the original Secure Hash Algorithm, produces a 160-bit hash represented as 40 hexadecimal characters. SHA-1 was believed to be significantly more secure than MD5, but theoretical weaknesses were identified as early as 2005. In 2017, researchers at Google published the first practical SHA-1 collision, called SHAttered, demonstrating two different PDF files with the same SHA-1 hash. SHA-1 is now deprecated for digital signatures and TLS certificates and must not be used in new systems, though it persists in some legacy applications and version control systems.

The SHA-2 family, designed by the NSA and standardized by NIST, is the current standard for cryptographic hashing. SHA-2 includes four main variants: SHA-224, SHA-256, SHA-384, and SHA-512, where the number indicates the output size in bits. SHA-256, producing a 256-bit hash represented as 64 hexadecimal characters, is the most widely deployed and is used in TLS certificates, Bitcoin, code signing, and countless other applications. SHA-512 provides a larger output and uses different internal operations that are particularly efficient on 64-bit processors. No practical attacks against SHA-2 are known as of 2025, and it is considered secure for all current applications.

SHA-3 is a completely different hash function standardized by NIST in 2015, designed as a backup in case SHA-2 was found to be vulnerable. SHA-3 is based on a sponge construction algorithm called Keccak, which operates on a fundamentally different internal structure than the Merkle-Damgard construction used by MD5, SHA-1, and SHA-2. SHA-3 supports the same output sizes as SHA-2 but is structurally independent, meaning a class of attacks that might break SHA-2 would likely not affect SHA-3. SHA-3 is not yet as widely deployed as SHA-2 but is available as an alternative in most cryptographic libraries.

Hash functions are used in a wide variety of practical security applications. File integrity verification relies on hashing: when a software vendor publishes a download, they also publish the SHA-256 hash of the file. After downloading, users compute the SHA-256 hash of their downloaded file and compare it to the published value. If the hashes match, the file is byte-for-byte identical to what the vendor published. If an attacker has tampered with the download on a mirror site, or if the file was corrupted during transfer, the computed hash will not match and the discrepancy will be detected. Digital forensics uses hashing extensively for chain of custody: investigators hash every storage device before and after imaging to prove that the forensic copy is identical to the original and that no changes were made during the investigation.

Password storage represents one of the most important security-critical uses of hashing. Storing passwords in plaintext is indefensible: a single database breach exposes every user's credential. The secure approach is to store a hash of the password rather than the password itself. During login, the user submits their password, the server hashes it and compares the result to the stored hash. If they match, authentication succeeds. The server never needs to know or store the actual password.

However, simply hashing passwords with a fast general-purpose hash function is insufficient because an attacker who obtains the hash database can mount an offline dictionary attack: hashing millions of common passwords and comparing the results to the stolen hashes. Rainbow tables, which are precomputed lookup tables mapping hash values to their input passwords, make this process even faster for common passwords.

Salting defeats rainbow tables. A salt is a unique, cryptographically random value generated separately for each user at the time their password is first set. The salt is concatenated with the password before hashing, and both the salt and the resulting hash are stored. Because each user has a different salt, even if two users choose the same password, their stored hashes will be completely different. An attacker who steals the hash database must now run their dictionary attack separately against each individual user's salt-password combination, which eliminates the efficiency advantage of precomputed rainbow tables and dramatically increases the cost of the attack.

Purpose-built password hashing functions go further by being intentionally slow, with an adjustable work factor that controls how many iterations of hashing are performed. bcrypt, scrypt, and Argon2 are the most widely recommended. bcrypt has been in use since 1999 and incorporates a cost factor that controls the number of iterations; as hardware becomes faster, the cost factor can be increased to maintain security. Argon2 won the Password Hashing Competition in 2015 and is considered the current state of the art; it has three variants that allow tuning for resistance to GPU-based attacks, memory-hard attacks, or both. PBKDF2, the Password-Based Key Derivation Function 2, applies a pseudorandom function such as HMAC-SHA-256 many times with a salt and a configurable iteration count. PBKDF2 is used in WPA2 and WPA3 for deriving Wi-Fi network keys from passwords, and is approved for password storage in many compliance frameworks.

HMAC, the Hash-based Message Authentication Code, combines a hash function with a shared secret key to provide both message integrity and message authentication. An HMAC is computed by applying the hash function to a combination of the message and the key in a specific way defined by RFC 2104. Because only parties who know the shared key can compute the correct HMAC, a valid HMAC proves that the message was produced by someone who knows the key and that the message has not been altered since it was sent. HMAC provides integrity and authentication, but it does not provide non-repudiation, because both the sender and the receiver share the same key and either could have produced the HMAC. HMAC is used extensively in TLS for message authentication, in IPsec for packet integrity, in JSON Web Tokens for API authentication, and in many other protocols.

Digital signatures combine asymmetric cryptography with hashing to provide authentication, integrity, and non-repudiation simultaneously. The non-repudiation property is the key advantage over HMAC: with a digital signature, only the holder of the private key could have created the signature, so the signer cannot later deny having signed the message.

The digital signature process works as follows. The sender begins with the message they want to sign. The sender's software computes a hash of the message using a secure hash algorithm such as SHA-256. The sender then encrypts this hash with their own private key, which produces the digital signature. The sender transmits the original message and the signature together. The signature is typically appended to the message or sent as a separate attachment.

When the recipient receives the message and signature, verification proceeds in two steps. First, the recipient decrypts the signature using the sender's public key, recovering the hash that the sender originally computed. Second, the recipient independently computes the hash of the received message using the same algorithm. If the two hashes match, the signature is valid, which proves two things: the message is authentic because only the holder of the sender's private key could have produced a signature that decrypts correctly with that public key, and the message is unaltered because any change to the message would produce a different hash. Because only the private key holder can create a valid signature, the sender cannot deny having signed the message, which is non-repudiation.

The hash is signed rather than the entire message for efficiency. Asymmetric cryptographic operations are slow, particularly RSA. Signing a large message directly with RSA would be prohibitively slow. By hashing the message first and signing only the fixed-length hash, the signature operation is fast regardless of message size.

The most widely used digital signature algorithm is RSA, where the signer encrypts the message hash with their RSA private key. DSA, the Digital Signature Algorithm, is a federal standard specifically designed for signing and is not used for encryption; it is based on the discrete logarithm problem rather than integer factorization. ECDSA, Elliptic Curve DSA, applies digital signature mathematics to elliptic curves, providing equivalent security to RSA with much smaller key sizes. ECDSA is used in Bitcoin to authorize cryptocurrency transactions, in modern TLS certificates, and in many other applications.

Code signing applies digital signatures to executable software. A software developer signs their application or driver with their private key before distribution. When a user installs or runs the signed software, the operating system verifies the signature using the developer's public key certificate, which was issued by a trusted code signing CA. Windows displays the developer's name during installation of signed software and warns prominently about unsigned software. Windows kernel driver signing is mandatory on 64-bit versions of Windows 10 and later; unsigned kernel code cannot be loaded, providing a defense against rootkits that attempt to load malicious kernel drivers.

Certificate signing is the mechanism by which Certificate Authorities validate digital certificates. When a CA signs an end-entity certificate, it is computing a digital signature over all the fields of the certificate using the CA's private key. Any party that trusts the CA and has the CA's public key can verify this signature, confirming that the certificate was issued by that CA and has not been tampered with since issuance. This is the foundation of the entire PKI trust model.

The birthday attack is a mathematical technique for finding hash collisions based on the birthday paradox from probability theory. The birthday paradox states that in a group of only 23 people, there is a greater than 50 percent chance that two people share a birthday, which is counterintuitively high given that there are 365 possible birthdays. Similarly, for an n-bit hash function, an attacker only needs to hash approximately 2 to the power of n divided by 2 random inputs to have a 50 percent chance of finding a collision, rather than the full 2 to the power of n that might be naively assumed. This means that a 128-bit hash function effectively provides only 64 bits of collision resistance, which is why SHA-256 and larger are used for security applications that require strong collision resistance.

Hash collisions, while generally not a concern for most users in everyday contexts, are a serious concern when hash functions are used for digital signatures or certificate signing. If an attacker can find two documents that hash to the same value, they can get a legitimate CA to sign a benign-looking certificate and then substitute a malicious certificate in its place without invalidating the signature. The MD5 collision was exploited in exactly this way in 2008 to create a rogue CA certificate. This is why only SHA-256 and stronger hash functions are acceptable for certificate signatures in the modern internet PKI.

Integrity and confidentiality are distinct security properties that hash functions and encryption provide respectively. Hashing provides integrity: it allows you to verify that data has not changed, but it provides no confidentiality because a hash of public data is itself public, and knowing the hash reveals no secret about the original data beyond what is already public. Encryption provides confidentiality: it hides the content of data from unauthorized parties, but encryption alone provides no integrity guarantee in most modes, because ciphertext can be modified without the receiver knowing unless an authenticated encryption mode is used. Combining hashing with encryption, as in HMAC or AEAD modes like AES-GCM, provides both confidentiality and integrity simultaneously.
