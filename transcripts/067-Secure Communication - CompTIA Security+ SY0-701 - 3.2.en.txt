Every time data moves between systems — whether across a local area network, between a branch office and headquarters, from an employee's laptop to the corporate network, or from a user's browser to a web server — there is an opportunity for that data to be intercepted, read, or modified if the communication channel is not adequately protected. Secure communications protocols and architectures provide the encryption, authentication, and integrity protection needed to ensure that data in transit is protected regardless of the network infrastructure it traverses. The Security+ exam expects candidates to understand these protocols in depth — their mechanisms, their appropriate uses, their weaknesses, and the specific scenarios where each is the right choice.

Virtual Private Networks, or VPNs, create an encrypted tunnel over an untrusted network — typically the public internet — that allows private communications to travel securely between endpoints. The VPN conceptually creates a private network connection even though the traffic physically traverses shared public infrastructure. VPN implementations fall into two primary categories based on their purpose and scope.

Site-to-site VPNs connect two complete networks — most commonly a branch office to a corporate headquarters or data center. All devices at the branch office can communicate with all devices at the headquarters as if they were on the same local network, with the VPN gateways at each end handling encryption and decryption transparently. Users and applications at the branch office do not need any VPN client software — they simply send traffic normally, and the local VPN gateway encrypts it before sending it across the internet, with the remote gateway decrypting it on arrival. Site-to-site VPNs are always-on — they are established automatically and maintained continuously, not initiated by individual users. IPsec is the most common protocol for site-to-site VPN implementations. These VPNs replace or supplement expensive private WAN circuits like MPLS, providing encrypted connectivity at significantly lower cost using commodity internet bandwidth.

Remote access VPNs serve individual users who need to connect to a corporate network from outside the office — working from home, traveling, or using a public network. Unlike site-to-site VPNs, remote access VPNs require client software on the user's device and are typically initiated by the user when they need access. Client-based remote access VPNs install VPN software on the endpoint — Cisco AnyConnect, GlobalProtect, or the native VPN client built into Windows, macOS, iOS, and Android — that authenticates to a VPN gateway and establishes an encrypted tunnel. Clientless remote access VPNs deliver access through a web browser using SSL/TLS, requiring no special software installation — the user authenticates through a web portal and accesses internal resources through the browser interface, which is useful for managed scenarios like contractor access from unmanaged devices.

IPsec, the Internet Protocol Security suite, is the foundational protocol for network-layer encryption and authentication in VPN implementations. IPsec is not a single protocol but a suite of protocols and mechanisms that work together. Authentication Header, or AH, provides data origin authentication and integrity protection for IP packets — it proves that a packet came from the expected sender and was not modified in transit — but it provides no encryption, leaving payload content readable. Encapsulating Security Payload, or ESP, provides both encryption and integrity/authentication. ESP is the component of IPsec actually used for VPN confidentiality, and in virtually all VPN deployments, ESP with encryption is used rather than AH alone. Internet Key Exchange, or IKE, manages the negotiation of security associations — the agreements between VPN endpoints about which cryptographic algorithms they will use and the exchange of keying material. IKEv2, the current version of the key exchange protocol, provides improved efficiency, reliability, and security compared to IKEv1, and supports features like MOBIKE that allow VPN sessions to survive changes in the client's IP address such as when a mobile user moves from Wi-Fi to cellular.

IPsec operates in two modes that determine which portions of the IP packet are protected. Transport mode encrypts only the payload — the data portion — of the IP packet, leaving the original IP header intact. Transport mode is used for host-to-host communication where the IP addresses do not need to be hidden, such as securing communications between two servers within a data center. Tunnel mode encrypts the entire original IP packet — header and payload — and wraps it in a new IP packet with new headers pointing to the VPN gateway endpoints. Because the original IP header is encrypted, the actual source and destination addresses within the tunnel are completely hidden from observers on the path. Tunnel mode is used in all VPN gateway implementations, including site-to-site VPNs and gateways for remote access VPN connections. A critical exam concept: tunnel mode hides the original IP addresses; transport mode does not.

The IKE key exchange uses Diffie-Hellman key exchange to allow two parties to establish a shared secret over an untrusted channel without any pre-shared secret being transmitted. Diffie-Hellman groups of different sizes provide different levels of security — larger group numbers correspond to more complex mathematics and stronger security but require more computation. In modern deployments, groups 14, 19, 20, and 21 — using elliptic curve Diffie-Hellman — are recommended. The ability to negotiate fresh Diffie-Hellman keys for each session, even if the long-term authentication credentials are subsequently compromised, provides Perfect Forward Secrecy — a critical property ensuring that compromise of long-term keys does not expose past session data.

SSL/TLS VPN is an alternative to IPsec VPN that uses the TLS protocol — the same protocol securing HTTPS web traffic — rather than the IPsec protocol suite. SSL/TLS VPN operates over TCP port 443, which has the significant practical advantage that port 443 is almost universally permitted through firewalls and network address translation devices. IPsec VPNs use UDP port 500 and 4500 and ESP protocol 50, which may be blocked by some firewalls or fail to traverse NAT correctly without additional configuration. OpenVPN, Cisco AnyConnect using SSL, and GlobalProtect SSL mode are common SSL/TLS VPN implementations. SSL/TLS VPN is the technology most commonly used for remote access scenarios where users connect from diverse network environments including hotel networks, coffee shops, and cellular networks where IPsec might be blocked.

Split tunneling versus full tunneling is an important design decision for remote access VPN. With full tunneling, all traffic from the VPN client — both traffic destined for corporate resources and traffic destined for the internet — is routed through the encrypted VPN tunnel to the corporate gateway, where the corporate network's security controls — web filtering, IPS, DLP — inspect and control all user traffic. Full tunneling provides maximum security visibility and control over what VPN-connected users do, but consumes more corporate network bandwidth and may increase latency for internet browsing. With split tunneling, only traffic destined for corporate IP address ranges is routed through the VPN tunnel; all other traffic — internet browsing, cloud application access — goes directly from the client to the internet. Split tunneling reduces bandwidth consumption and latency for non-corporate traffic, but the corporate security controls cannot monitor or filter that direct internet traffic, creating a potential security concern where malware on the client could communicate to its command-and-control server through the direct internet connection while the VPN tunnel is active. Always-on VPN ensures the VPN connection is established automatically when the device starts up and maintained at all times, preventing users from inadvertently operating on untrusted networks without VPN protection.

Transport Layer Security, or TLS, is the protocol that secures the vast majority of internet communications. HTTPS — the secure version of HTTP — is simply HTTP over TLS. Understanding TLS versions and their security implications is essential. TLS 1.3, the current version, was designed to eliminate the vulnerabilities that plagued earlier versions. TLS 1.3 requires Perfect Forward Secrecy for all cipher suites — RSA key exchange, which did not provide PFS, is completely removed. Only authenticated encryption ciphers — specifically AES in GCM mode and ChaCha20-Poly1305 — are supported, eliminating the CBC-mode cipher suites that were vulnerable to BEAST and Lucky13 attacks. The handshake is simplified and requires fewer round trips than TLS 1.2, reducing connection establishment time. TLS 1.2 is still widely deployed and acceptable when configured with PFS cipher suites, but it must be configured carefully to avoid weak cipher suites. TLS versions 1.0 and 1.1 are deprecated and should be disabled — they contain vulnerabilities including BEAST, POODLE, and CRIME. SSL 2.0 and SSL 3.0 are severely vulnerable and must never be used. Organizations should configure servers and network devices to accept only TLS 1.2 and TLS 1.3, with TLS 1.3 preferred.

TLS provides three fundamental security properties. Confidentiality is provided through symmetric encryption using keys negotiated during the handshake — AES-GCM in TLS 1.3. Integrity is provided through the authentication component of AEAD — Authenticated Encryption with Associated Data — cipher modes that detect any modification to the ciphertext. Authentication is provided through the server's digital certificate, which the client validates against trusted certificate authorities to verify it is communicating with the intended server and not an impersonator.

Secure Shell, or SSH, is the encrypted protocol for remote system administration, replacing the insecure Telnet protocol that transmitted everything — including usernames and passwords — in cleartext over TCP port 23. SSH operates on TCP port 22 and provides encrypted interactive shell sessions, file transfer through SCP and SFTP, and port forwarding — the ability to tunnel other protocols through an encrypted SSH connection. SSH supports two primary authentication methods. Password authentication requires the user to present a password, which is transmitted encrypted within the established SSH session. Public key authentication is significantly more secure: the administrator generates an asymmetric key pair, copies the public key to the server's authorized_keys file, and authenticates by proving possession of the corresponding private key without ever transmitting it. Public key authentication is immune to password brute-force attacks and credential theft from password capture. SSH key management — tracking which keys are authorized on which servers, rotating keys regularly, and revoking keys when staff depart or keys are compromised — is a critical operational security practice that organizations often neglect.

SFTP, the SSH File Transfer Protocol, provides encrypted file transfer capabilities using the SSH protocol and runs over TCP port 22. It is a completely different protocol from FTP despite the similar name. FTPS, FTP Secure, is FTP enhanced with TLS encryption — it is standard FTP extended with TLS, not SSH-based. FTPS has two modes: explicit FTPS, where the client establishes an FTP connection on the standard port 21 and then upgrades to TLS using the AUTH TLS command, and implicit FTPS, which establishes the TLS connection immediately on the alternate port 990. SFTP is generally preferred over FTPS for new deployments because its SSH basis is simpler to deploy and firewall, using a single port rather than the multiple ports FTP requires for data connections.

Real-time communications security addresses the protection of voice and video traffic in VoIP and video conferencing systems. SRTP, the Secure Real-time Transport Protocol, encrypts voice and video payload data, provides authentication to verify the source of media packets, and provides replay protection. SRTP operates alongside SRTCP, which secures the associated RTCP control protocol. The key exchange for SRTP is handled separately, often through DTLS — Datagram TLS — which applies TLS security to UDP-based protocols. DTLS is the TLS equivalent for UDP, providing equivalent confidentiality, integrity, and authentication without requiring TCP's connection-oriented delivery guarantees. WebRTC, the browser-based real-time communication standard, mandates DTLS and SRTP for all media streams.

Email protocols carry specific security implications based on which versions are used. SMTP on port 25 is the protocol mail servers use to transmit messages between each other. STARTTLS allows a SMTP connection on port 25 to opportunistically upgrade to TLS encryption — opportunistic because both sides must support it, but the connection proceeds in cleartext if one side does not, making STARTTLS vulnerable to downgrade attacks unless enforced. SMTPS uses implicit TLS from the start of the connection on port 465. IMAP on port 143 and POP3 on port 110 carry credentials and email content in cleartext. IMAPS on port 993 and POP3S on port 995 use TLS to protect these connections. Organizations should configure mail servers and clients to use encrypted variants exclusively and not permit plaintext connection fallback.

SNMP, the Simple Network Management Protocol, is used to monitor and manage network devices. SNMPv1 and SNMPv2c use community strings — effectively plaintext passwords — for authentication, transmitted unencrypted. Any observer on the network path between the management station and the managed device can capture these community strings and use them to query or, with write access community strings, reconfigure network devices. SNMPv3 adds proper authentication using HMAC-MD5 or HMAC-SHA and optional encryption using AES or DES, providing genuine security for network management traffic. SNMPv3 should be used in all environments where SNMP is required. Similarly, LDAP on port 389 transmits directory queries and, critically, authentication credentials in cleartext. LDAPS, LDAP over TLS on port 636, protects all LDAP communication with TLS encryption. The use of cleartext LDAP for authentication to Active Directory or other directory services is a significant security risk that enables credential capture on the network.

Security professionals should enforce minimum TLS version requirements — TLS 1.2 as the minimum with TLS 1.3 preferred — across all systems. HTTP Strict Transport Security, or HSTS, is an HTTP header that instructs browsers to always use HTTPS for all connections to a domain and to refuse cleartext HTTP connections, preventing protocol downgrade attacks. Certificate pinning associates a specific certificate or public key with a specific host in the application or browser, preventing attacks where a compromised or rogue CA issues a fraudulent certificate for a trusted domain. Strong cipher suite configuration eliminates weak or broken algorithms including RC4, DES, 3DES, and CBC-mode cipher suites vulnerable to padding oracle attacks, retaining only AEAD cipher suites that provide authenticated encryption.

SD-WAN provides encrypted tunnels between branch sites across whatever WAN links are available — MPLS, broadband, LTE — with centrally managed security policies and application-aware routing. SASE, Secure Access Service Edge, extends the SD-WAN model by moving the security stack — including NGFW, CASB, secure web gateway, and ZTNA — to cloud-delivered points of presence close to users and cloud applications. Where traditional VPN backhauled all user traffic to a central corporate data center for inspection before forwarding it to cloud services, SASE inspects and secures traffic at the cloud edge closest to the user and destination, dramatically improving performance for cloud-first organizations while maintaining consistent security policy enforcement for all users regardless of location.
