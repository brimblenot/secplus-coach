Security monitoring depends on data — the continuous collection, aggregation, and analysis of information from across the environment that allows defenders to detect attacks, investigate incidents, and understand the behavioral baseline of their networks and systems. Effective monitoring requires understanding the types of data available, what each data source reveals about network and system activity, how to collect and store data at scale, and how to balance the depth of monitoring against the operational and storage costs involved. The sources of monitoring data span network traffic, system logs, application logs, security-specific telemetry, and metadata, each providing a different lens on the same underlying activity.

Network traffic monitoring produces some of the richest behavioral data available to security teams without requiring access to encrypted content. NetFlow is a Cisco-developed protocol that exports records of IP flow data from routers and switches. A NetFlow record contains the source IP address, destination IP address, source port, destination port, protocol, number of bytes transferred, number of packets, and timestamps for the start and end of the flow. Critically, NetFlow does not capture payload content — only the metadata describing the flow. IPFIX, the Internet Protocol Flow Information Export standard, is the standards-based equivalent of NetFlow, providing the same type of flow data in a vendor-neutral format. sFlow, which stands for sampled flow, is an alternative approach used on high-throughput network links where capturing every packet's flow data would be prohibitively expensive; sFlow samples one out of every N packets to produce statistical traffic data at lower overhead. Flow data is extraordinarily valuable for detecting a wide range of threats. Port scans appear as one source IP making connections to many destination ports across many destination hosts. Data exfiltration shows up as unusually large outbound transfers, particularly to external destinations. Command-and-control beaconing manifests as regular, periodic connections from a compromised internal host to the same external IP address. Lateral movement by attackers appears as a workstation making many SMB connections to internal servers, behavior atypical for normal users. Flow data also enables baselining — establishing what normal traffic patterns look like so that deviations can be detected.

Full packet capture goes beyond flow metadata to record the actual content of every packet, including headers and payload. A complete packet capture provides a forensic record of every communication that occurred, allowing reconstruction of sessions, extraction of transferred files, and recovery of credentials if unencrypted protocols are in use. Full packet capture requires significant storage infrastructure because network traffic volumes are high. The open-source tool Wireshark provides a graphical interface for capturing and analyzing packet data from a local interface. The command-line tools tcpdump and tshark provide scriptable packet capture and filtering capabilities. Commercial and open-source network forensics platforms including NetWitness, ExtraHop, and Arkime (formerly Moloch) provide scalable full packet capture and indexing for enterprise environments, allowing analysts to search through captured traffic using queries rather than manually reviewing packet captures.

Deep packet inspection, or DPI, refers to the technique of inspecting packet payload content rather than just the headers. DPI is used by next-generation firewalls, intrusion prevention systems, and web proxies to understand what is actually inside network traffic, enabling content-based filtering and threat detection. DPI can identify specific applications even when they run on non-standard ports, detect malware signatures within file transfers, and enforce content policy at a granular level. DPI raises privacy considerations when applied to user traffic because it exposes content that users may expect to be private.

Log data from systems, applications, and network devices forms the primary record of security-relevant events. Syslog is the standardized logging protocol for network devices, using either UDP or TCP on port 514 or TCP on port 6514 with TLS encryption for transport security. Syslog messages include a severity level from 0 to 7: Emergency, Alert, Critical, Error, Warning, Notice, Informational, and Debug, with 0 being the most severe. Network infrastructure including routers, switches, firewalls, and wireless controllers sends syslog messages documenting interface status changes, routing updates, access control list matches, authentication events, and configuration changes. Windows Event Logs are the primary log source for Windows systems and contain three main security-relevant logs. The Security log records authentication and authorization events. The System log records OS-level events. The Application log records application-specific events. Security analysts need to know the critical Windows Event IDs: 4624 for successful logon, 4625 for failed logon, 4648 for logon using explicit credentials, 4672 for special privileges being assigned to a logon, 4688 for new process creation, 4698 for a scheduled task being created, 4720 for a user account being created, and 4732 for a user being added to a security group. Linux logging is distributed across multiple files in /var/log. The auth.log or secure file records authentication events including SSH logins, su and sudo usage, and PAM authentication. The syslog or messages file records general system events. The kern.log file records kernel events. When auditd is configured, the audit.log file in /var/log/audit records detailed kernel-level audit events matching administrator-specified rules.

Application logs provide visibility into the behavior of specific applications and are often the richest source of information for investigating web-based attacks. Web server access logs in Apache and nginx use the Combined Log Format, recording the client IP address, request timestamp, HTTP method and URL, response status code, number of bytes transferred, the Referer header, and the User-Agent string. This log data allows reconstruction of exactly what pages were requested, identification of scanning and exploitation attempts, and correlation with other events. Database query logs record which queries were executed, by which user, at what time, and against which tables. These logs are required by PCI DSS for cardholder data environments and are essential for detecting SQL injection attacks and unauthorized data access. Application-level authentication logs recording successful and failed logins, password changes, and MFA events provide visibility into account compromise attempts. Cloud platform logs are increasingly important as workloads move to cloud infrastructure. AWS CloudTrail records every API call made to AWS services, including the caller's identity, the time, the source IP address, and the specific resource affected. Azure Activity Log and GCP Cloud Audit Logs provide equivalent coverage for their respective platforms.

Security-specific monitoring data includes EDR telemetry, DNS query logs, web proxy logs, and centralized authentication logs. EDR agents installed on endpoints produce continuous telemetry covering process creation trees, file system operations, network connections initiated by processes, and registry modifications, providing rich behavioral data that goes far beyond what traditional antivirus and log sources offer. This telemetry allows threat hunters to query historical data across the entire endpoint fleet with questions like "show me all systems where PowerShell spawned a network connection in the last 30 days." DNS query logs record every domain resolved by every client, providing a particularly valuable data source because nearly all malware communicates with its infrastructure via DNS. Domain generation algorithm activity, communication with known malicious domains, and data tunneling through DNS are all visible in DNS query logs. Web proxy logs capture the full URL including query parameters for HTTP traffic and the hostname for HTTPS traffic, revealing application usage, malware downloads, shadow IT activity, and data exfiltration via web protocols.

SIEM systems aggregate all these data sources, normalizing different log formats into a common schema that enables correlation across sources. Common Event Format, or CEF, and Log Event Extended Format, or LEEF, are standardized log formats used by various security products and SIEM systems to represent events in a consistent structure. Log retention requirements vary by regulation and use case. Hot storage provides immediate access to recent log data, typically covering 30 to 90 days, and is hosted in the SIEM's primary storage. Warm storage provides somewhat slower access for compliance and investigation purposes, typically covering 6 to 12 months. Cold storage provides archival retention for regulatory requirements, potentially covering years, at significantly lower cost but with longer retrieval times.

Metadata analysis deserves special attention because it demonstrates that security-relevant information can be extracted from communications without decrypting their content. The metadata about communications — who communicated with whom, when, for how long, how frequently, and with what volume of data — can be as revealing as the content itself. A user who accesses a file server at 3 AM, then establishes a large outbound transfer to an external IP, reveals suspicious behavior entirely through metadata even if every byte of traffic is encrypted. This principle underlies much of modern network forensics and threat hunting.

The physical placement of monitoring sensors determines what data they can collect. SPAN ports, also called mirror ports, are a feature of managed switches that copy all traffic passing through specified interfaces to a designated monitoring port, allowing a sensor to see all traffic without being in the forwarding path. Network taps are passive hardware devices that physically split the signal on a network link, sending a copy to the monitoring sensor while allowing the original traffic to flow unimpeded. Taps are often preferred over SPAN ports for critical monitoring because they cannot be disabled by switch configuration errors and do not impose any processing overhead on the switch. Inline sensors are placed directly in the network path, meaning all traffic must pass through them. This placement allows inline sensors to block malicious traffic, as intrusion prevention systems do, but introduces latency and creates a potential single point of failure if the sensor malfunctions.
