A buffer is a contiguous region of memory allocated by a program to hold data of a fixed or expected size. Buffer overflows occur when a program writes more data to a buffer than the buffer is allocated to hold, causing the excess data to spill into adjacent memory regions. The adjacent memory that gets overwritten may contain other variables, control flow data, or pointers, and corrupting those values can cause the program to behave in unintended ways — ways that an attacker can exploit to take control of execution. Buffer overflows have been one of the most consequential vulnerability classes in the history of computing, responsible for worms, remote code execution vulnerabilities in major software, and significant real-world compromises.

The most common and historically significant form is the stack-based buffer overflow. To understand this, it helps to understand the call stack. When a function is called in a program, the system pushes a stack frame onto the call stack containing the function's local variables, the saved value of the frame pointer, and critically, the return address — the memory address of the instruction in the calling function where execution should resume when the called function returns. Stack-based buffer overflows exploit this layout.

Consider a vulnerable function that uses an unsafe operation to copy user-supplied input into a fixed-size local buffer on the stack. Unsafe C standard library functions like strcpy, gets, sprintf, and scanf with the %s format specifier will copy input until a null terminator is encountered, with no regard for the size of the destination buffer. If the function allocates a buffer of 64 bytes but the user provides 200 bytes of input, the copy operation writes 64 bytes into the buffer and then continues writing the remaining 136 bytes into adjacent stack memory, overwriting other local variables, the saved frame pointer, and the return address. An attacker who can control the content of that overflow can write whatever they choose into the return address location, redirecting execution to any memory address they specify when the function returns.

The classic exploit technique places shellcode — machine instructions that perform a desired action, commonly launching a command shell — at the beginning of the oversized input, followed by enough padding to reach the return address location, followed by the address pointing back to the shellcode. When the function returns, the CPU loads the attacker's specified address and begins executing the shellcode. Because the exact offset from the buffer start to the return address is consistent for a given vulnerable function on a given platform, attackers who discover a buffer overflow can reliably calculate the payload required. A NOP sled — a long sequence of NOP instructions, which stand for "no operation" — is often placed before the shellcode to increase the size of the valid landing zone. If the return address overwrite points anywhere in the NOP sled, execution slides through the NOPs and reaches the shellcode.

Heap-based buffer overflows corrupt dynamically allocated memory rather than stack memory. When programs use malloc or the C++ new operator to allocate memory at runtime, that memory comes from the heap rather than the stack. Overflowing into adjacent heap allocations can corrupt heap metadata or overwrite pointers in nearby objects, enabling attackers to control program behavior. Heap exploitation is generally more complex than stack exploitation because heap layout is less predictable and exploitation techniques vary by memory allocator and platform, but heap overflows have been used in major vulnerabilities.

Integer overflows are closely related to buffer overflows. When an arithmetic operation produces a result that exceeds the maximum value representable by the data type, the value wraps around — for example, if a 16-bit unsigned integer overflows its maximum of 65535, the next increment gives zero. If a program uses an integer variable to calculate the size of a buffer allocation, and that calculation overflows to a small or zero value, the program allocates a much smaller buffer than intended while still writing the expected large amount of data into it, creating a buffer overflow condition through the size calculation rather than directly.

Format string vulnerabilities arise when user-controlled input is passed directly as the format string argument to functions like printf, fprintf, or sprintf rather than as a data argument. The format string tells these functions how to interpret their remaining arguments: %d reads an integer, %s reads a string pointer, %x reads a value in hexadecimal, and %n writes the number of characters printed so far to a pointer argument. If an attacker controls the format string, they can read from arbitrary locations on the stack using %x or %s, and write to arbitrary memory locations using %n, achieving read-what-where and write-what-where capabilities that can be chained into arbitrary code execution.

The Heartbleed vulnerability (CVE-2014-0160) is a well-known example from OpenSSL, though it is technically a buffer over-read rather than a write overflow. The OpenSSL implementation of the TLS heartbeat protocol did not validate that the specified payload length matched the actual data length sent, allowing an attacker to request up to 64 kilobytes of memory adjacent to a small buffer — potentially exposing private keys, session tokens, passwords, and other sensitive data from the server's memory. EternalBlue (MS17-010) exploited a buffer overflow in the Windows SMBv1 protocol and was used by the WannaCry ransomware and the NotPetya destructive malware to spread between unpatched systems. The Morris Worm of 1988 — one of the first self-propagating internet worms — exploited a buffer overflow in the Unix fingerd daemon, demonstrating that this vulnerability class has been understood and exploited for decades.

Return-Oriented Programming, or ROP, is an advanced exploitation technique developed specifically to bypass Data Execution Prevention. Because DEP marks the stack and heap as non-executable, simply injecting shellcode and jumping to it fails — the CPU refuses to execute code in data pages. ROP circumvents this by not injecting any new code at all. Instead, the attacker chains together short sequences of existing legitimate executable code — sequences ending in a RET instruction, called gadgets — that are already present in the program's own code or in loaded libraries. By carefully constructing a chain of return addresses on the stack, the attacker redirects execution through a series of gadgets, each performing a small operation, such that the combined effect of the chain accomplishes a complex operation like calling a system function. Because ROP uses only existing code in executable memory regions, DEP cannot prevent it.

Stack canaries, also called stack guards or stack cookies, are the primary mitigation against stack-based buffer overflows. At the start of any function, the compiler inserts code to push a random value — the canary — onto the stack between the local variables and the saved return address. Before the function returns, the compiler inserts code to verify that the canary value has not changed. If a buffer overflow has occurred and overwrote the return address, it necessarily also overwrote the canary. When the validation check detects the changed canary value, the program terminates immediately rather than allowing compromised execution to continue. GCC implements this with the -fstack-protector flag; MSVC uses /GS. The canary value is randomized per process execution to prevent attackers from simply embedding the known canary value in their overflow payload.

ASLR — Address Space Layout Randomization — randomizes the addresses of the stack, heap, and loaded libraries, making it difficult for an attacker to know where their shellcode or useful ROP gadgets are located in memory. Without knowing the actual address, the attacker cannot reliably redirect execution. ASLR does not prevent buffer overflows from occurring but makes reliable exploitation much harder, especially when combined with stack canaries. Bypassing ASLR typically requires a secondary information leak vulnerability that reveals memory addresses before the overflow is triggered.

DEP, or Data Execution Prevention, uses the NX bit in modern processors to mark memory regions as non-executable. Data regions on the stack and heap cannot be used as execution targets. DEP stops shellcode injection directly but is bypassed by ROP. The combination of stack canaries plus ASLR plus DEP creates a defense stack that makes reliable exploitation substantially more difficult, though not impossible for sophisticated attackers.

SafeSEH and Control Flow Guard are Windows-specific mitigations. SafeSEH validates the chain of structured exception handler records on the stack before executing any exception handler, preventing attackers from overwriting an exception handler pointer with a redirect to shellcode. Control Flow Guard, or CFG, maintains a bitmap of valid indirect call targets and validates each indirect call at runtime, blocking ROP chains and other control flow hijacking techniques that target indirect branches.

Memory-safe programming languages represent the most fundamental solution. Rust, Go, Java, Python, and other managed or memory-safe languages either perform automatic bounds checking on all array accesses, use garbage collection to eliminate use-after-free vulnerabilities, or both. Programs written in these languages cannot suffer stack or heap buffer overflows at the language level. The fundamental problem is the ongoing massive installed base of C and C++ code — operating systems, databases, embedded systems, network stacks — that manages memory manually and remains vulnerable to these classes of bugs. Input validation, using safe string functions such as strncpy and snprintf that accept a maximum length argument, and static analysis tools that detect unsafe function usage are all important practices for reducing buffer overflow vulnerabilities in new and existing C and C++ code.
