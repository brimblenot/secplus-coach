The Domain Name System is one of the most critical pieces of infrastructure on the internet. DNS translates human-readable domain names such as www.example.com into the IP addresses that routers and hosts use to deliver traffic. Without DNS, users would have to remember numerical addresses for every service they access, making the modern internet effectively unusable. DNS operates primarily over UDP on port 53 and uses TCP on port 53 for zone transfers and large responses. The resolution process involves recursive resolvers, which receive client queries and perform the full lookup on the client's behalf; root name servers, which direct resolvers toward the correct top-level domain servers; TLD servers for each domain suffix such as .com, .org, or .gov; and authoritative name servers that hold the actual records for specific domains. Because DNS is so foundational and because its original design did not include strong security mechanisms, it has become a rich target for attackers across a wide range of attack categories.

DNS cache poisoning, also called DNS spoofing, is one of the most consequential DNS attacks. When a recursive resolver queries an authoritative server for a record it does not already have cached, an attacker positioned to respond to that query faster than the legitimate server can inject a fraudulent answer. If the resolver accepts the forged answer, it stores the malicious record in its cache and will serve it to every client that queries that resolver for the poisoned name until the record's time-to-live expires. A single poisoned resolver can redirect thousands or millions of users to attacker-controlled infrastructure while all of those users believe they are communicating with the legitimate site. The classic Kaminsky attack, disclosed in 2008, revealed that the predictability of DNS transaction IDs and UDP source ports made it feasible to flood a resolver with forged responses during the brief window of an outstanding query and have a high probability of one being accepted before the legitimate response arrived. The fix implemented broadly in the wake of that disclosure was to randomize source ports as well as transaction IDs, dramatically increasing the effort required to win the race. DNSSEC, described in detail below, provides cryptographic authentication and eliminates the possibility of cache poisoning for domains that deploy it. DNS over HTTPS and DNS over TLS protect client-to-resolver communication from interception and manipulation.

DNS hijacking refers to attacks that redirect DNS queries themselves to a resolver or server controlled by the attacker rather than inserting fraudulent records into a legitimate resolver's cache. There are several mechanisms through which this can occur. An attacker who compromises a home router or small office gateway can change the DNS server settings pushed to clients via DHCP, causing all queries from those clients to go to an attacker-controlled resolver that returns fraudulent answers for targeted domains. Malware running on a victim machine can modify the local DNS settings or alter the hosts file, which takes precedence over DNS queries entirely. On Windows, the hosts file is located at C:\Windows\System32\drivers\etc\hosts and contains static name-to-IP mappings that the operating system consults before issuing a DNS query. Domain hijacking at the registrar level is among the most severe variants. If an attacker gains access to an organization's domain registrar account through credential theft, social engineering, or brute force, they can change the authoritative name server settings for the entire domain, redirecting all traffic globally to attacker infrastructure. A documented 2016 incident involving a major Brazilian bank illustrated this risk: attackers modified the DNS settings for 36 of the bank's domains at the registrar level, briefly becoming the bank's entire internet presence and harvesting credentials from customers for a six-hour window. BGP hijacking, while distinct from DNS, can also redirect DNS traffic by causing routers to forward packets destined for a DNS resolver through attacker-controlled infrastructure.

DNS tunneling exploits the fact that DNS traffic is allowed through nearly every firewall and network control because DNS is essential for basic connectivity. An attacker who controls a domain and its authoritative name server can encode arbitrary data within DNS query subdomains. For example, a client running tunneling software might send a query for the subdomain aGVsbG8=.attacker.com, where the subdomain contains Base64-encoded data. The attacker's authoritative server decodes the data from the subdomain and can encode a response back in the DNS answer record. This creates a covert communication channel entirely within DNS traffic that most security devices will pass without inspection. Attackers and advanced persistent threat groups use DNS tunneling to exfiltrate data from environments that restrict direct outbound internet access, and to establish command and control channels that evade detection. Detection relies on behavioral signals rather than content inspection: unusually high query volumes from a single host, queries for domains with abnormally long or randomly structured subdomains, a high proportion of queries for TXT records which can carry more data than standard A records, or queries to recently registered domains that have no legitimate traffic history.

Domain generation algorithms are a related technique used by malware to make command and control infrastructure difficult to disrupt. Rather than hardcoding a fixed C2 domain that can be blocked and seized once discovered, the malware executes a deterministic algorithm using a seed value such as the current date to generate hundreds or thousands of domain names each day. The attacker knows the algorithm and pre-registers the specific domain from that day's list that the malware will connect to. Defenders blocking the domains generated by a known algorithm face an uphill battle because the list changes daily and most generated domains are never actually registered. Machine learning models that identify algorithmically generated domains based on statistical properties of the domain names, and threat intelligence feeds that share known DGA families and their algorithms, are the primary defenses.

Subdomain enumeration is a reconnaissance technique attackers use to map out an organization's attack surface before launching targeted attacks. Organizations often have dozens or hundreds of subdomains, each potentially running a different service that may have its own vulnerabilities. Attackers discover subdomains through brute force, trying common names like mail, vpn, dev, staging, and api against the target domain; through DNS zone transfers if servers are misconfigured; through certificate transparency logs, which publicly record every TLS certificate issued and therefore reveal every subdomain name for which a certificate has been obtained; and through OSINT tools such as Amass, Sublist3r, and theHarvester. The information gathered is used to identify services that may be less well-secured than the main public-facing infrastructure.

DNS zone transfer abuse exploits misconfigured authoritative name servers. Zone transfers, using the AXFR query type, are intended to synchronize zone data between a primary name server and authorized secondary servers. A zone transfer response contains every DNS record for the domain, including A records for all hosts, MX records for mail servers, NS records for name servers, and CNAME records for aliases. This is an extremely valuable reconnaissance payload for an attacker. Properly configured servers restrict AXFR requests to the IP addresses of authorized secondary servers, but misconfigured servers allow anyone to request a full zone transfer. The defense is straightforward: configure zone transfer access control lists on all authoritative name servers to permit transfers only from explicitly listed secondary server IP addresses.

Typosquatting, also called URL hijacking or brandjacking, involves registering domain names that resemble legitimate domains but contain deliberate misspellings or character substitutions. An attacker might register professorm3sser.com, profess0rmesser.com, or professormeser.com to capture traffic from users who mistype the legitimate address. The fake domain can serve phishing pages that steal credentials, deliver malware, or redirect users to competitors. Unicode character substitution, called a homograph attack, registers domains using visually identical characters from non-Latin scripts to create names that appear identical to the legitimate domain in a browser's address bar.

Fast flux DNS is a technique used by attackers to make their command and control infrastructure resistant to takedown. In single-flux fast flux, the attacker rotates through a large pool of IP addresses for a domain with very short TTL values, often updating the A record every few minutes. The IP addresses are typically compromised hosts acting as proxies, so taking down any individual IP has limited impact on the C2 infrastructure. Double-flux extends this technique by also rotating the authoritative name servers for the domain, making it harder to take down the infrastructure at the DNS level.

DNSSEC, the DNS Security Extensions, adds digital signatures to DNS responses to provide authentication and integrity verification. DNSSEC does not encrypt DNS traffic but ensures that the records returned in a response are genuine and have not been tampered with in transit. It creates a chain of trust from the IANA root through TLD registries to individual domain operators. Each delegation is secured with cryptographic signatures that a validating resolver can verify. A poisoning attack against a DNSSEC-validating resolver fails because the forged response cannot carry a valid signature for the domain. DNSSEC deployment has grown steadily but is still not universal across all domains and resolvers.

DNS over HTTPS sends DNS queries encapsulated within standard HTTPS connections to a compatible resolver on TCP port 443. Because the traffic is indistinguishable from ordinary web traffic, it cannot be blocked by simply filtering port 53 and is resistant to interception by anyone on the path between the client and the resolver. DNS over TLS provides the same privacy protection but uses a dedicated port, 853, making it easier for network operators to identify and potentially control DNS-over-TLS traffic at the network boundary. Both protocols protect the confidentiality of client DNS queries against eavesdroppers and prevent manipulation by network intermediaries who might otherwise intercept and modify unencrypted DNS responses.

A comprehensive DNS defense posture combines DNSSEC validation at recursive resolvers to prevent cache poisoning, DNS over HTTPS or DNS over TLS for client-to-resolver privacy, strict zone transfer restrictions on all authoritative servers, continuous monitoring of DNS query logs for anomalous patterns such as tunneling indicators and DGA-like domains, integration of threat intelligence feeds for known malicious domains, and regular audits of registrar account security and domain registration records to detect unauthorized changes.
