Application attacks target the logic, configuration, and implementation of software rather than the underlying network or operating system. As network perimeters have hardened, attackers have increasingly focused on vulnerabilities in web applications and APIs, which are exposed to the internet by design and often contain subtle flaws in how they handle user input, authorize access to resources, or manage session state. Understanding these vulnerability classes is essential because they consistently appear in real-world breaches and are heavily represented in the CompTIA Security+ exam objectives.

Insecure Direct Object Reference, abbreviated IDOR, is one of the most prevalent and damaging application vulnerabilities. It occurs when an application exposes a direct reference to an internal resource, such as a database record, file, or object, without verifying that the requesting user is authorized to access that specific resource. A typical example is a URL parameter containing a user or account identifier: a user who sees the URL ending in userId=123 might change it to userId=124 and find that they can access another user's private data. This works because the application retrieves the object identified by the parameter without checking whether the authenticated session belongs to an account that has permission to see it. IDOR vulnerabilities are extremely common in REST API endpoints, where resources are often addressed by numeric or sequential identifiers. Defenses include using indirect references that map user-visible identifiers to internal ones through a server-side table, enforcing per-request authorization checks that verify the requesting user's relationship to the specific resource being accessed, and relying on server-side validation rather than trusting client-supplied identifiers.

Directory traversal, also called path traversal, allows an attacker to access files outside the directory hierarchy that an application is intended to serve. Web applications that accept file paths or filenames as input parameters are vulnerable if they do not canonicalize and validate the resulting path before opening files. An attacker can inject sequences of dot-dot-slash characters, represented as ../ in Unix or ..\  in Windows, to navigate up the directory tree and reference arbitrary files on the server's filesystem. A request for the parameter value of ../../../../etc/passwd would attempt to read the system password file on a Linux server. URL encoding of these characters, representing the slash as %2f and the dot-dot sequence as %2e%2e, can bypass naive filters that look for the literal string ../. Successful traversal can expose application source code, configuration files containing database credentials, private keys, and system files. Defenses include rigorous input validation that rejects path separators, canonicalization of paths before file access to resolve all relative components, use of an allowlist of permitted filenames or a strictly controlled directory root, and running web server processes in a chroot jail that limits filesystem access even if traversal succeeds.

Server-Side Request Forgery, or SSRF, is a vulnerability in which an attacker causes the server-side application to make HTTP requests to destinations chosen by the attacker rather than the application's intended targets. Applications that fetch remote resources on behalf of the user, such as URL preview generators, image fetchers, or webhook receivers, are potential SSRF targets. An attacker can supply a URL pointing to internal services that are not accessible from the internet, such as internal APIs, database management interfaces, or the cloud provider's instance metadata service. In cloud environments, the metadata service at the link-local address 169.254.169.254 provides credentials, configuration, and other sensitive information about the instance, making it a particularly high-value SSRF target. Redis, Elasticsearch, and other services that bind to localhost by default become accessible if the application server can be made to connect to 127.0.0.1. SSRF is considered critical in cloud environments because it can expose the credentials used by the application to access cloud resources. Defenses include implementing an allowlist of permitted outbound destinations, blocking requests to private IP address ranges at the network level, disabling unnecessary URL schemes such as file:// and gopher://, and using network segmentation to isolate backend services from the application tier.

Command injection allows an attacker to execute arbitrary operating system commands by injecting shell metacharacters into input that the application passes to a system shell. Applications that construct shell commands by concatenating user input with a command string are vulnerable. If an application accepts a filename parameter and passes it to a system() call that runs ls -la {filename}, an attacker can supply a filename of legitimate.txt; cat /etc/passwd; and the shell will interpret the semicolons as command separators, executing all three commands. The vulnerability exists because the application does not separate the concept of data from the concept of commands. Defenses include never constructing shell commands from user input, using parameterized APIs for subprocess execution that pass arguments as arrays rather than strings, applying strict input allowlisting to reject any characters that have special meaning to the shell, and running applications with minimal privileges so that successful injection has limited impact.

XML External Entity injection, or XXE, exploits XML parsers that process external entity references. When an XML document declares an external entity that references a URI, a vulnerable parser will attempt to fetch and include the content of that URI in the document. An attacker who can supply XML input can declare an entity referencing a local file such as file:///etc/passwd, causing the server to read and include the file contents in the parsed document, which may then be reflected back to the attacker in the response. XXE can also be used for SSRF by referencing internal URLs. Defenses include disabling external entity processing in the XML parser configuration and using JSON instead of XML where possible.

LDAP injection targets applications that construct Lightweight Directory Access Protocol queries from user input. If an application builds an LDAP filter by concatenating unsanitized input, an attacker can inject additional filter conditions that bypass authentication logic, modify search scope, or dump directory contents. The principles are analogous to SQL injection applied to directory services.

Cross-site request forgery, abbreviated CSRF or XSRF and pronounced like the word surf, tricks an authenticated user's browser into submitting an unauthorized request to a web application on their behalf. When a user is logged into a web application, their browser automatically includes their session cookie with every request to that domain, regardless of where the request originates. An attacker who embeds a link or an image tag in a malicious page can cause the victim's browser to send a state-changing request, such as a funds transfer or a password change, to the application using the victim's valid session. The application receives a request that appears identical to one the user might have made themselves, complete with valid session credentials, and executes it. CSRF tokens are the primary defense: the server includes a unique, unpredictable value in each form that is verified on submission, so a forged request from another origin will not include the correct token and will be rejected. The SameSite cookie attribute instructs the browser not to include cookies with cross-origin requests, providing defense in depth against CSRF when set to Strict or Lax mode.

Clickjacking overlays an invisible or transparent iframe containing a malicious element over a visible, legitimate page. The victim believes they are clicking on a button on the legitimate page but are actually clicking the hidden malicious element underneath. The attacker can use this technique to trigger actions on authenticated applications, capture keystrokes on input fields positioned beneath decoy UI elements, or perform any action within the trusted page that can be triggered by a click. The X-Frame-Options HTTP header, set to DENY or SAMEORIGIN, instructs the browser to refuse to render the page within an iframe. The Content-Security-Policy header's frame-ancestors directive provides more granular control and is the modern equivalent.

Session fixation is an attack where the attacker pre-establishes a session identifier on the server, then tricks the victim into authenticating using that same session ID, after which the attacker uses the pre-established ID to access the authenticated session. For example, some applications accept a session ID provided in the URL. The attacker can embed a link with a session ID they control and, if the victim logs in through that link, the existing session is now authenticated. The defense is to generate a completely new session identifier upon successful authentication, invalidating the pre-authentication session.

Privilege escalation in web applications takes two forms. Horizontal privilege escalation accesses resources belonging to other users at the same privilege level, such as reading another user's private messages by changing an identifier in a request. Vertical privilege escalation gains access to functions or data intended for higher-privilege roles, such as accessing administrative functions as a regular user because the application only checks for authentication but not for the admin role. Both forms exploit insufficient authorization logic.

Insecure deserialization occurs when an application deserializes data from an untrusted source without validation. Many serialization formats allow the encoded data to specify the type and parameters of the object to be constructed. An attacker who can control the serialized data can supply a payload that, when deserialized by the application, causes execution of arbitrary code. Java deserialization vulnerabilities have been particularly severe, affecting major platforms including Apache Struts, WebLogic, and JBoss. PHP object injection and Python pickle deserialization present similar risks in other language ecosystems.

A comprehensive application security posture combines developer training on the OWASP Top 10 vulnerability categories, secure coding practices emphasizing input validation and output encoding, parameterized database queries to prevent injection, web application firewalls to detect and block common attack patterns, dynamic application security testing during quality assurance, static analysis of source code before deployment, API security testing against the OWASP API Security Top 10, and adherence to the principle of least privilege for all database and service accounts that applications use.
