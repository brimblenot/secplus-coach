Cross-site scripting, universally abbreviated XSS to avoid confusion with Cascading Style Sheets, is one of the most common and consequential vulnerabilities affecting web applications. In an XSS attack, an attacker injects malicious client-side script — almost always JavaScript — into web pages that are subsequently rendered and executed by other users' browsers. The fundamental reason XSS is so dangerous is that the browser cannot distinguish between legitimate scripts served by a trusted site and injected scripts that merely appear to come from that same origin. The same-origin policy, which restricts scripts on one domain from accessing resources on another, provides no protection here because the injected script is already inside the trusted domain — it was inserted into it.

XSS vulnerabilities are divided into three distinct categories based on how the malicious script reaches victims. Reflected XSS, also called non-persistent XSS, occurs when user-supplied input is included in the server's immediate HTTP response without being stored. A search page that echoes back the search term without encoding it is a classic example. An attacker crafts a URL containing a malicious script in the search parameter, then delivers that URL to a victim through email, a text message, or a social media post. When the victim clicks the link, the server reflects the script back in the response, and the victim's browser executes it in the context of the trusted domain. The attack is transient — it affects only users who follow the crafted link — but can still be devastating when combined with a convincing phishing message targeting high-value accounts.

Stored XSS, also called persistent XSS, is considered the most dangerous variant because the malicious script is saved permanently on the server — in a database, log file, or content management system — and is then served to every user who subsequently loads the affected page. A script embedded in a forum comment, product review, user profile field, or social media post executes in the browser of every visitor without any individual targeting. A single successful injection can compromise millions of users. Social media platforms that allow posts to propagate virally are particularly dangerous vectors: if the injected script includes code that reposts itself, the malicious payload can spread organically across the platform's user base.

DOM-based XSS is fundamentally different from the other two types because the vulnerability exists entirely in client-side JavaScript rather than in server-side code. The server never receives or processes the malicious input. Instead, a client-side script reads data from a URL fragment, the document location property, or another browser-controlled source and writes it directly into the Document Object Model without sanitization. Because the server is not involved, server-side input filtering cannot catch DOM-based XSS. Detecting and preventing it requires careful auditing of all client-side code that reads from browser-controlled inputs and writes to the DOM.

Once an attacker achieves script execution in a victim's browser, the range of possible actions is broad. Session hijacking is the most immediate threat: the injected script reads the document.cookie property to extract the session token and transmits it to an attacker-controlled server, where it can be replayed to impersonate the victim. The HttpOnly cookie attribute directly counters this technique by making session cookies inaccessible to JavaScript. Credential harvesting involves injecting a fake login form that captures usernames and passwords and submits them to the attacker before or alongside the legitimate request. Keylogging scripts capture every keystroke the victim types anywhere on the page. Drive-by download attacks redirect the victim's browser to a site serving malware. XSS can also be used for UI defacement, for performing actions on behalf of the victim in ways similar to cross-site request forgery, and for conducting internal network port scans using the victim's browser as a proxy. Tools like the Browser Exploitation Framework, known as BeEF, allow attackers to maintain persistent control over a hooked browser, issuing commands long after the initial compromise.

A real-world illustration of XSS consequences came from research on the Subaru vehicle management website. A security researcher discovered that authentication tokens issued after login never expired and could authorize any vehicle service request, including adding additional email addresses to other owners' accounts. A reflected XSS vulnerability on the same site allowed an attacker to steal a victim's token through a crafted link. Because the token never expired, a single theft granted the attacker permanent access to the victim's vehicle and, through the account-sharing feature, to any other vehicle they could link. The researcher disclosed the issue to Subaru responsibly, and the vulnerabilities were remediated before public disclosure.

The most important defense against XSS is output encoding, also called output escaping. Every time user-supplied data is inserted into an HTML page, all HTML special characters must be converted to their safe entity equivalents before rendering. The less-than sign becomes its entity, the greater-than sign becomes its entity, the ampersand becomes its entity, quotation marks become their entities, and apostrophes become their entities. In PHP this is accomplished with the htmlspecialchars function, in .NET with the HtmlEncoder encode method, and in JavaScript with the DOMPurify library for sanitizing HTML fragments. The key insight is that encoding must happen at the point of output into the specific context — HTML body, HTML attribute, JavaScript, CSS, and URL contexts each require different encoding rules.

Content Security Policy, delivered as an HTTP response header, provides a complementary layer of defense. A properly configured CSP tells browsers which sources of scripts are permitted, effectively blocking inline scripts and scripts loaded from unauthorized domains even if injection occurs. A policy restricting script sources to the same origin prevents most XSS payloads from executing. This defense is especially valuable as a safety net when output encoding is imperfect.

Input validation rejects or strips input that does not match expected patterns before it is stored or processed, reducing the attack surface. However, input validation alone is insufficient because context varies — a string that is safe in one context may be dangerous in another — and validation rules are difficult to make exhaustive. It supplements but does not replace output encoding. The HttpOnly flag on session cookies prevents JavaScript from reading them, directly neutralizing the most common XSS exploit goal. The SameSite cookie attribute reduces the risk of cookies being sent in cross-site requests. Keeping browsers and applications updated closes known vulnerabilities in browser implementations. For application developers, conducting dynamic application security testing regularly surfaces injection points before attackers find them.

For the Security+ exam, candidates must understand all three XSS types and be able to distinguish them, recognize that the same-origin policy does not prevent XSS, and identify output encoding as the primary technical control. The HttpOnly flag, Content Security Policy, and input validation round out the defensive picture that the exam expects candidates to articulate.
