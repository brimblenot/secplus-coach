One of the most underappreciated attack vectors in physical office and campus environments is the humble Ethernet jack. An unoccupied conference room wall port, a switch port in an unlocked equipment closet, or a network drop in a lobby waiting area represents a direct physical pathway onto the internal network for anyone who can plug in a cable. Port security is the collection of controls — both physical and logical — that governs which devices and users are permitted to connect to individual network switch ports and wireless access points, ensuring that physical access to a network jack does not automatically translate into network access.

The foundational standard for port-based network access control is IEEE 802.1X, a protocol that enforces authentication at Layer 2 before granting network access. When a device connects to a switch port or wireless access point configured for 802.1X, the port remains in an unauthorized state — the device cannot pass any traffic except for 802.1X authentication messages — until the device successfully completes the authentication process. Only after successful authentication does the switch place the port into an authorized state and begin forwarding normal traffic.

The 802.1X framework involves three roles. The supplicant is the device requesting network access — a workstation, a laptop, a smartphone, or any other device seeking to connect. The authenticator is the switch port or wireless access point that enforces the access control — it receives the supplicant's credentials and enforces the authentication outcome, but it does not make the authentication decision itself. The authentication server is the backend system that actually validates credentials and makes the pass or fail decision — in virtually all enterprise 802.1X deployments, this is a RADIUS server, which may in turn query an Active Directory domain controller, LDAP directory, or other identity store. RADIUS is the Remote Authentication Dial-In User Service protocol, used for centralized authentication, authorization, and accounting across network access infrastructure.

The authentication process begins when the supplicant connects to the switch port. The authenticator detects the new connection and sends an EAP Request identity message to the supplicant. EAP, the Extensible Authentication Protocol, is the framework that carries authentication information between the supplicant and the authentication server, using the authenticator as a relay. The supplicant responds with its identity — typically a username. The authenticator forwards this to the RADIUS authentication server, which responds with a challenge based on the specific EAP method configured. The supplicant responds to the challenge with its credentials. The authentication server validates the credentials and returns either an Access-Accept or Access-Reject message to the authenticator. On Access-Accept, the authenticator moves the port to the authorized state and the supplicant gains network access. On Access-Reject, the port remains unauthorized.

Multiple EAP methods can be used within the 802.1X framework, each with different security characteristics. EAP-TLS, TLS standing for Transport Layer Security, is the strongest EAP method and is the recommended approach for high-security environments. EAP-TLS requires that both the supplicant and the authentication server authenticate each other using digital certificates — the supplicant presents a client certificate proving its identity, and the server presents a server certificate proving the authentication server's identity. This mutual certificate-based authentication provides strong cryptographic proof of identity for both sides and is immune to credential theft attacks that exploit password-based authentication. The operational requirement for EAP-TLS is a functional Public Key Infrastructure capable of issuing and managing certificates for all devices and the authentication server. PEAP, Protected EAP, creates a TLS tunnel between the supplicant and the authentication server first, and then authenticates the user with a password-based mechanism — typically MSCHAPv2 — inside that encrypted tunnel. The TLS tunnel protects the password from interception during transmission. PEAP is widely used in Windows environments because it leverages existing Active Directory credentials without requiring per-device certificates. Only the server presents a certificate in PEAP — the client authenticates with a username and password. EAP-TTLS, Tunneled TLS, is similar to PEAP but more flexible in the inner authentication method it supports. EAP-FAST, Flexible Authentication via Secure Tunneling, was developed by Cisco as an alternative that avoids the certificate requirement by using Protected Access Credentials — pre-shared keys provisioned to devices out-of-band — but is less commonly used than PEAP or EAP-TLS in modern deployments.

When 802.1X authentication fails or when a device does not support 802.1X, the switch port remains in an unauthorized state and the device cannot access the network. For environments where some devices genuinely cannot support 802.1X — older printers, legacy IP phones, certain IoT devices — MAC Authentication Bypass, or MAB, provides a fallback mechanism. In MAB, the switch uses the device's MAC address as both the username and password when querying the RADIUS server. The RADIUS server either accepts or rejects access based on a list of approved MAC addresses. MAB is far weaker than certificate or password-based 802.1X authentication because MAC addresses are easily observed on the network and trivially spoofed — any attacker who observes a permitted MAC address can configure their interface to use that address and bypass MAB. MAB should be used only for devices that genuinely cannot support 802.1X, and the devices permitted via MAB should be isolated onto restricted VLANs that allow only the minimum network access they require.

802.1X enables dynamic VLAN assignment based on the authenticated user or device identity. After successful authentication, the RADIUS server can return a VLAN attribute that instructs the authenticator to place the port into a specific VLAN rather than a default VLAN. This allows different users to get different network access based on their role: an employee authenticating with corporate credentials gets placed in the corporate VLAN with full internal access, a contractor authenticating with a different credential set gets placed in a restricted contractor VLAN, and an IoT device authenticating via MAB gets placed in an isolated IoT VLAN with only the specific access it requires. This dynamic, identity-driven VLAN assignment is far more secure and manageable than static VLAN assignment per port, especially in environments where many users with different roles use the same physical network infrastructure.

A Guest VLAN is a separate network segment configured on 802.1X-enabled switches to provide limited, typically internet-only access to devices that fail 802.1X authentication. Rather than leaving visitors or unregistered devices without any network access, the guest VLAN allows them to reach the internet for legitimate purposes while preventing access to internal corporate resources. Guest VLANs must be carefully firewalled to ensure that guest devices truly cannot reach internal systems even if they attempt to.

MAC address filtering is a simpler form of access control that permits traffic only from pre-approved MAC addresses. While easy to implement, MAC address filtering provides very weak security. MAC addresses are transmitted unencrypted in Ethernet frame headers and are trivially observable by any device on the same network segment. More critically, MAC addresses are trivially spoofed — on any major operating system, an attacker can change their network interface's MAC address to any value they choose in seconds using simple command-line tools. For this reason, MAC filtering should not be considered a security control against determined attackers. It may be useful for asset inventory tracking or preventing accidental unauthorized connections, but it must not be the sole access control mechanism relied upon for security.

CAM table overflow attacks exploit the finite size of a switch's MAC address table. A switch learns MAC addresses by observing source addresses in frames — when a new source MAC address arrives on a port, the switch adds it to the CAM table with the associated port. When the CAM table is full and a new MAC address arrives, the switch cannot add it and falls back to flooding behavior — forwarding the frame out all ports, as a hub would. An attacker using tools like macof or Ettercap can rapidly generate thousands of frames with randomized source MAC addresses, filling the CAM table and forcing the switch into hub mode, where all traffic is broadcast to all ports and can be captured by the attacker. Port security with a maximum MAC address limit prevents this attack by restricting how many MAC addresses can be learned on a single port and disabling the port if the limit is exceeded. Sticky MAC learning automatically records the first MAC address observed on each port and restricts that port to only that MAC address going forward, without requiring manual configuration of individual MAC addresses.

DHCP snooping is a switch security feature that protects against rogue DHCP servers. In a normal network, a DHCP server assigns IP addresses to clients that request them. An attacker who connects a rogue DHCP server to the network can offer clients IP addresses with a gateway setting pointing to the attacker's machine — a man-in-the-middle attack that causes all client traffic to flow through the attacker. DHCP snooping prevents this by configuring switch ports as either trusted or untrusted. Only trusted ports — those connecting to legitimate DHCP servers or uplinks to the rest of the network — are permitted to send DHCP offer and DHCP acknowledgment messages. Untrusted ports — those connecting to end devices — are blocked from sending DHCP server messages. The switch maintains a DHCP snooping binding table recording the IP address, MAC address, VLAN, and port for each lease granted by the legitimate DHCP server. This binding table is then used by Dynamic ARP Inspection and IP Source Guard.

Dynamic ARP Inspection, or DAI, protects against ARP spoofing and ARP poisoning attacks. The Address Resolution Protocol allows devices to discover the MAC address associated with a known IP address. ARP has no authentication — any device can send an ARP reply claiming any IP-to-MAC mapping. An attacker can broadcast gratuitous ARP replies claiming that the default gateway's IP address resolves to the attacker's MAC address, causing all devices on the segment to send traffic destined for the gateway to the attacker instead — a man-in-the-middle attack at Layer 2. DAI validates all ARP packets against the DHCP snooping binding table. An ARP reply claiming an IP-to-MAC mapping that contradicts the binding table is dropped. Only ARP traffic from trusted ports bypasses inspection. DAI effectively prevents ARP poisoning without requiring any configuration changes on end devices.

IP Source Guard validates source IP addresses on untrusted switch ports against the DHCP snooping binding table. A device that attempts to use a source IP address different from what the DHCP server assigned to it — a technique used to impersonate another host or bypass access controls — has its traffic dropped by the switch. IP Source Guard is particularly effective in environments where precise traffic accounting is required and IP address spoofing could be used to circumvent network-based access controls.

Spanning Tree Protocol, or STP, prevents Layer 2 loops in networks with redundant paths by blocking all but one active path between any two points. STP manipulation attacks exploit the protocol to force topology changes that redirect traffic through attacker-controlled switches. BPDU Guard prevents these attacks on access ports: if the switch receives a Bridge Protocol Data Unit — an STP protocol message — on a port configured with BPDU Guard, it immediately shuts the port down. End devices should never send STP BPDUs, so receiving one on an access port indicates that an unauthorized switch has been connected. Root Guard prevents a connected device from claiming to be the STP root bridge, which would cause the switch to defer to it in path selection calculations. Loop Guard prevents switch ports from entering a forwarding state when they stop receiving BPDUs — preventing the forwarding loops that can occur due to unidirectional link failures.

Storm control protects against broadcast storms — cascading loops of broadcast traffic that can consume all available bandwidth and CPU resources on every switch in the affected segment. Storm control sets thresholds for broadcast, multicast, or unknown unicast traffic on each port; when traffic exceeds the threshold, the switch suppresses or drops the excess, preventing the storm from propagating.

Physical port security measures complement logical controls. Unused switch ports should be administratively disabled — a port that is not assigned to a device should not be active, preventing anyone from connecting to it and gaining network access. Network jacks in public areas like lobbies, conference rooms, and hallways present particular risk and should be connected only to a separate, restricted guest VLAN or disabled entirely when not in active use. Cable locks on wall jacks in physical access-controlled areas provide an additional deterrent. Port labeling and documentation ensure that administrators have accurate knowledge of what is connected where. Physical access controls on network closets — locked doors with access logging — prevent unauthorized physical access to the switches that everything else depends on.
