Application security encompasses all the practices, techniques, and tools used to find and fix security vulnerabilities in software before and after it reaches production. The fundamental principle of application security is that security must be built into the software development process from the beginning rather than evaluated as an afterthought after development is complete. Retrofitting security into a finished application is far more expensive, less effective, and more disruptive than addressing security requirements at each phase of development.

The Secure Software Development Lifecycle, abbreviated SSDLC, integrates security activities into every phase of the development process. In the Requirements phase, security requirements are defined alongside functional requirements. Security requirements specify what the application must do to protect data, authenticate users, authorize access, handle errors, and comply with applicable regulations. Threat modeling during the requirements phase identifies what an attacker might want to accomplish against this application and what data is at risk. In the Design phase, architects perform architecture reviews to assess whether the proposed design introduces unnecessary risk, conduct formal threat modeling to identify threats against the specific architecture, and apply security design patterns including defense in depth and least privilege. In the Implementation phase, developers follow secure coding standards, avoid known dangerous patterns such as direct string concatenation in SQL queries, and conduct peer code reviews with security awareness. In the Testing phase, security testing is integrated with functional testing through automated scanning tools and manual techniques. In the Deployment phase, systems are deployed with hardened configurations, secrets are managed through dedicated platforms rather than embedded in code, and deployment processes themselves are secured. In the Maintenance phase, the organization monitors for newly disclosed vulnerabilities in components used by the application, maintains a patch process, and updates the application as threats and the environment evolve.

Input validation is the process of evaluating all data supplied by users or external systems before the application processes or stores it. Proper input validation is the primary defense against injection attacks including SQL injection, command injection, and cross-site scripting. Allowlist validation, also called whitelist validation, accepts only input that explicitly matches a known-good specification and rejects everything else. Allowlist validation is the most secure approach because the developer defines exactly what is acceptable — a ZIP code field accepts only five digits optionally followed by a hyphen and four more digits; anything else is rejected. Denylist validation, also called blacklist validation, attempts to identify and reject known-malicious patterns while accepting everything else. Denylist validation is inherently less secure because it depends on the developer's ability to anticipate every possible attack pattern, and attackers routinely find encoding tricks and syntax variations that bypass denylists. Type validation ensures that the value provided matches the expected data type — a field that should contain an integer should reject any input that cannot be parsed as an integer. Length validation enforces maximum and minimum length constraints to prevent buffer overflows and other length-dependent attacks. Range validation ensures that numeric values fall within an expected range. Format validation uses regular expressions to verify that values like email addresses, phone numbers, and dates conform to their expected structure. A critical rule of input validation is that server-side validation must always be performed regardless of whether client-side validation is also implemented. Client-side validation is easily bypassed by disabling JavaScript, modifying requests with a web proxy, or crafting raw HTTP requests — the server must never trust that client-side validation has already filtered malicious input.

Output encoding prevents user-supplied data from being interpreted as code when it appears in application output. When an application includes user-supplied data in an HTML page, that data must be HTML-encoded so that characters with special meaning in HTML, such as angle brackets and quotation marks, are converted to their HTML entity equivalents. Inserting user-supplied data into a URL requires URL encoding. Inserting user-supplied data into a JavaScript context requires JavaScript encoding. Database interactions should use parameterized queries or prepared statements rather than string concatenation, which separates the SQL code structure from user-supplied values and makes SQL injection impossible regardless of what the user provides.

Error handling must be implemented carefully to avoid information disclosure. When an application encounters an error, the error message presented to the user should be generic — revealing stack traces, SQL query syntax, file system paths, server hostnames, or software version numbers provides attackers with valuable reconnaissance information. Detailed error information should be written to protected log files accessible only to administrators and developers, while users see only a generic error page. Custom error pages should be configured for all web applications to replace the default error pages that often reveal server and framework version information.

Static Application Security Testing, abbreviated SAST, analyzes source code or compiled binary code without executing it to identify security vulnerabilities. SAST tools integrate into the development workflow and can be run automatically on every code commit through a CI/CD pipeline, providing developers with immediate feedback about security issues in newly written code. SAST tools identify issues including SQL injection vulnerabilities created by string concatenation in database queries, hard-coded credentials such as API keys and passwords embedded in source code, use of dangerous functions that perform no bounds checking, insecure randomness using predictable random number generation, and improper certificate validation. Commercial SAST platforms include Veracode, Checkmarx, and Micro Focus Fortify. Open-source and free options include SonarQube, Semgrep, and GitHub's CodeQL. SAST has limitations — it analyzes code statically and cannot detect vulnerabilities that only manifest at runtime, such as authentication logic flaws or business logic issues.

Dynamic Application Security Testing, abbreviated DAST, tests a running application by sending malicious inputs and observing the responses. Unlike SAST, DAST does not require access to source code — it interacts with the application exactly as an attacker would, through the application's external interface. DAST finds runtime vulnerabilities that SAST cannot detect, including authentication weaknesses, session management flaws, and vulnerabilities that depend on specific application state. DAST is run against deployed test environments rather than production systems. OWASP ZAP is a widely used free DAST tool that can perform automated scanning or act as an intercepting proxy for manual testing. Burp Suite is the industry standard for professional web application security testing, providing an intercepting proxy, automated scanner, and extensive manual testing tools. Rapid7 AppSpider is a commercial DAST platform.

Interactive Application Security Testing, abbreviated IAST, instruments a running application during testing — typically by injecting a sensor into the application runtime — to observe the application's internal behavior while test cases are executed. IAST combines the accuracy of SAST, because it can see inside the application, with the coverage of DAST, because it tests the application while it is actually running. IAST produces lower false positive rates than either SAST or DAST alone because it can observe whether a vulnerability is actually reachable and exploitable during real test execution.

Software Composition Analysis, abbreviated SCA, scans application dependencies — the open-source libraries, frameworks, and packages that modern applications rely on — for known vulnerabilities. Applications today consist substantially of third-party code, and vulnerabilities in popular libraries like Log4Shell affect every application that includes the vulnerable dependency. SCA tools identify which versions of which libraries are in use, match them against vulnerability databases such as the National Vulnerability Database, and generate alerts when vulnerable versions are detected. SCA tools also produce Software Bills of Materials, abbreviated SBOMs, which are machine-readable inventories of all components in an application. Commercial SCA tools include Snyk and Black Duck. Open-source options include OWASP Dependency-Check and GitHub Dependabot.

Fuzzing, also called fuzz testing, sends randomly generated, malformed, or boundary-condition input to an application's inputs to discover unexpected behavior including crashes, hangs, assertion failures, and memory corruption. Fuzzing is particularly effective at discovering memory corruption vulnerabilities, format string vulnerabilities, and input parsing errors that might not be found by code review or structured test cases. When the application crashes or behaves unexpectedly, the fuzzing engine records the input that caused the behavior for developer investigation. American Fuzzy Lop, libFuzzer, and Boofuzz are commonly used fuzzing frameworks. The CERT/CC Basic Fuzzing Framework provides another approach. Fuzzing is almost always automated because finding vulnerabilities through fuzzing requires running enormous numbers of test cases — sometimes millions — before a crash-inducing input is discovered.

Code review — the practice of having developers examine each other's code for security vulnerabilities and logic errors — complements automated testing tools. Peer review catches design-level issues that automated tools miss, validates that security controls are implemented correctly, and shares security knowledge across the development team. Security-focused code review by specialists examines code specifically for security weaknesses and is often performed at security milestones in the development lifecycle. Bug bounty programs extend code review to external security researchers who test production applications and report vulnerabilities in exchange for monetary rewards. Platforms such as HackerOne, Bugcrowd, and Synack connect organizations with vetted security researchers.

Secrets management is the practice of keeping credentials, API keys, cryptographic keys, and connection strings out of source code and configuration files. When developers embed secrets in code, those secrets are frequently committed to version control repositories where they persist in history even after removal, becoming accessible to anyone with repository access. Secret management platforms such as HashiCorp Vault, AWS Secrets Manager, and Azure Key Vault store secrets centrally and provide applications with access to secrets at runtime through authenticated API calls, eliminating the need to embed secrets in application code or configuration files. Git secret scanning tools such as GitHub Advanced Security, truffleHog, and git-secrets scan repositories for patterns that match credentials and alert developers when potential secrets are found.

HTTP security headers are response headers that instruct browsers to apply additional security protections when processing responses from a web application. HTTP Strict Transport Security, known as HSTS, instructs browsers to only communicate with the server using HTTPS, preventing downgrade attacks to unencrypted HTTP. Content Security Policy, known as CSP, defines which sources of content the browser is permitted to load, substantially reducing the impact of cross-site scripting attacks by preventing execution of injected scripts. X-Frame-Options prevents the application from being embedded in frames on other domains, protecting against clickjacking attacks. X-Content-Type-Options prevents browsers from MIME-sniffing responses away from the declared content type. Referrer-Policy controls what information is included in the Referer header when users navigate from the application to external sites.

API security requires several layers of control. Authentication for API access uses API keys for simple service-to-service communication, OAuth 2.0 for delegated authorization allowing applications to act on behalf of users, and JSON Web Tokens for conveying identity and authorization claims between services. Rate limiting prevents abuse by limiting how many requests a client can make in a given time period, protecting against denial of service and automated scanning. All API inputs must be validated server-side regardless of client behavior. All API communication must occur over HTTPS. API endpoints should be designed with least privilege in mind, meaning each API scope or key grants only the minimum permissions required for its purpose, so that a compromised key or token limits the damage an attacker can cause.

Code signing allows software distributors to cryptographically sign their code using a private key, enabling users and operating systems to verify both the integrity of the code and the identity of its publisher. When an operating system checks the digital signature on a software package before installation, it can confirm that the code has not been modified since it was signed and that it originates from the claimed publisher. Certificate authorities issue code signing certificates to verified publishers, and operating systems and browsers maintain trust stores of accepted certificate authorities. If code is modified after signing, the signature verification fails and the operating system alerts the user or refuses to execute the code. Code signing is an important supply-chain security control that helps prevent distribution of trojanized software.
