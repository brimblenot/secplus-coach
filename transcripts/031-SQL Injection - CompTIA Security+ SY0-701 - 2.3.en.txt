SQL injection, commonly abbreviated as SQLi, is one of the most prevalent and consequential code injection attacks targeting web applications. It occurs when an attacker inserts malicious SQL code into input fields that an application uses to construct database queries, causing the database engine to execute commands that were never intended by the developer. Because SQL is the dominant language for application-database interaction, SQLi vulnerabilities appear across virtually every technology stack and industry sector. The attack requires no special tools in its basic form — a browser and a text field are often sufficient.

To understand how SQL injection works, consider the normal flow of a database-backed application. A login form collects a username and passes it into a query such as SELECT everything FROM users WHERE name equals the submitted value. If a developer constructs that query by concatenating user input directly into the SQL string, an attacker can close the intended string early and append additional SQL logic. The classic example is submitting a value that makes the condition read WHERE name equals anything OR one equals one. Because one always equals one, the database returns every row in the table rather than a single matching record. This single technique can expose entire databases in moments.

SQL injection attacks are categorized into three broad families based on how results are returned to the attacker. In-band SQLi is the most straightforward: query results travel back through the same HTTP channel used to send the attack. Error-based in-band SQLi deliberately forces the database to generate error messages that reveal the database type, version, table names, and column names. For example, submitting a division-by-zero expression causes the database engine to emit a verbose error exposing its internal structure. Union-based in-band SQLi appends a UNION SELECT statement to the original query, piggybacking on the legitimate result set to pull data from entirely different tables. A successful union-based attack requires the injected SELECT to have the same number of columns as the original query and compatible data types, but once those conditions are met an attacker can retrieve usernames and hashed passwords from an admin_users table in a single request.

Blind SQL injection is used when the application does not display database output directly. Boolean-based blind SQLi sends pairs of true and false conditions and observes whether the application responds differently — perhaps returning a product page versus a blank page. By systematically asking questions such as whether the first character of the administrator password equals the letter a, then b, then c, and so on, an attacker iterates through every character until the full value is reconstructed. This is slow but completely reliable. Time-based blind SQLi is used when even behavioral differences are absent. The attacker injects a database delay function — SLEEP in MySQL, WAITFOR DELAY in Microsoft SQL Server, and the pipe receive message function in Oracle — so that if a condition is true the server pauses for several seconds before responding. By measuring response time, the attacker extracts information bit by bit using timing as the side channel. Out-of-band SQLi is less common and relies on the database server initiating a separate outbound connection, such as a DNS lookup or HTTP request to an attacker-controlled server, to exfiltrate data. It is used when in-band communication is unreliable or blocked.

Authentication bypass is one of the most immediately impactful SQL injection techniques. If an attacker submits the string admin followed by two dashes as a username, the resulting query places the double-dash comment delimiter immediately after the username value. Everything after those two dashes, including the AND password equals portion of the WHERE clause, is treated as a comment and ignored entirely. The database authenticates the attacker based solely on the username, granting access without any password check. This single-line attack bypasses login forms in seconds on vulnerable applications.

Beyond reading data, SQL injection can modify, insert, or delete records, call stored procedures, and in some configurations execute operating system commands. Microsoft SQL Server exposes a stored procedure called xp_cmdshell that, when enabled, allows arbitrary shell commands to run under the database service account. MySQL supports reading and writing files on the server filesystem through LOAD FILE and INTO OUTFILE syntax. An attacker who achieves command execution via SQL injection has effectively turned a web form into a remote shell. Automated tools amplify this threat further. SQLmap is a widely available open-source tool that automatically detects injection points, identifies the database type, and extracts schema and data with minimal manual effort. It supports all SQLi techniques and can automate privilege escalation within the database.

A more subtle variant called second-order or stored SQL injection occurs when malicious input is safely stored in the database on first insertion but later retrieved and used in a different query without proper sanitization at the point of reuse. The initial insertion appears harmless, bypassing validation that runs at input time, but when the stored value is later incorporated into another query its malicious content executes.

The primary and most reliable defense against SQL injection is the use of parameterized queries, also called prepared statements. In a parameterized query, the SQL statement structure is compiled by the database driver before any user input is considered. The input is then passed as a separate parameter bound to a placeholder, and the driver treats it as literal data rather than executable SQL regardless of its content. An attacker who submits an apostrophe or a UNION keyword sees those characters stored as data, not interpreted as SQL syntax. Properly implemented stored procedures provide equivalent protection when they avoid dynamic SQL construction internally. Object-relational mapping frameworks such as SQLAlchemy, Hibernate, and Entity Framework use parameterized queries by default and dramatically reduce developer error.

Additional layers of defense reinforce parameterized queries. Input validation and allowlisting reject values that do not match expected formats, such as rejecting non-numeric input in a field that should only accept integers. Web application firewalls inspect incoming HTTP requests and block patterns associated with SQL injection syntax, providing a protective layer even for applications that cannot be immediately patched. Database account least privilege is critical: application accounts should have SELECT access only on the specific tables they need and should never hold data definition language rights, administrative roles, or the ability to execute extended procedures. Suppressing verbose error messages in production environments prevents attackers from using error-based enumeration. Regular vulnerability scanning and penetration testing ensure that new injection points introduced during development are caught before reaching production.

The combination of parameterized queries at the code level, least-privilege database accounts, WAF filtering, and suppressed error output creates a defense-in-depth posture that makes SQL injection attacks either impossible or extremely difficult to execute successfully. For the Security+ exam, parameterized queries are the single most important technical control, and candidates should be able to identify SQL injection attempts by the OR one equals one pattern, the comment-sequence authentication bypass, and the UNION SELECT technique, as well as articulate why input sanitization alone is insufficient compared to true query parameterization.
