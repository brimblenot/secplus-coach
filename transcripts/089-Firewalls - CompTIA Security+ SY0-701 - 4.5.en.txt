Firewalls are the primary network security control responsible for enforcing access policy between network segments by permitting or denying traffic based on defined rules. Every modern network, from a home broadband connection to a global enterprise, relies on firewalls as a foundational control. Understanding how firewalls work, how rules are structured and evaluated, how modern Next Generation Firewalls extend beyond port-based filtering, and how firewalls are deployed in network architectures is essential for the Security+ exam.

The earliest firewalls were packet filters that inspected individual packets and made permit or deny decisions based on the packet header fields: source IP address, destination IP address, source port, destination port, and protocol (TCP, UDP, or ICMP). Packet filters are stateless — they evaluate each packet independently without any awareness of whether that packet belongs to an established communication session. Stateful firewalls, which became standard in the 1990s, maintain a connection state table that tracks the state of each TCP session and the expected behavior of UDP conversations. When a TCP three-way handshake is completed, the firewall creates an entry in its state table recording the source and destination addresses and ports and marks the connection as established. Subsequent packets matching that state table entry are permitted without re-evaluating the rule base for every packet, which improves both performance and security by ensuring that only traffic belonging to legitimately initiated sessions is permitted through. Unsolicited inbound packets that do not match any existing state table entry are automatically denied, blocking attacks that attempt to send spoofed return packets.

Next Generation Firewalls, abbreviated NGFWs, extend stateful inspection with application awareness and additional security services. An NGFW performs deep packet inspection to identify the application generating the traffic regardless of the port being used. This capability, called App-ID by Palo Alto Networks, can distinguish a SharePoint access from a generic HTTPS connection, identify Netflix video streaming versus casual web browsing, recognize SSH tunneling even when it arrives on a non-standard port, and identify Remote Desktop Protocol traffic even when it has been redirected to a different port to evade detection. Application identification enables security policies that control access by application rather than just port and protocol — an organization can allow web browsing while blocking specific categories of web applications such as file sharing or gambling platforms, even though both use HTTPS on port 443. NGFWs often include integrated Intrusion Prevention System functionality, URL filtering, SSL/TLS decryption and inspection, and malware scanning of file transfers within a single appliance.

Firewall rules, also called Access Control Lists or ACLs in some vendor implementations, define the specific conditions under which traffic is permitted or denied. A typical firewall rule includes a source zone or interface, a source IP address or network range, a destination zone or interface, a destination IP address or network range, the protocol (TCP, UDP, ICMP), the destination port or port range, and the action to take (allow, deny, or reject). Additional matching criteria in NGFWs include the identified application, the URL category, the user identity from directory integration, and threat prevention profile assignments. Each rule also typically specifies whether to log matching traffic and at what level of detail.

Rule evaluation follows a top-down, first-match model in virtually all firewall implementations. The firewall evaluates the rule base starting from the first rule and proceeds sequentially until it finds a rule that matches the packet's attributes. When a matching rule is found, the firewall takes the action specified by that rule (permit or deny) and stops evaluating further rules. This model requires that more specific rules appear before more general rules in the rule base. If a general permit rule appears before a specific deny rule, the general rule will match first and the specific deny will never be evaluated. The implicit deny at the bottom of every firewall rule base ensures that any traffic not explicitly matched by a permit rule is automatically denied. Some implementations use an explicit deny-all rule at the bottom of the rule base to make this behavior visible in logs, while others rely on the implicit deny that is built into the firewall engine.

Firewall rule examples illustrate how policies are expressed. A rule permitting inbound HTTPS traffic from any source to a web server might be expressed as: source=any, destination=10.10.0.10, protocol=TCP, destination-port=443, action=allow. A rule blocking all traffic from an untrusted network segment to the sensitive HR data server might be expressed as: source=192.168.50.0/24, destination=10.20.0.50, protocol=any, action=deny. A rule permitting established return traffic for internal users would be handled automatically by stateful inspection rather than requiring an explicit rule. Rule documentation should include a human-readable description of the business purpose for each rule — "Permit web server to receive HTTPS from internet" — and the change request number authorizing the rule. Periodic rule reviews should identify and remove stale rules for systems that no longer exist or access requirements that have changed.

Network Address Translation, abbreviated NAT, is commonly implemented on firewall appliances. Port Address Translation, also called PAT or IP masquerade, allows many internal hosts sharing a private address space to access the internet using a single public IP address. The firewall maintains a translation table mapping each internal host's private address and source port to the public address with a unique translated port number, allowing it to return responses to the correct internal host. Static NAT creates a one-to-one permanent mapping between a private internal address and a public address, used for servers that must be reachable from the internet at a consistent address. Destination NAT, also called DNAT or port forwarding, redirects inbound traffic destined for a specific port on the public IP address to an internal server — incoming traffic on TCP port 443 directed to the public IP is forwarded to the internal web server at 192.168.1.10.

Demilitarized Zone, abbreviated DMZ, is a network architecture concept implemented using firewall policies to create a semi-trusted network segment that hosts systems accessible from the internet while protecting the internal network. In a three-interface firewall deployment, the outside interface connects to the internet, the DMZ interface connects to the segment hosting internet-facing servers such as web servers and mail relays, and the inside interface connects to the trusted internal network. The critical firewall policies for a DMZ are: traffic from the internet to the DMZ is permitted for specific services (HTTP, HTTPS, SMTP); traffic from the internal network to the DMZ is permitted for management; traffic from the DMZ to the inside network is explicitly denied — this is the most important rule, because it prevents an attacker who compromises a DMZ server from pivoting directly to the internal network; and traffic from the DMZ to the internet is permitted for services the DMZ servers need (such as outbound HTTPS for web content fetching or DNS resolution). The DMZ rule blocking DMZ-to-inside traffic is often called the inside deny rule and should be one of the first things verified in any firewall security review.

Firewall log analysis provides valuable security intelligence. Denied traffic logs reveal which systems are attempting unauthorized connections to protected resources, with patterns that may indicate scanning, probing, or attempted exploitation. Permitted traffic logs can reveal unusual patterns such as large outbound data transfers, connections to unusual destinations at unusual hours, or connections from systems that have no business need to communicate with the outside network. Exporting firewall logs to a SIEM enables correlation with logs from other sources — a connection to a known malicious IP that was permitted through the firewall can be correlated with endpoint logs to identify the specific process that made the connection.

Firewall high availability ensures that the firewall does not become a single point of failure for network connectivity. Active-passive high availability deploys two firewall appliances in a pair where the primary firewall processes all traffic while the secondary continuously monitors the primary's health through a dedicated heartbeat link and configuration synchronization channel. When the primary fails, the secondary detects the heartbeat loss and takes over processing of traffic within seconds to minutes, depending on the implementation. Active-active high availability has both firewalls simultaneously processing traffic, distributing the load and providing redundancy, but requires session synchronization between the firewalls to ensure that stateful traffic is handled correctly regardless of which firewall receives each packet.

Virtual firewalls and cloud-native firewall implementations extend firewall protection to virtualized and cloud environments. Cloud security groups, such as AWS Security Groups and Azure Network Security Groups, function as virtual firewalls controlling which traffic is permitted to reach cloud instances. Security groups apply to individual instances or groups of instances and define permitted inbound and outbound traffic by protocol, port, and source or destination. Virtual firewall appliances such as the Palo Alto VM-Series and Fortinet FortiGate VM deploy full-featured NGFW functionality as software running on standard hypervisors or within cloud environments, providing the same policy control and visibility as physical appliances. Cloud Web Application Firewall services such as AWS WAF, Azure Application Gateway WAF, and Cloudflare WAF provide Layer 7 protection for web applications hosted in cloud environments without requiring appliance management.

Zone-based firewall policies organize network interfaces into security zones and define traffic policies between zones rather than between individual interface pairs. In a zone-based model, the internet-facing interface belongs to the untrusted zone, the DMZ servers interface belongs to the DMZ zone, and the corporate network interface belongs to the trusted zone. Policies are then defined at the zone level: traffic from the untrusted zone to the DMZ zone is permitted for web services; traffic from the trusted zone to the DMZ zone is permitted for management; traffic from the DMZ zone to the trusted zone is denied. Zone-based policies scale more cleanly than interface-pair policies when the firewall has many interfaces, and the zone model more naturally expresses the intent of the security policy.

Intrusion Prevention Systems, abbreviated IPS, are often integrated into NGFW platforms and operate alongside the firewall rule base as a second layer of traffic analysis. While the firewall makes access control decisions based on who is allowed to communicate with whom, the IPS analyzes the content of permitted traffic for attack signatures and anomalous patterns. When an IPS detects an attack signature in permitted traffic — such as a SQL injection payload in an HTTPS request that the firewall's rule base allows to reach the web server — the IPS can block that specific session while allowing legitimate traffic to continue. IPS rule bases contain thousands of signatures for known exploits, malware communication patterns, and protocol anomalies, organized into categories that allow administrators to enable, disable, or tune signatures in groups. Inline IPS deployment places the IPS in the traffic path so it can actively block detected attacks, while passive IDS deployment monitors a copy of traffic and generates alerts without blocking. Most modern NGFWs deploy inline threat prevention as an integrated component of the platform rather than as a separate appliance.
