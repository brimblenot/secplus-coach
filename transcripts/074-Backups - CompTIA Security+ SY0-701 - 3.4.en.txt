Backups are the last line of defense against data loss. No combination of security controls prevents all incidents. Ransomware encrypts data despite the best endpoint protection. Hardware fails despite RAID redundancy. Administrators accidentally delete critical data despite access controls. Natural disasters destroy entire data centers despite geographic redundancy planning. In every one of these scenarios, the ability to recover depends on whether a clean, complete, and verified backup exists from which the missing or corrupted data can be restored. Backups deserve the same security attention as the primary systems they protect, because an unprotected backup is as valuable to an attacker as unprotected production data, and an untested backup is no more reliable than no backup at all.

Planning a comprehensive backup strategy requires decisions across multiple dimensions: what data to back up, how frequently to back it up, what backup method to use, what media to store it on, where to store that media, how long to retain backups, and how to verify that backups are restorable when needed. Each of these decisions has security implications, cost implications, and operational implications, and the optimal choices depend on the criticality of the data, regulatory retention requirements, and recovery time and recovery point objectives.

Full backups copy every selected byte of data to the backup destination, regardless of when that data was last changed. A full backup creates a complete, self-contained copy of the source data that can be restored in a single operation without reference to any other backup. The advantages of full backups are simplicity and restore speed: restoring from a full backup requires reading only one backup set, minimizing both the complexity of the restore process and the time required to complete it. The disadvantages are storage consumption and backup duration. Full backups consume the most storage of any backup type because they copy everything every time, regardless of what has changed, and they take the longest to complete, which may be problematic for large datasets with limited backup windows. Full backups of all systems are typically impractical on a daily basis for organizations with large data volumes, so full backups are commonly scheduled weekly with more frequent incremental or differential backups filling the intervals.

Incremental backups copy only data that has changed since the last backup of any kind, whether that last backup was a full or another incremental. A typical schedule might run a full backup on Sunday night and incremental backups on each subsequent night through Saturday. Monday's incremental captures everything changed since Sunday's full. Tuesday's incremental captures only changes since Monday's incremental. Each incremental backup is small and fast to create because only a day's worth of changes must be copied. Storage consumption is minimized across the week because no data is duplicated unnecessarily. The disadvantage of incremental backups is restore complexity and restore time. To restore a system to its Saturday night state requires restoring the full backup from Sunday and then applying each incremental in sequence through Saturday, potentially six separate restore operations. Any gap in the incremental chain, such as a failed Thursday backup, means that Friday and Saturday incrementals cannot be applied correctly, complicating restoration.

Differential backups occupy the middle ground between full and incremental. A differential backup copies all data that has changed since the most recent full backup, regardless of whether any intermediate differential backups have been taken. Using the same weekly schedule, Monday's differential captures changes since Sunday's full. Tuesday's differential captures all changes since Sunday's full, including those already captured in Monday's differential. Each differential backup is therefore larger than the corresponding incremental because it accumulates all changes since the last full rather than only since the last backup. However, restoring from a differential requires only two operations: restoring the most recent full backup and then applying the most recent differential. This is simpler and faster than incremental restoration, which may require applying many individual incrementals. The trade-off is that differential backups consume more storage than incrementals because they reduplicate previously backed-up changed data with each run.

Snapshot backups capture the state of a storage volume or virtual machine at a specific point in time using a copy-on-write mechanism. When a snapshot is taken, the system notes the current state of all data blocks. As subsequent write operations occur, the original version of each modified block is preserved in the snapshot before being overwritten. This allows the snapshot to represent the storage state at the moment it was taken, even as the live storage continues to change. Snapshots are extremely fast to create and have minimal performance impact on production systems, making them practical for frequent or even continuous backup of critical systems. Virtualization platforms including VMware and Hyper-V support VM snapshots that capture the complete state of a virtual machine, including memory state in some configurations, enabling rapid rollback to a known-good state. Storage arrays from vendors including NetApp and Pure Storage support volume-level snapshots at the storage layer, independent of the operating system. Database systems including Oracle RMAN and SQL Server using Volume Shadow Copy Service support application-consistent snapshots that guarantee database consistency at the snapshot point.

A critical limitation of snapshots is that they do not constitute independent backups if they reside on the same storage array as the data they snapshot. If the storage array fails, is corrupted by ransomware, or is physically destroyed, all snapshots on that array are lost along with the primary data. Snapshots are valuable as a fast recovery mechanism for accidental deletion or corruption but must be supplemented with backups that copy data to independent storage.

Replication creates near-real-time copies of data at one or more remote locations. Unlike backup, which creates point-in-time recovery points at defined intervals, replication continuously mirrors changes as they occur, with replication lag typically measured in seconds to minutes. Replication is particularly valuable for hot site disaster recovery, where the secondary site must be kept current enough to assume production operations with minimal data loss. Synchronous replication guarantees zero data loss by requiring confirmation from the remote site before acknowledging each write to the application, at the cost of added write latency. Asynchronous replication minimizes latency by acknowledging writes at the primary site immediately and propagating them to the secondary site afterward, at the cost of a potential data loss window equal to the replication lag. Replication alone is not a substitute for backup because replication faithfully propagates all changes including corruption and ransomware encryption to the secondary site, eliminating its value as a recovery point for those scenarios.

Backup media and destinations span a range from local disk to cloud, each with distinct trade-offs. Local disk backup to a network-attached storage device or tape library provides the fastest backup and restore speeds and the simplest logistics. Its primary weakness is that it is co-located with the primary systems: a fire, flood, ransomware attack that compromises the backup server, or any other disaster affecting the primary site may also affect local backups. Tape backup to LTO Ultrium cartridges offers high capacity per cartridge, low per-gigabyte cost, and the ability to store backup media offline, physically disconnected from any network. Offline tape backups are immune to ransomware because ransomware can only encrypt storage accessible to the compromised systems, and a tape in a vault is not accessible. Tapes can be transported to off-site storage facilities for geographic separation from the primary site. LTO tape generations currently in use support cartridge capacities of twelve terabytes native and beyond, making them economically attractive for archiving large datasets. The disadvantage of tape is slower restore speed compared to disk and the operational overhead of physical media management.

Cloud backup is off-site by nature and eliminates the physical media management burden of tape. AWS S3 Glacier, Azure Blob Storage, and services from backup vendors including Veeam, Acronis, and Cohesity provide cloud backup destinations that scale to virtually unlimited capacity. Cloud backup can be configured with immutability features, specifically object lock in AWS S3 and similar features in other cloud providers, that prevent backup objects from being deleted or modified for a specified retention period. In S3 compliance mode, even accounts with the highest administrative privileges cannot delete objects within the lock period, making these backups extremely resistant to ransomware. The trade-off of cloud backup is that restore speed is limited by network bandwidth and may be inadequate for recovering large datasets within aggressive recovery time objectives.

The 3-2-1 backup rule is the foundational guidance for backup architecture: maintain three copies of data, store them on two different types of media, and keep one copy off-site. Three copies means production data plus two backup copies. Two media types means the backup copies are not stored on identical media, so a failure mode or attack that affects one media type does not affect all copies simultaneously. One off-site copy provides geographic separation to protect against site-level disasters. The extended 3-2-1-1-0 rule adds two requirements: one copy must be offline and completely disconnected from any network, and zero errors means all backups must be verified as restorable. The offline copy requirement directly addresses ransomware, which can reach any storage accessible across the network from a compromised system but cannot reach physically disconnected media.

Backup encryption is mandatory for any backups stored off-site, transported via courier, or stored in cloud services, and is a strong recommendation for on-site backups as well. Backup data contains all the same sensitive information as production data. Backup media that is lost or stolen while containing unencrypted data is a reportable data breach in most jurisdictions. Backup data must be encrypted both in transit during transfer to the backup destination using TLS, and at rest using AES-256. The backup encryption key must be stored separately from the encrypted backup data. Storing the decryption key within the backup is equivalent to locking a house and leaving the key under the mat. Keys should be stored in a separate key management system, hardware security module, or a separately secured location from the encrypted backups. Key management procedures must ensure that keys are available to authorized personnel when recovery is needed but are not accessible to unauthorized parties.

Backup verification is one of the most critical and most neglected aspects of backup management. A backup that has never been tested is of unknown reliability. Storage media degrades over time through a process called bit rot, causing data corruption even with no other adverse event. Backup software may contain bugs that result in incomplete or corrupted backups that appear successful in status reports. Backup jobs may complete without errors but fail to capture specific data because of open file locks, permission issues, or scope configuration errors. Regularly testing restoration from backups, whether by restoring specific files, databases, or entire systems to test environments, is the only way to verify that backups will work when needed. Automated backup verification systems that perform test restores and validate the restored data against checksums or application-level consistency checks provide continuous validation without relying on manually scheduled restore tests. The operationally crucial distinction between a completed backup and a verified backup must be internalized: the backup job completing is only the first step; verified restorability is the actual goal.

Backup retention policies define how long backup copies are kept before being overwritten or deleted. Retention requirements derive from multiple sources. Regulatory frameworks impose specific minimums: HIPAA requires covered entities to retain certain records for six years; Sarbanes-Oxley requires retention of financial records for seven years; PCI DSS requires audit log retention for at least one year with three months immediately available. Business requirements may mandate point-in-time recovery capability extending months into the past to support investigation of data corruption that may not be immediately detected. Legal holds may require that backup data potentially relevant to anticipated litigation be preserved beyond normal retention policy and must not be deleted even if normal retention schedules would call for their deletion. Backup retention policies must be implemented in backup software configuration and reviewed regularly to ensure compliance with current regulatory and business requirements.

Journaling is a technique used by file systems and databases to protect against data corruption from interrupted write operations, such as those caused by unexpected power failures. When a write operation is initiated, the intent of the write is first recorded to a dedicated journal area on the storage device. If power fails or the system crashes during the write, the file system or database can read the journal on restart to determine whether a partial write occurred and complete or roll back the operation to restore consistency. Journaling eliminates the file system corruption that previously required lengthy disk consistency checks after unexpected shutdowns and is standard in modern file systems including NTFS, ext4, and APFS.

Ransomware recovery deserves specific attention in any discussion of backup strategy. Sophisticated ransomware actors, before deploying their encryption payload, deliberately attempt to identify, access, and corrupt or delete backup repositories to eliminate the victim's recovery options. Security controls for backup infrastructure must therefore be as strong as those for production systems. Backup servers should not be joined to the domain whose systems they back up, so that compromised domain credentials do not provide access to backup systems. Backup service accounts should have minimal permissions, sufficient to write backup data but not to delete it. Offline or air-gapped backups are the ultimate defense against ransomware targeting backup systems. When ransomware strikes, recovery begins with identifying the most recent backup confirmed to predate the infection, verifying that the backup itself is clean, restoring systems to an isolated environment for malware scanning before reconnection to production networks, and then reconnecting validated clean systems to production.
