Log data is the raw material of security monitoring, incident investigation, and forensic analysis. Every device, operating system, and application in a modern IT environment generates event logs that record what happened, when it happened, and in many cases who was involved and what the outcome was. Collectively, these logs constitute the most complete record available of everything that has occurred in an environment. Effective log management is not simply a matter of collecting and storing log data but encompasses selecting appropriate log sources, ensuring that security-relevant events are being captured at the right verbosity, centralizing log data for correlation, protecting logs against tampering, retaining logs for the appropriate period, and analyzing log data to detect threats and support investigations. Security practitioners must understand what each major log source contains, what events are most security-relevant, and how all these sources fit together in a comprehensive monitoring architecture.

Windows Event Logs are one of the most important log sources for security monitoring in Windows environments. The Security log is the primary security-relevant log, capturing authentication and authorization events. Understanding critical Windows Event IDs is essential for both security monitoring and the exam. Event ID 4624 is generated for every successful logon and includes the account name, domain, logon type (2 for interactive, 3 for network, 10 for remote interactive), the source IP, and the logon process used. Event ID 4625 is generated for every failed logon attempt and includes the same fields plus a failure reason code, making it essential for detecting brute force and password spraying attacks. Event ID 4648 indicates that a logon was attempted using explicit credentials, which occurs when a user runs a program as a different account and is a technique also used by attackers during lateral movement. Event ID 4672 indicates that special privileges were assigned to a new logon session, identifying when a user with administrative or sensitive privileges logs in. Event ID 4688 records the creation of a new process and, when command-line auditing is enabled, includes the full command line, providing visibility into what programs are being launched and with what arguments. Event ID 4698 records the creation of a new scheduled task, a common attacker persistence technique. Event ID 4720 records the creation of a user account. Event ID 4732 records the addition of a member to a security-enabled local group. Event ID 4740 records an account being locked out. Event ID 4719 records a change to the system audit policy. Event ID 4697 records installation of a new service, another common persistence mechanism. Event ID 4946 and 4948 record changes to Windows Firewall rules. Event ID 1102 records that the Security audit log was cleared, which is highly anomalous in a well-managed environment and often indicates an attacker covering their tracks.

Linux system logs are distributed across multiple files in the /var/log directory, each covering a different scope of events. The /var/log/auth.log file on Debian-based systems, or /var/log/secure on Red Hat-based systems, records all authentication-related events including successful and failed SSH login attempts, sudo command executions with the executing user's identity and the command run, su authentication attempts, and PAM authentication events from any PAM-integrated application. This file is the primary source for detecting authentication attacks, unauthorized access attempts, and privilege escalation on Linux systems. The /var/log/syslog or /var/log/messages file records general system events from the kernel and system daemons. The /var/log/kern.log file records kernel-specific events including hardware issues and kernel module loading. The /var/log/audit/audit.log file is generated by the auditd daemon when audit rules are configured and contains detailed kernel-level audit records of system calls, file access events, network connections, and process execution. Auditd is particularly valuable in high-security environments because it can audit nearly any system activity and generate tamper-resistant records of all privileged operations.

Network device logs from routers, switches, firewalls, and wireless controllers use the Syslog protocol for transmission to a centralized log collector. Syslog messages follow a standardized format defined by RFC 5424 and RFC 3164, containing a priority field encoding the facility and severity, a timestamp, the hostname of the sending device, and the message content. Syslog uses UDP port 514 for connectionless delivery, which is efficient but provides no guarantee of delivery, or TCP port 514 for reliable delivery, or TCP port 6514 for TLS-encrypted transmission. Firewall logs are among the most security-valuable network device logs, recording every permitted and denied connection with source IP address, destination IP address, source port, destination port, protocol, action taken, and often the rule that triggered the action. Next-generation firewall logs include additional information such as the application identified in the traffic, the URL category for web traffic, the user identity if available, and threat or anomaly indicators. Router and switch logs record interface state changes, routing protocol updates, access control list matches, and authentication events for device access. These logs enable detection of network topology changes that may indicate attacker activity.

Web server access logs in Apache and nginx use the Combined Log Format, which records for each HTTP request the client IP address, the timestamp with timezone, the HTTP method and full URL path including query parameters, the HTTP status code returned, the number of bytes in the response, the Referer header showing the page that linked to the request, and the User-Agent string identifying the browser or tool making the request. Web server access logs are critical for investigating web application attacks: SQL injection attempts show characteristic query parameter patterns, directory traversal attacks appear as path sequences with ../ characters, vulnerability scanning tools generate characteristic User-Agent strings or patterns of requests to non-existent URLs, and successful exploitation is often visible in the transition from probing requests to requests that return unusual status codes followed by access to shell command execution URLs.

Database query logs provide visibility into how databases are being accessed and are required by PCI DSS for systems that store, process, or transmit cardholder data. Database logs capture which queries were executed against which tables, by which database user, at what time, from which application or IP address, and with what result. The slow query log records queries that exceed a defined execution time threshold, which can indicate both performance issues and potentially malicious queries such as those performing full table scans to extract large amounts of data. Application-level security logs record authentication events, authorization failures, input validation failures, and application errors that may indicate exploitation attempts or misuse.

Cloud platform audit logs are increasingly important as organizations move workloads to cloud infrastructure. AWS CloudTrail records every AWS API call made to the account, including calls made through the management console, CLI, SDKs, and other AWS services. Each CloudTrail record includes the API action performed, the identity of the caller including account, user, and assumed role, the source IP address, the time, and the specific resources affected. CloudTrail is the primary audit mechanism for AWS and is essential for investigating unauthorized access, detecting privilege escalation, and identifying misconfiguration changes in cloud environments. Azure Activity Log and Azure AD Sign-in logs provide equivalent coverage in Azure, recording management plane operations and authentication events. GCP Cloud Audit Logs cover admin activity and data access events across GCP services.

SIEM systems are the central aggregation, correlation, and analysis platform for log data from all these sources. Log forwarders and agents installed on endpoints and servers collect local log data and forward it to the SIEM. Popular log forwarders include the Splunk Universal Forwarder, Elastic Beats for the Elastic Stack, Fluentd and Logstash for flexible log routing and transformation. Syslog collectors such as rsyslog and syslog-ng receive syslog messages from network devices. Log normalization converts the different formats used by different log sources into a common schema that enables correlation across sources. Common Event Format, or CEF, and Log Event Extended Format, or LEEF, are standardized event representation formats. Elastic Common Schema, or ECS, provides a normalization standard for the Elastic Stack.

Log retention requirements are driven by regulatory compliance obligations and operational security needs. PCI DSS requires that audit logs be retained for at least 12 months with the most recent three months available for immediate analysis. HIPAA requires medical records and associated information to be retained for six years from creation or last active use. SOX requires that financial records including audit logs be retained for seven years. Many security frameworks recommend 12 to 24 months of log retention as a security baseline, with longer periods for high-value systems. Retention is typically structured in tiers: hot storage in the SIEM provides fast query access to the most recent 30 to 90 days of data; warm storage provides compliant access to older data covering the past 6 to 12 months at somewhat higher latency; cold or archive storage holds data for long-term regulatory compliance, often using cost-efficient object storage services.

Log protection and integrity are critical because attackers routinely delete logs to conceal their activities. A compromised endpoint's local logs can be cleared by the attacker, but if those logs have been forwarded to a centralized log server with restricted write permissions, the attacker cannot retroactively delete them from the SIEM. Write-once WORM, or write once read many, storage provides a hardware-enforced guarantee that log data cannot be modified or deleted after being written. Cryptographic log chaining, where each log record includes a hash of the previous record, allows detection of any deletion or modification in the chain. Centralized log infrastructure should be configured so that only log sources can write log data and only authorized analysts can read it, minimizing the number of accounts that could be used to tamper with logs.

Log analysis at scale requires automated tooling because the volume of log data in any significant environment exceeds what can be reviewed manually. SIEM correlation rules trigger alerts when specific patterns of events occur across one or more log sources — for example, alerting when a single source IP generates more than ten failed authentication events within five minutes, or alerting when a new scheduled task is created on a system within an hour after a failed authentication attempt from the same account. UEBA, User and Entity Behavior Analytics, applies statistical analysis and machine learning to baseline normal behavior patterns for individual users and systems, then alerts when observed behavior deviates significantly from that baseline. Threat hunting uses log data as the primary evidence source for proactive investigations driven by threat intelligence and hypotheses about attacker behavior, querying historical log data to answer specific questions rather than waiting for automated alerts to surface anomalies.
