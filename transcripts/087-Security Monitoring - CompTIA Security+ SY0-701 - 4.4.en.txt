Security monitoring is the continuous observation of organizational systems, networks, applications, and user activities to detect threats, policy violations, anomalous behavior, and compliance issues in real time or near-real time. The goal of security monitoring is to reduce the time between attacker activity and defender awareness — the longer an attacker operates undetected, the more damage they can cause. A 2022 IBM Security report documented that the average time for an organization to identify and contain a breach was approximately nine months. During that nine-month window, attackers explore the network, escalate privileges, access sensitive systems, and establish persistent footholds. Effective continuous monitoring compresses this detection time from months to hours or minutes.

The Security Information and Event Management system, commonly abbreviated SIEM, is the central platform for log aggregation, correlation, alerting, and reporting. A SIEM collects log data from every significant source in the environment — firewalls, intrusion detection and prevention systems, servers, workstations, applications, databases, network devices, cloud services, and endpoint security tools — and normalizes the data into a common format that enables correlation across what were previously incompatible log sources. The SIEM stores this normalized data in a centralized database that supports complex queries and correlation rules.

Log aggregation is the collection process that pulls log data from distributed sources into the central SIEM repository. Some sources push logs to the SIEM using syslog or API-based forwarding. Others require the SIEM to pull data by querying APIs, reading log files from network shares, or using database queries. Log normalization extracts common fields — timestamp, source IP, destination IP, user, action, result — from widely varying log formats and maps them to a consistent schema that enables consistent querying and correlation across sources.

Correlation rules define patterns across multiple log sources that together indicate suspicious or malicious activity. A single failed login attempt is unremarkable. A hundred failed login attempts from the same IP address against ten different user accounts within five minutes, followed by a successful login from that same IP address, is a strong indicator of a credential stuffing or password spraying attack that succeeded. Correlation rules codify these multi-source patterns and trigger automated alerts when they are matched. Examples of effective correlation rules include detecting authentication to a VPN or cloud service from a geographic location inconsistent with the user's normal behavior, detecting privilege escalation events shortly after an authentication failure sequence, detecting high-volume outbound data transfer following an inbound connection from a known-malicious IP address, and detecting process creation of known attack tools such as Mimikatz or PowerShell with encoded commands.

Real-time alerting notifies security analysts immediately when correlation rules match or when individual events exceed defined thresholds. Alerts should be prioritized by severity so that analysts focus attention on the highest-risk events first rather than reviewing all alerts in chronological order. Alert tuning is the ongoing process of adjusting alert thresholds and suppressing known-good activity to reduce false positives — an alert that fires hundreds of times per day for legitimate activity trains analysts to ignore it, a phenomenon called alert fatigue that leads to genuine threats being missed amid the noise. Good alert tuning requires establishing behavioral baselines for the environment and suppressing alerts that consistently correspond to legitimate activity.

Security Orchestration, Automation and Response, abbreviated SOAR, extends the SIEM by automating responses to common alert types. SOAR playbooks define automated response actions that execute when specific alerts fire: when a phishing email is detected, a playbook might automatically extract the sender address, embedded URLs, and file attachments, query threat intelligence platforms for reputation information on each indicator, block the sender and URLs across email and web filtering systems, scan all received emails for matching indicators, and create an investigation ticket in the case management system — all within seconds and without analyst intervention. For malware detections on endpoints, a playbook might automatically isolate the affected endpoint from the network, collect a memory dump and disk image for forensic analysis, query the EDR platform for other endpoints that have seen the same file hash, and notify the affected user's manager. Automation through SOAR reduces mean time to respond from hours to minutes for common incident types, freeing analysts to focus on novel and complex incidents requiring human judgment.

Log sources cover every major component of the IT environment and each provides distinct visibility. Firewall logs contain records of permitted and denied connections including source and destination IP addresses, ports, protocols, and action taken — denied traffic analysis reveals scanning, probing, and blocked attack attempts, while permitted traffic analysis identifies unusual communication patterns that may indicate compromise. Intrusion detection and prevention system alerts document detected attack signatures, protocol anomalies, and behavioral indicators. DNS logs are among the most valuable security data sources because DNS is used in nearly every attack: command-and-control beaconing uses DNS to resolve C2 infrastructure, data exfiltration via DNS tunneling generates high volumes of unusual TXT or NULL queries, and malware connecting to Domain Generation Algorithm domains creates distinctive patterns of NXDOMAIN responses as the malware cycles through generated domains looking for the active C2 domain. Web proxy logs record all user web traffic including the URL visited, bytes transferred, HTTP status code, and user identity — malware communicating with C2 servers over HTTP or HTTPS appears in proxy logs, large file downloads from unusual sources may indicate malware delivery, and uploads to unapproved cloud storage may indicate data exfiltration.

Windows Event Logs provide detailed records of operating system activity that are essential for detecting attack techniques on Windows systems. Event ID 4624 records successful logon events including the logon type, source workstation, and source IP address for network logons — monitoring for logons at unusual times or from unusual sources detects credential abuse. Event ID 4625 records failed logon attempts, and a sequence of 4625 events followed by a 4624 event may indicate successful brute force. Event ID 4672 records special privileges assigned to a logon, indicating that an account with administrative privileges has authenticated. Event ID 4688 records process creation with the command line used, enabling detection of attacker tools like Mimikatz, PowerShell with encoded commands, and LOLBAS techniques where legitimate Windows binaries are abused for malicious purposes. Event ID 4648 records explicit credential use, detecting pass-the-hash and credential substitution techniques.

Network monitoring provides visibility into traffic flows that individual host logs cannot capture. NetFlow and IPFIX protocols capture traffic metadata — source and destination IP addresses, ports, protocols, bytes transferred, and duration — without capturing payload content. NetFlow analysis identifies C2 beaconing through regular periodic connections to the same external endpoint, detects lateral movement through unusual internal-to-internal connections, reveals data exfiltration through large outbound transfers to unusual destinations, and identifies port scanning through high numbers of connection attempts to sequential port numbers. Full packet capture stores the complete content of network traffic and enables retrospective analysis of traffic involved in an incident, but is expensive in storage terms and is typically deployed only at key network chokepoints. Network Detection and Response platforms such as Darktrace, ExtraHop, and Vectra AI apply machine learning to network traffic to establish behavioral baselines and detect anomalies that signature-based detection would miss.

User and Entity Behavior Analytics, abbreviated UEBA, establishes behavioral baselines for individual users and systems and generates alerts when behavior deviates significantly from the established baseline. UEBA can detect impossible travel — a user account authenticating from New York and then from London within 30 minutes is impossible with commercial air travel and indicates either account compromise or VPN use not visible to the monitoring system. UEBA detects unusual data access patterns such as a financial analyst account suddenly accessing engineering source code repositories at 3 AM. UEBA detects unusual privileged access such as a standard user account using administrative tools it has never accessed before. UEBA-based detection is particularly valuable for insider threat scenarios where the attacker already has legitimate credentials and therefore does not trigger signature-based detection.

Monitoring for specific high-priority threat patterns enables more effective detection of common attacker techniques. Lateral movement detection monitors for WMI connections, PsExec execution, SMB sessions established between workstations, and Remote Desktop Protocol connections from non-administrative systems. Ransomware indicators include mass file operations with renamed extensions, deletion of Windows Volume Shadow Copies using vssadmin or wmic commands, and network shares accessed at unusually high volumes. Data exfiltration detection monitors for large outbound data transfers, DNS queries with unusually long subdomains indicating DNS tunneling, and connections to cloud storage services not used by the organization. Command-and-control beaconing detection looks for regular periodic connections to the same external IP addresses or domains, particularly when those connections have consistent byte sizes and intervals that indicate automated rather than human-initiated communication.

Simple Network Management Protocol, known as SNMP, provides a standardized mechanism for collecting operational metrics from network devices, servers, and applications. Network Management Stations poll SNMP agents on managed devices at regular intervals to retrieve counters and gauges from the Management Information Base, which contains device-specific operational data organized by Object Identifiers. SNMP traps provide proactive alerting — the SNMP agent sends an unsolicited notification to the management station when a specific condition is met, such as interface utilization exceeding a threshold or a hardware fault occurring, without waiting for the next polling interval. SNMPv3 with authentication and encryption is the only acceptable version for production use — earlier versions transmit community strings in plaintext over the network.

Continuous monitoring programs must address both the technical and operational dimensions of effective security observation. The technical dimension includes deploying log sources, configuring the SIEM, writing and tuning correlation rules, and maintaining monitoring infrastructure. The operational dimension includes staffing a Security Operations Center with analysts capable of investigating and responding to alerts, maintaining playbooks that define the expected response to each alert type, conducting regular threat hunting to find threats that automated detection missed, and measuring and reporting monitoring effectiveness metrics. Organizations without the resources for an internal SOC can leverage Managed Security Service Providers, abbreviated MSSPs, or Managed Detection and Response, abbreviated MDR, services that provide 24/7 monitoring capabilities delivered by external security professionals.
