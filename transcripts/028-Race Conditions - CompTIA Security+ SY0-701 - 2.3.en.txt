A race condition is a class of software vulnerability that occurs when the correctness or security of a program's behavior depends on the relative timing or ordering of operations, and that timing can be influenced in ways the developer did not anticipate. In a concurrent system — one where multiple processes, threads, or users may be interacting with shared resources simultaneously — operations that were designed to be sequential can interleave in unexpected ways, producing states that the developer never intended. Race conditions are notoriously difficult to find through testing because they may only manifest when two operations happen to be scheduled in a particular order, which may be rare or highly environment-dependent.

The most important race condition in the security context is the Time-of-Check to Time-of-Use vulnerability, universally abbreviated as TOCTOU and pronounced "tock-too." A TOCTOU vulnerability arises when a program checks a condition or property at one point in time and then acts on the assumption that the condition remains valid at a later point in time, without verifying that it has not changed in between. The gap between the check and the use is the window of vulnerability: if an attacker can modify the checked condition during that gap, they can cause the program to take an action based on stale information.

A classic file system TOCTOU example illustrates the concept precisely. A privileged program needs to write data to a file specified by the user, but it first checks whether the file path is safe — for example, verifying that the file is not a symlink pointing to /etc/shadow. If the check passes, the program opens the file and writes to it. An attacker who can run code simultaneously exploits the gap between the check and the open by replacing the checked file with a symbolic link pointing to /etc/shadow during that interval. When the program opens the file, it follows the symlink and writes to the sensitive file, bypassing the security check entirely. The check found a safe file; the use opened a dangerous one. The attacker wins the race between their symlink creation and the program's file open call.

Web application TOCTOU vulnerabilities frequently appear in e-commerce and banking contexts. Consider an application that checks whether a product is in stock before processing a purchase. The check confirms availability, the purchase proceeds, and the inventory count is decremented. If two users submit purchase requests for the last unit of an item simultaneously, both requests may reach the stock check before either decrement executes. Both checks confirm availability, both purchases are processed, and the inventory goes negative — the item is sold twice. A more severe financial example involves withdrawal processing: a banking application checks the account balance, determines that the requested withdrawal amount does not exceed the available funds, and then processes the withdrawal. If a user submits two concurrent withdrawal requests, both balance checks may execute before either withdrawal is posted. Both checks show sufficient funds, both withdrawals are approved, and the account is overdrawn by the full amount of the second withdrawal. This double-spend pattern is a fundamental concern in financial software design.

The practical two-user example works as follows. Account A and Account B both start with $100. User One wants to transfer $50 from Account A to Account B. User Two also wants to transfer $50 from Account A to Account B. Both users check the balance of Account A and see $100. Both deposits to Account B are processed immediately: Account B now holds $200. Now both users attempt their withdrawals from Account A. Because the application processes withdrawals without immediate ledger updates, both users see Account A as having $100 when they check before withdrawing. Both withdrawals are approved for $50. The final state has Account A at $0 (which is correct), but the total money in the system has increased from $200 to $200 + $100 = $300 that shouldn't exist, or alternatively Account A should be at $0 but both withdrawals succeeded when only one had sufficient backing. The exact outcome depends on implementation details, but the fundamental problem — that the balance check is not atomic with the balance update — enables financial fraud.

The Dirty COW vulnerability (CVE-2016-5195) is the most famous race condition exploit in Linux kernel history and earned its name from "Dirty Copy-On-Write." The Linux kernel uses a memory optimization called copy-on-write: when a process requests a writable mapping of a read-only file, the kernel does not immediately create a private copy of the file's pages. Instead, it marks the mapping as copy-on-write, meaning a copy will be created only when the process actually writes to it. The Dirty COW race condition existed in the kernel's handling of this copy-on-write mechanism. An attacker could race between two operations — writing to the private copy and discarding the private copy — in a way that caused the kernel to write data to the original read-only file rather than to the private copy. Because even read-only system files like /etc/passwd can be mapped and exploited through this mechanism, any local unprivileged user could overwrite arbitrary read-only files on the system. Writing a new root user entry to /etc/passwd with a known password, for example, immediately grants root access. Dirty COW was present in the Linux kernel for over nine years and affected Android devices, Linux servers, and embedded systems worldwide. It remains one of the most severe local privilege escalation vulnerabilities ever discovered.

Race conditions that occur in safety-critical systems can have consequences beyond security. The Mars Rover Spirit experienced a race condition in 2004 where a file system error triggered a safety mechanism that forced a reboot, but the reboot process immediately encountered the same file system error, creating an infinite reboot loop. The flight software team was able to transmit new code to the rover to bypass the error condition and restore normal operation. While not a security attack, this illustrates that race conditions in software controlling physical systems can produce catastrophic operational failures.

Race conditions have also appeared in modern consumer technology. At the Pwn2Own hacking competition in Vancouver in 2023, researchers demonstrated a TOCTOU race condition vulnerability in the Tesla Model 3's infotainment system, accessible through Bluetooth. By exploiting the race condition, they were able to escalate privileges to the root user of the infotainment system. The successful exploit earned the researchers a $100,000 prize and, per Pwn2Own rules, the Tesla itself.

The fundamental solution to race conditions is ensuring that operations that must be treated as a unit are executed atomically — meaning as a single, indivisible operation that cannot be interleaved with any other concurrent operation. Mutexes (mutual exclusion locks) are synchronization primitives that allow only one thread or process at a time to hold the lock and execute the protected code region; all other threads must wait until the mutex is released. Semaphores are more generalized signaling mechanisms that can control access by multiple threads simultaneously — a counting semaphore allows up to N threads to proceed concurrently, while a binary semaphore with values of zero and one behaves identically to a mutex. Atomic CPU operations such as Compare-And-Swap (CAS) provide hardware-guaranteed atomicity for simple operations: CAS atomically reads a value, compares it to an expected value, and writes a new value only if the comparison matched, all in a single uninterruptible instruction. Database transactions provide atomicity for database operations, ensuring that all steps in a transaction either complete together or are rolled back together, preventing partial updates that create inconsistent state.

File system race conditions can be mitigated by using atomic file operations where available. On Unix systems, creating a file with the O_EXCL flag combined with O_CREAT guarantees that the creation succeeds only if the file did not previously exist, and the check-and-create is atomic — no race window exists between checking and creating. Minimizing the time between a check and a use reduces the probability of exploitation but does not eliminate the race window. The strongest mitigation is architectural: designing systems to avoid shared mutable state where possible, using thread-safe data structures and algorithms, and ensuring that security-sensitive operations combine the check and the action in a single atomic step. Static code analysis tools can identify patterns associated with TOCTOU vulnerabilities, and security-focused code review should specifically examine all code paths where a resource is checked and subsequently used.
