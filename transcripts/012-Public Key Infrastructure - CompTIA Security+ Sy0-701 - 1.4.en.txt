Public Key Infrastructure, commonly abbreviated as PKI, is a broad term in cryptography that refers to the complete set of policies, procedures, hardware, and software responsible for creating, distributing, managing, storing, revoking, and otherwise handling the full lifecycle of digital certificates. Even in smaller organizations, implementing PKI involves a great deal of planning and a substantial number of decisions about which encryption methods and certificate types to use. PKI also serves as the framework for associating certificates with specific people or devices, generally working in conjunction with a Certificate Authority to establish and verify that a particular user or device really is who they claim to be.

Before diving into public key encryption specifically, it is essential to understand symmetric encryption, because the two approaches are used together in almost every modern secure system. Symmetric encryption means that the same key is used to both encrypt and decrypt information. In other words, the single shared secret key that locks the data is the same key that unlocks it. This is sometimes described as a secret key algorithm, and the shared key must be distributed to anyone who needs to decrypt the data. The core strength of symmetric encryption is its speed and low computational overhead. It is far more efficient than asymmetric encryption and is therefore used for the bulk encryption of data, such as encrypting files on a hard drive or encrypting the payload of network traffic. Common symmetric algorithms include the Advanced Encryption Standard with 128-bit or 256-bit keys, which is the current gold standard for bulk data encryption, Triple DES which applies the older Data Encryption Standard algorithm three times and is now considered deprecated, and DES itself which uses only a 56-bit key and is considered completely broken and unsuitable for any security purpose.

The critical weakness of symmetric encryption is the key distribution problem. If you must share the secret key with every person or device that needs to decrypt your data, you immediately face serious scalability challenges. Once an organization grows beyond a handful of individuals, distributing keys securely becomes difficult, and managing which key belongs to which person or device becomes operationally complex. If the key is intercepted during distribution, every piece of data encrypted with that key is compromised.

Asymmetric encryption, also called public key cryptography, solves the key distribution problem by using two mathematically related keys created simultaneously during a single cryptographic operation. One key is designated the private key, which is kept secret by one person or device and never shared with anyone. The other key is designated the public key, which can be freely distributed to the world. The mathematical relationship between the two keys is constructed so that data encrypted with the public key can only be decrypted with the corresponding private key, and vice versa. Critically, you cannot derive the private key from the public key even though they are mathematically related, because the underlying mathematics, typically based on the difficulty of factoring very large prime numbers or computing discrete logarithms, makes reverse engineering computationally infeasible.

The power of this arrangement is that anyone in the world can encrypt a message using your public key, but only you can decrypt it because only you hold the private key. For example, if Alice generates a public and private key pair and publishes her public key on her website, Bob can use that public key to encrypt a message to Alice. Even if that encrypted message is intercepted in transit, an attacker who has the public key cannot use it to decrypt the ciphertext. Only Alice's private key can do that. Asymmetric encryption is used primarily for key exchange and digital signatures rather than for bulk data encryption, because it is significantly slower than symmetric encryption.

In practice, modern secure systems combine both approaches: asymmetric cryptography is used to securely exchange a symmetric session key, and then that fast symmetric key is used to encrypt the actual data. This hybrid approach gets the security benefits of asymmetric key exchange and the performance benefits of symmetric bulk encryption.

A PKI is built around several key components. The Certificate Authority, or CA, is the entity that signs and issues digital certificates. When a CA signs a certificate, it is vouching for the identity of the certificate's subject, whether that subject is a web server, an individual user, or a device. The trust in a PKI flows from the CA: if your system trusts the CA, it will trust any certificate that CA has signed.

At the top of a PKI hierarchy sits the root CA. The root CA is self-signed, meaning its certificate is signed by its own private key rather than by any higher authority, and it is the ultimate anchor of trust in the hierarchy. Because the root CA's private key is so valuable, it must be protected with extreme care. Best practice requires the root CA to be kept offline, meaning it is not connected to any network, and it is only brought online when it needs to sign the certificates of subordinate CAs. Keeping the root CA offline dramatically limits the attack surface.

Beneath the root CA in the hierarchy sit intermediate CAs, also called subordinate CAs. These are the CAs that sign end-entity certificates for actual web servers, users, and devices. Using intermediate CAs is a critical security practice because it limits the exposure of the root CA's private key. If an intermediate CA is compromised, that CA's certificate can be revoked and a new intermediate CA issued, without needing to revoke the root CA and invalidate every certificate in the entire infrastructure. Each link in this chain, from root CA to intermediate CA to end-entity certificate, is signed by the CA one level above it, creating a chain of trust that clients can verify.

The Registration Authority, or RA, is the component responsible for verifying the identity of certificate applicants before forwarding their certificate signing requests to the CA. The RA handles the identity verification process so that the CA itself does not need to interact directly with every individual applicant. In some PKI deployments the RA and CA functions are combined in a single system, while in larger deployments they are separate.

When a certificate needs to be declared invalid before its natural expiration date, for example when a server's private key is compromised or when an employee leaves an organization, PKI provides two main revocation mechanisms. The Certificate Revocation List, or CRL, is a periodically published list of serial numbers of certificates that have been revoked. Clients download the CRL and check whether a certificate's serial number appears on it. The fundamental weakness of CRLs is latency: a certificate may be used between the time it is revoked and the time the next CRL is published and downloaded. During that window, the revoked certificate is still being treated as valid.

The Online Certificate Status Protocol, or OCSP, addresses the latency problem by allowing clients to query the CA's OCSP responder in real time for the status of a specific certificate. The OCSP responder returns a signed response indicating whether the certificate is good, revoked, or unknown. This is faster and more timely than downloading a full CRL, but it introduces a privacy concern: every time a user visits a website, the CA's OCSP responder learns which sites that user visits, because the browser is querying the responder with specific certificate details.

OCSP stapling solves the privacy problem while also improving performance. With OCSP stapling, the web server itself periodically fetches a signed OCSP response from the CA's responder, typically every few hours, and caches it locally. When a client connects, the server presents this cached signed OCSP response alongside its certificate during the TLS handshake. The client receives fresh revocation status information directly from the server without needing to contact the CA at all. Because the OCSP response is signed by the CA, the client can verify its authenticity without trusting the server to be honest. This eliminates the privacy concern, reduces the load on CA infrastructure, and speeds up the handshake.

Key escrow is the practice of storing copies of private keys with a trusted third party. Escrow enables key recovery when the original key is lost, for example when an employee leaves the company or when a hardware device containing a private key fails and encrypted data must still be accessed. In some regulatory and law enforcement contexts, key escrow is required so that government agencies can obtain decryption keys under lawful process. While handing private keys to a third party may seem controversial, it is sometimes necessary for maintaining availability of encrypted organizational data.

Certificate pinning is a technique in which an application hardcodes the expected certificate or public key fingerprint for a specific server. When the client connects, it checks whether the server's presented certificate matches the hardcoded expectation. If the certificate does not match, the connection is rejected, even if the presented certificate is signed by a CA that the operating system's trust store considers valid. Pinning provides protection against attacks where a trusted but rogue CA has issued a fraudulent certificate for a domain it does not control, and it is commonly used in mobile applications.

Trust stores are the collections of trusted root CA certificates maintained by operating systems and web browsers. When your browser connects to a website, it checks whether the certificate chain leads back to a root CA present in the trust store. Commercial public CAs pay to have their root certificates included in major operating system and browser trust stores, which is why certificates from these CAs are automatically trusted by virtually all clients worldwide. Organizations can also run their own internal PKI using an internal CA. In that case, the internal CA's root certificate must be deployed to all client devices within the organization, typically through group policy or mobile device management, so that internal certificates are trusted without error messages.

Wildcard certificates use an asterisk as a placeholder in the domain name, such as the format star-dot-example-dot-com, to cover all subdomains at a single level under a given domain with a single certificate. A wildcard certificate for that format would be valid for www, mail, ftp, and any other subdomain directly under example.com, but it would not cover deeper subdomain levels such as sub.sub.example.com.

Subject Alternative Name certificates, also called SAN certificates or multi-domain certificates, allow a single certificate to list multiple domain names, IP addresses, and other identifiers in their extension fields. Modern TLS relies on SANs rather than the older Common Name field for hostname verification. Large organizations like Google and Microsoft use SAN certificates to secure dozens or hundreds of different domain names with a single certificate, simplifying management.

Certificate-based authentication offers significant security advantages over password-based authentication. A password is a shared secret that can be guessed, phished, or stolen from a server-side credential store. A private key used in certificate authentication never leaves the device, and the authentication challenge-response process means the private key material itself is never transmitted across the network. This makes certificate-based authentication resistant to credential theft and replay attacks. For enterprise environments where employees may leave and encrypted data must remain accessible, a combination of certificate-based authentication and key escrow provides both security and operational continuity.
