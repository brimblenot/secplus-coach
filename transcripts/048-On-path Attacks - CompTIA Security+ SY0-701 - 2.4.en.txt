An on-path attack, historically called a man-in-the-middle attack, occurs when an attacker secretly positions themselves between two communicating parties and intercepts, and potentially modifies, the traffic flowing between them. Both parties believe they are communicating directly with each other, and from their perspective the conversation appears entirely normal. The attacker relays messages between the two parties, maintaining the appearance of a valid connection while having full visibility into the communication. In some implementations, the attacker can also modify data in transit in real time, changing transaction amounts, injecting commands, or altering content before it reaches the intended recipient. The invisibility of the attack to the victim parties is what makes on-path attacks particularly dangerous and why they form the foundation for several other attack categories.

ARP spoofing, also called ARP poisoning, is one of the most common techniques for executing an on-path attack on a local area network. The Address Resolution Protocol maps IP addresses to MAC addresses within a local network segment. When a device wants to communicate with another device on the same subnet, it sends a broadcast ARP request asking which device holds a particular IP address, and the device with that IP responds with its MAC address. The requesting device caches this mapping so it does not have to repeat the resolution on every packet. ARP was designed without any authentication mechanism. A device on the network can send an unsolicited ARP reply, called a gratuitous ARP, at any time, and other devices will update their ARP cache with the new mapping regardless of whether they requested it.

An attacker exploits this by sending gratuitous ARP replies to victim devices, mapping the IP addresses of trusted hosts such as the default gateway or a server to the attacker's own MAC address. When the victim's laptop wants to send traffic to the router, its ARP cache says the router's MAC address is the attacker's MAC address, so the packet is physically delivered to the attacker's machine. The attacker receives the frame, can read or modify it, and then forwards it to the actual router using the router's real MAC address. The same poisoning is applied in the other direction, so the router's ARP cache maps the laptop's IP to the attacker's MAC. This places the attacker's device in the middle of every conversation between the victim and the gateway, enabling full interception and modification of traffic on the local segment. Tools such as arpspoof, Ettercap, and Bettercap automate this process. Dynamic ARP Inspection, a feature of managed switches, defends against ARP spoofing by validating ARP packets against a trusted binding table populated by the DHCP snooping process. If an ARP reply's claimed IP-to-MAC mapping does not match the DHCP binding table, the switch drops the frame and optionally generates a log entry. Static ARP entries for the most critical hosts, VLAN segmentation, and port security are complementary defenses.

SSL stripping, also called an HTTPS downgrade attack, is an on-path technique that degrades a victim's connection from encrypted HTTPS to unencrypted HTTP. When a user types a domain name into a browser without explicitly specifying HTTPS, the initial request goes out over HTTP. The attacker, positioned on the path, intercepts this HTTP request, establishes an HTTPS connection to the legitimate server on behalf of the victim, and returns only an HTTP response to the victim's browser. The victim sees no padlock icon and no HTTPS in the address bar but assumes the site is legitimate. From this point forward, all communication between the victim and the attacker flows as cleartext HTTP, while the attacker maintains an encrypted HTTPS session with the actual server. The attacker can read every username, password, session token, and piece of sensitive data submitted by the victim. HTTP Strict Transport Security, or HSTS, is the primary defense against SSL stripping. When a server sends the HSTS header, the browser caches a record that the domain must always be accessed over HTTPS, and the browser refuses to make any plain HTTP request to that domain for the duration of the max-age period. HSTS preloading goes further by including the domain in a list hardcoded into browsers before they have ever contacted the server, preventing the initial HTTP connection that SSL stripping requires.

BGP hijacking exploits the Border Gateway Protocol, the routing protocol that controls how traffic is routed across the internet between autonomous systems. BGP relies on trust between network operators, and there is no cryptographic verification of route announcements in traditional BGP. An attacker who controls a BGP-speaking router can announce a more specific or equivalent route for a target IP prefix, causing other networks to forward traffic destined for the victim through the attacker's infrastructure. BGP hijacking has been used to intercept cryptocurrency transactions, conduct mass credential harvesting, and surveil communications. The attack can affect traffic globally in a matter of minutes. Resource Public Key Infrastructure, or RPKI, provides cryptographic attestation of route origin, allowing routers to verify that an autonomous system has the right to announce a given prefix, and is the primary technical defense against BGP hijacking.

Session hijacking involves stealing a valid, already-authenticated session token and using it to impersonate the victim to a web application without needing their credentials. After a user authenticates to a web application, the server creates a session token, typically stored in a browser cookie, and includes it in subsequent requests to identify the authenticated session. An attacker who obtains this token can present it to the server and access the application as the authenticated user. Session tokens can be captured through cross-site scripting attacks that cause the victim's browser to send the cookie contents to the attacker, through packet sniffing on unencrypted connections, or through sidejacking, which was popularized by the Firesheep Firefox extension that captured unencrypted session cookies on open wireless networks. Defenses include using HTTPS for all communications to prevent sniffing, setting the HttpOnly flag on session cookies to prevent JavaScript access, setting the Secure flag to ensure cookies are only sent over HTTPS, using short session token lifetimes that limit the window of opportunity for replay, and regenerating session tokens after privilege changes such as login or role elevation.

TLS inspection, also called SSL inspection or HTTPS interception, is a form of intentional on-path interception deployed by enterprise security appliances. A corporate firewall or web proxy terminates the TLS connection from the client, decrypts the traffic for inspection by data loss prevention or malware detection engines, re-encrypts the traffic, and forwards it to the destination. The client is presented with a certificate signed by the organization's internal certificate authority rather than the website's actual certificate. This is legitimate and authorized in enterprise environments where users are informed of the practice and the organization's CA certificate is installed in the trust store of corporate devices, but it creates an organizational man-in-the-middle that processes all encrypted web traffic.

Downgrade attacks force communication parties to negotiate weaker cryptographic protocols or cipher suites than they would prefer. Several historically significant vulnerabilities fall into this category. POODLE, Padding Oracle On Downgraded Legacy Encryption, exploited the fallback mechanism in some TLS implementations that would attempt SSL version 3 when TLS negotiation appeared to fail. SSLv3 uses CBC mode padding that is vulnerable to a padding oracle attack, allowing an attacker to decrypt traffic by making repeated requests and analyzing error responses. BEAST, Browser Exploit Against SSL and TLS, targeted a weakness in CBC mode as implemented in TLS 1.0 that allowed an attacker to perform a chosen-plaintext attack against the session. DROWN, Decrypting RSA with Obsolete and Weakened eNcryption, allowed servers that supported both SSLv2 and modern TLS to have their TLS traffic decrypted by exploiting the SSLv2 export-grade key exchange. The defense across all of these variants is to disable obsolete protocol versions entirely. TLS 1.0 and TLS 1.1 should be disabled; TLS 1.2 should be treated as the minimum acceptable version, with TLS 1.3 preferred because its handshake design eliminates entire classes of downgrade attacks through authenticated negotiation.

ICMP redirect attacks send crafted ICMP Redirect messages to a victim host, instructing it to update its routing table to send traffic through the attacker as a next hop for a particular destination. While modern operating systems ignore ICMP redirects by default for security reasons, misconfigurations or older systems may still be vulnerable.

Defending against on-path attacks comprehensively requires strong transport encryption using TLS 1.3 with mutual authentication where both sides present certificates, certificate pinning in mobile applications to prevent acceptance of fraudulent certificates, VPN tunnels that encrypt all traffic end-to-end regardless of the application protocol, Dynamic ARP Inspection and DHCP snooping on managed switches to prevent local ARP poisoning, HSTS and HSTS preloading to prevent SSL stripping, DNSSEC to prevent DNS-based redirection, RPKI to prevent BGP hijacking, network monitoring for anomalous ARP traffic patterns, and public key infrastructure that establishes verified identities for communicating parties.
