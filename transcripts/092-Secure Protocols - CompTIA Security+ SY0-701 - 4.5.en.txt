Protocol security is built on a simple principle: always choose encrypted, authenticated protocols over their plaintext equivalents. Every protocol used on a network represents either a protected channel or an exposed one, and the choice between secure and insecure versions often comes down to nothing more than configuration. Understanding the security properties of common protocols, their associated port numbers, and the specific attacks that exploit insecure versions is central to the Security+ examination and to practical network defense. The goal is not merely to know that encryption exists but to understand what each protocol protects, what it does not protect, and what the consequences are when the insecure version is deployed.

Web protocols form the foundation of modern internet communication. HTTP operates on port 80 and transmits all content in plaintext. Every URL, every form submission, every cookie, and every response body is visible to anyone positioned to capture traffic on the network path between client and server. This exposure enables passive eavesdropping, session hijacking through cookie theft, and manipulation of content in transit. HTTPS, which runs on port 443, is HTTP transported over TLS. The TLS layer encrypts all HTTP traffic so that neither request content nor response content can be read by network observers. TLS also provides server authentication through the certificate presented by the server, which is validated against the client's trusted certificate authority store. A valid certificate proves that the server is who it claims to be, protecting against impersonation attacks. HTTPS should be mandatory for all web services; running any web application over HTTP in the modern environment represents an unacceptable risk to user data and session integrity.

File transfer protocols cover the movement of files between systems, and this category has evolved significantly as the security weaknesses of older protocols became clear. FTP uses ports 20 and 21, transmitting both credentials and file content in clear text across the network. Anyone who can capture traffic between an FTP client and server can read the username, password, and every file transferred. FTP has been effectively replaced by more secure alternatives in most environments, though it may still appear on legacy systems. SFTP, which stands for SSH File Transfer Protocol, operates on port 22 and runs as a subsystem over an established SSH connection. All data is encrypted within the SSH tunnel, and authentication uses the SSH authentication mechanisms including public key authentication. SFTP is functionally a separate protocol from FTP despite the similar name and provides a complete replacement for FTP in secure environments. FTPS, which stands for FTP over SSL or TLS, is actual FTP protected by a TLS layer, and it is important to understand that FTPS and SFTP are completely different protocols despite their similar names. FTPS operates in two modes: explicit mode, which starts on port 21 and upgrades the connection to TLS using the STARTTLS command, and implicit mode, which uses port 990 and assumes TLS from the beginning of the connection. FTPS maintains compatibility with the FTP protocol structure while adding TLS encryption, whereas SFTP is entirely different and uses the SSH protocol family.

Remote access protocols provide terminal access to systems, and the contrast between Telnet and SSH illustrates the evolution of security thinking clearly. Telnet operates on port 23 and transmits everything in plaintext, including all commands typed, all output received, and all credentials entered during the session. An attacker capturing Telnet traffic can reconstruct an entire session, reading every command executed and potentially harvesting credentials for further attacks. Telnet has been replaced by SSH in virtually all environments, though it may still be found on legacy network devices. Secure Shell, or SSH, operates on port 22 and provides an encrypted, authenticated remote administration channel. SSH supports public key authentication, where the client holds a private key and the server holds the corresponding public key. Public key authentication is more secure than password authentication because there is no password to capture from the wire and brute forcing an asymmetric key pair is computationally infeasible with appropriate key lengths. Beyond interactive sessions, SSH supports SCP for encrypted file copy operations, SFTP for full file transfer operations, and port forwarding, which tunnels other protocols through the encrypted SSH channel.

Email protocols span the full lifecycle of message delivery and retrieval, and each stage has both secure and insecure versions. SMTP, the Simple Mail Transfer Protocol, operates on port 25 and handles mail transfer between servers. Port 25 traffic should use STARTTLS for opportunistic encryption, though this is not guaranteed. Port 587 is the designated mail submission port and should require STARTTLS, providing TLS-protected mail submission from email clients. Port 465 is used for SMTPS, where SMTP operates over TLS from the beginning of the connection. IMAP, the Internet Message Access Protocol, runs on port 143 in its unencrypted form and allows email clients to access and manage messages stored on a mail server. IMAPS, IMAP over TLS, runs on port 993 and should always be used instead of port 143. POP3, the Post Office Protocol version 3, provides a simpler mail retrieval service on port 110, downloading messages from the server to the client. POP3S, POP3 over TLS, operates on port 995. In any environment, the unencrypted versions of these email protocols should be disabled in favor of their TLS-protected equivalents to prevent credential and message content exposure.

Directory services use LDAP, the Lightweight Directory Access Protocol, to query and update directory databases such as Active Directory. Standard LDAP on port 389 transmits all data in plaintext, which means that authentication credentials, including passwords submitted during LDAP bind operations, travel across the network without protection. LDAPS, LDAP over TLS, operates on port 636 and encrypts all directory traffic including authentication. In any environment where LDAP is used for authentication, LDAPS should be required. Some environments implement STARTTLS-based LDAP encryption on port 389 as an alternative, but the key requirement is that plaintext LDAP be prohibited, particularly for authentication traffic.

Network management protocols, specifically SNMP, are important security considerations in infrastructure management. SNMP versions 1 and 2c use community strings as a form of authentication, but those community strings are transmitted in plaintext as part of every management message. A community string is effectively a password, and transmitting passwords in plaintext means any attacker capturing network traffic can harvest the community string and use it to query or potentially modify managed devices. SNMPv3 addresses these weaknesses by adding authentication and encryption. The authentication option uses HMAC with MD5 or SHA, and the privacy option uses DES or AES to encrypt the message payload. The SNMPv3 authPriv mode, which enables both authentication and privacy, should be the only version permitted in secure environments.

Time synchronization using NTP is a critical but often overlooked security protocol requirement. NTP operates on port 123 and provides clock synchronization across network devices. Accurate time is essential for security systems for two reasons. First, Kerberos authentication, used in Active Directory environments, requires that clocks between a client and an authentication server be within five minutes of each other. A clock skew beyond this threshold causes authentication failures that can be exploited to deny service. Second, log correlation across multiple devices requires accurate timestamps. If system clocks drift, correlating events from different devices to reconstruct an attack timeline becomes unreliable. NTPsec is a modernized, security-hardened implementation of NTP that supports authenticated NTP to prevent clock manipulation attacks. Internal NTP hierarchies, where servers synchronize from a trusted external source and internal clients synchronize from internal servers, reduce exposure to manipulation of external time sources.

Voice and video communication protocols introduce distinct security requirements. SIP, the Session Initiation Protocol, handles call setup and signaling for VoIP communications. Unencrypted SIP uses port 5060, while SIPS, the secure version, uses port 5061 with TLS. SIP establishes voice calls, but the actual audio is carried by RTP, the Real-time Transport Protocol, which itself is unencrypted. SRTP, the Secure Real-time Transport Protocol, provides encryption and authentication for the media streams, protecting the actual voice and video content from eavesdropping. Using SIPS for signaling and SRTP for media provides end-to-end protection for VoIP calls. DTLS, Datagram Transport Layer Security, is TLS adapted for UDP transport and is used in WebRTC, the browser-based real-time communication framework, to secure media streams without requiring dedicated signaling infrastructure.

DNS security deserves careful attention because DNS underpins nearly all internet communication. Standard DNS operates on port 53 using UDP for queries and TCP for large responses, and it transmits all queries and responses in plaintext. This means that anyone monitoring network traffic can see every domain name a client resolves, revealing browsing activity, application usage, and potentially sensitive business information. Plaintext DNS is also vulnerable to cache poisoning attacks, where attackers inject false records into resolver caches, redirecting clients to attacker-controlled systems. DNSSEC, DNS Security Extensions, addresses the integrity concern by adding cryptographic signatures to DNS responses. Each DNS zone signs its resource records with a private key, and resolvers can verify these signatures using the published public key, establishing a chain of trust from the DNS root down through each level of the hierarchy. DNSSEC prevents cache poisoning by making it impossible to forge valid signed records, but it does not encrypt queries and does not provide confidentiality. DoH, DNS over HTTPS, sends DNS queries as HTTPS traffic on port 443, encrypting the query content and making it indistinguishable from normal web traffic. This protects query privacy but makes it harder for network administrators to monitor DNS traffic. DoT, DNS over TLS, uses port 853 as a dedicated encrypted DNS channel, providing query confidentiality while remaining identifiable as DNS traffic for network monitoring purposes.

IPsec provides security at the IP layer, below the transport and application layers, making it protocol-agnostic. The Encapsulating Security Payload, or ESP, uses protocol number 50 and provides both encryption and authentication for IP packets. The Authentication Header, or AH, uses protocol number 51 and provides authentication and integrity without encryption. Internet Key Exchange, IKE, uses UDP ports 500 and 4500 to negotiate security associations and manage cryptographic keys. IPsec operates in two modes: tunnel mode wraps the original IP packet entirely within a new encrypted packet, hiding both payload and original headers, and is used for VPN connections between networks. Transport mode encrypts only the payload of the original packet while leaving the IP headers in place, and is used for host-to-host security. IPsec is the underlying technology for many enterprise VPN solutions and for protocols like L2TP/IPsec.

The key exam expectation for secure protocols is knowing port numbers for both secure and insecure versions of each protocol family, understanding what attacks are enabled by using the insecure version, and knowing when to choose one secure protocol over another. The pattern is consistent: plaintext protocols expose credentials and content to any network observer, while their secure counterparts add TLS or SSH encryption to protect data in transit. For the exam and in practice, there is almost never a justification for using Telnet over SSH, HTTP over HTTPS, FTP over SFTP, LDAP over LDAPS, or IMAP over IMAPS in any environment where security is a concern.
