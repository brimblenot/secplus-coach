Firewalls are the most fundamental network security control, deployed at network perimeters, between internal segments, within cloud environments, and on individual hosts. They control the flow of traffic between network zones by evaluating packets or sessions against defined rules and either permitting or denying passage. Not all firewalls are equivalent, however — they vary enormously in the depth of traffic inspection they perform, the criteria they use to make decisions, and the capabilities they bring beyond basic traffic filtering. Understanding the distinct characteristics of each firewall type, and selecting the appropriate type for a given security requirement, is essential knowledge for the Security+ exam.

The simplest form of firewall is the packet filtering firewall, which operates at Layer 3 and Layer 4 of the OSI model. Packet filtering firewalls examine individual packets in isolation, evaluating only the header information: source IP address, destination IP address, source port, destination port, and protocol — typically TCP, UDP, or ICMP. Access control lists define what combinations of these header values are permitted or denied. Packet filtering is stateless — each packet is evaluated independently, with no knowledge of whether it belongs to an established connection or represents an unsolicited inbound attempt. This statelessness is both the source of the packet filter's speed advantage and its fundamental security weakness. A packet filter cannot determine whether an inbound TCP packet with the ACK flag set is a legitimate response to an outbound connection or a crafted packet designed to probe the firewall. It cannot detect IP fragmentation attacks that split malicious content across multiple fragments. It cannot detect session hijacking or connection state manipulation. Packet filtering is appropriate for high-throughput environments where the performance overhead of stateful inspection is prohibitive, or as a coarse outer filter in front of more capable devices, but it provides inadequate protection as the sole perimeter security control.

Stateful inspection firewalls, also described as circuit-level gateways or stateful packet inspection firewalls, address the fundamental limitation of packet filtering by tracking the state of active network connections in a state table. When an internal host initiates a TCP connection to an external server — completing the three-way handshake with SYN, SYN-ACK, and ACK — the firewall records this connection in its state table, noting the source IP, destination IP, ports, and expected sequence numbers. When the external server responds with inbound packets, the firewall checks these packets against the state table and permits them only if they match an entry representing a legitimate established session. An inbound packet that does not correspond to any established session in the state table is blocked. This dramatically improves security compared to packet filtering because unsolicited inbound connection attempts — regardless of what port or address they target — are blocked unless an explicit firewall rule permits them independent of state. The state table also enables correct handling of complex protocols like FTP that use separate control and data connections. Stateful inspection firewalls remain the most common type deployed for network perimeter protection and are the baseline expectation when the term firewall is used without further qualification.

Application-layer firewalls, sometimes called application-aware firewalls or proxy-based firewalls, operate at Layer 7 and understand specific application protocols. Rather than simply allowing or blocking based on port and IP address, an application-layer firewall parses the actual application protocol — HTTP, FTP, SMTP, DNS, or others — and enforces policies based on application-layer content. An HTTP proxy firewall can block specific HTTP methods, enforce URL filtering, detect HTTP protocol anomalies that might indicate command injection, and inspect request content for malicious patterns. Application-layer inspection can detect attacks that are invisible to stateful firewalls: FTP PORT command injection, DNS zone transfer abuse, SMTP relay abuse, and HTTP methods not used by legitimate browsers. The tradeoff is significantly greater processing overhead compared to stateful inspection, because the firewall must fully parse and understand each application session rather than simply tracking connection state.

Next-Generation Firewalls, universally abbreviated as NGFW, represent the current state of the art in network perimeter security. NGFWs perform stateful inspection as a baseline and extend it with deep packet inspection — the ability to read, parse, and analyze payload content across all traffic flows. Application identification, often called App-ID in Palo Alto Networks terminology, allows the NGFW to identify what application is generating traffic based on behavioral signatures and protocol characteristics rather than relying on port numbers. This is critical in the modern network where applications routinely use non-standard ports, tunnel within other protocols, or use port 80 and port 443 for all communication. A NGFW can identify that traffic on port 443 is Netflix video streaming versus corporate VPN versus encrypted file exfiltration and apply different policies accordingly. User identity awareness — User-ID — links traffic flows to specific authenticated users by integrating with Active Directory or other identity providers, enabling policies like permitting a marketing team to access social media platforms while blocking engineering team members from the same sites based on group membership rather than IP address.

NGFWs integrate intrusion prevention system capabilities directly, applying IPS signature matching and behavioral analysis to traffic that the NGFW would otherwise permit based on firewall rules. SSL/TLS inspection — sometimes called SSL decryption or man-in-the-middle inspection — allows the NGFW to decrypt encrypted HTTPS and other TLS-protected traffic, inspect the decrypted content for threats and policy violations using all available inspection capabilities including IPS, anti-malware, URL filtering, and application identification, and then re-encrypt the traffic before forwarding it. Without SSL inspection, up to ninety percent of modern internet traffic would be opaque to security inspection. Threat intelligence integration feeds the NGFW with continuously updated information about known malicious IP addresses, domains, and file hashes, allowing automatic blocking of traffic to and from known command-and-control infrastructure, phishing domains, and malware distribution sites. Cloud-based sandboxing allows suspicious files to be forwarded to a cloud analysis environment where they are executed and their behavior observed before being delivered to the end user, detecting zero-day malware that evades signature-based detection. Palo Alto Networks NGFWs, Fortinet FortiGate, and Cisco Firepower are leading commercial NGFW platforms.

Web Application Firewalls serve a distinct and complementary purpose to NGFWs. While a NGFW is designed to protect a network segment broadly — examining all types of traffic and making decisions about what is permitted based on application identity, user identity, and threat signatures — a WAF is purpose-built specifically to protect web applications from attacks targeting the application layer of HTTP and HTTPS traffic. A WAF is typically deployed as a reverse proxy in front of web servers, receiving all inbound HTTP and HTTPS connections from the internet and forwarding only validated, non-malicious requests to the backend web application.

WAFs detect and block attacks that directly target web application vulnerabilities. SQL injection attacks insert malicious SQL code into parameters that a web application includes in database queries, potentially exposing, modifying, or deleting database contents. Cross-site scripting attacks inject client-side scripts into content that is then rendered in other users' browsers. Cross-site request forgery tricks authenticated users into unknowingly making requests to an application they are authenticated to. Application layer denial of service uses valid HTTP requests — often in high volumes — to overwhelm web servers in ways that network-layer DDoS defenses do not address. WAFs operate using two complementary security models. A positive security model defines what constitutes a valid legitimate request — acceptable characters in each parameter, valid URL structures, expected request sizes, allowed HTTP methods — and rejects anything that deviates from this defined valid pattern. Positive security models provide strong protection even against completely novel attacks because anything not explicitly permitted is blocked, but they require detailed modeling of the application's expected inputs. A negative security model maintains a database of known attack patterns and blocks requests matching those patterns — easier to implement initially but requiring continuous updates to remain effective against new attack variants. AWS WAF, Cloudflare WAF, ModSecurity with the OWASP Core Rule Set, and Azure Application Gateway WAF provide WAF capabilities for various deployment environments. PCI DSS requirement 6.6 mandates either a WAF or a comprehensive code review for web applications that handle payment card data.

Unified Threat Management appliances combine firewall functionality with multiple additional security functions in a single device. A UTM typically includes a stateful firewall, IDS and IPS, VPN concentrator, antivirus and anti-malware scanning, web content filtering, email anti-spam, and sometimes WAN connectivity functions. The appeal of UTM is management simplicity: a single device with a single management interface provides comprehensive security coverage without requiring expertise in operating multiple separate specialized products. UTM is most appropriate for smaller organizations that lack the security staff to manage a complex multi-device security architecture. The tradeoffs are significant: UTM devices generally do not achieve best-of-breed performance in any individual security function, performance degrades substantially when multiple functions are enabled simultaneously on high-traffic networks, and many UTM devices operate only at Layer 4 for firewall decisions, lacking the application-layer awareness of NGFWs. Fortinet FortiGate models targeting small businesses, SonicWall, and Sophos are well-known UTM vendors.

Cloud-based firewall deployment takes several forms. NGFW as a service delivers next-generation firewall capabilities from cloud infrastructure without requiring hardware procurement or management — traffic is redirected to cloud-hosted firewall instances for inspection before being forwarded to its destination. This model is particularly relevant for organizations implementing SASE architectures. Security groups in AWS, Azure Network Security Groups, and equivalent constructs in other cloud providers function as stateful instance-level firewalls that control which traffic can reach individual virtual machine instances or containers. Security group rules specify allowed traffic by source IP or security group, protocol, and port — traffic that does not match an allow rule is implicitly denied. Because security groups are stateful, return traffic for established connections is automatically permitted. Network Access Control Lists in AWS VPCs apply at the subnet level rather than the instance level. Unlike security groups, NACLs are stateless — both inbound and outbound rules must be explicitly defined, and return traffic must be permitted by an explicit outbound rule. NACLs provide a coarse additional filtering layer at the subnet level that complements the fine-grained instance-level security groups.

Host-based firewalls run as software on individual computers and servers, enforcing traffic rules for traffic flowing to and from that specific host. Windows Defender Firewall, iptables, nftables, and firewalld on Linux systems are common host-based firewall implementations. Host-based firewalls protect systems in two scenarios where network firewalls may not provide sufficient coverage: when a device is used on untrusted networks — a laptop on a hotel Wi-Fi network is not protected by the corporate perimeter firewall — and when an attacker has achieved a foothold inside the trusted network and attempts lateral movement between internally networked hosts. Network perimeter firewalls do not inspect traffic flowing between two systems on the same internal segment — the traffic never crosses the perimeter firewall. Host-based firewalls provide the control layer that limits lateral movement even within the trusted interior network.

East-west firewalls extend perimeter security concepts to traffic flowing between servers within a data center or cloud environment, as opposed to the traditional north-south traffic model of filtering traffic entering and leaving the network perimeter. In modern data centers and cloud environments, the majority of traffic flows east-west — between application tiers, microservices, databases, and supporting infrastructure. If an attacker compromises one server in a data center where all east-west traffic is implicitly trusted, they can move freely to any other server on the same segment. East-west firewalls or microsegmentation controls apply the same deny-by-default principles to internal data center traffic that perimeter firewalls apply at the network edge.

Implicit deny versus explicit deny is a foundational concept for firewall rule design. Implicit deny means that any traffic not explicitly permitted by a rule is automatically dropped at the end of the rule list — the firewall requires no explicit deny-all rule at the bottom because the default action for unmatched traffic is to deny it. This is the correct and expected behavior for any properly configured firewall and ensures that traffic can only flow when a deliberate rule explicitly permits it. Explicit deny means there is a specific rule in the rule base that actively matches specific traffic and denies it, often used to ensure a specific block is logged or to override a more general permit rule earlier in the rule base.
