Operating systems are the foundational software layer of every computing device — the platform upon which all applications run, all user interactions occur, and all security controls are implemented. Because every device runs an operating system, and because the operating system has privileged access to all hardware resources and all user data, operating systems represent an exceptionally attractive target for attackers. A vulnerability in the operating system is potentially more severe than a vulnerability in any single application because the operating system's compromised state can undermine every security control built on top of it.

The complexity of modern operating systems guarantees the presence of vulnerabilities. Windows 11 is estimated to contain tens of millions of lines of code. The Linux kernel alone runs to tens of millions of lines. No software of that size and complexity has ever been written without security vulnerabilities, and the only question is which vulnerabilities exist and whether attackers will find them before defenders. Security researchers, both in the vendor's employ and working independently, continuously analyze operating system code to discover vulnerabilities. When found, these vulnerabilities are documented as CVEs — Common Vulnerabilities and Exposures — and patches are developed and released. Microsoft has institutionalized this through Patch Tuesday, the second Tuesday of every month, when Microsoft releases its accumulated security patches as a coordinated batch. A single Patch Tuesday can address dozens or hundreds of vulnerabilities. For example, on May 9, 2023, Microsoft released nearly 50 separate security patches addressing vulnerabilities including eight elevation of privilege vulnerabilities, four security feature bypass vulnerabilities, and twelve remote code execution vulnerabilities. The April 2023 Patch Tuesday addressed nearly 100 vulnerabilities. The Microsoft Security Response Center at msrc.microsoft.com documents all security bulletins, CVE details, affected products, and patch availability.

Unpatched operating systems are one of the most reliably exploited targets in the threat landscape because attackers can use publicly documented, proven exploits against known vulnerabilities. Once a patch is released, the existence of the underlying vulnerability becomes widely known — the patch itself describes what was fixed, and security researchers and attackers alike can reverse engineer the patch to understand the vulnerability. The time between patch release and functional exploit code available in the wild has shrunk dramatically over the years, sometimes measured in hours. The EternalBlue exploit (MS17-010) demonstrates this concretely: Microsoft released the patch for the SMBv1 vulnerability in March 2017. The WannaCry ransomware campaign using EternalBlue as a worm propagation mechanism launched in May 2017, approximately eight weeks after the patch was available. Organizations that had not patched their Windows systems in those eight weeks were left vulnerable to one of the most damaging ransomware outbreaks in history. The principle is clear: once a patch is released, the window between patch availability and active exploitation closes rapidly, and unpatched systems face an increasing risk that grows with every passing day.

End-of-life operating systems create a particularly difficult challenge because the vendor no longer releases security patches, leaving discovered vulnerabilities permanently unaddressed. Windows XP reached its end-of-life in April 2014. Windows Server 2003 support ended in July 2015. Windows 7 reached end-of-life in January 2020. Despite these dates, all three operating systems remain in active use in healthcare organizations running medical devices, manufacturing facilities running industrial control systems, government agencies with legacy infrastructure, and financial institutions running critical applications that have never been migrated. After end-of-life, every vulnerability discovered in these systems is a zero-day with no vendor remedy — no patch will ever be available. Organizations that must continue running end-of-life systems must implement compensating controls: network isolation to prevent direct internet connectivity, application allowlisting to prevent execution of unauthorized software, enhanced monitoring for anomalous behavior, and host-based firewalls to restrict which services and ports are accessible. The discovery and maintenance of a complete asset inventory is essential — organizations have found legacy systems running unsupported operating systems on old hardware under desks or in storage rooms that the IT department did not know existed, systems that represent unprotected entry points into the network.

Default configurations are a significant source of operating system vulnerability because vendor defaults prioritize functionality, compatibility, and ease of use over security. Windows systems historically shipped with services enabled by default that are not needed in most environments: the Print Spooler service (which has been the source of multiple serious vulnerabilities including PrintNightmare), the Telnet server (which transmits all data including credentials in cleartext), SMBv1 (which was exploited by EternalBlue and should have been disabled globally years before WannaCry), and NetBIOS and LLMNR (which can be abused for credential capture). Default administrative network shares such as ADMIN$, C$, and IPC$ provide access to file system and administrative functions across the network and are sometimes accessible with default or weak credentials. Default account names — Administrator on Windows, root on Linux — are known to attackers, and using known usernames reduces the work required for brute force or credential stuffing attacks. Configuration hardening using established benchmarks — the Center for Internet Security (CIS) Benchmarks and the Defense Information Systems Agency (DISA) Security Technical Implementation Guides (STIGs) — provides prescriptive, tested guidance for securing each operating system type to a defensible baseline.

Kernel vulnerabilities are the highest-impact class of operating system vulnerability because the kernel runs in ring 0, the most privileged processor mode, with unrestricted access to all hardware resources, all memory, and all system operations. A vulnerability in kernel code that allows arbitrary code execution gives the attacker complete control of the system, below any security controls implemented by the operating system's user-space components. Dirty COW (CVE-2016-5195) is a landmark example: a race condition in the Linux kernel's copy-on-write page handling allowed any local unprivileged user to write to any read-only memory-mapped file, including /etc/passwd, achieving full root privilege escalation. PrintNightmare (CVE-2021-1675 and CVE-2021-34527) was a critical Windows Print Spooler vulnerability that allowed both local privilege escalation and remote code execution, extensively exploited before patches were available. Kernel vulnerabilities are particularly dangerous when combined with remote code execution vulnerabilities in network-facing services, because the combination allows an external attacker to achieve remote root or SYSTEM access without any user interaction.

Device driver vulnerabilities are closely related to kernel vulnerabilities in severity, because device drivers run in kernel space and have the same privilege level as the kernel itself. A bug in a device driver is effectively a kernel-level code execution vulnerability. A particularly notable attacker technique is BYOVD — Bring Your Own Vulnerable Driver. Attackers package a legitimately signed but vulnerable driver and install it on target systems, then exploit the known vulnerability in the signed driver to gain kernel-level code execution. Because the driver is legitimately signed by a trusted certificate authority, Secure Boot and code signing requirements do not block it. BYOVD allows attackers to bypass security controls that rely on kernel integrity, including security product drivers that monitor system behavior.

Privilege escalation is the process of moving from a limited account to a more privileged one. Vertical privilege escalation means moving from user-level to administrator or root. Horizontal privilege escalation means accessing resources that belong to another user at the same privilege level. Many of the most dangerous exploits chain initial access with a privilege escalation vulnerability: a phishing email provides code execution as a limited user, and a kernel exploit or misconfiguration elevates that to SYSTEM or root, enabling full system compromise.

Windows-specific privilege escalation vectors include unquoted service paths: when a Windows service executable path contains spaces and is not enclosed in quotes, the Service Control Manager may attempt to run executables at each space-delimited segment of the path, which can be exploited by placing a malicious executable at a guessable location. Weak service permissions may allow non-administrative users to modify the executable associated with a service that runs as SYSTEM, replacing it with a malicious binary. DLL search order hijacking places a malicious DLL in a directory that Windows searches before the directory containing the legitimate DLL, causing the malicious DLL to be loaded instead. Registry key permission misconfigurations may allow standard users to modify registry keys that control service behavior or application startup. LSASS (Local Security Authority Subsystem Service) memory reading via tools like Mimikatz extracts cached credential hashes and plaintext passwords from memory, enabling lateral movement.

Linux-specific privilege escalation vectors include SUID and SGID bit misconfigurations. When the SUID (Set User ID) bit is set on an executable, it runs with the permissions of the file's owner — often root — rather than the permissions of the user who executed it. Legitimate uses of SUID include commands like passwd and sudo, but unnecessary SUID binaries that can be exploited to break out into a root shell are a common privilege escalation path. World-writable directories in the PATH environment variable allow a user to place malicious programs that are executed instead of system binaries when they appear earlier in the search path. Sudo misconfigurations — entries in /etc/sudoers granting users the ability to run specific programs as root without a password (NOPASSWD) — are frequently exploited, particularly when those programs can be used to spawn shells. Cron job files and scripts that are writable by non-root users but executed as root can be modified to include attacker-controlled commands. The /tmp directory's world-writable nature enables symlink attacks against programs that create predictably named temporary files.

Boot-level threats represent the deepest level of operating system compromise. Bootkits are malware that installs itself in the Master Boot Record or EFI System Partition, executing before the operating system loads and persisting across operating system reinstallations because they exist below the OS layer. UEFI firmware vulnerabilities can allow attackers to modify the firmware itself, creating persistence that survives even full disk replacement. Secure Boot is a UEFI standard that validates the cryptographic signature of each component in the boot chain — bootloader, kernel, drivers — before allowing it to execute. Secure Boot prevents unauthorized or modified bootloaders from loading, protecting against bootkits, though it depends on the integrity of the signing certificates and the UEFI implementation itself. TPM — Trusted Platform Module — chips provide hardware-based storage for cryptographic keys and can be used to attest that the boot chain has not been tampered with.

Defenses against operating system vulnerabilities combine technical controls with process discipline. Patch management must be timely and systematic: patches should be prioritized by CVSS score and known exploitation status, with critical patches targeting network-facing services applied as rapidly as testing allows, and automated patching deployed for systems where testing overhead is low. Before patching complex production environments, patches should be tested on representative systems to verify that they do not break applications. Backups must be maintained so that problematic patches can be rolled back. Configuration hardening using CIS Benchmarks and STIGs brings systems to a secure baseline from default. Least privilege ensures that user accounts do not have administrative rights they do not require, and services run as dedicated minimal-permission accounts rather than as SYSTEM or root. Removing unnecessary services and applications reduces attack surface by eliminating potential entry points. Endpoint detection and response products monitor for behavioral indicators of compromise, including privilege escalation patterns, unusual process behavior, and credential dumping activity. Application allowlisting prevents the execution of unauthorized programs, which is one of the most effective compensating controls for end-of-life systems that cannot be patched. Vulnerability scanning with authenticated credentials reveals the actual patch state and configuration posture of all systems. File integrity monitoring detects unauthorized changes to critical system files, which may indicate that an attacker has modified system binaries to maintain persistence.
