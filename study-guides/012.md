## Public Key Infrastructure (PKI)

PKI is the complete framework — policies, hardware, software, and procedures — for creating, distributing, managing, and revoking digital certificates. It matters because nearly every secure system you interact with (HTTPS, VPNs, email encryption) depends on it.

---

### Symmetric encryption: one key does everything

**Symmetric encryption** is a method where the exact same secret key is used to both encrypt and decrypt data — whoever wants to read the data must possess that same key.

- Fastest encryption method; lowest computational cost
- Used for **bulk encryption** — encrypting files, hard drives, or large network payloads
- The sender must securely deliver the key to every recipient — the **key distribution problem**

| Algorithm | Key Size | Status |
|---|---|---|
| **AES** (Advanced Encryption Standard) | 128-bit or 256-bit | Current gold standard |
| **3DES** (Triple DES — applies old DES algorithm 3×) | 112/168-bit effective | Deprecated |
| **DES** (Data Encryption Standard) | 56-bit | Completely broken |

> Think of symmetric encryption like a physical padlock: both people need a copy of the same physical key, which means you have to hand someone a copy — and handing it over is the risky part.

---

### Asymmetric encryption: a matched key pair

**Asymmetric encryption** (also called **public key cryptography**) solves the key distribution problem by using two mathematically linked keys generated together — one **private key**, kept secret and never shared, and one **public key**, freely distributed to anyone.

- Data encrypted with the public key can **only** be decrypted by the matching private key — and vice versa
- You **cannot reverse-engineer** the private key from the public key — the math (factoring huge prime numbers, discrete logarithms) makes it computationally infeasible
- Much **slower** than symmetric encryption, so it is used for **key exchange and digital signatures**, not bulk data

> Think of the public key as a mail slot: anyone can drop an encrypted envelope through it, but only you hold the key to the locked mailbox on the other side.

---

### Hybrid approach: combining both

Modern secure systems (like TLS/HTTPS) use **asymmetric encryption to securely exchange a symmetric session key**, then switch to fast symmetric encryption for all actual data. This gets the security of asymmetric key exchange plus the speed of symmetric bulk encryption — neither approach alone would be as effective.

---

### PKI components

**Certificate Authority (CA)** — the entity that signs and issues digital certificates, vouching for the identity of a server, user, or device. If your system trusts a CA, it trusts every certificate that CA signed.

**Root CA** — the top of the PKI hierarchy; its certificate is **self-signed** (no higher authority signs it), making it the ultimate trust anchor. Because its private key is so critical, **best practice keeps the root CA offline** and air-gapped, only brought online to sign subordinate CA certificates.

**Intermediate CA** (also called **subordinate CA**) — sits below the root CA and actually signs end-entity certificates (web servers, users, devices). If an intermediate CA is compromised, its certificate can be revoked without invalidating the entire PKI. This chain — root → intermediate → end-entity — is the **chain of trust**.

**Registration Authority (RA)** — verifies the identity of certificate applicants before forwarding requests to the CA. The RA handles the vetting process so the CA doesn't interact with every individual applicant directly.

---

### Certificate revocation

When a certificate must be invalidated before it naturally expires (e.g., private key is stolen, employee leaves):

| Mechanism | How it works | Key weakness |
|---|---|---|
| **CRL** (Certificate Revocation List) | CA publishes a periodic list of revoked serial numbers; clients download and check it | **Latency** — revoked cert stays trusted until next CRL is downloaded |
| **OCSP** (Online Certificate Status Protocol) | Client queries CA's OCSP responder in real time for a single cert's status | **Privacy** — CA learns every site the user visits |
| **OCSP Stapling** | Server fetches and caches a signed OCSP response, presents it during the TLS handshake | Solves both problems — no CA contact, no privacy leak |

> OCSP stapling is like a store pre-printing a "verified fresh" label (signed by the supplier) so every customer doesn't have to call the supplier themselves.

---

### Certificate types

**Wildcard certificate** — uses `*.example.com` to cover **all single-level subdomains** (www, mail, ftp) under one domain with a single certificate. Does **not** cover deeper levels like `sub.sub.example.com`.

**SAN certificate** (Subject Alternative Name, also called **multi-domain certificate**) — lists multiple domain names, IP addresses, and identifiers in one certificate. Modern TLS uses SANs for hostname verification (not the older Common Name field).

---

### Other PKI concepts

**Key escrow** — storing a copy of a private key with a trusted third party to allow recovery if the original is lost (employee departure, hardware failure, or lawful government process).

**Certificate pinning** — an application hardcodes the expected certificate or public key fingerprint for a specific server; if the presented certificate doesn't match — even if a trusted CA signed it — the connection is rejected. Protects against rogue CAs issuing fraudulent certificates.

**Trust store** — the collection of trusted root CA certificates built into an OS or browser. Commercial CAs pay to be included; internal CAs must have their root cert pushed to devices via group policy or MDM (**Mobile Device Management** — a system for centrally managing device settings).

**Certificate-based authentication vs. passwords** — a password is a shared secret that can be phished or stolen from a server. A **private key never leaves the device** and is never transmitted, making certificate auth resistant to credential theft and replay attacks.

---

### Recap

- **Symmetric** = one shared key, fast, bulk encryption; **asymmetric** = key pair, slow, used for key exchange and signatures; real systems use both together
- Root CA stays **offline**; intermediate CAs sign end-entity certs; compromise of an intermediate doesn't destroy the whole PKI
- **CRL** has latency problems → **OCSP** fixes latency but leaks privacy → **OCSP stapling** fixes both
- Wildcard certs cover one subdomain level; SAN certs cover multiple domains in one certificate
- Certificate-based auth is stronger than passwords because the private key never leaves the device and is never transmitted

### Exam flags

- **CRL vs. OCSP vs. OCSP stapling** — know what problem each solves and what weakness remains
- **Root CA offline / chain of trust** — why the root CA is kept offline and what happens if an intermediate CA is compromised
- **Symmetric vs. asymmetric trade-offs** — which is used for bulk encryption vs. key exchange, and why hybrid systems exist
