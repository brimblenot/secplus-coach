## Application Attacks

Application attacks target the logic and implementation of software — not the network or OS beneath it. As perimeters have hardened, attackers shifted focus to web apps and APIs, which are internet-exposed by design and often handle user input carelessly. This lesson covers the major vulnerability classes you'll see on the exam.

---

### Insecure Direct Object Reference (IDOR)

**IDOR** — Insecure Direct Object Reference — occurs when an application exposes a reference to an internal resource (a database record, file, or object) without checking whether the requesting user is *authorized* to access that specific resource.

- Classic example: URL ends in `userId=123` → attacker changes it to `userId=124` → sees someone else's private data
- Extremely common in **REST APIs** — Representational State Transfer APIs — where resources are addressed by sequential numeric IDs
- Fix: use indirect references (a server-side table maps what the user sees to the real ID), enforce per-request authorization, validate server-side

> Think of IDOR like a hotel: the front desk gives you key card for room 123, but the door to room 124 opens anyway because nobody checks that the key matches *that room specifically*.

---

### Directory traversal

**Directory traversal** (also called **path traversal**) lets an attacker read files outside the directory an application is meant to serve, by injecting `../` sequences into a file-path parameter to climb up the directory tree.

- `../../../../etc/passwd` on Linux → reads the system password file
- Attackers bypass naive filters using **URL encoding** — representing characters as percent-encoded values: `%2e%2e%2f` instead of `../`
- Exposes source code, config files, credentials, private keys
- Fix: reject path separators in input, **canonicalize** — resolve all `..` references — before opening files, use an allowlist of valid filenames, run the web server in a **chroot jail** — a restricted filesystem environment where the process cannot see files outside a designated root directory

> It's like a parking garage attendant who's told "stay on level 2," but you hand them directions saying "go up two ramps, then down three" — if they follow the directions literally, they end up somewhere they're not supposed to be.

---

### Server-Side Request Forgery (SSRF)

**SSRF** — Server-Side Request Forgery — tricks the server into making HTTP requests to destinations the attacker chooses, rather than the application's intended targets.

- Targets apps that fetch remote content on the user's behalf (URL previewers, image fetchers, webhooks)
- High-value target in cloud: the **instance metadata service** at `169.254.169.254` — a link-local address exposing credentials and config for the cloud VM — can be reached if the server fetches attacker-supplied URLs
- Also reaches `127.0.0.1` services like **Redis** (an in-memory data store) or **Elasticsearch** (a search/analytics engine) that bind to localhost and assume they're unreachable from outside
- Fix: allowlist permitted outbound destinations, block private IP ranges at the network level, disable unnecessary URL schemes (`file://`, `gopher://`), network-segment backend services

> SSRF is like tricking a bank teller into going to the back vault on your behalf — you can't get back there yourself, but you convinced someone with access to fetch things for you.

---

### Command injection

**Command injection** lets an attacker execute arbitrary OS commands by embedding **shell metacharacters** — special characters like `;`, `|`, and `&` that a shell interprets as command separators or operators — into input the application passes to a system shell.

- Example: app runs `ls -la {filename}` → attacker supplies `file.txt; cat /etc/passwd;` → shell executes all three commands
- Root cause: application does not separate *data* from *commands*
- Fix: never build shell commands from user input; use **parameterized subprocess APIs** — functions that pass arguments as arrays, not concatenated strings — so user input is always treated as data, never parsed as shell syntax; allowlist permitted input characters; run with minimal privileges

> It's like a form that lets you write in the subject line of an email, but someone writes "; delete all emails" — if the system blindly runs it as a command, chaos follows.

---

### XML External Entity injection (XXE)

**XXE** — XML External Entity injection — exploits **XML parsers** — software that reads and processes XML-formatted data — that honor external entity references embedded in the document.

- Attacker declares an entity pointing to `file:///etc/passwd` → vulnerable parser fetches and includes that file's contents in the response
- Can also pivot to **SSRF** by referencing internal URLs
- Fix: disable external entity processing in the parser config; prefer JSON over XML where possible

> It's like a document template that says "insert the contents of file X here" — and the attacker writes the name of your secret configuration file as file X.

---

### LDAP injection

**LDAP injection** targets applications that build **LDAP** — Lightweight Directory Access Protocol, a protocol for querying directory services like Active Directory — queries by concatenating unsanitized user input.

- Attacker injects extra filter conditions to bypass authentication, broaden searches, or dump directory contents
- Same principle as SQL injection, applied to directory services instead of databases

---

### Cross-Site Request Forgery (CSRF)

**CSRF** (also **XSRF**, pronounced *surf*) — Cross-Site Request Forgery — tricks an authenticated user's browser into sending an unauthorized request to a web app on their behalf, using their valid session cookie.

- Browser automatically attaches session cookies to every request for a domain, regardless of where the request originates
- Attacker embeds a malicious link or `<img>` tag → victim's browser fires a state-changing request (funds transfer, password change) while the victim is logged in
- Fix: **CSRF tokens** — unique, unpredictable values the server embeds in each form and verifies on submission, so a forged request from another origin lacks the correct token and is rejected; **SameSite cookie attribute** — a browser instruction (`Strict` or `Lax` mode) to withhold cookies on cross-origin requests, providing defense-in-depth

> Imagine someone mails you a pre-addressed, pre-stamped letter and tells you to "just sign here." You sign without reading, and it turns out you just authorized a wire transfer — your signature was real, but the action wasn't yours.

---

### Clickjacking

**Clickjacking** overlays an invisible or transparent **iframe** — an HTML element that embeds another webpage inside the current page — containing a malicious target over a visible, legitimate page, so victims click what they can see but trigger what they can't.

- Can hijack authenticated actions, capture keystrokes from hidden input fields, or perform any click-triggered action on a trusted page
- Fix: **X-Frame-Options** HTTP header set to `DENY` or `SAMEORIGIN` — tells the browser to refuse to render the page inside any iframe; **Content-Security-Policy `frame-ancestors` directive** — the modern, more flexible equivalent

---

### Session fixation

**Session fixation** is an attack where the attacker pre-establishes a known session ID on the server, tricks the victim into authenticating with that same ID, then uses it to access the now-authenticated session.

- Some apps accept a session ID in the URL → attacker embeds a link with their own controlled session ID → victim logs in through the link → attacker's pre-known ID is now authenticated
- Fix: generate a **completely new session identifier** upon successful login, invalidating the pre-authentication session

---

### Privilege escalation

**Privilege escalation** in web applications exploits insufficient authorization logic to gain access beyond what a user should have.

| Type | What it does |
|---|---|
| **Horizontal escalation** | Accesses resources of *other users at the same privilege level* (e.g., reading another user's messages by changing an ID) |
| **Vertical escalation** | Gains access to *higher-privilege functions or data* (e.g., reaching admin features as a regular user) |

> Horizontal is sneaking into a neighbor's apartment on the same floor; vertical is taking the elevator to the penthouse management suite.

---

### Insecure deserialization

**Deserialization** — the process of reconstructing an object from encoded data — becomes dangerous when the application deserializes data from an untrusted source without validation.

- Many serialization formats allow the data itself to specify the object *type* and parameters to instantiate → attacker crafts a payload that triggers **arbitrary code execution** when deserialized
- Java deserialization vulnerabilities hit **Apache Struts**, **WebLogic**, and **JBoss** — major enterprise platforms — severely
- **PHP object injection** and **Python pickle deserialization** carry the same risk in those ecosystems

> It's like a self-assembling furniture kit where the instructions come from the customer — if nobody checks the instructions, the customer can tell the machine to build something dangerous instead.

---

### Defenses: the bigger picture

**OWASP Top 10** — the Open Web Application Security Project's list of the most critical web application vulnerability categories — is the industry-standard reference for secure development priorities.

- Developer training on OWASP Top 10
- Input validation and **output encoding** — escaping special characters before rendering user-supplied data in a page, to prevent injection
- **Parameterized queries** — database queries that keep data separate from SQL syntax, preventing SQL injection
- **WAF** — Web Application Firewall — a security control that inspects HTTP traffic and blocks common attack patterns
- **DAST** — Dynamic Application Security Testing — automated attack-style scanning of a running application during QA
- **SAST** — Static Application Security Testing — source code analysis before deployment
- **Principle of least privilege** for all database and service accounts

---

### Recap

- **IDOR** = accessing another user's resource by changing an identifier; fix with per-request authorization checks
- **Directory traversal** uses `../` sequences (and URL-encoded variants) to escape the intended directory; fix with canonicalization and allowlists
- **SSRF** makes the server fetch attacker-chosen URLs — especially dangerous in cloud where `169.254.169.254` exposes instance credentials
- **CSRF** hijacks a logged-in user's browser to send forged requests; CSRF tokens and the SameSite cookie attribute are the primary defenses
- **Session fixation** is countered by issuing a new session ID at login; **insecure deserialization** can lead to remote code execution

---

### Exam flags

- **IDOR vs. CSRF vs. session fixation** — know what each exploits and what its specific defense is (authorization checks vs. CSRF tokens vs. new session ID at login)
- **SSRF in cloud environments** — the metadata service at `169.254.169.254` is a named high-value target; expect scenario questions involving cloud credential theft via SSRF
- **Clickjacking defenses** — `X-Frame-Options` and `Content-Security-Policy frame-ancestors` are the specific HTTP headers; know both
