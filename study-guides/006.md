## Gap Analysis

Gap analysis is the structured process of comparing what your security program *actually* does against what a chosen standard *requires* — then documenting every shortfall so you can fix it. It's the backbone of compliance programs, post-incident reviews, and security budget justifications.

---

### What a gap analysis is and why organizations run one

A **gap analysis** is a formal evaluation that compares an organization's current security posture to a defined target state and documents the differences — called **gaps** — between the two. The output is a prioritized list of shortfalls and a roadmap for fixing them.

Organizations run gap analyses for five main reasons:

- **Regulatory compliance** — HIPAA, PCI DSS, and CMMC require proof that specific controls exist
- **Pre-audit preparation** — find deficiencies before external auditors do
- **Program development** — reveal which foundational controls are missing when building a new security program
- **Post-incident review** — identify the control failures that allowed a breach
- **Budget justification** — quantify shortfalls to justify spending to executives and boards

> Think of it like a pre-inspection walkthrough before a health department visit: you tour the kitchen yourself first, find every violation, and fix them before the official inspector arrives.

---

### The five steps of a gap analysis

**Step 1 — Define the target baseline**
Pick the standard that represents "good security" for your organization. Common choices:

| Framework / Standard | Best fit for |
|---|---|
| **NIST CSF** — a flexible risk-based cybersecurity framework | Most organizations |
| **NIST SP 800-53** — comprehensive catalog of security controls | Federal systems |
| **NIST SP 800-171** — controls for protecting **CUI** (Controlled Unclassified Information) on non-federal systems | Defense contractors |
| **ISO/IEC 27001** — international standard for an **ISMS** (Information Security Management System) | Global enterprises |
| **PCI DSS** — Payment Card Industry Data Security Standard | Orgs that handle card data |
| **HIPAA Security Rule** | Healthcare organizations |

**Step 2 — Assess the current state**
Gather evidence of what controls actually exist. Methods include:

- **Interviews** — IT staff, HR, business unit leaders, system admins
- **Documentation review** — policies, configs, network diagrams, audit logs
- **Technical testing** — vulnerability scanning, penetration testing, config reviews
- **Direct observation** — watch whether procedures are actually followed

> The gap between what policies *say* should happen and what *actually* happens is where the biggest gaps hide.

Assessment covers three dimensions:

- **People** — security team qualifications, staff training, defined roles
- **Technology** — controls in place, proper configuration, logging/monitoring, coverage of cloud/endpoints/OT
- **Processes and policies** — documented policies, management approval, consistent enforcement, incident response and vendor risk management procedures

**Step 3 — Identify the gaps**
Document every area where current state falls short. Specificity matters enormously:

- ❌ Vague (useless): *"Security could be better."*
- ✅ Specific (actionable): *"The org does not review privileged user accounts regularly, violating NIST SP 800-53 control AC-2(7)."*

**Step 4 — Prioritize by risk**
Not all gaps are equal. Rank by: likelihood of exploitation, potential business impact, remediation cost/complexity, and regulatory deadlines. **Heat maps** — color-coded grids where red = critical, yellow = moderate, green = minor — are the standard visualization tool.

**Step 5 — Build the remediation roadmap**
Assign each gap an owner, timeline, resource requirement, and success metric. This roadmap drives budget requests and executive reporting.

---

### Technical vs. policy gaps — both must be addressed

| Type | Examples of gaps found |
|---|---|
| **Technical** | Missing MFA, unpatched software, insecure configs, no encryption, no network segmentation |
| **Policy/Process** | No written policy, policy exists but isn't followed, untrained staff, no incident response procedure |

Technical controls without supporting policies get misconfigured or bypassed. Policies without technical controls can't be reliably enforced. You need both.

---

### Gap analysis vs. risk assessment

These are related but distinct:

| | Gap analysis | Risk assessment |
|---|---|---|
| Core question | "What controls do we have or lack vs. a standard?" | "How likely is a specific threat to exploit a specific vulnerability?" |
| Measured against | An external or internal standard/framework | Specific threat scenarios |

Gap analysis findings *feed into* risk assessments — each gap is a potential vulnerability a threat could exploit.

### Zero trust gap analysis

**Zero trust** is a security model that eliminates implicit trust inside the network, requiring strong identity verification for every access request regardless of where the user or device is located. It also requires **microsegmentation** — dividing the network into small zones so a compromise in one area can't reach others — plus device health verification and continuous validation.

A **zero trust gap analysis** specifically identifies: where implicit trust currently exists (e.g., a flat internal network where any device can reach any other), which identity verification mechanisms are missing, and what steps lead to full zero trust implementation.

> On a flat network, once an attacker gets inside, they can move anywhere — like a thief who breaks into a building lobby and finds every internal door propped open.

---

### OT environments and gap analysis challenges

**OT** (Operational Technology) environments — including **ICS** (Industrial Control Systems) and **SCADA** (Supervisory Control and Data Acquisition) systems that control physical processes like power grids or manufacturing lines — are uniquely hard to assess because:

- Legacy OS that cannot be patched
- Proprietary protocols that standard security tools don't understand
- High availability requirements make scanning potentially disruptive

**IEC 62443** is the framework specifically designed for OT security gap analysis.

---

### Recap

- A gap analysis compares current security posture to a target baseline (NIST, ISO, PCI, etc.) and documents shortfalls
- The five steps are: define target → assess current state → identify gaps → prioritize by risk → build remediation roadmap
- Assessment covers people, technology, and processes — all three must be evaluated
- Gap analysis asks "what's missing vs. a standard?"; risk assessment asks "how likely/impactful is a specific threat?" — they're complementary, not the same
- OT environments (ICS/SCADA) require specialized frameworks like IEC 62443 due to patching and availability constraints

### Exam flags

- **Gap analysis vs. risk assessment** — know the distinct question each answers and how gap findings feed into risk assessments
- **Framework selection** — know which standard applies to which context (NIST 800-171 for CUI/defense contractors, PCI DSS for card data, HIPAA for healthcare, IEC 62443 for OT)
- **Zero trust gap analysis** — know what it specifically evaluates: implicit trust relationships, identity verification gaps, and microsegmentation readiness
