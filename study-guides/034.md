## Virtualization Vulnerabilities

Virtualization lets one physical server run dozens of isolated workloads — but that shared hardware creates attack paths that don't exist on dedicated machines. This lesson covers the vulnerabilities the exam tests: hypervisor types, VM escape, VM sprawl, isolation failures, container weaknesses, and Kubernetes misconfigurations.

---

### Type 1 vs. Type 2 hypervisors

A **hypervisor** is the software layer that creates, runs, and manages virtual machines (VMs).

| Type | How it runs | Examples | Security posture |
|------|-------------|----------|-----------------|
| **Type 1 (bare-metal)** | Directly on hardware — no host OS underneath | VMware ESXi, Microsoft Hyper-V, KVM | Smaller attack surface; used in production |
| **Type 2 (hosted)** | As an app on top of an existing host OS | VMware Workstation, VirtualBox, Parallels | Inherits every host OS vulnerability; dev/test only |

*Analogy:* A Type 1 hypervisor is a bank vault built into the building's foundation. A Type 2 is a safe sitting inside a regular office — anything that breaks into the office can also attack the safe.

---

### VM escape — the most severe virtualization vulnerability

**VM escape** is an attack where malicious code inside a guest VM exploits a flaw in the hypervisor or hardware emulation layer to break out of the VM boundary and reach the hypervisor itself or other VMs on the same host.

- One successful escape can expose **every tenant** on that physical host simultaneously.
- **VENOM** (CVE-2015-3456) — a real VM escape exploiting a flaw in the **QEMU** (Quick Emulator — the hardware emulation layer used by several hypervisors) virtual floppy disk controller; affected Xen, KVM, and VirtualBox.
- A 2017 Pwn2Own attack chained a browser bug → Windows kernel bug → VMware hardware simulation bug to hop between VMs.
- **Primary control:** patch the hypervisor first, before any other system, because a single unpatched flaw endangers all tenants.

*Analogy:* VM escape is like a prisoner discovering a secret tunnel from their cell directly into the warden's office — and from there, into every other cell in the prison.

---

### VM sprawl — forgotten VMs become forgotten vulnerabilities

**VM sprawl** is the uncontrolled accumulation of unmanaged, abandoned, or redundant virtual machines that nobody is actively maintaining.

- Forgotten VMs stop receiving security patches, becoming easy targets.
- **Snapshots** — point-in-time copies of a VM's state — can preserve old vulnerabilities, credentials, or session tokens indefinitely.
- Controls: lifecycle management policies, regular discovery scanning, mandatory ownership tagging, formal decommissioning.

*Analogy:* Sprawl is like never throwing away old house keys — each forgotten copy is a lock that nobody is changing.

---

### VM isolation failures — when logical walls break down

**VM isolation failure** is when the intended separation between VMs on the same host breaks down, allowing unintended communication or data leakage.

- Misconfigured **virtual networks** (**VLANs** — logically separated network segments) can let VMs talk directly when they shouldn't.
- **Shared clipboard** between host and guest is a data-leakage channel.
- **Memory overcommitment** — allocating more virtual RAM across VMs than physical RAM exists — forces the hypervisor to swap memory; a bug in that layer could let one VM read another's memory.

*Analogy:* Memory overcommitment with a bug is like a hotel that overbooks and starts moving guests' belongings between rooms — a mix-up could put your documents in a stranger's room.

---

### Container security — shared kernel, weaker isolation

A **container** is a lightweight runtime environment that shares the host OS kernel instead of running its own — making it faster than a VM but providing weaker isolation.

- **Container escape** exploits kernel or container-runtime vulnerabilities to reach the host.
- **Overprivileged containers** — containers run as root or with the Docker `--privileged` flag unnecessarily; a compromised process then has root on the host.
- **Excessive Linux capabilities** — permissions like loading kernel modules granted when not needed.
- **Unpatched base images** — containers built months ago accumulate vulnerabilities no one updates.
- **Embedded secrets** — credentials baked into Docker images or passed as plaintext environment variables are exposed to anyone who pulls the image.

*Analogy:* Containers sharing a kernel is like offices sharing one set of load-bearing walls — faster to build, but if the walls crack, every office is affected.

---

### Kubernetes misconfigurations — orchestration at scale

**Kubernetes** is the dominant platform for orchestrating (scheduling, scaling, and managing) large numbers of containers. Its complexity creates security risks.

- **RBAC** (Role-Based Access Control — a permission model that assigns actions to roles) misconfigurations: wildcard permissions, unnecessary **cluster-admin** rights.
- The **API server** — the control plane component all cluster management flows through — must never be internet-exposed; misconfigured clusters frequently are.
- **Privileged pods** and **hostPath mounts** (mappings of the host filesystem into a container) enable container breakout.
- **etcd** — the key-value database that stores all cluster state including secrets — must be encrypted at rest; without it, secrets are plaintext.
- Permissive **network policies** allow unrestricted pod-to-pod traffic across namespaces, undermining namespace isolation.

*Analogy:* An exposed Kubernetes API server is like leaving the master control panel of an entire factory unlocked and facing the street.

---

### Shared hardware and snapshot risks

**Spectre-class vulnerabilities** — attacks that exploit the shared CPU cache between workloads running on the same physical processor — are a realistic multi-tenant cloud risk: your VM and a stranger's VM may time-share the same CPU core.

**Snapshot and image risks:** snapshots can capture session tokens, cached credentials, or in-memory encryption keys. Shared VM templates in image repositories may carry old vulnerabilities or be tampered with if the repository is compromised.

---

### Recap

- **Type 1** hypervisors run on bare metal (smaller attack surface); **Type 2** run on a host OS (inherit its vulnerabilities).
- **VM escape** breaks out of a guest VM into the hypervisor or neighboring VMs — patching the hypervisor is the top priority control.
- **VM sprawl** creates unpatched, forgotten attack surfaces; snapshots compound the risk.
- **Containers** share the host kernel — weaker isolation than VMs; key risks are overprivileged containers, unpatched base images, and embedded secrets.
- **Kubernetes** key risks: RBAC wildcard permissions, exposed API server, unencrypted etcd.

### Exam flags

- **VM escape definition and VENOM** — expect a scenario question asking what attack breaks out of a guest VM and which real-world vulnerability demonstrated it.
- **Type 1 vs. Type 2 hypervisor security posture** — know why Type 2 is less secure (inherits host OS vulnerabilities) and where each is used.
- **Kubernetes RBAC misconfigurations and exposed API server** — high-probability scenario items in cloud/container security questions.
