## States of Data (Domain 3)

Data is never just "sitting safely somewhere" — it exists in one of three states, each with its own attack surface. Understanding all three is non-negotiable because, as the 2013 Target breach showed, protecting only two states still leaves 110 million credit card numbers exposed.

---

### Data at rest

**Data at rest** is any data persistently stored on a medium and not currently being transmitted or processed — think hard drives, SSDs, USB drives, cloud storage buckets, or database servers.

**Encryption** is the primary defense:
- **AES-256** — the Advanced Encryption Standard with a 256-bit key — is the accepted standard; it is computationally infeasible to brute-force.
- **Full disk encryption** (e.g., **BitLocker** on Windows, **FileVault** on macOS) encrypts every sector, including swap and temp files.
- **Column-level encryption** encrypts only sensitive database fields (e.g., SSNs, card numbers), leaving other fields readable for performance.
- **Self-encrypting drives** perform encryption in drive firmware with no software overhead.

**Access control** works alongside encryption:
- File system permissions control who can read, modify, or delete files.
- **Role-based access control (RBAC)** — assigning permissions by job function — ensures a payroll clerk can reach salary data but not healthcare records on the same server.

**Physical security** covers media theft:
- Server rooms require badge readers, biometrics, **man traps** (a double-door entry that lets only one person through at a time), and video surveillance.
- Backup tapes leaving the building must be encrypted *before* transport; they exit the physical security perimeter.

**Cloud-specific risk — misconfiguration:**
- Publicly accessible **S3 buckets** (Amazon), **Azure Blob Storage** containers, or **Google Cloud Storage** buckets have caused major breaches.
- Mitigations: verify bucket permissions, enable default encryption, use customer-managed keys, monitor for **configuration drift** (when settings silently change away from a secure baseline).

> *Analogy: Think of data at rest like cash in a bank vault — the vault (encryption) makes the cash worthless to a thief, but you still need a locked door (access control) and a security guard (physical controls) to stop them getting near the vault in the first place.*

---

### Data in transit

**Data in transit** (also called **data in motion**) is data actively traveling across any network — LAN, WAN, Wi-Fi, the public internet, or a dedicated circuit. Any packet capture tool on any network segment between sender and receiver can read unencrypted traffic.

**Encryption protocols:**

| Protocol | What it does |
|---|---|
| **TLS 1.2 / 1.3** — Transport Layer Security | Encrypts web and API traffic; HTTPS is HTTP carried over TLS |
| **TLS 1.3** (preferred over 1.2) | Removes weak cipher suites, mandates **forward secrecy** (past sessions stay safe even if a key is later compromised), and is faster |
| **SSH** — Secure Shell | Encrypts remote admin sessions; replaces **Telnet**, which sends credentials in cleartext |
| **IPsec** — Internet Protocol Security suite | Encrypts at the network layer; foundation of most VPNs |
| **S/MIME / PGP** | End-to-end email encryption |

**On-path attacks** (historically called **man-in-the-middle attacks**) go beyond passive eavesdropping — the attacker relays traffic while reading or modifying it. Defenses:
- **Certificate validation**: the client checks the server's digital certificate against a trusted **certificate authority (CA)** — a third party that vouches for a server's identity — before the session opens.
- **HSTS** — HTTP Strict Transport Security — tells browsers to refuse any unencrypted connection to a site, blocking **SSL stripping** (downgrading HTTPS to HTTP).
- **Replay attacks** — retransmitting a captured session to impersonate the original sender — are defeated by TLS's unique per-connection session keys and sequence numbers.

**VPNs** protect transit for remote users:
- A **client VPN** tunnels all traffic from a device to the org's network, even over untrusted public Wi-Fi.
- A **site-to-site VPN** connects entire offices over an encrypted tunnel, replacing expensive dedicated WAN links.

> *Analogy: Data in transit is like a letter in the mail — TLS is a sealed, tamper-evident envelope, and certificate validation is checking that the return address is stamped by a post office you trust, not forged by the mail carrier.*

### Data in use

**Data in use** is data actively loaded into **RAM** — memory that the CPU can directly read — displayed on screen, or being processed by an application. This is the hardest state to protect because data *must* be decrypted to be processed, creating a window even when at-rest and in-transit encryption are perfect.

**Memory attacks:**
- **Memory scraping** — malware reads RAM contents while data is decrypted. This is exactly how the Target breach worked: malware on point-of-sale terminals grabbed card data the instant it was decrypted for processing.
- **DEP / NX bit** — Data Execution Prevention, enforced partly by a CPU hardware flag called the **NX (No-Execute) bit** — prevents memory regions holding data from running as executable code, limiting some attack paths.
- **ASLR** — Address Space Layout Randomization — randomizes where system components load in memory, making it harder to locate target data structures.
- **Cold boot attacks** exploit the fact that **DRAM** (the common type of volatile RAM) retains data for seconds to minutes after power is cut, especially when cooled. An attacker removes power, chills the RAM, transplants it, and images the contents — potentially extracting full-disk encryption keys. Countermeasures: memory encryption in newer CPUs, physical security, clearing memory on shutdown.

**Screen and input attacks:**
- **Shoulder surfing**: someone reads your screen directly; **privacy screens** (physical filters limiting viewing angle) mitigate this.
- **Keyloggers**: hardware (plugged between keyboard and system) or software (running in background) capture every keystroke.
- **Clipboard hijacking**: malware reads data you copy/paste — passwords, account numbers — from the clipboard.

**Hardware-based trusted execution environments** are the strongest protection for data in use:
- **Intel SGX** — Software Guard Extensions — lets apps mark memory regions as **secure enclaves** encrypted by the CPU, unreadable even by the OS or hypervisor.
- **AMD SEV** — Secure Encrypted Virtualization — encrypts each VM's memory with processor-managed keys, so the hypervisor cannot read VM contents. Valuable in multi-tenant cloud.
- **Apple Secure Enclave**: a dedicated security processor in iOS/macOS that stores biometric and payment keys in isolated hardware, inaccessible even with full software access.

> *Analogy: Data in use is like surgery — the patient (data) must be fully exposed on the table to be operated on, so no matter how secure the waiting room (at rest) or the ambulance (in transit) was, there's an unavoidable window where the attacker just needs to get into the operating room.*

---

### Recap
- Three states: **at rest** (stored), **in transit** (moving across a network), **in use** (in RAM/being processed) — each needs its own controls.
- Data at rest → **AES-256 encryption** + access control + physical security + cloud misconfiguration prevention.
- Data in transit → **TLS 1.3**, **IPsec/VPN**, certificate validation, HSTS; defend against on-path and replay attacks.
- Data in use is the hardest to protect — memory scraping, cold boot, and input/screen attacks all target this window; **SGX/SEV** enclaves are the strongest defense.
- The **Target breach** is the canonical exam example: card data stolen *in use* from POS RAM, bypassing all other controls.

### Exam flags
- **Matching attack types to data states** — e.g., memory scraping targets data in use, packet capture targets data in transit, cold boot attacks target data in use.
- **Encryption standard per state** — AES-256 for at rest, TLS 1.3 for in transit; know *why* TLS 1.3 is preferred over 1.2 (removes weak ciphers, mandates forward secrecy).
- **Cloud misconfiguration as a data-at-rest threat** — publicly exposed storage buckets are a tested scenario.
