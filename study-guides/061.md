## Infrastructure Considerations

Infrastructure design is never just a technical exercise — every choice about availability, cost, recovery, and scalability carries direct security implications. This lesson maps those trade-offs so you can reason through exam scenarios where "perfect" isn't on the menu.

---

### Availability: keeping systems reachable

**Availability** — the "A" in the **CIA triad** (Confidentiality, Integrity, Availability) — means legitimate users can access systems and data when they need them. Attacks like **DDoS** (Distributed Denial of Service — flooding a target with traffic to exhaust its resources) and ransomware threaten availability directly.

**Designing for availability means eliminating single failure points:**

- **Redundant power supplies** — multiple PSUs in one server so one failure doesn't kill it
- **Redundant network paths** — alternate routes so a dead switch doesn't cause an outage
- **Geographic dispersion** — spreading data centers so a regional disaster (flood, fire) doesn't wipe everything

**Clustering** groups multiple servers to look like one logical system:

| Cluster type | How it works | What happens when a node fails |
|---|---|---|
| **Active-passive** | One node active, one on standby | Standby takes over (seconds of downtime) |
| **Active-active** | All nodes share load simultaneously | Capacity drops, but service continues |

**Load balancing** distributes requests across servers and uses **health checks** to route around failed nodes automatically.

**Single Point of Failure (SPOF) analysis** — the process of systematically finding components whose failure would take down an entire service, then adding redundancy to eliminate those failure modes.

**High availability** is expressed in "nines" of uptime:

| Nines | Uptime % | Max downtime/year |
|---|---|---|
| Three nines | 99.9% | ~8.7 hours |
| Four nines | 99.99% | ~52 minutes |
| Five nines | 99.999% | ~5 minutes |

Each additional nine costs exponentially more. Not every system justifies five nines.

> *Think of active-active clustering like a team of cashiers: if one goes home sick, the line slows but the store stays open. Active-passive is one cashier with a backup sitting in the break room.*

### Reliability: measuring how well it stays healthy

**Reliability** asks not just *is it running?* but *is it performing correctly and consistently?* Three metrics matter:

- **MTBF** (Mean Time Between Failures) — average time between failures for a repairable system; **higher = more reliable**
- **MTTR** (Mean Time to Repair) — average time to restore service after failure; **lower = faster recovery**
- **MTTF** (Mean Time to Failure) — expected lifespan for a *non-repairable* component before it dies

> *MTBF and MTTR are like a car's maintenance record: MTBF tells you how long between breakdowns, MTTR tells you how long it sits at the shop.*

---

### Cost and TCO

**Total Cost of Ownership (TCO)** — the full lifetime cost of a system, not just the sticker price. It includes acquisition, deployment, licensing, electricity, cooling, physical space, labor, maintenance, upgrades, and eventual decommissioning.

Security investment is justified by comparing TCO against **risk reduction**: potential loss × reduced probability of incident. That math is hard to do precisely — you're estimating things that might never happen — but the framework is valid.

### Responsiveness: latency and throughput

**Latency** — the delay between a request and a response. High-latency systems feel slow; some applications (real-time databases, web apps) can't tolerate it.

Ways to reduce latency:
- Place compute **geographically close** to users
- Use a **CDN** (Content Delivery Network — a globally distributed system that caches static content at edge locations near users)
- **Application-layer caching** with tools like **Redis** or **Memcached** (in-memory data stores that serve repeated queries without hitting the database)
- **Edge computing** — processing data closer to the source rather than routing everything to a central data center

**Security trade-off:** Adding encryption or inspection layers increases latency. Security controls must be tuned and placed carefully to avoid violating latency requirements.

### Scalability: growing without breaking

**Vertical scaling** — add more CPU/RAM/storage to one existing server. Simple but has a hardware ceiling.

**Horizontal scaling** — add more servers. Theoretically unlimited; the basis of cloud-native design.

**Auto-scaling** — cloud capability that automatically spins instances up or down based on real-time demand.

**Security risk of auto-scaling:** Security monitoring tools that were configured for the original set of servers won't automatically cover new instances. Security architecture must scale *with* the application — not assume a static host list.

### Ease of deployment: Infrastructure as Code

**Infrastructure as Code (IaC)** — defining infrastructure (servers, networks, security rules) in version-controlled code files rather than clicking through a console or typing manual commands. Tools include **Terraform**, **AWS CloudFormation**, **Ansible**, and **Puppet**.

Benefits:
- Eliminates **configuration drift** — the gradual divergence that happens when admins make undocumented manual changes
- Security controls are embedded in templates, so every resource launches with correct settings
- **GitOps** workflows require changes to go through pull request review, creating an audit trail

**Critical warning:** Never hardcode credentials, API keys, or cryptographic material in IaC files stored in version control. Use dedicated secrets tools: **HashiCorp Vault**, **AWS Secrets Manager**, or **Azure Key Vault** (all are services that store, rotate, and inject secrets securely at deployment time).

**Kubernetes** — a container orchestration platform that standardizes deployment and provides network policy enforcement, pod security controls, and secrets management across large fleets of containers.

> *IaC is like a recipe: every chef who follows it produces the same dish. Manual configuration is like describing the dish verbally — everyone's version drifts slightly.*

### Ease of recovery: RTO, RPO, and DR

**Disaster Recovery (DR)** planning defines what it takes to restore services after a major incident.

Two defining metrics:

| Metric | Stands for | What it measures | Example |
|---|---|---|---|
| **RTO** | Recovery Time Objective | Max acceptable downtime after an incident | "We must be back online within 2 hours" |
| **RPO** | Recovery Point Objective | Max acceptable data loss, measured in time | "We can afford to lose at most 1 hour of transactions" |

Tight RTO → need automated failover with pre-provisioned standby systems. Tight RPO → need continuous or near-continuous replication.

**Backup testing** — regularly restoring backups in a test environment to confirm they actually work. Untested backups fail when needed most.

**DR site exercises** — simulated recovery scenarios to verify procedures, staff roles, and standby infrastructure are all functional.

---

### Risk transference: cyber insurance

**Risk transference** — shifting the financial consequences of a risk to a third party instead of absorbing them internally.

**Cyber insurance** is the primary mechanism. Policies can cover:
- Incident response and forensics costs
- Business interruption losses
- Regulatory fines
- Legal defense
- Customer notification and credit monitoring
- Ransom payments

Cyber insurance **does not prevent incidents** — it reduces financial impact when they happen. Insurers typically require baseline controls (MFA, endpoint detection, patch management, backups) before issuing a policy, which indirectly pushes organizations toward better security hygiene.

---

### Recap

- **Availability** is the CIA triad's third pillar; design it by eliminating SPOFs through redundancy, clustering, and geographic dispersion
- **MTBF** (higher = better), **MTTR** (lower = better), and **MTTF** are the core reliability metrics
- **RTO** = max downtime; **RPO** = max data loss — together they drive backup and replication strategy
- **IaC** ensures consistent, auditable deployments and eliminates configuration drift — but secrets must never be hardcoded in version-controlled files
- **Cyber insurance** transfers financial risk but requires baseline controls; it does not prevent incidents

---

### Exam flags

- **RTO vs. RPO** — expect scenario questions where you must identify which metric a given recovery requirement describes
- **Active-active vs. active-passive clustering** — know what happens to capacity and uptime when a node fails in each model
- **Auto-scaling security blind spots** — security monitoring must scale dynamically or new instances go unmonitored
