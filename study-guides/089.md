## Firewalls (Domain 4)

Firewalls are the primary control for enforcing access policy between network segments — they decide what traffic gets through and what doesn't. This lesson covers how firewalls evolved, how rules work, what NGFWs add, and how firewalls fit into real network architectures.

---

### How firewalls evolved: stateless → stateful → NGFW

**Packet-filter firewalls** — the earliest type — inspect individual packets and make permit/deny decisions based only on header fields: source/destination IP, source/destination port, and protocol (TCP, UDP, ICMP).

- **Stateless** — each packet is judged alone, with no memory of prior packets
- Cannot tell if a packet belongs to a real ongoing session
- Vulnerable to spoofed "return" packets that look legitimate

**Stateful firewalls** — introduced in the 1990s — maintain a **connection state table**, a record of every active TCP session (source/destination address + port, connection status).

- When a TCP three-way handshake completes, an entry is added to the table
- Later packets are checked against the table, not the full rule base — faster and more secure
- Unsolicited inbound packets with no matching table entry are **automatically denied**

> 🔑 Stateless = judges each packet alone; Stateful = remembers the conversation.

**Next Generation Firewalls (NGFWs)** — extend stateful inspection with **deep packet inspection (DPI)**, which reads inside the packet payload to identify the actual application generating traffic, regardless of port.

- Can identify Netflix, SharePoint, SSH tunneling, or RDP even on non-standard ports
- Enables policy by **application**, not just port — block file-sharing apps while allowing HTTPS browsing even though both use port 443
- Often bundle IPS, URL filtering, SSL/TLS inspection, and malware scanning in one appliance

> 🔑 Unlike a stateful firewall (which only sees port 443 = "web traffic"), an NGFW sees port 443 carrying SharePoint vs. a gambling site and can treat them differently.

*Analogy: A stateless firewall is a bouncer checking only your ID type ("do you have a ticket?"). A stateful firewall also checks whether you actually entered through the front door. An NGFW reads your name badge and knows exactly which event you're attending.*

### How firewall rules are structured

**Access Control Lists (ACLs)** — the rule sets that define what traffic is permitted or denied. A typical rule specifies:

| Field | Example |
|---|---|
| Source zone / IP | `any` or `192.168.50.0/24` |
| Destination zone / IP | `10.10.0.10` |
| Protocol | TCP, UDP, ICMP, any |
| Destination port | 443, 80, any |
| Action | allow, deny, reject |
| Logging | yes/no |

NGFWs add: identified application, URL category, user identity, threat-prevention profile.

**Top-down, first-match evaluation** — the firewall reads rules from Rule 1 downward and stops at the first match.

- More **specific** rules must come **before** general ones — a general "allow all" above a specific "deny HR server" means the deny is never reached
- **Implicit deny** — built into every firewall: any traffic not matched by a permit rule is automatically dropped, even without an explicit deny-all rule
- Some implementations add an **explicit deny-all** at the bottom so denies appear in logs

*Analogy: Think of rules like a bouncer's checklist read top to bottom — the first item that matches decides your fate. If "VIP guests enter free" is listed before "no one under 21," every teenager wearing a VIP badge walks right in.*

### NAT: hiding private addresses

**Network Address Translation (NAT)** — a mechanism, commonly implemented on firewalls, that maps private internal IP addresses to public ones.

| Type | What it does |
|---|---|
| **PAT / IP masquerade** — Port Address Translation | Many internal hosts share one public IP; firewall tracks unique source ports per host |
| **Static NAT** | One-to-one permanent mapping; used for servers needing a consistent public address |
| **DNAT / port forwarding** — Destination NAT | Inbound traffic on a public IP + port is redirected to a specific internal server |

*Analogy: PAT is like a hotel front desk — many guests (private IPs) share one street address (public IP), and the desk (firewall) knows which room to send each reply to.*

### DMZ architecture

A **DMZ** (Demilitarized Zone) is a semi-trusted network segment hosting internet-facing servers (web servers, mail relays) that sits between the internet and the internal network.

In a **three-interface firewall** setup:

| Interface | Connected to |
|---|---|
| Outside | Internet |
| DMZ | Public-facing servers |
| Inside | Trusted internal network |

**Critical DMZ rules:**

- ✅ Internet → DMZ: allowed for specific services (HTTP, HTTPS, SMTP)
- ✅ Inside → DMZ: allowed for management
- ❌ **DMZ → Inside: explicitly denied** — the most important rule; stops an attacker who compromises a DMZ server from reaching the internal network
- ✅ DMZ → Internet: allowed for necessary outbound (DNS, HTTPS fetching)

*Analogy: The DMZ is like a hotel lobby — customers (internet) can enter the lobby (DMZ) but cannot walk into the staff offices (inside network). Even if a thief gets into the lobby, a locked internal door stops them.*

### High availability: no single point of failure

**Active-passive HA** — one firewall handles all traffic; the secondary monitors via a **heartbeat link** and takes over if the primary fails.

**Active-active HA** — both firewalls process traffic simultaneously; requires **session synchronization** so stateful traffic is handled correctly by either unit.

---

### Firewalls in cloud and virtual environments

**Security groups** (AWS Security Groups, Azure NSGs — Network Security Groups) act as virtual firewalls controlling inbound/outbound traffic per instance by protocol, port, and source/destination.

**Virtual NGFW appliances** (e.g., Palo Alto VM-Series) run full NGFW software on a hypervisor or in cloud — same policy control as physical hardware.

**Cloud WAF** — **Web Application Firewall** — (AWS WAF, Azure Application Gateway WAF, Cloudflare WAF) provide Layer 7 protection for web apps without managing physical appliances.

---

### IPS integration

An **IPS** (Intrusion Prevention System) works *alongside* the firewall rule base as a second analysis layer.

- The firewall decides **who** can talk to whom
- The IPS inspects the **content** of permitted traffic for attack signatures (e.g., SQL injection in an HTTPS request the firewall already allowed through)
- When it detects an attack, it blocks that specific session while legitimate traffic continues

> The firewall is the gatekeeper at the door; the IPS is the security camera watching what people do *after* they're inside.

---

### Recap

- **Stateless** inspects each packet alone; **stateful** tracks sessions; **NGFW** identifies applications via DPI
- Rules evaluate **top-down, first-match**; specific rules must appear before general ones; implicit deny catches everything not explicitly permitted
- The most critical DMZ rule is **DMZ → inside: deny**, preventing pivot attacks from compromised DMZ servers
- **NAT/PAT** lets many private hosts share one public IP; **static NAT / DNAT** serve inbound access to servers
- The **IPS** inspects content *within* traffic the firewall already permitted — it's a second layer, not a replacement

### Exam flags

- **Top-down, first-match rule evaluation and implicit deny** — expect scenario questions where rule order determines whether traffic is blocked or allowed
- **DMZ architecture** — know which traffic flows are permitted vs. denied, especially the DMZ-to-inside deny rule
- **NGFW vs. stateful firewall** — know that NGFWs add application-layer identification via DPI, enabling policy beyond port/protocol
