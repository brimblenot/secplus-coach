## Recovery Testing

Recovery testing validates that your disaster recovery plan actually works before a real crisis forces you to find out. This lesson covers every major test type — from low-disruption discussion exercises to live production failovers — and the metrics and documentation that make testing meaningful.

---

### Why testing matters

An untested DR plan is a hypothesis, not a plan. Testing validates four things:

- **Recovery procedures** are accurate and executable as written
- **Personnel** can perform them under stress, not just in calm conditions
- **Recovery Time Objectives** — the maximum acceptable downtime for a system — can actually be met
- **No critical steps** were accidentally omitted

> **Compliance note:** **PCI DSS**, **HIPAA**, and **SOC 2** all require at least annual DR testing — so this is a legal obligation, not just a best practice.

*Analogy: Discovering your fire escape is bolted shut during an actual fire is the worst possible moment to find out.*

---

### The testing spectrum

Tests range from zero-disruption to full production risk. Choose based on system criticality, compliance requirements, DR program maturity, and disruption tolerance. An immature program should start low and move up as confidence grows.

| Test Type | Systems touched? | Production risk | Best for |
|---|---|---|---|
| **Tabletop exercise** | None | None | Gap discovery, decision authority |
| **Walkthrough** (paper test) | None | None | Verifying procedure accuracy & completeness |
| **Simulation** | Isolated test env | None | Specific components or security controls |
| **Parallel test** (parallel processing) | DR site + production both active | None | First-time DR site validation |
| **Full cutover** (full failover) | DR site takes live traffic | High — real outage if it fails | Complete end-to-end + failback validation |
| **Functional recovery test** | Individual component | Low | Routine backup/restore verification |
| **Chaos engineering** | Production | Medium-High | Resilience at scale, mature orgs only |
| **Red team DR test** | Full environment | High | Combined incident response + DR validation |

---

### Tabletop exercise

A **tabletop exercise** is a discussion-based simulation where stakeholders walk through a disaster scenario verbally — no systems are touched. A facilitator presents a scenario (e.g., ransomware hitting 200 servers at 2 a.m.) and then introduces **injects** — escalating developments that drive the conversation forward.

- Participants answer: who gets called first, what order do systems recover, where are the credentials, who talks to regulators?
- Consistently surfaces: unclear decision authority, outdated contact lists, unaccounted system interdependencies

*Analogy: Like a tabletop wargame — you move pieces around a map and debate strategy without anyone firing a shot.*

---

### Walkthrough (paper test)

A **walkthrough** has each team review their own recovery procedures step by step — reading and verifying, not executing. It confirms procedures are detailed enough for someone unfamiliar with the system and that credentials, IP addresses, and access paths are current.

- Especially valuable after **infrastructure changes** — old procedures may be wrong for redesigned systems

---

### Simulation

A **simulation** executes specific recovery procedures in an **isolated test environment** that cannot affect production. Examples: restoring a database backup to a test server and checking row counts, or running failover scripts against a test network segment.

- More realistic than tabletop/walkthrough because real systems move
- Scope is limited — tests components, not end-to-end recovery

**Phishing simulations** fit here: craft a realistic phishing email, send it to staff, measure click rates, check whether email security controls quarantine it before delivery.

---

### Parallel test

A **parallel test** brings the **DR site** fully online while production keeps running normally. Both environments process work simultaneously; outputs are compared for consistency.

- No production risk: if DR fails, users never notice
- Validates: DR infrastructure, data synchronization accuracy, personnel execution

*Analogy: Running a dress rehearsal on a second stage while the main show plays — audiences see nothing different.*

---

### Full cutover test

A **full cutover test** actually redirects live production traffic to the DR site, then fails back to primary when done. This is the only test that validates the **complete recovery chain including failback** — which is itself a failure point.

- Highest disruption: real users experience an outage if anything goes wrong
- Should only be attempted after successful parallel testing
- Schedule during lowest-impact windows (e.g., weekend maintenance)

---

### Functional recovery test

A **functional recovery test** focuses on a single component: restore one server from backup, recover one database, bring up one application after a simulated crash. Validates that individual backup/restore procedures work correctly.

- Should be run **regularly for all critical systems**, not just once a year for the overall DR plan

---

### Chaos engineering

**Chaos engineering** deliberately injects random failures into **production systems** to verify that resilience mechanisms hold. Rather than scripted scenarios, failures happen continuously and unpredictably.

- **Netflix** pioneered this with **Chaos Monkey** — randomly terminates VM instances in production — and **Chaos Gorilla** — terminates entire cloud **availability zones** (isolated data center sections within a cloud region)
- Requires mature engineering culture, comprehensive monitoring, and automated recovery to be safe
- Discovers weaknesses that only appear under specific failure combinations

*Analogy: Chaos Monkey is like randomly yanking cords in a server room to see if the building stays lit — only safe if you've already proven the backup generators work.*

---

### Red team DR test

A **red team DR test** combines adversarial attack simulation with disaster recovery. The **red team** (attackers) simulates a realistic scenario — ransomware spreading from a phishing-compromised endpoint. The **blue team** (defenders, including both incident response and DR staff) must detect, contain, eradicate, and recover using normal procedures.

- Tests incident response and DR processes simultaneously
- Reveals how the two teams coordinate (or fail to)
- Most realistic DR test type

---

### Key metrics to validate

During any test, measure:

- **RTO** — **Recovery Time Objective**: did recovery finish within the allowed downtime window?
- **RPO** — **Recovery Point Objective**: how much data was lost, and is that within acceptable limits?
- Were procedures accurate, or did staff have to improvise?
- Were roles clear under stress conditions?
- Were all resources available — credentials, backup media, vendor contacts, spare hardware?

---

### Documentation requirements

| Document | What it contains |
|---|---|
| **Pre-test plan** | Objectives, scope, success criteria, safety constraints |
| **Test execution log** | Actual times, actions taken, deviations, issues encountered |
| **Post-test report** | Results vs. objectives, gaps found, lessons learned, corrective actions with owners and deadlines |

> Finding the same gap repeatedly without fixing it means your testing program provides diminishing value. Fix procedures before the next test.

---

### Ransomware-specific recovery drills

Ransomware testing deserves dedicated attention beyond general DR exercises:

- Identify **clean backups predating the infection**
- Restore and verify restored systems are **free of the original malware**
- Verify backup systems **themselves were not compromised** — sophisticated ransomware actors deliberately corrupt backups before deploying their payload

---

### Recap

- An untested DR plan is a hypothesis; testing reveals gaps before a real disaster does
- Tests range from zero-disruption (tabletop, walkthrough) to high-disruption (full cutover, chaos engineering) — match the test to maturity and risk tolerance
- **Parallel test** = DR site goes live alongside production (no risk); **full cutover** = live traffic moves to DR (real risk, most realistic)
- Always measure against **RTO** and **RPO**; document pre-test, execution, and post-test results
- Mature programs use **chaos engineering** and **red team DR tests** to find gaps that scripted scenarios miss

---

### Exam flags

- **Test type matching**: be ready to identify which test type fits a scenario — especially distinguishing parallel test (no production risk) from full cutover (production risk, tests failback)
- **Tabletop exercise injects**: know that injects are the escalating scenario developments a facilitator introduces to drive discussion
- **Compliance requirement**: PCI DSS, HIPAA, and SOC 2 all explicitly require at least annual DR testing
