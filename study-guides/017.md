## Hashing and Digital Signatures

Hashing and digital signatures are two of the most fundamental cryptographic tools in security — hashing guarantees data integrity, and digital signatures add authentication and non-repudiation on top of it. This lesson covers how each works, which algorithms are safe to use today, and how they're applied in real systems.

---

### What a cryptographic hash function is

A **cryptographic hash function** is an algorithm that takes any input — a single byte or a 10 GB file — and produces a fixed-length output called a **hash** (also called a **message digest** or **fingerprint**). It is strictly one-way: you cannot reverse a hash to recover the original input the way you can decrypt ciphertext with a key.

Key properties every secure hash function must have:

- **One-way / preimage resistant** — given a hash output, it is computationally infeasible to find any input that produces it
- **Deterministic** — the same input always produces the same hash
- **Fixed-length output** — a 1-byte file and a 1 TB file produce hashes of the same size
- **Avalanche effect** — changing even one bit in the input produces a completely different output
- **Collision-resistant** — it must be computationally infeasible to find two different inputs that produce the same hash

> **Analogy:** A hash function is like a paper shredder that always shreds the same document into the same confetti pattern — identical input, identical shreds — but you can never reconstruct the original document from the confetti.

---

### The hash algorithms: what's safe and what's broken

| Algorithm | Output size | Status | Notes |
|---|---|---|---|
| **MD5** — Message Digest 5 | 128-bit (32 hex chars) | ❌ Broken | Practical collision attacks demonstrated in 2004; never use for signatures, certificates, or passwords |
| **SHA-1** — Secure Hash Algorithm 1 | 160-bit (40 hex chars) | ❌ Deprecated | First practical collision (Google's *SHAttered*) in 2017; banned from TLS certs and new systems |
| **SHA-256** (SHA-2 family) | 256-bit (64 hex chars) | ✅ Secure | Most widely deployed; used in TLS, Bitcoin, code signing |
| **SHA-512** (SHA-2 family) | 512-bit | ✅ Secure | Efficient on 64-bit processors; larger margin |
| **SHA-3 / Keccak** | 224–512-bit variants | ✅ Secure | Completely different internal design (**sponge construction**) vs. MD5/SHA-1/SHA-2's **Merkle–Damgård construction** — a class of attacks that breaks SHA-2 would likely not affect SHA-3 |

> **Analogy:** MD5 and SHA-1 are like combination locks where someone published the master bypass — they still *look* like locks, but they're not protecting anything.

---

### How hashing is used in practice

**File integrity verification:** A vendor publishes the SHA-256 hash of a download. After downloading, you compute the hash yourself and compare. A mismatch means tampering or corruption.

**Digital forensics:** Investigators hash every storage device before and after imaging — this proves the forensic copy is byte-for-byte identical and that no changes occurred during the investigation (**chain of custody**).

**Password storage:** Storing passwords in plaintext is indefensible. Instead, servers store the hash. At login, the server hashes the submitted password and compares it to the stored hash — the server never sees or stores the actual password.

---

### Why fast hashes are dangerous for passwords — and how salting fixes it

A fast general-purpose hash (like SHA-256) lets an attacker run an **offline dictionary attack** — hashing millions of common passwords and comparing results against a stolen hash database. **Rainbow tables** — precomputed lookup tables mapping hashes back to their input passwords — make this even faster.

A **salt** is a unique, cryptographically random value generated per user when their password is first set. The salt is concatenated with the password before hashing, and both the salt and the resulting hash are stored. Even if two users choose the same password, their stored hashes differ completely — the attacker must now run a separate dictionary attack per user, destroying the value of precomputed rainbow tables.

**Purpose-built password hashing functions** add an adjustable **work factor** (iteration count) that makes the hash intentionally slow:

| Function | Key detail |
|---|---|
| **bcrypt** | In use since 1999; cost factor is tunable as hardware gets faster |
| **Argon2** | Won the 2015 Password Hashing Competition; tunable for GPU resistance, memory hardness, or both — current best practice |
| **PBKDF2** — Password-Based Key Derivation Function 2 | Applies **HMAC** (defined below) many times with a salt and iteration count; used in WPA2/WPA3 for Wi-Fi key derivation; approved in many compliance frameworks |

> **Analogy:** A salt is like making every user's password lock out of a different alloy — even if two people pick the same combination, no master key works on both.

### HMAC: integrity + authentication with a shared key

**HMAC** — Hash-based Message Authentication Code — combines a hash function with a **shared secret key** to produce a code that proves both that a message hasn't been altered and that it came from someone who knows the key.

- Provides **integrity** (message not tampered) and **authentication** (came from a keyholder)
- Does **not** provide **non-repudiation** — because both sender and receiver share the same key, either could have generated the HMAC, so neither can prove the other did it
- Used in: TLS message authentication, IPsec packet integrity, **JWT** — JSON Web Tokens — for API authentication

> **Analogy:** HMAC is like a wax seal both you and your business partner share the mold for — it proves the message is intact and from one of you, but not *which* one of you.

---

### Digital signatures: authentication + integrity + non-repudiation

A **digital signature** combines asymmetric cryptography with hashing. The critical advantage over HMAC is **non-repudiation**: only the holder of the private key can produce a valid signature, so the signer cannot later deny having signed.

**Signing process:**
1. Sender computes SHA-256 hash of the message
2. Sender encrypts that hash with their **private key** → this is the digital signature
3. Sender transmits message + signature together

**Verification process:**
1. Recipient decrypts the signature with the sender's **public key** → recovers the original hash
2. Recipient independently hashes the received message
3. If both hashes match → signature is valid, message is authentic and unaltered

The hash is signed (not the full message) because asymmetric operations like RSA are slow — signing a fixed-length hash is fast regardless of message size.

**Signature algorithms:**

| Algorithm | Basis | Notes |
|---|---|---|
| **RSA** — Rivest–Shamir–Adleman | Integer factorization | Most widely used; signer encrypts hash with private key |
| **DSA** — Digital Signature Algorithm | Discrete logarithm problem | Federal standard; signing only, not encryption |
| **ECDSA** — Elliptic Curve DSA | Elliptic curve mathematics | Same security as RSA with much smaller key sizes; used in Bitcoin, modern TLS |

**Code signing** applies digital signatures to software. A developer signs their app with their private key; the OS verifies the signature using the developer's public key certificate (issued by a trusted **CA** — Certificate Authority) at install time. Windows warns prominently about unsigned software.

> **Analogy:** A digital signature is like a wax seal that only the king's unique signet ring can produce — anyone can verify it's authentic by pressing it against the known ring mold, but only the king could have created it.

---

### Recap

- Hash functions are **one-way, fixed-length, and collision-resistant** — they cannot be reversed like encryption
- **MD5 and SHA-1 are broken** (practical collisions exist); use **SHA-256 or higher** for all security-critical purposes
- **Salting** defeats rainbow tables; **bcrypt/Argon2/PBKDF2** add slow work factors for password storage
- **HMAC** gives integrity + authentication but **not non-repudiation** because the key is shared
- **Digital signatures** (hash → encrypt with private key) provide **authentication + integrity + non-repudiation**

### Exam flags

- **Broken vs. secure algorithms** — expect questions asking which algorithm is appropriate; know MD5/SHA-1 are broken and why (practical collisions), SHA-2 is current standard
- **What digital signatures provide vs. HMAC** — non-repudiation is the distinguishing property; know the signing/verification steps
- **Password storage mitigations** — salt defeats rainbow tables; bcrypt/Argon2/PBKDF2 are the approved slow functions
