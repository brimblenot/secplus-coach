## Application Security

Application security covers the practices, tools, and techniques used to find and fix vulnerabilities in software — ideally before attackers do. This lesson matters because the exam tests both the *what* (tools, headers, concepts) and the *why* (why one approach beats another in a given situation).

---

### The Secure Software Development Lifecycle (SSDLC)

The **SSDLC** — Secure Software Development Lifecycle — is a framework that integrates security activities into *every* phase of development, rather than bolting security on after the application is finished. Retrofitting security into finished software is more expensive, less effective, and more disruptive than building it in from the start.

| Phase | Security Activity |
|---|---|
| Requirements | Define security requirements; perform initial **threat modeling** (identifying what attackers want and what data is at risk) |
| Design | Architecture review; formal threat modeling against the specific design; apply defense-in-depth and least privilege |
| Implementation | Secure coding standards; avoid dangerous patterns (e.g., string concatenation in SQL); peer code review |
| Testing | Automated scanning + manual security testing alongside functional tests |
| Deployment | Hardened configurations; secrets managed via dedicated platforms, not embedded in code |
| Maintenance | Monitor for newly disclosed vulnerabilities; patch components; adapt as threats evolve |

> Think of SSDLC like building a house: it's far cheaper to put the deadbolt in the door *frame* during framing than to chisel it in after the drywall is up.

### Input validation

**Input validation** is the process of checking all data supplied by users or external systems *before* the application processes or stores it. It is the primary defense against injection attacks — **SQL injection** (attacker-crafted database queries), **command injection** (attacker-crafted OS commands), and **cross-site scripting** — **XSS** (malicious scripts injected into web pages).

**Allowlist validation** (also called whitelist validation) accepts *only* input that matches a known-good specification and rejects everything else — a ZIP code field accepts only five digits, optionally a hyphen, then four more digits; anything else is rejected outright. This is the **most secure** approach.

**Denylist validation** (also called blacklist validation) rejects known-bad patterns and accepts everything else. This is **less secure** because attackers routinely bypass it with encoding tricks and syntax variations the developer didn't anticipate.

Additional validation types:

- **Type validation** — rejects input that can't be parsed as the expected data type (e.g., a string in an integer field)
- **Length validation** — enforces min/max length to prevent buffer overflows
- **Range validation** — ensures numeric values fall within an expected range
- **Format validation** — uses **regular expressions** (pattern-matching rules) to verify structure (e.g., email, phone, date)

> **Critical rule:** **Server-side validation** must *always* run, even if client-side validation (JavaScript in the browser) is also present. Client-side validation is trivially bypassed by disabling JavaScript, modifying requests with a **web proxy** (a tool that intercepts and edits HTTP traffic), or sending raw HTTP requests — the server must never trust it already happened.

> Think of client-side validation like a "please be honest" sign at a self-checkout kiosk — a server-side check is the actual cashier audit.

### Output encoding

**Output encoding** converts user-supplied data into a safe representation before it appears in application output, so the browser (or database) treats it as *data*, not *code*.

| Output context | Required encoding |
|---|---|
| HTML page | HTML encoding — converts `<`, `>`, `"` to HTML entity equivalents so they render as text, not tags |
| URL | URL encoding — converts special characters to `%xx` format |
| JavaScript context | JavaScript encoding |
| Database query | **Parameterized queries** / **prepared statements** — separate SQL code structure from user-supplied values at the database driver level, making SQL injection impossible regardless of input |

> Think of output encoding like putting user input in a sealed display case: the browser can *see* the text but can't *execute* it.

### Error handling

**Error handling** is the practice of managing what an application shows users (and logs internally) when something goes wrong.

- Users should see only a **generic error page** — no stack traces, SQL syntax, file paths, server hostnames, or version numbers
- Detailed error info goes to **protected log files** accessible only to administrators
- **Custom error pages** must be configured to replace default server error pages, which often leak server and framework version information

> Showing a stack trace to a user is like handing a burglar your building's blueprints — they now know exactly where every door and weak point is.

### Security testing tools

#### SAST — Static Application Security Testing

**SAST** analyzes source code or compiled binaries *without executing them* to find security vulnerabilities. It integrates into a **CI/CD pipeline** — an automated build-and-deploy system — and runs on every code commit.

Finds: SQL injection from string concatenation, hard-coded credentials, dangerous functions, insecure randomness, improper certificate validation.

**Limitation:** Cannot detect vulnerabilities that only appear at runtime (e.g., authentication logic flaws, business logic issues) because it never runs the code.

Tools: Veracode, Checkmarx, Micro Focus Fortify (commercial); SonarQube, Semgrep, GitHub CodeQL (free/open-source).

> SAST is like a grammar checker on a recipe — it spots missing ingredients and bad syntax before anyone tries to cook it.

#### DAST — Dynamic Application Security Testing

**DAST** tests a *running* application by sending malicious inputs and observing responses — exactly as an attacker would, through the external interface. It requires *no access to source code*.

Finds: authentication weaknesses, session management flaws, runtime vulnerabilities that depend on application state — things SAST cannot see because SAST never executes the code.

Run against test/staging environments, *not* production.

Tools: **OWASP ZAP** (free, automated scanning and intercepting proxy), **Burp Suite** (industry-standard intercepting proxy + scanner + manual tools), Rapid7 AppSpider (commercial).

> DAST is like hiring someone to actually try picking your lock — SAST just read the locksmith's manual.

#### IAST — Interactive Application Security Testing

**IAST** injects a sensor into the application *runtime* and observes internal behavior while test cases execute — combining SAST's ability to see inside the code with DAST's real-execution coverage.

- Lower **false positive rate** — a false positive is a reported vulnerability that isn't actually exploitable — than SAST or DAST alone, because IAST can confirm whether a flaw is actually reachable during real execution.

> IAST is like a doctor doing an MRI *while* the patient runs on a treadmill — internal view plus live activity.

| Tool | Needs source code? | App must be running? | Best at |
|---|---|---|---|
| SAST | Yes | No | Finding code-level flaws early |
| DAST | No | Yes | Runtime/auth/session flaws |
| IAST | No (sensors) | Yes | High-accuracy combined coverage |

### Software Composition Analysis (SCA)

**SCA** — Software Composition Analysis — scans an application's third-party dependencies (open-source libraries, frameworks, packages) for known vulnerabilities. Modern apps are largely third-party code; a single vulnerable library like **Log4Shell** (a critical remote-code-execution vulnerability in the popular Log4j Java logging library, disclosed in 2021) can affect every application that includes it.

- Matches library versions against vulnerability databases such as the **NVD** — National Vulnerability Database, NIST's public catalog of known CVEs
- Generates **SBOMs** — **Software Bills of Materials**, machine-readable inventories of every component in an application
- Tools: Snyk, Black Duck (commercial); OWASP Dependency-Check, GitHub Dependabot (free)

> SCA is like a recalled-ingredient scanner at a food manufacturer — it checks every supplier's ingredient against a known-bad list before the product ships.

### Fuzzing

**Fuzzing** (also called **fuzz testing**) automatically sends randomly generated, malformed, or boundary-condition inputs to an application to discover crashes, hangs, and unexpected behavior — particularly **memory corruption** vulnerabilities, **format string vulnerabilities**, and input parsing errors that code review or structured tests miss.

- When the app crashes, the fuzzer records the exact input that caused it for developer investigation
- Almost always automated — finding crash-inducing inputs can require millions of test cases
- Tools: **American Fuzzy Lop** (AFL), **libFuzzer**, **Boofuzz**, CERT/CC Basic Fuzzing Framework

> Fuzzing is like a toddler randomly mashing every button on a control panel — occasionally they hit a combination that crashes the whole system.

### Code review and bug bounties

**Code review** is the practice of developers examining each other's code for security vulnerabilities and logic errors. It catches design-level issues automated tools miss and spreads security knowledge across the team.

**Bug bounty programs** pay external security researchers to find and responsibly disclose vulnerabilities in production applications. Platforms: **HackerOne**, **Bugcrowd**, **Synack**.

---

### Secrets management

**Secrets management** is the practice of keeping credentials, API keys, cryptographic keys, and connection strings *out* of source code and configuration files.

- Secrets embedded in code get committed to **version control** (e.g., Git) and persist in history even after deletion — anyone with repo access can recover them
- **Secret management platforms** — HashiCorp Vault, AWS Secrets Manager, Azure Key Vault — store secrets centrally and deliver them to applications at runtime via authenticated API calls
- **Git secret scanning tools** — GitHub Advanced Security, **truffleHog**, **git-secrets** — scan repos for credential-shaped patterns and alert developers

> Embedding a password in source code is like writing your ATM PIN in the margin of a library book — it feels private, but anyone who checks out the book sees it forever.

---

### HTTP security headers

**HTTP security headers** are response headers sent by a web server that instruct browsers to apply additional protections.

| Header | Full name | What it does |
|---|---|---|
| **HSTS** | HTTP Strict Transport Security | Tells browsers to use only HTTPS — prevents downgrade attacks to unencrypted HTTP |
| **CSP** | Content Security Policy | Defines which sources of scripts, styles, and media are trusted — limits XSS impact |

> Security headers are like the fine print on a signed contract telling the browser "here are the rules you must follow when handling my content."

### Recap

- **SSDLC** integrates security at every phase — requirements through maintenance — because retrofitting security is costlier than building it in
- **Allowlist validation** is more secure than denylist because it defines exactly what's acceptable; **server-side validation is always required** regardless of client-side checks
- **SAST** finds code-level flaws without running the app; **DAST** finds runtime flaws by actually running it; **IAST** instruments the running app for higher accuracy and lower false positives
- **SCA** detects vulnerable third-party dependencies and produces SBOMs; **fuzzing** discovers crashes through massive automated malformed-input testing
- **Secrets management platforms** keep credentials out of source code and version control history

### Exam flags

- **SAST vs. DAST vs. IAST** — know what each requires (source code? running app?), what each finds, and why IAST has lower false positives
- **Allowlist vs. denylist validation** — know which is more secure and why
