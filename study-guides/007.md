## Zero Trust (Domain 1)

Zero trust is the architectural answer to a world where there is no longer a meaningful network perimeter to defend. This lesson covers what zero trust is, why it replaced perimeter-based thinking, and the specific components, controls, and technologies the exam tests.

---

### Why the old model broke down

**Perimeter-based security** — the traditional model in which a firewall/VPN wall separates "trusted inside" from "untrusted outside" — assumed three things that are no longer true:

- All employees work at one physical site
- All apps run in an on-premises data center
- The inside/outside boundary is clearly defined

Modern reality breaks every assumption: remote workers, cloud apps (AWS, Azure, GCP), mobile devices, contractors, and **insider threats** — employees or contractors who already have legitimate access — all exist inside or bypass the perimeter.

**Lateral movement** — an attacker's ability to pivot from one compromised internal system to others — is nearly unchecked on a flat, implicitly trusting network. The 2020 SolarWinds and 2021 Colonial Pipeline incidents are the textbook examples of this failure.

> Think of the old model as a castle with a moat: once you're inside the gate, everyone assumes you belong there. Zero trust tears down the moat and puts a locked door on every room.

---

### The core principle

**Zero trust** is a security model built on "never trust, always verify." No user, device, or connection is granted access based on network location or prior authentication alone. Every request is treated as potentially hostile and must be explicitly authenticated, authorized, and **continuously validated**.

---

### Control Plane vs. Data Plane

Zero trust architecture is organized around two functional planes:

| Plane | Role | Key Components |
|-------|------|---------------|
| **Control Plane** | Makes policy *decisions* | Policy Engine, Policy Administrator |
| **Data Plane** | *Enforces* those decisions | Policy Enforcement Point (PEP) |

- **Policy Engine** — evaluates every access request against contextual signals (user identity, device health, resource sensitivity, time, location, behavior, threat intel) and outputs a grant/deny/revoke decision.
- **Policy Administrator** — communicates the Policy Engine's decision downstream; if access is granted, it issues the access token or credential.
- **PEP** (**Policy Enforcement Point**) — sits between the user/device and the resource; intercepts every request, hands it to the Control Plane, then allows or blocks based on the response. The PEP *enforces* but never *decides*.

> The Control Plane is the judge; the PEP is the bailiff who carries out the ruling.

---

### Key zero trust controls

**Adaptive identity** — dynamically adjusts authentication strength based on real-time risk signals. Same user, low-risk context (known device, normal hours, usual location) → lighter challenge. High-risk context (new country, 3 AM, sensitive data) → stronger challenge or outright denial.

**Microsegmentation** — divides the internal network into very small, isolated segments, each with its own access policy. Traffic between segments requires explicit authorization, just like traffic from outside. Implemented with **SDN** (Software-Defined Networking — a technology that controls network behavior through software rather than hardware configuration) and next-generation firewalls. Stops lateral movement even after an initial compromise.

**MFA** (**Multi-Factor Authentication**) — requires more than one credential type so that stealing a password alone is not enough. Zero trust treats identity as the primary security boundary, making MFA non-negotiable. **FIDO2/WebAuthn** — a phishing-resistant hardware-key standard — is preferred because it cannot be captured and replayed the way OTP codes can.

**Least privilege + JIT access** — users get only the minimum permissions needed, scoped to specific resources and time windows. **JIT** (**Just-in-Time**) access provisions elevated rights only when needed and auto-revokes them afterward.

**Continuous validation** — authentication is not a one-time event. Sessions are periodically re-evaluated; if risk signals change (device goes out of compliance, unexpected location change, anomalous behavior), the session is terminated and re-authentication is required. Traditional session tokens, by contrast, remain valid for their full lifetime regardless of changing conditions.

**Device health verification / endpoint posture checking** — before granting access, the system checks that the device has current OS patches, active endpoint protection, disk encryption, MDM enrollment, and is not jailbroken/rooted. **NAC** (**Network Access Control**) — a technology that enforces device compliance checks at the network access layer — is the primary tool for implementing this at scale.

---

### Security zones in a zero trust world

Zero trust still uses the concept of zones to describe traffic origins, but applies explicit verification to *all* inter-zone traffic — including internal-to-internal:

| Zone | What it represents |
|------|--------------------|
| **Untrusted** | Internet / external networks |
| **Trusted** | Corp-owned, authenticated, compliant devices/users |
| **Internal** | Data center resources and applications |

---

### SASE and ZTNA

**SASE** (**Secure Access Service Edge**, pronounced "sassy") — a cloud-delivered architecture that merges wide-area networking (**SD-WAN** — software-defined wide-area networking) with security services (**CASB** — Cloud Access Security Broker; **SWG** — Secure Web Gateway; **FWaaS** — Firewall-as-a-Service) into one platform. It extends zero trust to distributed workforces without backhauling traffic through a central data center.

**ZTNA** (**Zero Trust Network Access**) — the component within SASE that replaces traditional VPN by granting access only to the specific applications a user is authorized for, rather than placing the device on the full internal network.

---

### Software-Defined Perimeter

**SDP** (**Software-Defined Perimeter**) — implements zero trust by making all services **dark by default** (invisible and unresponsive to unauthenticated probes). Only after identity and device are verified does the SDP controller provision a one-to-one, encrypted connection to the specific authorized resource. Unlike VPN, which exposes the full network once connected, SDP exposes only what the user is explicitly allowed to reach.

---

### Recap

- Zero trust = "never trust, always verify" — location grants no implicit trust; every request is evaluated explicitly
- **Control Plane** decides (Policy Engine + Policy Administrator); **Data Plane** enforces (PEP)
- Adaptive identity adjusts auth strength to real-time risk; continuous validation means sessions can be revoked mid-stream
- Microsegmentation stops lateral movement; NAC enforces device health; MFA (preferably FIDO2) protects identity
- SASE bundles networking + security in the cloud; ZTNA replaces VPN; SDP makes services dark by default

### Exam flags

- **Control Plane vs. Data Plane components** — knowing which component (Policy Engine, Policy Administrator, PEP) belongs to which plane and what each one does is a high-frequency question type
- **ZTNA vs. traditional VPN** — expect a scenario asking which technology grants access to specific apps only (ZTNA) rather than full network access (VPN)
- **Adaptive identity and continuous validation** — scenario questions often describe a session being terminated or authentication being escalated mid-session and ask you to name the zero trust principle at work
