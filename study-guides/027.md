## Buffer Overflows

Buffer overflows are one of the oldest and most dangerous vulnerability classes in computing. This lesson covers how they work, how attackers exploit them, and the mitigations defenders use to stop them.

---

### What a buffer overflow is

A **buffer** is a fixed-size region of memory a program reserves to hold data. A **buffer overflow** occurs when a program writes more data into a buffer than it was allocated to hold — the excess data spills into adjacent memory, corrupting whatever was stored there.

- Adjacent memory may hold other variables, control data, or pointers
- Corrupting those values lets an attacker redirect what the program does next

> Think of a buffer like a parking lot with 10 spaces. If 15 cars try to park, the extras spill into the neighboring lot — and if that lot was reserved for something important, chaos follows.

---

### Stack-based buffer overflows

**Stack-based buffer overflow** — the most common form — exploits the layout of the **call stack** (the data structure that manages active function calls).

When a function is called, the system pushes a **stack frame** onto the call stack containing:
- Local variables (including buffers)
- The **saved frame pointer** — a reference to the caller's stack position
- The **return address** — where execution resumes after the function finishes

**Unsafe C functions** — `strcpy`, `gets`, `sprintf`, `scanf %s` — copy input until a null character with no size check. If a 64-byte buffer receives 200 bytes, the extra 136 bytes overwrite the return address.

An attacker who controls that overflow controls where the CPU jumps next.

**Classic exploit payload structure:**

| Payload section | Purpose |
|---|---|
| **NOP sled** — a sequence of `NOP` ("no operation") instructions | Creates a large valid landing zone; execution slides through it |
| **Shellcode** — machine instructions that perform the attacker's action (e.g., open a shell) | The actual malicious code to execute |
| **Padding** | Fills from buffer end to the return address location |
| **Overwritten return address** | Points back into the NOP sled |

> Imagine writing a fake forwarding address on someone's mail — when the post office (CPU) returns the letter, it delivers it to the attacker's address instead.

---

### Heap-based buffer overflows

**Heap-based buffer overflow** — corrupts dynamically allocated memory (memory requested at runtime via `malloc` or C++'s `new` operator) rather than stack memory.

- Overflowing into adjacent heap allocations can corrupt **heap metadata** or overwrite pointers in nearby objects
- Generally harder to exploit than stack overflows because heap layout is less predictable

---

### Integer overflows

An **integer overflow** occurs when an arithmetic result exceeds the maximum value a data type can hold, causing it to wrap around (e.g., a 16-bit unsigned integer maxes out at 65,535 — the next increment gives 0).

- If a program uses an overflowed integer to calculate buffer size, it allocates a tiny buffer but writes a large amount of data into it
- Creates a buffer overflow indirectly, through the size calculation

---

### Format string vulnerabilities

A **format string vulnerability** arises when user input is passed directly as the format string argument to functions like `printf` or `sprintf` instead of as a data argument.

Format specifiers tell these functions how to interpret memory:

| Specifier | Behavior |
|---|---|
| `%d` | Reads an integer |
| `%s` | Reads a string pointer |
| `%x` | Reads a value as hexadecimal |
| `%n` | **Writes** the count of characters printed so far to a pointer |

An attacker controlling the format string can read arbitrary stack memory (`%x`, `%s`) or write to arbitrary addresses (`%n`) — enabling full code execution.

---

### Real-world examples

- **Heartbleed (CVE-2014-0160)** — a **buffer over-read** (reads too much, rather than writing too much) in OpenSSL's TLS heartbeat handler; exposed up to 64 KB of adjacent server memory, leaking private keys, passwords, and session tokens
- **EternalBlue (MS17-010)** — buffer overflow in Windows SMBv1; used by **WannaCry** ransomware and **NotPetya** destructive malware to spread between unpatched systems
- **Morris Worm (1988)** — exploited a buffer overflow in the Unix `fingerd` daemon; one of the first self-propagating internet worms

---

### Mitigations

**Stack canaries** (also called **stack guards** or **stack cookies**) — a random value the compiler inserts on the stack between local variables and the return address. Before the function returns, the program checks that this value is unchanged. An overflow that overwrites the return address must also overwrite the canary — if the canary changed, the program terminates immediately.
- GCC flag: `-fstack-protector`; MSVC flag: `/GS`
- Canary is randomized per process run so attackers can't just embed the known value

**ASLR** — **Address Space Layout Randomization** — randomizes the memory addresses of the stack, heap, and loaded libraries each time a program runs, so an attacker cannot know where shellcode or ROP gadgets are located.
- Does not prevent overflows, but makes reliable exploitation much harder
- Bypassing ASLR requires a secondary **information leak** — a separate vulnerability that reveals actual memory addresses before the overflow fires

**DEP** — **Data Execution Prevention** — uses the **NX bit** (a CPU hardware flag) to mark stack and heap memory as non-executable, so injected shellcode cannot run.
- Stops classic shellcode injection
- **Bypassed by ROP** (see below)

**ROP** — **Return-Oriented Programming** — an advanced technique that bypasses DEP by chaining together short snippets of *existing* legitimate executable code, called **gadgets** — each ending in a `RET` instruction — already present in the program or its libraries. Because no new code is injected, DEP cannot block it.

**SafeSEH** — a Windows mitigation that validates the **SEH chain** (**Structured Exception Handler** chain — the list of error-handling routines registered on the stack) before executing any handler, blocking attackers from redirecting exception handling to shellcode.

**CFG** — **Control Flow Guard** — a Windows mitigation that maintains a table of valid indirect call targets and checks each indirect call at runtime, blocking ROP chains that exploit indirect branches.

**Memory-safe languages** — Rust, Go, Java, Python perform automatic bounds checking or use garbage collection, preventing buffer overflows at the language level. The core problem is the enormous existing codebase of C and C++ that manages memory manually.

**Safe string functions** — `strncpy` and `snprintf` accept a maximum-length argument, unlike unsafe equivalents (`strcpy`, `sprintf`), preventing writes beyond the buffer.

| Mitigation | What it stops | What bypasses it |
|---|---|---|
| Stack canaries | Stack return-address overwrites | Brute force or canary leak |
| ASLR | Hardcodes addresses in exploit payloads | Information leak vulnerability |
| DEP / NX bit | Shellcode injection | ROP |
| ROP + ASLR + canaries combined | Most reliable exploitation | Sophisticated chained attacks |
| Memory-safe languages | Buffer overflows at language level | N/A (architectural fix) |

---

### Recap

- A buffer overflow writes past a buffer's boundary, corrupting adjacent memory — on the stack, an attacker can overwrite the return address to hijack execution
- The classic payload uses a NOP sled + shellcode + overwritten return address; format string bugs and integer overflows are related paths to the same outcome
- Heartbleed is a **over-read**, not a write overflow; EternalBlue and the Morris Worm are write-overflow examples
- Stack canaries catch overwrites at return time; ASLR randomizes addresses; DEP blocks shellcode injection; ROP bypasses DEP by reusing existing code
- Memory-safe languages (Rust, Go, Java) are the most fundamental fix

### Exam flags

- **Stack canaries vs. ASLR vs. DEP** — know what each prevents and what bypasses each (especially that ROP bypasses DEP)
- **Format string `%n` specifier** — know that attacker-controlled format strings can write to arbitrary memory, not just read
- **Heartbleed classification** — it is a buffer over-read (not a write overflow), leaking adjacent memory rather than corrupting it
