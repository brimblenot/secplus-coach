## Analyzing Vulnerabilities

Vulnerability scanners produce raw findings — this lesson covers how to interpret those findings using CVSS scoring, temporal and environmental adjustments, false positive/negative analysis, and contextual risk factors to build a prioritized remediation plan.

---

### Raw scanner output is not a plan

A vulnerability scanner may return thousands of findings. Without analysis, you might waste time patching low-risk issues while a critical, internet-facing hole stays open. Effective analysis applies risk context to produce a **prioritized remediation list**.

---

### The CVSS base score

**CVSS** (Common Vulnerability Scoring System) is the industry-standard framework for rating vulnerability severity, producing a score from **0.0–10.0** based on six metrics. Each metric has discrete values you must recognize.

#### Attack Vector (AV) — how the attacker reaches the target

| Value | Abbreviation | Meaning |
|---|---|---|
| Network | AV:N | Exploitable from the internet — highest risk |
| Adjacent | AV:A | Requires same LAN/Wi-Fi/Bluetooth range |
| Local | AV:L | Requires authenticated session on the machine |
| Physical | AV:P | Requires physical contact — lowest risk |

#### Attack Complexity (AC) — conditions needed beyond access

| Value | Meaning |
|---|---|
| AC:L (Low) | Attack is reliable and repeatable at will |
| AC:H (High) | Requires race conditions, special config, or prep work |

#### Privileges Required (PR) — what access the attacker needs first

| Value | Meaning |
|---|---|
| PR:N (None) | No authentication needed — any stranger can try |
| PR:L (Low) | Needs a regular user account |
| PR:H (High) | Needs admin/root — attacker is already deeply in |

#### User Interaction (UI) — does a victim need to do something?

| Value | Meaning |
|---|---|
| UI:N (None) | Attacker triggers it alone — higher risk |
| UI:R (Required) | Victim must click/open/visit — social engineering can bridge this gap |

#### Scope (S) — can exploitation jump to other components?

- **S:U (Unchanged)** — impact stays inside the vulnerable component
- **S:C (Changed)** — exploitation escapes to other components (e.g., **hypervisor escape** — a breakout from a virtual machine that then affects the physical host, or a **container escape** that reaches the underlying OS)

#### Impact metrics (CIA triad)

Each of Confidentiality, Integrity, and Availability is rated **High / Low / None** — High means complete loss of that property on the component.

> Think of the six CVSS metrics as a crime report: *How did the burglar get in? Did they need a key? Did they need an accomplice inside? Did they steal only from this apartment or access the whole building?*

### Severity ranges and remediation timelines

| Score | Severity | Patch target |
|---|---|---|
| 9.0–10.0 | Critical | 24–48 hours |
| 7.0–8.9 | High | 7–14 days |
| 4.0–6.9 | Medium | 30 days |
| 0.1–3.9 | Low | Quarterly patch cycle |
| 0.0 | Informational | No direct attack risk; best-practice note |

---

### Temporal score — current real-world exploitability

The **CVSS Temporal Score** adjusts the base score based on the current exploitation landscape, not just theoretical severity.

- **Exploit Code Maturity** — the most impactful factor:
  - *Unproven* → *Proof-of-Concept* → *Functional* (public exploit exists) → *High* (automated/worm-like)
- **Remediation Level** — vendor patch available, workaround only, or no fix at all
- **Report Confidence** — vendor-confirmed vs. unverified researcher report

> A vulnerability with a *Functional* public exploit should jump the queue over a higher base-score finding where exploitation is still theoretical.

---

### Environmental score — your organization's context

The **CVSS Environmental Score** lets you weight each CIA impact metric by how much that property matters **to your specific system**. Set **Availability Requirements: High** for a critical production database; set **Confidentiality Requirements: Low** for a public-facing static site with no sensitive data. This produces a score tuned to real organizational risk, not just generic severity.

### False positives and false negatives

**False positive** — the scanner reports a vulnerability that does not actually exist or is not exploitable in your environment.

- Causes: version-string detection (patch applied without changing version number), compensating controls already blocking exploitation, inaccurate scanner plugin logic
- **Authenticated scans** — scans that log in to the target and read actual installed-patch records — dramatically reduce false positives vs. unauthenticated scans, which guess vulnerability status from version numbers alone
- Always validate Critical/High findings before opening a change-management ticket

**False negative** — a real vulnerability the scanner missed entirely.

- Common causes: **zero-days** (vulnerabilities not yet in any public database), custom application code scanners don't test, vulnerabilities that only appear under specific runtime conditions
- Scanner results must be supplemented with **penetration testing**, **application security testing**, and **threat intelligence**

### NVD and CWE

**NVD** (National Vulnerability Database), maintained by NIST at *nvd.nist.gov*, enriches **CVE** identifiers (Common Vulnerabilities and Exposures — unique IDs assigned to specific known vulnerabilities) with CVSS scores, affected versions, patches, and CWE classifications.

**CWE** (Common Weakness Enumeration) categorizes the *root-cause weakness type* behind a vulnerability — not the specific instance, but the class of flaw:

| CWE ID | Weakness |
|---|---|
| CWE-89 | SQL Injection |
| CWE-79 | Cross-Site Scripting |
| CWE-119 | Improper Restriction of Buffer Operations |
| CWE-20 | Improper Input Validation |

If multiple findings share a CWE root cause, one remediation approach (e.g., input validation) may fix several issues at once.

### Contextual risk factors beyond CVSS

CVSS alone is not enough. Layer these factors on top:

- **Internet exposure** — a Critical finding on a public web server is orders of magnitude more urgent than the same finding on an isolated internal system
- **Active exploitation in the wild** — confirmed by the **CISA Known Exploited Vulnerabilities (KEV) catalog** — means attackers are hitting it *right now*
- **Lateral movement / privilege escalation potential** — makes a finding especially attractive to attackers who already have limited access
- **Data sensitivity** — the actual classification of data reachable through the vulnerable system
- **Compensating controls** — network segmentation, **WAF** (Web Application Firewall — a filter that inspects and blocks malicious HTTP traffic), or **IPS** (Intrusion Prevention System — inline network device that detects and blocks attack traffic) may reduce real-world exploitability even if CVSS stays the same

---

### Recap

- **CVSS** produces a 0–10 base score from six metrics (AV, AC, PR, UI, Scope, CIA Impact); know every value and what it means
- **Temporal score** adjusts for exploit availability and patch status; *Functional* exploit code is a major urgency trigger
- **Environmental score** customizes CVSS to your organization's actual CIA requirements
- **False positives** waste remediation effort; **false negatives** (especially zero-days and custom-code flaws) mean scanning alone is never exhaustive
- Contextual factors — internet exposure, active exploitation (KEV), lateral movement potential, data sensitivity — must overlay CVSS scores to produce a truly prioritized list

---

### Exam flags

- **CVSS metric values and their risk direction** (especially AV:N vs. AV:P, PR:N vs. PR:H, S:C vs. S:U) are heavily tested — know every abbreviation and what higher/lower means for risk
- **Temporal score factors**, especially Exploit Code Maturity levels (Unproven → High), are a common scenario question trigger
- **False positive vs. false negative** definitions, causes, and which scan type (authenticated vs. unauthenticated) reduces each
