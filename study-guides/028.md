## Race Conditions

Race conditions are a class of software vulnerability where security breaks down because two operations happen in the wrong order — and an attacker can influence that order. This lesson covers the core concept, real-world examples, and the defenses that close the window of vulnerability.

---

### What a race condition is

A **race condition** is a vulnerability that occurs when a program's correct behavior depends on the timing or ordering of operations, and that timing can be manipulated by an attacker.

- Happens in **concurrent systems** — where multiple threads, processes, or users share resources at the same time
- Operations designed to run in sequence can **interleave** in unintended ways
- Hard to catch in testing because the bad ordering may be rare or environment-dependent

> Think of two cashiers both checking the same "last item in stock" shelf at once — each sees it available, so both sell it, and now you've sold something you don't have.

---

### TOCTOU: the core attack pattern

**TOCTOU** (Time-of-Check to Time-of-Use) — pronounced *"tock-too"* — is a vulnerability where a program checks a condition at one moment, then acts on it later, assuming nothing changed in between.

- The gap between the **check** and the **use** is called the **window of vulnerability**
- An attacker who can modify the checked resource *during that gap* causes the program to act on stale, incorrect information

**Classic file system example:**
- A privileged program checks: "Is this file safe to write to? (Not a symlink to `/etc/shadow`?)" ✅
- Attacker immediately replaces the file with a **symlink** — a pointer that redirects the file path to `/etc/shadow`
- Program opens the file and writes to `/etc/shadow`, bypassing the security check entirely
- The check found a safe file; the use opened a dangerous one

> It's like a bouncer checking your ID at the door, then turning away while someone swaps in a different person — by the time they open the VIP room, the wrong person walks in.

---

### TOCTOU in web apps: double-spend and overdraft

Web apps hit TOCTOU constantly in e-commerce and banking:

**Inventory example:** Two users simultaneously buy the last item. Both requests hit the stock check *before* either decrement runs → both checks pass → item sold twice → inventory goes negative.

**Withdrawal/double-spend example:**

| Step | User 1 | User 2 | Account A Balance (stored) |
|------|--------|--------|---------------------------|
| Check balance | Sees $100 | Sees $100 | $100 |
| Approve withdrawal | $50 approved | $50 approved | Still $100 (not updated yet) |
| Post withdrawal | −$50 | −$50 | $0 (but $100 paid out total) |

Both withdrawals succeed because the balance check is not **atomic** with the balance update — they are two separate steps with a gap between them.

---

### Dirty COW: the most famous race condition exploit

**Dirty COW** (CVE-2016-5195) — short for "Dirty Copy-On-Write" — is a Linux kernel race condition that allowed any unprivileged local user to overwrite read-only files, achieving full root access.

- **Copy-on-write (COW)** — a kernel memory optimization where a private writable copy of a read-only file's memory is only created *when the process actually writes to it*, not immediately
- The race: an attacker could interleave two operations — *writing to the private copy* and *discarding the private copy* — fast enough to trick the kernel into writing to the **original read-only file** instead
- Even protected files like `/etc/passwd` were vulnerable → attacker writes a new root entry with a known password → instant root access
- Present in the Linux kernel for **over 9 years**; affected Linux servers, Android devices, and embedded systems worldwide

> Imagine a "do not modify" master document in a locked room. The copy machine is supposed to give you a personal copy to edit — but if you yank the copy out at exactly the right moment, the machine accidentally edits the master instead.

### Real-world impact beyond hacking

- **Mars Rover Spirit (2004):** A race condition caused a file system error that triggered a reboot — which immediately hit the same error — creating an **infinite reboot loop**. Engineers transmitted a patch to break the cycle. Not a security attack, but shows race conditions can cause catastrophic failure in safety-critical systems.
- **Tesla Model 3 (Pwn2Own 2023):** Researchers exploited a TOCTOU race condition in the infotainment system via Bluetooth, escalating to **root access**. Prize: $100,000 and the car.

---

### Defenses: closing the window

The core fix is **atomicity** — making a check and its resulting action a single, indivisible operation with no gap.

| Defense | What it is | What it prevents |
|--------|-----------|-----------------|
| **Mutex** (mutual exclusion lock) | A lock allowing only one thread at a time into a protected code region | Two threads racing through the same check-then-act path |
| **Semaphore** | A generalized lock allowing up to *N* threads simultaneously; a binary semaphore (0 or 1) behaves like a mutex | Concurrent access beyond a defined limit |
| **CAS** (Compare-And-Swap) | A hardware CPU instruction that atomically reads, compares, and writes a value in one uninterruptible step | Race on a single shared variable |
| **Database transactions** | A grouped set of DB operations that either all succeed or all roll back together | Partial updates that leave inconsistent state |
| **`O_EXCL` + `O_CREAT` flag** | Unix file-open flags that atomically check-and-create a file — succeeds only if the file did not already exist | File system TOCTOU on creation |

**Other mitigations:**
- Minimize time between check and use (reduces probability, does NOT eliminate the window)
- Design to avoid **shared mutable state** — use thread-safe data structures
- **Static code analysis** tools can flag TOCTOU patterns
- Security-focused code review should specifically scrutinize all check-then-use code paths

---

### Recap

- A **race condition** occurs when concurrent operations interleave in an order the developer didn't anticipate, producing an unintended — and exploitable — state
- **TOCTOU** is the key pattern: check passes, attacker modifies the resource, use operates on the now-dangerous resource
- **Dirty COW** exploited a Linux kernel COW race to let any local user write to read-only files and gain root
- The fundamental fix is **atomicity** — combining check and action into one indivisible operation via mutexes, semaphores, CAS, transactions, or atomic file flags
- Real-world impact ranges from financial fraud to privilege escalation to physical system failures

### Exam flags

- **TOCTOU** is the highest-probability race condition topic — know the pattern (check → gap → use), the file system symlink example, and the banking/inventory double-spend scenario
- Know **Dirty COW** by name and its mechanism: a COW race condition in the Linux kernel enabling local privilege escalation to root via read-only file overwrite
- Know the defenses — **mutex**, **semaphore**, **atomic operations**, and **database transactions** — and that the goal of all of them is **atomicity**
