## Deception and Disruption

Deception and disruption technologies flip the script on attackers: instead of only blocking or detecting known threats, they plant fake targets throughout your environment, guarantee near-zero false positives, and gather intelligence on attacker behavior. This lesson covers every deception tool the exam tests and how they fit together.

---

### Honeypots: decoy systems that catch attackers in the act

A **honeypot** is a deliberately exposed decoy system — mimicking a real server, workstation, or service — that has no legitimate business function and exists only to attract and log attacker activity. Because no real user ever has a reason to touch it, any connection is automatically suspicious.

Honeypots exist on a spectrum:

| Type | What it exposes | Risk | Best for |
|---|---|---|---|
| **Low-interaction honeypot** | Surface-level service responses only (no real OS) | Low — little for attacker to exploit | Detecting automated scans and initial recon |
| **High-interaction honeypot** | Full OS and applications; attacker can log in and run commands | Higher — attacker might pivot to production if isolation fails | Deep intelligence on attacker TTPs |

> *Think of a low-interaction honeypot as a storefront mannequin — convincing from the street, but there's nothing inside. A high-interaction honeypot is a furnished model home with hidden cameras in every room.*

---

### Honeynets: simulating an entire fake organization

A **honeynet** is a network of multiple interconnected honeypots designed to mimic a full production environment — fake workstations, servers, routers, firewalls, printers, all organized like a real org. This gives sophisticated attackers enough to explore across multiple stages (initial access → lateral movement → exfiltration), while security teams watch every move.

- Particularly valuable for studying **APTs** — **Advanced Persistent Threats**, attackers who conduct slow, multi-stage intrusions over weeks or months
- Intelligence gathered on **TTPs** — **Tactics, Techniques, and Procedures**, the attacker's specific methods — feeds back into real production defenses
- **Project Honey Pot** — an internet-distributed honeynet that aggregates threat intelligence from honeypots worldwide on scanning patterns, attack sources, and malware behavior

> *A honeynet is like a fake city built on a movie studio backlot — realistic enough that an attacker wanders around for hours thinking it's real, while the film crew records everything.*

### Honeyfiles and canary tokens: fake files that tattle on intruders

A **honeyfile** is a fake file placed in a file system, network share, or cloud storage, given a name specifically chosen to attract an attacker (e.g., `passwords.txt`, `salary_data.xlsx`, `confidential_merger_plans.docx`). The contents are false or meaningless, but the name triggers attacker interest.

- Key implementation: embed **canary tokens** — tracking triggers hidden inside a document (a unique URL, an embedded pixel, or a fake credential) that fire an alert to the **SOC** — **Security Operations Center** — the moment the file is opened
- No legitimate user should ever open a honeyfile → any access is immediately high-priority

> *A honeyfile is like a decoy wallet left on a table in a sting operation — the thief grabs it, and the moment they open it, a dye pack goes off and the alarm sounds.*

---

### Honeytokens: fake data values that expose theft

A **honeytoken** is a fake data item — not a whole file, but a single data value — planted in accessible locations and monitored for use. Examples include:

- **Fake credentials** — usernames/passwords that appear in a config file or credential dump but don't work on any real system
- **Fake API keys** / **AWS access key IDs** — planted in code repos or cloud storage; not tied to any real resource
- **Fake database records** — invented names, addresses, or account numbers mixed into real data
- **Fake email addresses** — never associated with a real person; if they appear in a spam list or phishing database, data was stolen and shared
- **Fake software license keys** — non-functional keys monitored for use attempts

When an attacker steals and uses a honeytoken, the authentication attempt or outbound call triggers an immediate alert. Especially effective at detecting **credential theft** and **insider threats**.

> *A honeytoken is like a marked $20 bill left in a cash register — looks real, but the serial number is recorded. When it shows up at another store, you know exactly who took it.*

---

### DNS sinkholing: cutting off malware's phone home

**DNS sinkholing** is a technique where the **DNS** — **Domain Name System**, the service that translates domain names to IP addresses — resolver is configured to redirect known malicious domain names to a controlled IP address instead of the attacker's real **C2** — **Command-and-Control** — server.

- Malware tries to contact its C2 using a domain name → sinkhole intercepts the lookup → malware's traffic goes nowhere useful
- The sinkhole server **logs the connection attempt**, revealing which internal device is infected
- Implemented at the **recursive DNS resolver** — the server that performs lookups on behalf of clients — often using vendor **threat intelligence feeds** listing known malicious domains
- Integrate sinkhole logs with **SIEM** — **Security Information and Event Management**, the platform that aggregates logs and generates alerts — for automated incident creation

> *DNS sinkholing is like quietly rerouting every call from a criminal's burner phone to a recording booth — the malware thinks it's talking to its boss, but it's just leaving messages nobody acts on, while you log every call.*

### Dark web monitoring: finding your data before attackers use it

**Dark web monitoring** is a threat intelligence service that searches dark web forums, underground marketplaces, and paste sites for an organization's stolen data. The **dark web** is the portion of the internet not indexed by standard search engines, typically accessed via anonymizing networks like **Tor** — an anonymizing network that routes traffic through multiple relays to hide the user's identity.

- Monitors for domain names, email addresses, IP ranges, executive names, API keys, credential dumps, and source code
- Uses automated crawlers and human analysts
- When a match is found → organization is alerted → can force password resets, revoke API keys, or open an incident before attackers exploit the data

> *Dark web monitoring is like having an informant in a criminal marketplace who texts you the moment someone puts your house keys up for sale.*

### Fake telemetry and tactical deception

**Fake telemetry** is the practice of presenting false information about the network to any attacker who gains a foothold — misleading their reconnaissance so they waste time on dead ends.

- Fake **routing tables** — network maps that tell routers where to send traffic — suggesting a different topology than actually exists
- False **service banners** — the text a service sends when a client connects, advertising its name and version — advertising outdated or vulnerable software to attract and study attackers
- Fake usernames in directory services that act as honeytokens

**Tactical deception** is the broader strategy: make the environment appear larger, more complex, and richer in valuable data than it really is, increasing the probability an attacker touches a deception asset and triggers detection.

---

### Why deception alerts are almost always real

Signature-based detection and behavioral analytics generate frequent **false positives** — alerts triggered by legitimate activity that merely looks suspicious — because real users perform actions that resemble attack patterns.

Deception systems produce near-**zero false positives** because no legitimate user or process ever touches a honeypot, honeyfile, honeytoken, or sinkhole. Any alert from a deception system means something abnormal is definitively happening. Configure SIEM to create **high-priority incidents** for every deception alert and route them to on-call analysts immediately.

---

### Legal considerations for honeypots

- **Entrapment** — the legal defense that law enforcement induced someone to commit a crime they wouldn't have otherwise committed — applies only to government actors, **not** private organizations
- Private orgs may legally operate honeypots because the attacker chose to attack; the honeypot didn't induce the crime
- **Edge case**: an aggressively advertised honeypot that could be argued to have lured an otherwise non-criminal actor creates legal complexity — consult legal counsel before deployment, especially if prosecuting
- **Critical**: isolate honeypots completely from production; if an attacker uses a poorly isolated honeypot to attack third parties, the organization may face liability

---

### Recap

- **Honeypot** = single decoy system; **honeynet** = network of decoys simulating a full environment; both produce near-zero false-positive alerts
- **Honeyfiles** lure attackers with enticing filenames; **canary tokens** embedded inside fire alerts the moment the file is opened
- **Honeytokens** are fake data values (credentials, API keys, DB records) that expose theft when an attacker tries to use them
- **DNS sinkholing** redirects malware's C2 lookups to a controlled address, cutting off communication and identifying infected hosts
- Deception alerts are high-fidelity by design — no legitimate user ever touches these assets, so every alert warrants immediate investigation

---

### Exam flags

- **Honeyfile vs. honeytoken distinction** — know that honeyfiles are entire fake files with canary tokens embedded; honeytokens are individual fake data values (credentials, API keys, records) monitored for use
- **DNS sinkholing purpose** — expect a scenario question asking what technique identifies infected internal hosts and disrupts C2 communication simultaneously
- **Low- vs. high-interaction honeypot tradeoffs** — know that high-interaction provides richer intelligence but carries pivot risk if not isolated from production
