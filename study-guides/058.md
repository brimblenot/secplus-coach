## Cloud Infrastructures

Cloud security isn't just about locking down servers — it's about knowing *who is responsible for what* across a range of service and deployment models. This lesson maps the full cloud landscape the exam tests: service models, deployment models, the shared responsibility model, and key cloud security constructs.

---

### Service models: what the provider manages vs. what you manage

Each cloud service model draws the responsibility line in a different place. The more abstracted the service, the less infrastructure you manage — but you always own your data and identities.

**IaaS** — **Infrastructure as a Service** — the provider supplies physical hardware, networking, storage, and the **hypervisor** (the software layer that runs virtual machines). The customer manages everything above the hypervisor: OS, middleware, app code, and data.
- Examples: AWS EC2, Azure Virtual Machines, Google Compute Engine
- Most control, most security burden — you patch the OS, harden configs, manage firewalls inside the instance
- *Analogy: Renting an empty warehouse. The landlord handles the building and utilities; you furnish it, lock it, and run everything inside.*

**PaaS** — **Platform as a Service** — the provider also manages the OS, runtime, and middleware. You only manage app code and data.
- Examples: AWS Elastic Beanstalk, Azure App Service, Google App Engine
- Smaller infrastructure attack surface, but you're still fully responsible for writing secure code and securing your data
- *Analogy: Renting a fully equipped commercial kitchen — the equipment and plumbing are maintained for you; you just bring your recipes and ingredients.*

**SaaS** — **Software as a Service** — the provider manages everything through the application itself. You manage data, user access, and settings inside the app.
- Examples: Microsoft 365, Salesforce, Dropbox, Google Workspace
- The customer does NOT patch servers or configure TLS — but misconfiguring access (e.g., leaving SharePoint public) is entirely the customer's fault
- *Analogy: Leasing a fully staffed office with IT support — you just decide who gets a key and what they're allowed to touch.*

**FaaS** — **Function as a Service**, also called **serverless computing** — customers deploy only individual units of code (functions) that run in response to specific events; no servers or platforms are provisioned at all.
- Examples: AWS Lambda, Azure Functions, Google Cloud Functions
- OS, patching, scaling: completely invisible to the customer; billed only when functions execute
- Security focus: secure function code, use **least privilege IAM roles** (identity and access management roles scoped to minimum necessary permissions), protect secrets in environment variables, authenticate event triggers
- *Analogy: A vending machine — you provide the snack recipe; the machine handles manufacturing, refrigeration, and delivery on demand.*

| Model | Provider manages | Customer manages |
|-------|-----------------|-----------------|
| IaaS | Hardware, hypervisor | OS, middleware, app, data |
| PaaS | + OS, runtime, middleware | App code, data |
| SaaS | + Application | Data, user access, settings |
| FaaS | + Everything infrastructure | Function code, permissions, secrets |

### Deployment models: who shares the infrastructure

**Public cloud** — infrastructure owned by a provider (AWS, Azure, GCP) and shared across many customers, each logically isolated. Maximum scalability and cost efficiency; reduced physical control; potential regulatory concerns in multi-tenant environments.

**Private cloud** — infrastructure dedicated to one organization, hosted on-premises or by a third party on dedicated hardware. Technologies include VMware vSphere, Azure Stack, OpenStack. Greatest control and **data sovereignty** (the organization retains exclusive jurisdiction over where its data lives and who can access it), but higher cost. Required by heavily regulated organizations (defense, healthcare).

**Hybrid cloud** — public + private combined, with data/workloads moving between environments. Adds flexibility but significantly increases complexity: different auth systems, log formats, network configs, and tooling. Environments are connected via **VPNs** (encrypted tunnels across public internet) or dedicated private connections such as **AWS Direct Connect** or **Azure ExpressRoute** — links that bypass the public internet entirely for lower latency and more predictable performance.

**Community cloud** — shared among organizations with common regulatory requirements (e.g., federal agencies under **FedRAMP** — the U.S. government's cloud security authorization program — or healthcare organizations under HIPAA).

**Multi-cloud** — using services from multiple providers simultaneously (e.g., AWS for compute, Azure for directory services, GCP for ML). Reduces vendor lock-in and adds redundancy; security challenge is achieving unified visibility across providers with different IAM systems, logging formats, and compliance postures.

### Shared responsibility model

The defining framework for cloud security accountability: the boundary of responsibility shifts by service model.

- **Security *of* the cloud** — provider's responsibility: physical data centers, hardware, hypervisor, global network
- **Security *in* the cloud** — customer's responsibility: data, identities, access controls, encryption choices, network rules, and (depending on model) OS and app code
- Regardless of model, **identity and access management, data classification, and client-side encryption** are nearly always the customer's responsibility

*Analogy: A bank vault. The bank (provider) secures the building and the vault door; you (customer) decide what you put inside, who has your PIN, and how you label your safe-deposit box.*

### Cloud security constructs

**Security groups** — virtual **stateful firewalls** (they track connection state, so return traffic for an allowed session is automatically permitted) that operate at the instance or network interface level in AWS and Azure. Rules specify allowed source/destination IPs, protocols, and ports.

**NACLs** — **Network Access Control Lists** — subnet-level access controls that are **stateless** (each direction of traffic needs its own explicit rule). They provide coarser control that complements security groups.

| Feature | Security groups | NACLs |
|---------|----------------|-------|
| Level | Instance/interface | Subnet |
| Stateful? | Yes | No |
| Rule scope | Finer-grained | Coarser |

**VPC** — **Virtual Private Cloud** — a logically isolated network within a public cloud where you configure your own IP ranges, subnets, route tables, and internet gateways, resembling a traditional on-premises network on shared hardware.
- **VPC peering** — a direct connection between two VPCs so traffic flows between them without touching the public internet
- **AWS Transit Gateway** — a central routing hub for connecting many VPCs at scale
- **AWS PrivateLink** — exposes services through private **interface endpoints** inside the VPC, so traffic never hits the public internet

**CASB** — **Cloud Access Security Broker** — a security control that sits between users and cloud services to provide visibility, enforce **DLP** (data loss prevention — policies that stop sensitive data from leaving the organization), apply access controls, and detect **shadow IT** (unsanctioned cloud apps employees use without IT approval). Can be deployed in-line (inspects live traffic) or via API (integrates with SaaS management APIs directly).

**SASE** — **Secure Access Service Edge** — an architectural framework that bundles multiple network security functions — including **CASB**, **secure web gateways** (proxies that filter web traffic for malware and policy violations), **zero trust network access** (access granted per-session based on identity and context, not network location), **firewall-as-a-service**, and **SD-WAN** (software-defined wide area networking — intelligently routing traffic across multiple WAN links) — into a single cloud-delivered platform. Rather than backhauling all traffic to a central data center for inspection, SASE applies security at the cloud edge close to the user.

*Analogy: SASE is like a TSA checkpoint that travels with you — security is applied wherever you are, not only when you return to headquarters.*

---

### Recap

- **IaaS → PaaS → SaaS → FaaS**: each step abstracts more infrastructure away from the customer, but the customer always owns data and identity management
- The **shared responsibility model** divides security *of* the cloud (provider) from security *in* the cloud (customer); the exact boundary shifts by service model
- **Security groups** are stateful and instance-level; **NACLs** are stateless and subnet-level — they work together
- **CASBs** provide visibility and control over SaaS use, including shadow IT detection
- **Hybrid and multi-cloud** add flexibility but require deliberate effort to unify security controls across environments

### Exam flags

- **Shared responsibility boundaries by service model** — which layer the customer is responsible for in IaaS vs. PaaS vs. SaaS is a high-frequency scenario question
- **CASB use cases** — expect a scenario describing shadow IT discovery or SaaS DLP enforcement and needing you to name the control
- **Security groups vs. NACLs** — stateful/instance-level vs. stateless/subnet-level is a classic compare-and-contrast target
