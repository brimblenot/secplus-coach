## Operating System Vulnerabilities

Operating systems sit beneath every application and security control, so a single OS vulnerability can unravel an entire security stack. This lesson covers why OSes are high-value targets, how patching failures enable attacks, and the specific escalation and boot-level techniques attackers exploit.

---

### Why operating systems are prime targets

**Operating systems** are the foundational software layer that controls all hardware, memory, and user data on a device — every application and security control runs on top of them.

- Modern OSes contain tens of millions of lines of code; no codebase that large is vulnerability-free
- A compromised OS undermines *every* security control built above it
- **CVE** — Common Vulnerabilities and Exposures — the standardized ID system for documented vulnerabilities; each flaw gets a unique CVE number and description

Think of the OS as a building's foundation: crack it and every floor above becomes structurally unsafe, no matter how well each floor was built.

---

### Patch Tuesday and the shrinking exploit window

**Patch Tuesday** is Microsoft's practice of releasing accumulated security patches on the second Tuesday of every month; a single release can address dozens to nearly 100 vulnerabilities.

- The **Microsoft Security Response Center (MSRC)** at msrc.microsoft.com publishes all bulletins, CVE details, and patch availability
- Once a patch ships, attackers reverse-engineer it to understand the underlying flaw — the patch *describes* what was broken
- The window between patch release and working exploit code in the wild has shrunk to **hours in some cases**

**EternalBlue (MS17-010)** is the clearest proof: Microsoft patched the **SMBv1** — Server Message Block version 1, a file-sharing protocol — vulnerability in March 2017. Eight weeks later, **WannaCry** ransomware used EternalBlue as a worm to spread globally, hitting every unpatched Windows system.

Think of patch release like publishing the answer key to a test: the moment it's out, everyone — students and cheaters — can see exactly what the questions were.

### End-of-life operating systems

An **end-of-life (EOL)** OS is one the vendor no longer supports — no more security patches, ever. Every newly discovered vulnerability becomes a permanent zero-day.

| OS | EOL Date |
|---|---|
| Windows XP | April 2014 |
| Windows Server 2003 | July 2015 |
| Windows 7 | January 2020 |

EOL systems persist in healthcare (medical devices), manufacturing (industrial control systems), government, and finance — often on hardware that IT doesn't even know exists.

**Compensating controls** for EOL systems:
- **Network isolation** — no direct internet connectivity
- **Application allowlisting** — only pre-approved software can execute
- **Enhanced monitoring** for anomalous behavior
- **Host-based firewalls** — restrict accessible services and ports
- **Complete asset inventory** — you cannot protect systems you don't know exist

An EOL system on your network is like a door with a lock the manufacturer stopped making keys for — once someone finds the bypass, it stays open forever.

### Default configurations as vulnerabilities

Vendor defaults favor ease-of-use over security, leaving services enabled that most environments don't need.

**Risky Windows defaults:**
- **Print Spooler** service — exploited by **PrintNightmare (CVE-2021-1675 / CVE-2021-34527)**, which allowed both local privilege escalation and remote code execution
- **Telnet server** — a remote access protocol that transmits all data, including passwords, in cleartext (unencrypted)
- **SMBv1** — the file-sharing protocol exploited by EternalBlue; should have been globally disabled before WannaCry
- **NetBIOS / LLMNR** — name-resolution protocols abusable for credential capture
- **Default admin shares** (ADMIN$, C$, IPC$) — network-accessible file system and admin functions, sometimes reachable with weak credentials
- **Known default account names** (Administrator / root) — knowing the username cuts the work of brute-force attacks in half

**Hardening benchmarks** provide prescriptive, tested guidance to reach a defensible baseline:
- **CIS Benchmarks** — Center for Internet Security configuration guides
- **DISA STIGs** — Defense Information Systems Agency Security Technical Implementation Guides

Shipping an OS with all features on is like handing someone a Swiss Army knife with every blade already open — most blades are just ways to get cut.

### Kernel vulnerabilities

The **kernel** is the core of the OS, running in **ring 0** — the most privileged processor mode — with unrestricted access to all hardware, memory, and system operations.

- A kernel exploit gives an attacker complete system control, *below* any user-space security controls
- **Dirty COW (CVE-2016-5195)** — a **race condition** (a bug where two processes compete to access a resource in an unsafe order) in Linux's memory handling; any local unprivileged user could write to read-only files including `/etc/passwd`, achieving full root access
- Kernel exploits chained with remote code execution vulnerabilities allow an *external* attacker to reach root/SYSTEM with no user interaction

---

### Device driver vulnerabilities and BYOVD

**Device drivers** run in kernel space and share ring-0 privilege — a bug in a driver is effectively a kernel-level vulnerability.

**BYOVD** — Bring Your Own Vulnerable Driver — attackers install a *legitimately signed* but known-vulnerable driver onto a target, then exploit its known flaw to gain kernel-level code execution.

- Because the driver has a valid signature from a trusted certificate authority, **Secure Boot** and code-signing requirements do not block it
- BYOVD can disable security product drivers that monitor system behavior

Think of BYOVD like a thief who brings a known-faulty master key that is still officially cut by a licensed locksmith — the building's "is this key real?" check passes, but the lock still opens wrong.

### Privilege escalation

**Privilege escalation** is moving from a limited account to a more privileged one.

| Type | Direction | Example |
|---|---|---|
| **Vertical** | User → Administrator/root | Exploiting a kernel bug to get SYSTEM |
| **Horizontal** | User → another user at same level | Reading another user's files without permission |

Attackers commonly **chain** initial access (e.g., phishing → limited shell) with a privilege escalation exploit to reach full control.

---

### Windows privilege escalation vectors

- **Unquoted service paths** — when a service executable path contains spaces and no quotes, Windows may try to run executables at each space-delimited segment; a malicious binary placed at a guessable path gets executed as SYSTEM
- **Weak service permissions** — non-admin users can replace the executable of a SYSTEM-level service with a malicious binary
- **DLL search order hijacking** — **DLL** (Dynamic Link Library) is a shared code file Windows loads at runtime; placing a malicious DLL in a directory Windows searches *before* the legitimate one causes it to load instead
- **Registry key misconfigurations** — standard users can modify keys that control service behavior or startup
- **LSASS memory reading** — **LSASS** (Local Security Authority Subsystem Service) stores credential hashes and sometimes plaintext passwords in memory; tools like **Mimikatz** extract these, enabling lateral movement across the network

---

### Linux privilege escalation vectors

- **SUID/SGID misconfigurations** — **SUID** (Set User ID) is a permission bit that makes an executable run with the *file owner's* privileges (often root) instead of the caller's; **SGID** (Set Group ID) does the same for group permissions; unnecessary SUID binaries that can spawn shells are a classic escalation path
- **World-writable PATH directories** — placing a malicious program earlier in the **PATH** (the OS's ordered list of directories to search for commands) causes it to run instead of a legitimate system binary
- **Sudo misconfigurations** — **sudo** lets users run commands as root; entries in `/etc/sudoers` granting `NOPASSWD` on programs that can spawn shells are frequently exploited
- **Writable cron job scripts** — **cron** is the Linux scheduled-task system; scripts run by cron as root but writable by non-root users can be modified to include attacker commands
- **Symlink attacks on /tmp** — **symlink** (symbolic link) is a file that points to another file; because `/tmp` is world-writable, attackers replace predictably named temp files with symlinks to sensitive targets

### Boot-level threats

**Bootkits** are malware installed in the **Master Boot Record (MBR)** or **EFI System Partition** — the very first code that runs when a machine powers on — so they execute *before* the OS loads and survive OS reinstallation.

**UEFI** — Unified Extensible Firmware Interface — is the modern firmware standard that initializes hardware before the OS; firmware-level vulnerabilities can allow persistent modification that survives even full disk replacement.

**Secure Boot** is a UEFI standard that validates the cryptographic signature of each component in the boot chain (bootloader, kernel, drivers) before allowing it to execute, blocking unauthorized or modified bootloaders.

- Secure Boot depends on the integrity of its signing certificates and the UEFI implementation — BYOVD exploits this trust by using a legitimately signed driver

**TPM** — Trusted Platform Module — is a dedicated security chip on the motherboard that stores cryptographic keys and can attest (cryptographically confirm) that the boot chain has not been tampered with.

Think of Secure Boot + TPM like a notarized chain of custody: each step in the boot process has to show a verified signature before the next step is allowed to proceed.

---

### Recap

- **Patch fast** — once a patch ships, the vulnerability is public and exploit code follows within hours to weeks (EternalBlue/WannaCry is the canonical example)
- **EOL systems** have no vendor remedy for new vulnerabilities; compensating controls (isolation, allowlisting, monitoring) are the only mitigation
- **Default configurations** leave unnecessary services (Print Spooler, SMBv1, Telnet, LLMNR) enabled — hardening to CIS/DISA STIG benchmarks closes these gaps
- **Kernel and driver vulnerabilities** operate at ring 0 and defeat user-space security controls; BYOVD abuses legitimate signing to install exploitable drivers
- **Privilege escalation** (vertical and horizontal) commonly chains with initial access; Windows vectors include unquoted paths and DLL hijacking; Linux vectors include SUID misuse and sudo misconfigurations

---

### Exam flags

- **EternalBlue / WannaCry timeline** — expect scenario questions about the risk of delaying patches after a CVE is published; know that SMBv1 was the vulnerable protocol and the patch preceded the outbreak by ~8 weeks
- **EOL OS compensating controls** — be able to identify the correct mitigations (network isolation, allowlisting, enhanced monitoring) when an organization cannot replace a legacy system
- **SUID bit and unquoted service paths** — these are the go-to Linux and Windows privilege escalation techniques in scenario-based questions; know what each exploits and how
