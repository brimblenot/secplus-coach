## Intrusion Prevention (IDS/IPS)

Firewalls decide *which ports* get through — but a rule that allows port 443 lets in every HTTPS packet, including ones carrying malware. **Intrusion Detection Systems (IDS)** and **Intrusion Prevention Systems (IPS)** fix this by reading the *content* of traffic and either alerting on it or blocking it outright. This lesson covers how each works, how they detect threats, and where they live in the network.

---

### IDS vs. IPS: the core difference

An **IDS** — *Intrusion Detection System* — monitors traffic or host activity and generates alerts when it sees something suspicious. It is **passive**: traffic flows to its destination whether or not the IDS fires an alert. It cannot stop an attack in progress.

- Fails **open**: if the IDS crashes, traffic keeps flowing unimpeded.
- Best when availability is the top priority, or when the team needs visibility before committing to blocking rules.
- Risk: no blocking means a detected attack still hits its target.

An **IPS** — *Intrusion Prevention System* — does the same analysis but sits **inline**: every packet must pass through the IPS before reaching its destination. When it sees malicious traffic, it **drops those packets in real time**.

- Fails **open** *or* **closed** — a deliberate engineering choice (see below).
- Risk: a misconfigured IPS can block legitimate traffic and cause outages.

> 🔑 **Fail-open vs. fail-closed** — when an inline IPS crashes or loses power:

| Fail mode | What happens | Trade-off |
|---|---|---|
| **Fail-open** | Traffic passes through without inspection | Availability preserved; security lost during failure |
| **Fail-closed** | All traffic stops | Security preserved; network goes down until IPS is restored |

*Analogy: An IDS is a security camera — it records everything but doesn't stop the burglar. An IPS is a locked turnstile — nothing gets through without being checked, but if it jams, so does the whole entry.*

---

### False positives and false negatives

Both failure modes hurt — just differently.

- **False positive** — the system flags *legitimate* traffic as malicious.
  - For IDS: wastes analyst time; contributes to **alert fatigue** (analysts become desensitized and miss real threats buried in noise).
  - For IPS: directly *blocks* legitimate business traffic → operational disruption.
- **False negative** — the system *misses* genuinely malicious traffic; the attack reaches its target.

Tuning is the ongoing work of pushing both numbers down. There is always a trade-off: more sensitivity catches more attacks but also more false positives.

---

### Three detection methodologies

**Signature-based detection** compares traffic against a database of known attack patterns (byte sequences, port/flag combos, specific request strings).

- Very accurate and fast for *known* threats; rare false positives when signatures are precise.
- **Cannot detect unknown threats** — novel malware or zero-days have no signature yet.
- Signatures must be continuously updated; there is a window of exposure between a new threat emerging and its signature being deployed.

*Analogy: Like a bouncer with a wanted-poster book — great at spotting known criminals, useless against someone not in the book.*

**Anomaly-based detection** (also called **behavior-based detection**) first builds a **baseline** of normal behavior — typical traffic volumes, connection patterns, user activity — then alerts when deviations exceed defined thresholds.

- **Can detect zero-days and novel attacks** that deviate from normal patterns, even without a signature.
- Generates more **false positives**, especially during the learning phase or when legitimate behavior shifts (mergers, migrations, seasonal cycles).
- Requires careful, ongoing threshold tuning.

*Analogy: Like a bank flagging your card because you bought something in a city you've never visited — it doesn't know the transaction is fraud specifically, just that it's unusual.*

**Rule-based and heuristic detection** sits in between. Predefined rules catch broad suspicious patterns (port scanning, brute-force attempts, protocol misuse) without requiring an exact signature match. **Heuristic analysis** — applying logic to evaluate whether behavior *resembles* malicious activity — and **machine learning** extend this to subtle patterns that neither signatures nor simple rules would catch.

---

### Network-based vs. host-based systems

**NIDS/NIPS** — *Network Intrusion Detection/Prevention System* — monitor traffic across network segments from strategic placement points (perimeter, DMZ boundary, server zone borders).

- **Passive NIDS** uses a **network tap** (a device that physically splits the signal to send a copy to the sensor) or a **SPAN port** — a switch feature that mirrors traffic to a designated monitoring port — so the sensor is never in the live traffic path.
- **NIPS** is inline; all production traffic flows through it.
- **Critical limitation:** neither can read encrypted content without **SSL/TLS inspection** — decrypting traffic for analysis, then re-encrypting before forwarding. The rise of HTTPS has dramatically reduced network-layer visibility.

**HIDS/HIPS** — *Host-based Intrusion Detection/Prevention System* — run as software agents on individual endpoints and servers, watching system calls, file/registry changes, process creation, and privilege escalation.

- Can see threats invisible to network tools: attacks entirely within one host, malware using encrypted channels, insider threats from authenticated users.
- Because the agent runs *inside* the encrypted channel, transport encryption is irrelevant.
- Notable platforms: **OSSEC** and **Wazuh** (open-source HIDS); **EDR** — *Endpoint Detection and Response* — products like Windows Defender for Endpoint (commercial, adds behavioral analysis and memory scanning).
- Requires deploying agents on every monitored host; imposes CPU/memory overhead.

---

### Alert tuning and SIEM integration

**Alert tuning** is the ongoing process of suppressing rules that consistently fire false positives in a specific environment, elevating rules that reliably find real threats, and adjusting anomaly thresholds to match the real baseline.

**SIEM** — *Security Information and Event Manager*, a platform that collects and correlates logs from many sources — amplifies IDS/IPS value by correlating IDS/IPS events with authentication logs, DNS logs, endpoint data, and cloud logs. That enriched context separates false alarms from genuine incidents far faster than IDS/IPS alerts alone.

**UTM** — *Unified Threat Management* — appliances bundle IDS/IPS with firewall, VPN, antivirus, web filtering, and email security in one device. Simpler to manage for smaller organizations, but typically do not match the performance or depth of best-of-breed dedicated tools.

---

### Recap

- **IDS is passive** (alerts only, fails open); **IPS is inline** (blocks in real time, fail behavior is a design choice).
- **False positive** = legitimate traffic flagged (alert fatigue for IDS; outage risk for IPS); **false negative** = real attack missed.
- **Signature-based** = fast and accurate for known threats, blind to zero-days; **anomaly-based** = catches unknowns, more false positives.
- **NIDS/NIPS** see network-wide traffic but are blind to encrypted content without SSL inspection; **HIDS/HIPS** see inside the host regardless of encryption.
- **SIEM integration** correlates IDS/IPS events with other log sources to reduce noise and speed response.

### Exam flags

- **IDS vs. IPS fail behavior** — know that IDS fails open by design; know the availability vs. security trade-off between IPS fail-open and fail-closed.
- **Signature-based vs. anomaly-based** — be ready to identify which methodology detects zero-days (anomaly) and which generates more false positives (anomaly) vs. which requires updated databases (signature).
- **NIDS passive deployment methods** — network tap and SPAN port are the two mechanisms; understand why passive placement means the sensor cannot disrupt traffic.
