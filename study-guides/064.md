## Network Appliances (Domain 3)

Network appliances are purpose-built hardware/software devices that each handle a specific security or traffic-management job. This lesson maps out what each appliance *is*, where it sits in the network, and what problem it solves — all high-frequency exam territory.

---

### Jump servers

A **jump server** (also called a **bastion host** or **jump host**) is a hardened server that acts as the *single authorized gateway* through which administrators reach systems on a protected network segment. Instead of every admin workstation having direct access to every internal server (huge attack surface), all admin traffic funnels through one tightly controlled chokepoint.

- Admins connect via **SSH** (Linux) or **RDP** (Windows) with **MFA** — **multi-factor authentication**, requiring two or more verification factors.
- Target servers accept admin connections *only from the jump server's IP*, not from arbitrary workstations.
- Must be hardened: minimal software, immediate patching, restricted admin list.
- **Session recording** — a full video capture of every command and screen — creates an audit trail for compliance and incident investigation.

**PAM platforms** — **Privileged Access Management** platforms such as CyberArk, BeyondTrust, and Delinea — extend this further: admins authenticate via a web portal, the platform injects credentials automatically so the admin never sees the actual password, and **just-in-time access** grants elevated privileges only for the duration of a specific task, then revokes them automatically.

> Think of a jump server as a security checkpoint at a military base: every visitor must pass through the one gate, show ID, and be escorted — no sneaking in through the back fence.

### Load balancers

A **load balancer** sits in front of a pool of backend servers, distributing incoming client requests so no single server is overwhelmed, and removing failed servers from rotation via **health checks** — periodic test requests that confirm each server is operational.

**Layer 4 vs. Layer 7:**

| Feature | **Layer 4 load balancer** | **Layer 7 load balancer** |
|---|---|---|
| OSI layer | Transport (TCP/UDP) | Application (HTTP/HTTPS) |
| Routing basis | IP address + port only | URL path, hostname, cookies, headers |
| Protocol awareness | Any TCP/UDP service | HTTP/HTTPS only |
| SSL termination | No | Yes |
| Examples | AWS Network LB, HAProxy TCP mode | AWS Application LB, nginx, HAProxy HTTP mode |

**SSL termination** — the load balancer decrypts HTTPS from clients and forwards plain HTTP to backend servers — offloads expensive crypto work, centralizes certificate management, and lets the balancer inspect decrypted content.

**Algorithms** (how the balancer picks which server gets each request):

| Algorithm | How it works | Best when… |
|---|---|---|
| **Round-robin** | Rotates through servers sequentially | Requests and servers are roughly equal |
| **Least-connections** | Sends to the server with fewest active connections | Requests vary in duration/load |
| **IP hash** | Hashes client IP → always same server | App stores session state locally |
| **Weighted** | Proportional share based on server capacity | Servers have different power |

**Session persistence** (a.k.a. **sticky sessions**) — the load balancer sets a cookie on the client encoding which backend server it's assigned to, so all future requests from that client go to the same server.

> A load balancer is like a maître d' at a busy restaurant: they direct each arriving party to an available table so no one waiter is buried while others stand idle.

### Proxy servers

A **proxy server** sits between clients and destination servers, making requests *on behalf of* clients. It provides caching, content inspection, access control, and anonymization.

**Forward proxy** — sits on the *client side*, serving internal users who want internet resources.
- **Explicit proxy**: clients are configured to point at the proxy's address.
- **Transparent proxy** (a.k.a. **intercepting proxy**): intercepts traffic via firewall rules with no client configuration — invisible to users.
- Enforces URL category blocking, logs all web activity, caches responses, and can perform **SSL/TLS inspection** — decrypting HTTPS, inspecting content, re-encrypting before forwarding. Requires the proxy's **CA certificate** — **Certificate Authority certificate**, the credential that lets clients trust the proxy's re-signed connections — to be distributed to all clients (typically via group policy).

**Reverse proxy** — sits on the *server side*, intermediating internet clients connecting to backend servers.
- Hides backend server IPs and internal structure from the internet.
- Provides SSL termination, load distribution, response caching, and can host **WAF** functionality (see below).
- Examples: nginx, Apache HTTPD (on-premises); AWS CloudFront, Cloudflare, Azure Front Door (cloud).

**Open proxy** — a proxy available to *any* internet user without restriction. Security risk: may be operated by malicious parties who can read, modify, or log all passing traffic; also used to bypass organizational web filters.

> A forward proxy is like a personal assistant who makes calls on your behalf — the person you're calling sees the assistant's number, not yours. A reverse proxy is like a corporate receptionist who answers all calls and routes them to the right department — callers never know which internal extension they actually reached.

### Web Application Firewalls

A **WAF** — **Web Application Firewall** — is a specialized reverse proxy that analyzes HTTP/HTTPS request parameters, headers, cookies, and bodies to block application-layer attacks.

Core threats a WAF defends against (drawn from the **OWASP Top 10** — the Open Web Application Security Project's list of the ten most critical web app risks):
- **SQL injection** — attacker inserts malicious SQL into input fields to manipulate database queries.
- **Cross-site scripting (XSS)** — malicious scripts injected into pages viewed by other users.
- **Cross-site request forgery (CSRF)** — tricks an authenticated user into performing unintended actions.

**Two WAF models:**

| Model | How it works | Weakness |
|---|---|---|
| **Positive security model** | Defines what IS valid; blocks everything else | Complex to configure |
| **Negative security model** | Maintains list of known-bad patterns; blocks matches | Needs constant updates; novel attacks can bypass it |

**PCI DSS** — **Payment Card Industry Data Security Standard**, the compliance framework for organizations handling payment card data — mandates WAF deployment.

Examples: AWS WAF, Cloudflare WAF, ModSecurity, Azure Application Gateway with WAF.

> A negative-model WAF is like a bouncer with a photo of every known troublemaker — anyone new who causes trouble gets in anyway. A positive-model WAF is like a VIP-only door — if your name isn't on the approved list, you're not getting in, period.

---

### Recap

- A **jump server** is the single hardened gateway for admin access; PAM platforms add credential injection and just-in-time access.
- **Layer 4** load balancers route by IP/port; **Layer 7** load balancers route by HTTP content and support SSL termination.
- A **forward proxy** serves internal clients going outward; a **reverse proxy** protects backend servers from inbound internet traffic.
- A **WAF** inspects HTTP application content; positive model blocks everything not explicitly allowed; negative model blocks known bad patterns.
- **PCI DSS** requires WAF deployment for payment card environments.

---

### Exam flags

- **Jump server scenario**: given a requirement to securely administer isolated servers, the correct appliance is a jump server/bastion host — not a VPN alone, not direct RDP exposure.
- **L4 vs. L7 load balancer**: know that L7 is required for URL-path-based routing and SSL termination; L4 cannot inspect HTTP content.
- **Positive vs. negative WAF model**: know which blocks novel attacks (positive) and which requires signature updates (negative).
