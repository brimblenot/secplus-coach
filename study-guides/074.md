## Backups (Domain 3)

Backups are the last line of defense against data loss — when ransomware hits, hardware fails, or a disaster wipes a site, recovery depends entirely on whether a clean, verified backup exists. This lesson covers every major decision in a backup strategy: methods, media, architecture rules, encryption, and verification.

---

### Backup methods compared

There are four core backup types. Each makes a different trade-off between creation speed, storage cost, and restore complexity.

**Full backup** — copies every selected byte of data every time it runs, producing one complete, self-contained copy that can be restored in a single operation.
- Simplest to restore: one backup set, no dependencies
- Slowest to create and consumes the most storage
- Typically run weekly; other methods fill the gaps

**Incremental backup** — copies only data changed since the *last backup of any kind* (full or incremental).
- Fast to create, minimal storage per run
- Restore is complex: you must apply the full backup *plus every incremental in order* — one gap in the chain breaks restoration
- *Analogy: like saving only today's edits to a document — fast to save, but to reconstruct Friday's version you need every day's edits back to Sunday.*

**Differential backup** — copies all data changed since the *most recent full backup*, regardless of intermediate differentials.
- Grows larger each day (re-copies previously backed-up changes)
- Restore requires only two steps: the full backup + the latest differential
- Middle ground: more storage than incremental, simpler restore than incremental

| Property | Full | Incremental | Differential |
|---|---|---|---|
| What it copies | Everything | Changes since last backup | Changes since last full |
| Backup speed | Slowest | Fastest | Medium |
| Storage use | Highest | Lowest | Medium |
| Restore steps | 1 | Many (full + all incrementals) | 2 (full + latest diff) |

**Snapshot** — captures the state of a storage volume or VM at a point in time using a **copy-on-write** mechanism (a technique where the system saves the *original* version of a data block before overwriting it, so the snapshot always reflects the moment it was taken).
- Near-instant to create; minimal performance impact on live systems
- Supported by VMware/Hyper-V (VMs), NetApp/Pure Storage (volumes), and Oracle RMAN/SQL Server VSS (databases)
- **Critical limitation:** snapshots on the *same storage array* as production data are destroyed if that array fails or is hit by ransomware — they are *not* independent backups
- *Analogy: like a photograph of your whiteboard — fast to take, but if someone burns the room down, the photo burns with it.*

---

### Replication

**Replication** — continuously mirrors data changes to one or more remote locations, with lag typically measured in seconds to minutes (unlike backups, which capture point-in-time snapshots at intervals).

- **Synchronous replication** — the primary site waits for the remote site to confirm each write before acknowledging it; guarantees zero data loss but adds write latency
- **Asynchronous replication** — the primary site acknowledges writes immediately and propagates them afterward; lower latency but a potential data-loss window equal to the replication lag
- **Key limitation:** replication faithfully copies *everything*, including ransomware encryption and corruption — making it useless as a recovery point for those scenarios

### Backup media and destinations

| Media | Strengths | Weaknesses |
|---|---|---|
| Local disk / NAS | Fastest backup and restore | Co-located — same disaster hits backups and production |
| **LTO Ultrium** tape | Offline (immune to ransomware), low cost/GB, 12 TB+ per cartridge | Slower restore; physical media management overhead |
| Cloud (S3 Glacier, Azure Blob, Veeam, Acronis, Cohesity) | Off-site by nature; scales without limits; supports immutability | Restore speed limited by network bandwidth |

**Object lock / immutability** — a cloud feature (e.g., **AWS S3 compliance mode**) that prevents any account, including admins, from deleting or modifying backup objects during a set retention period, making them ransomware-resistant.

### The 3-2-1 and 3-2-1-1-0 rules

**3-2-1 rule** — the foundational backup architecture standard:
- **3** copies of data (production + 2 backups)
- **2** different media types (so one failure mode can't hit all copies)
- **1** copy off-site (geographic separation from site-level disasters)

**3-2-1-1-0 rule** — extends the above with two additions:
- **1** copy offline (physically disconnected from any network — ransomware can only encrypt storage it can reach)
- **0** errors — all backups must be verified as restorable

*Analogy: 3-2-1-1-0 is like keeping your only copy of a will in a fireproof safe, a bank vault, and a lawyer's office — and actually confirming you can open each one.*

---

### Backup encryption

Backup data contains the same sensitive information as production data — an unencrypted backup on lost media is a reportable breach.

- **In transit:** protect with **TLS** (Transport Layer Security — encrypts data moving over a network)
- **At rest:** protect with **AES-256** (the current standard symmetric encryption algorithm)
- **Key storage:** encryption keys must be stored *separately* from the encrypted backups — in a **key management system** or **HSM** (Hardware Security Module — a dedicated device for storing and managing cryptographic keys)
- Storing the decryption key inside the backup is like locking a house and leaving the key under the mat

---

### Backup verification

An untested backup is no more reliable than no backup at all. Several failure modes can produce backups that *look* successful but are unrestorable:

- **Bit rot** — gradual, spontaneous corruption of data on storage media over time, with no external trigger
- Backup software bugs that silently produce incomplete copies
- Open file locks, permission issues, or misconfigured scope that exclude critical data

Verification requires actually restoring data — not just checking that the backup job reported success.

---

### Recap
- Full = complete/simple restore; incremental = fast creation but complex multi-step restore; differential = two-step restore but growing storage cost
- Snapshots are fast recovery tools, not independent backups if stored on the same array
- Replication propagates ransomware/corruption — it does not substitute for backups
- 3-2-1-1-0: three copies, two media types, one off-site, one offline, zero unverified backups
- Backup encryption keys must be stored separately from the backups they protect

### Exam flags
- **3-2-1 vs. 3-2-1-1-0 rule** — know what each number means and why the offline copy specifically defeats ransomware
- **Incremental vs. differential restore complexity** — incremental requires full + every incremental in order; differential requires only full + latest differential
- **Snapshot limitation** — snapshots on the same array as production data are not independent backups and are lost in the same disaster
