## Protecting Data (Domain 3)

Data protection isn't one control — it's a layered stack. This lesson covers the tools, from DLP and encryption to privacy-enhancing techniques, that together prevent sensitive data from being exposed, stolen, or misused.

---

### Data Loss Prevention (DLP)

**DLP** — technology that identifies, monitors, and controls the movement of sensitive data to stop unauthorized disclosure.

- Detects sensitive data using **regex patterns** (e.g., 16-digit credit card numbers), keyword lists, document fingerprinting, and ML classifiers
- Response options: log, alert, quarantine, or block

Three deployment modes:

| Mode | Where it runs | What it monitors |
|---|---|---|
| **Network DLP** | Inline at network chokepoint | Email, web uploads, FTP, cloud sync — may miss encrypted traffic without TLS inspection |
| **Endpoint DLP** | Agent on each device | USB copies, email attachments, browser uploads, print jobs, screenshots |
| **Cloud DLP** | Integrated with cloud provider | Cloud storage buckets, SaaS file sharing (e.g., Microsoft Purview, Google Cloud DLP) |

> Think of network DLP as a customs checkpoint at the border — everything leaving gets scanned. Endpoint DLP is a guard standing *next to your desk*, watching what you plug in.

### Information Rights Management (IRM)

**IRM** (also called **DRM** — Digital Rights Management — in consumer contexts) embeds persistent access controls *inside* the file itself, encrypting it and attaching usage rules that travel with it wherever it goes.

- Traditional access controls protect the *container* (folder, server) — once a file is copied out, those controls are gone
- IRM protects the *file itself* regardless of location
- Can restrict: printing, copy-paste, forwarding, opening after an expiration date, or opening outside approved countries
- Examples: **Microsoft Purview Information Protection**, **Adobe PDF DRM**

> **Key exam distinction:** Access controls = protect *where* data is stored. IRM = protects the *data itself*, even after it leaves.

> Analogy: IRM is like a self-destructing envelope — even if the recipient forwards it, the letter inside won't let itself be read by the wrong person.

### Access controls for data

| Model | How it works |
|---|---|
| **RBAC** — Role-Based Access Control | Permissions tied to job role; changing a user's role automatically adjusts access |
| **ABAC** — Attribute-Based Access Control | Adds context: department, clearance, time of day, location |
| **DAC** — Discretionary Access Control | Data *owner* sets permissions (NTFS on Windows, POSIX on Linux) |
| **MAC** — Mandatory Access Control | Classification labels control access; users need matching clearance *and* need-to-know |

Two additional principles:
- **Least privilege** — users get only the minimum access their job requires
- **Separation of duties** — sensitive tasks (e.g., initiating *and* approving a payment) split between different people so no one can abuse access undetected

### Encryption and key management

**AES-256** — the standard symmetric encryption algorithm for **data at rest**; computationally infeasible to break with current technology.  
**TLS 1.3** — the standard protocol protecting **data in transit**.

Key management matters as much as the algorithm:

- **HSM** (Hardware Security Module) — a tamper-resistant hardware device that stores cryptographic keys so they can't be extracted even by admins
- **Key rotation** — regularly replacing encryption keys to limit damage if one is compromised
- **Key escrow** — storing a copy of the key with a trusted third party so data can be recovered if the primary key is lost

> An HSM is like a bank vault for keys: the vault staff can use what's inside, but they can't take it home.

### Database security

Databases are the highest-value targets — they concentrate the most sensitive data in one place.

- **TDE** (Transparent Data Encryption) — encrypts the entire database *file on disk* at the storage layer; someone who steals the raw files can't read them without going through the database engine. Used in SQL Server, Oracle, MySQL.
- **Column-level encryption** — encrypts only specific sensitive fields (e.g., SSN, credit card columns) for finer granularity when only some fields are sensitive
- **DAM** (Database Activity Monitoring) — real-time surveillance of all database queries; alerts on anomalies like an account suddenly pulling thousands of rows when it normally retrieves one
- Application database accounts should have **least-privilege** permissions (e.g., access to specific stored procedures, not whole tables); DBA accounts should require **MFA**

### Data masking and tokenization

**Data masking** replaces real sensitive data with realistic but fake substitute data, preserving format and referential integrity so apps behave correctly.

- **Static masking** — creates a masked copy of the database for dev/test environments
- **Dynamic masking** — applies substitution at *query time*; authorized users see real values, others see masked values

**Tokenization** replaces a sensitive value (e.g., a credit card number) with a randomly generated **token**, with the real value stored only in a secure **token vault**.

- The token has *no mathematical relationship* to the original — useless if stolen
- Extensively used in **PCI DSS** — payment card compliance — because merchants store tokens, not real card numbers (**PAN** — Primary Account Number), removing large portions of their infrastructure from compliance scope

> Masking is like using a prop dollar bill in a movie — looks real, works for the scene, but can't be spent. Tokenization is like a coat-check ticket — the ticket means nothing without the vault that holds the real coat.

---

### Privacy-enhancing technologies

- **Differential privacy** — adds calibrated mathematical noise to aggregate query results so analysts get accurate statistics but cannot reconstruct any individual's data (used by Apple and Google for usage telemetry)
- **K-anonymity** — ensures any record in a dataset is indistinguishable from at least *k−1* other records on quasi-identifier fields, preventing re-identification
- **Federated learning** — trains ML models on data that *never leaves* its original location; only model parameter updates are shared, not raw data

---

### Data minimization

**Data minimization** — the principle that organizations should collect *only* the personal data strictly necessary for a specific purpose, retain it only as long as needed, then delete it.

- Enshrined in **GDPR** (General Data Protection Regulation — the EU's comprehensive data privacy law) as a core requirement
- Security benefit: data you don't hold can't be breached

---

### Recap

- **DLP** has three deployment modes — network (chokepoint), endpoint (agent), and cloud — each covering different exfiltration vectors
- **IRM** embeds controls in the file itself and travels with it; traditional access controls only protect the storage container
- **TDE** encrypts database files on disk; **column-level encryption** targets only sensitive fields; **DAM** monitors query behavior in real time
- **Tokenization** stores real values in a vault and is the primary tool for reducing **PCI DSS** scope in payment processing
- **Data minimization** limits breach impact by ensuring unneeded data is not retained

### Exam flags

- Distinguishing **IRM vs. access controls** — exam loves scenarios asking which protects data *after* it leaves the organization
- **Tokenization vs. masking** — know that tokenization uses a vault and is PCI-focused; masking produces fake-but-realistic data for dev/test
- **DAM** — expect a scenario describing unusual bulk query behavior and asking what detects it
