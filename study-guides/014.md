## Key Exchange

This lesson covers how two parties securely establish a shared encryption key over an untrusted network — the foundational challenge behind every HTTPS connection you've ever made. Get this right and you'll understand why TLS 1.3 looks the way it does.

---

### The key distribution problem

The **key distribution problem** is the challenge of securely establishing a shared secret between two parties who have never met, over a network an attacker may be watching.

- Two parties can't encrypt a key exchange with a key they don't yet share — classic chicken-and-egg
- Billions of devices must solve this in real time with servers they've never contacted before

**Out-of-band key exchange** delivers the key through a completely separate channel (courier, phone call, in-person meeting) — not the insecure network.

- Perfectly secure in principle; completely unscalable for the internet
- *Analogy:* A diplomat hand-carrying a locked briefcase — secure, but you can't do that for every web page you visit.

**In-band key exchange** negotiates key material over the same untrusted channel that will carry the encrypted traffic.

- The challenge: make it useless to an eavesdropper watching every packet

---

### Key transport vs. key agreement

**Key transport** (e.g., RSA key exchange) is a method where one party generates the session key and *sends* it to the other, encrypted under the recipient's public key.

- **RSA** — **R**ivest–**S**hamir–**A**dleman, an asymmetric algorithm used here to encrypt the session key
- Used in older TLS versions; **removed in TLS 1.3** because it lacks Perfect Forward Secrecy (explained below)
- Fatal flaw: if the server's long-term RSA private key is ever stolen, every previously recorded session can be decrypted retroactively

**Key agreement** is a method where *both* parties contribute to the shared secret and neither party ever transmits it — the secret is independently computed by each side.

| Property | Key Transport (RSA) | Key Agreement (DH) |
|---|---|---|
| Who picks the session key? | Client alone | Both parties jointly |
| Session key sent over network? | Yes (encrypted) | Never |
| Retroactive decryption risk? | Yes, if private key leaks | No (with ephemeral keys) |
| In TLS 1.3? | Removed | Required |

---

### Diffie-Hellman key agreement

**Diffie-Hellman (DH)** is a key agreement protocol (1976) that lets two parties independently derive the same shared secret without ever transmitting it.

- Both agree on public parameters: a large prime and a **generator** (a base value used in the math)
- Each generates a private value → computes a public value → exchanges public values
- Each then combines their own private value with the other's public value → both arrive at the same shared secret
- Security rests on the **discrete logarithm problem** — knowing the public values, an attacker cannot efficiently reverse-engineer the private values
- *Analogy:* Two people mix their secret paint colors into a shared base color. They swap the mixtures publicly, then each adds their private color again — both end up with the identical final color, and a spy watching the swap can't reconstruct it.

---

### Static DH vs. ephemeral DH (DHE) and Perfect Forward Secrecy

**Static DH** uses the same long-term private key for every session.

- If an attacker records traffic now and steals the private key later, they can decrypt *all past sessions*

**DHE** — **D**iffie-**H**ellman **E**phemeral — generates a brand-new temporary DH key pair for every session, then immediately discards the private key after the shared secret is derived.

- **Perfect Forward Secrecy (PFS)** — the property that compromise of long-term keys cannot decrypt past sessions, because the ephemeral keys that produced them no longer exist
- DHE enables PFS; static DH does not

---

### Elliptic curve variants: ECDH and ECDHE

**ECDH** — **E**lliptic **C**urve **D**iffie-**H**ellman — applies the same key agreement concept using elliptic curve math instead of modular integer arithmetic.

- The **elliptic curve discrete logarithm problem** is harder to solve than the integer version for a given key size
- A 256-bit ECDH key ≈ security of a 3072-bit traditional DH key
- Smaller keys → less handshake data, faster computation, less memory — critical on constrained devices

**ECDHE** — **E**lliptic **C**urve **D**iffie-**H**ellman **E**phemeral — combines elliptic curve efficiency with ephemeral key pairs for PFS.

- The dominant key exchange in **TLS 1.3** and essentially all modern HTTPS
- *Analogy:* ECDHE is DHE that went to the gym — same forward-secrecy guarantee, much lighter to carry.

| Method | Elliptic Curve? | Ephemeral? | PFS? | TLS 1.3? |
|---|---|---|---|---|
| Static DH | No | No | No | No |
| DHE | No | Yes | Yes | Allowed |
| ECDH | Yes | No | No | No |
| ECDHE | Yes | Yes | Yes | Default |

---

### TLS 1.3 handshake flow

The **TLS 1.3 handshake** is the negotiation sequence that establishes a secure session.

1. **ClientHello** — client sends supported cipher suites and ECDHE public key shares
2. **ServerHello** — server picks cipher suite, sends its own ECDHE key share
3. Both sides compute the shared secret independently
4. **HKDF** — **H**MAC-based **K**ey **D**erivation **F**unction — stretches the raw shared secret into symmetric session keys; **HMAC** is a keyed hash used here to extract and expand key material
5. Session data is encrypted with **AES-GCM** — **A**dvanced **E**ncryption **S**tandard in **G**alois/**C**ounter **M**ode, a fast authenticated symmetric cipher
6. The server's long-term certificate and private key authenticate identity only — they play no role in deriving session keys, which is why PFS holds even if that key is later stolen

---

### Session keys and hybrid cryptography

**Session keys** are temporary symmetric keys produced by the key exchange, used to encrypt the actual data of a session.

- Generated fresh per session, discarded at session end — ephemeral by nature
- Asymmetric key exchange sets them up; symmetric encryption (AES) does the bulk work
- This combination is the **hybrid cryptography** model: asymmetric for key establishment, symmetric for data

---

### Key wrapping

**Key wrapping** is the process of encrypting one symmetric key with another key for secure storage or transmission.

- Example: a backup of an AES session key encrypted under an RSA public key and stored in a **key management system**
- The **wrapping key** protects the **wrapped key** at rest; the wrapped key does the actual data encryption
- Common in **HSMs** — **H**ardware **S**ecurity **M**odules, tamper-resistant devices that store and manage cryptographic keys

---

### Key Derivation Functions (KDFs)

A **KDF** — **K**ey **D**erivation **F**unction — takes raw key material (like a DH shared secret) and produces cryptographic keys ready for use in ciphers and MACs.

- **HKDF** (defined in RFC 5869) is the KDF used in TLS 1.3
- Two steps: **extract** (concentrates entropy into a pseudorandom key) → **expand** (stretches it into as many key bytes as needed)
- Needed because a raw DH output isn't directly usable as an AES key

---

### Key management lifecycle

The **key management lifecycle** is the full sequence of operations that must be performed on a cryptographic key from creation to destruction. Failure at any step breaks security regardless of algorithm strength.

| Phase | What happens |
|---|---|
| **Generation** | Created with a cryptographically secure random number generator |
| **Distribution** | Delivered to authorized parties via secure channels |
| **Storage** | Kept in protected locations (HSM, encrypted key store) |
| **Rotation** | Replaced on schedule or after potential compromise |
| **Revocation** | Marked invalid when no longer trustworthy |
| **Destruction** | Key material is unrecoverably wiped |

*Analogy:* Think of key lifecycle like a classified badge — issued securely, stored in a safe, renewed annually, revoked the day someone quits, and shredded on exit, not tossed in a trash can.

---

### Recap

- **Key agreement (DH/ECDHE) > key transport (RSA)** because the session key is never transmitted, eliminating retroactive decryption risk
- **Ephemeral keys enable PFS** — the private key is discarded after each session so there's nothing for an attacker to steal later
- **ECDHE = DHE + elliptic curve math** — same PFS guarantee, far smaller keys; it's the default in TLS 1.3
- **RSA key exchange was removed from TLS 1.3** specifically because it lacks PFS
- **HKDF** transforms raw DH output into usable symmetric keys; the server's certificate authenticates but does not establish keys

### Exam flags

- **PFS and why RSA key exchange lacks it** — expect a scenario where an attacker records traffic and later steals a private key; you must identify that DHE/ECDHE protects past sessions but RSA key exchange does not
- **ECDHE as the TLS 1.3 standard** — know why it replaced DHE (smaller keys, faster, equivalent security) and what "ephemeral" means for forward secrecy
- **Key management lifecycle phases** — know all six phases (generation → distribution → storage → rotation → revocation → destruction) and what a failure at each step could cause
