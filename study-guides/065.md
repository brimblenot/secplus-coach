## Port Security (Domain 3)

Physical access to a network jack has historically been treated as equivalent to network access — plug in and you're in. This lesson covers the layered controls that break that assumption, from 802.1X authentication through switch-level defenses against spoofing and flooding attacks.

---

### 802.1X: port-based network access control

**IEEE 802.1X** is a standard that enforces authentication at Layer 2 — the data-link layer, where Ethernet frames live — before a connected device can pass any traffic. Until authentication succeeds, the port stays **unauthorized**: it carries only authentication messages, nothing else.

Three roles make this work:

- **Supplicant** — the device trying to connect (laptop, phone, etc.)
- **Authenticator** — the switch port or wireless AP that enforces the outcome but doesn't decide it
- **Authentication server** — the backend that actually validates credentials; almost always a **RADIUS** (**Remote Authentication Dial-In User Service**) server, which may query Active Directory or an **LDAP** (Lightweight Directory Access Protocol) directory behind the scenes

The handshake uses **EAP** (**Extensible Authentication Protocol**) — a flexible framework that carries credential information between the supplicant and the RADIUS server, with the authenticator acting as a relay. On success → **Access-Accept** → port goes authorized. On failure → **Access-Reject** → port stays blocked.

> *Think of 802.1X like a hotel key-card door: plugging in a cable is just touching the door handle — you still can't enter until the lock (RADIUS) verifies your card.*

---

### EAP methods compared

Four EAP methods appear in the transcript. Each differs in what credentials are used and whether certificates are required.

- **EAP-TLS** (**Transport Layer Security**-based EAP) — strongest method; both the client and server prove identity with **digital certificates** (mutual authentication). Requires a full **PKI** (**Public Key Infrastructure** — the system of certificate authorities that issues and manages certificates) for every device.
- **PEAP** (**Protected EAP**) — builds a TLS tunnel using only a **server certificate**, then passes a username/password (typically **MSCHAPv2** — Microsoft's challenge-response password protocol) inside that tunnel. No client certificate needed; works with existing Active Directory passwords.
- **EAP-TTLS** (**Tunneled TLS**) — similar to PEAP but more flexible in which inner authentication method it accepts.
- **EAP-FAST** (**Flexible Authentication via Secure Tunneling**) — Cisco-developed; avoids certificates entirely by using **PACs** (**Protected Access Credentials** — pre-shared keys provisioned to devices in advance). Less common in modern deployments.

| Method | Client cert required? | Server cert required? | Notes |
|---|---|---|---|
| EAP-TLS | ✅ Yes | ✅ Yes | Strongest; needs full PKI |
| PEAP | ❌ No | ✅ Yes | Common in Windows/AD environments |
| EAP-TTLS | ❌ No | ✅ Yes | More flexible inner auth |
| EAP-FAST | ❌ No | ❌ No | Uses PACs; Cisco-specific |

> *EAP-TLS is like both parties showing government-issued photo ID — maximum trust, maximum paperwork. PEAP is like the bouncer showing their badge but accepting your verbal name — the channel is secure, but only one side is cryptographically proven.*

### Fallback and assignment: MAB, Guest VLAN, dynamic VLAN

**MAC Authentication Bypass (MAB)** is a fallback for devices that can't run 802.1X (legacy printers, IoT). The switch sends the device's **MAC address** — a hardware identifier burned into every network interface — as both the username and password to RADIUS. The weakness: MAC addresses travel unencrypted in every Ethernet frame and can be **spoofed** (copied) trivially on any OS with a single command. MAB devices should be confined to restricted VLANs.

**Dynamic VLAN assignment** lets RADIUS return a VLAN attribute after successful authentication, placing different users on different network segments automatically — employees on the corporate VLAN, contractors on a restricted VLAN, IoT devices on an isolated VLAN — all from the same physical port.

A **Guest VLAN** catches devices that fail 802.1X entirely, giving them internet-only access while blocking all internal resources. It must be firewalled so guests truly can't reach internal systems.

---

### Switch-level attack defenses

**MAC address filtering** allows traffic only from pre-approved MAC addresses. Provides weak security because MAC addresses are observable and trivially spoofed — not a standalone security control.

**CAM table overflow** exploits the fact that a switch's **CAM table** (**Content Addressable Memory** table — the switch's mapping of MAC addresses to ports) is finite. Tools like **macof** flood a switch with thousands of random source MACs, filling the table. The switch then falls back to **flooding** — broadcasting every frame out every port like a hub — letting an attacker capture all traffic. **Port security** with a maximum MAC limit stops this by shutting down the port when the limit is exceeded. **Sticky MAC learning** automatically locks a port to the first MAC address it sees, requiring no manual configuration.

**DHCP snooping** blocks **rogue DHCP servers** — attacker-controlled servers that hand out IP addresses pointing to the attacker as the default gateway, intercepting all client traffic. The switch marks ports as **trusted** (legitimate servers/uplinks) or **untrusted** (end devices). Only trusted ports can send DHCP offers. The switch builds a **DHCP snooping binding table** — a record of which IP, MAC, VLAN, and port belong together — used by the next two features.

**Dynamic ARP Inspection (DAI)** prevents **ARP spoofing** — **ARP** (**Address Resolution Protocol**) has no authentication, so an attacker can broadcast fake ARP replies claiming the gateway's IP maps to the attacker's MAC, intercepting all traffic. DAI validates every ARP reply against the DHCP snooping binding table and drops any that contradict it.

**IP Source Guard** validates the source IP on every packet from untrusted ports against the binding table. A device using an IP address other than the one DHCP assigned it gets its traffic dropped — stopping host impersonation and IP spoofing.

> *DHCP snooping, DAI, and IP Source Guard are a three-layer stack: snooping builds the ground-truth table, DAI uses it to police MAC-to-IP claims, and IP Source Guard uses it to police IP-to-port claims. Together they make forging identity at Layer 2 extremely difficult.*

---

### Recap

- **802.1X** keeps a port unauthorized until RADIUS authenticates the supplicant via EAP; the authenticator enforces but doesn't decide
- **EAP-TLS** = mutual certificates (strongest); **PEAP** = server cert + password in tunnel (most common in Windows); **EAP-FAST** = PACs, no certs
- **MAB** is a weak fallback using MAC address as credentials — easily spoofed; restrict MAB devices to isolated VLANs
- **CAM table overflow** forces hub-mode flooding; port security with MAC limits (and sticky MAC) prevents it
- **DHCP snooping** blocks rogue DHCP servers and builds the binding table that **DAI** and **IP Source Guard** rely on to stop ARP spoofing and IP spoofing

---

### Exam flags

- **802.1X roles** (supplicant / authenticator / authentication server) and which EAP method requires client certificates (EAP-TLS only)
- **MAB weakness**: MAC addresses are unencrypted and trivially spoofed — MAB devices must be isolated to restricted VLANs
- **DHCP snooping → DAI → IP Source Guard** as a dependent chain: each later feature relies on the binding table the previous one builds
