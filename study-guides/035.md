## Cloud-Specific Vulnerabilities

Cloud environments introduce a unique set of security risks that don't map neatly onto on-premises thinking. This lesson covers the major vulnerability classes — misconfigured storage, insecure APIs, IAM excess, serverless risks, and SSRF — plus the tools defenders use to catch them.

---

### The shared responsibility model

The **shared responsibility model** defines exactly who secures what in a cloud environment — the provider handles infrastructure; the customer handles everything they configure on top of it.

- **Provider's job ("security *of* the cloud"):** physical data centers, hardware, global network, hypervisors, foundational services
- **Customer's job ("security *in* the cloud"):** OS patching, app security, IAM config, network rules, encryption choices
- In **IaaS** — where customers rent raw compute/storage and manage their own OS — the customer controls the most; in **PaaS** — where the provider also runs the runtime and middleware — the customer still owns app code, data, and access controls
- Most breaches happen in the **customer-controlled layer** because organizations assume the provider secured more than the contract says

> Think of it like a rented apartment: the landlord maintains the building's structure and plumbing, but if you leave your front door unlocked, that's on you.

---

### Misconfigured cloud storage

**Misconfigured cloud storage** means a storage bucket or container (e.g., Amazon S3, Azure Blob Storage, Google Cloud Storage) has been set to allow public internet access, exposing all data inside it.

- A single permission change can open a bucket to the entire internet
- The **2019 Capital One breach** chained three flaws: a misconfigured web application firewall, a **server-side request forgery (SSRF)** vulnerability (explained below), and an overly permissive **IAM** — *Identity and Access Management* — role; result: 100M+ customer records exposed
- **S3 Block Public Access** — an AWS account-level setting that enforces private-by-default on all buckets — was introduced as a direct response
- Full defense: Block Public Access + explicit bucket policies + access logging + automated permission audits

> Leaving a bucket public is like putting your filing cabinet on the sidewalk and assuming nobody walks by.

---

### Insecure cloud APIs

**Cloud APIs** — *Application Programming Interfaces*, the management interfaces cloud providers expose so customers can create VMs, modify storage, and adjust network rules — are internet-accessible by design, making them a primary attack surface.

- **API keys hardcoded** in source code and pushed to public GitHub repos are leaked at thousands per day
- Keys with **excessive permissions** give an attacker full account control if leaked
- APIs without **rate limiting** — controls that cap how many requests a client can make per unit time — let attackers enumerate resources and test credentials at machine speed

> Hardcoding an API key into public source code is like taping your house key to the front door with your address written on it.

---

### Insufficient IAM access controls

**Excessive IAM permissions** — granting identities more access than their job requires — is the most systemic cloud vulnerability class.

- The **principle of least privilege** (give only the minimum access needed) is routinely violated, especially in early projects where broad permissions are set for convenience and never revisited
- Common findings: policies that allow all actions on all resources; service accounts with admin rights they never use; cross-account trust relationships that are too permissive
- **Permission chaining / privilege escalation:** an attacker who compromises a low-privilege identity can assume a more privileged role that the first identity is authorized to use, escalating to admin access

> Giving every employee the master key to every room "just in case" means one stolen badge compromises the whole building.

---

### Serverless and event injection

**Serverless computing** — running code in short-lived, event-triggered functions (e.g., **AWS Lambda**, Azure Functions, Google Cloud Functions) rather than persistent servers — introduces its own vulnerability patterns.

- **Function/event injection:** malicious data submitted through function parameters or event sources (S3 uploads, SQS messages, API Gateway requests) that the function processes without validation
- **Insecure dependencies:** quickly assembled function packages often include outdated third-party libraries
- Lambda functions frequently receive IAM roles far broader than the single S3 bucket or database table they actually need

> A serverless function with admin IAM is like hiring a temp to file one folder — and handing them the master key to the whole building.

---

### Cloud metadata API abuse via SSRF

**SSRF** — *Server-Side Request Forgery* — is a vulnerability where an attacker tricks a web application into making HTTP requests to arbitrary URLs on the attacker's behalf.

- All major cloud providers expose an **instance metadata service** at the internal IP address **169.254.169.254**, which returns IAM role credentials, instance identity, and bootstrap scripts that may contain secrets
- If the app is SSRF-vulnerable, an attacker can direct it to fetch `http://169.254.169.254/...` and retrieve live IAM credentials
- **IMDSv2** — *Instance Metadata Service version 2*, an AWS countermeasure — requires apps to first make a PUT request to get a session token before metadata can be retrieved, breaking simple one-step SSRF exploitation
- Defense: enforce IMDSv2 + grant instance roles only minimum required permissions

> SSRF against the metadata endpoint is like calling the front desk and convincing them to read you the manager's private notes over the phone.

---

### Shadow IT and Infrastructure as Code risks

**Shadow IT** occurs when employees provision unauthorized cloud resources — personal buckets, unapproved SaaS apps, experimental infrastructure — outside IT governance.

- These resources may hold corporate data with no security controls and create compliance exposure
- **Infrastructure as Code (IaC)** — tools like **Terraform**, **CloudFormation**, and **Pulumi** that define cloud infrastructure in configuration templates — can deploy insecure configurations at scale if templates contain hardcoded credentials, overly open security groups, or unencrypted storage

> Shadow IT is like a developer setting up a second office in a closet — IT doesn't know it exists, so nobody locks the door.

### Cloud security tooling

| Tool Category | Full Name | What It Does |
|---|---|---|
| **CSPM** | Cloud Security Posture Management | Continuously scans cloud resource configs against security benchmarks; flags misconfigs in real time (e.g., Prisma Cloud, AWS Security Hub, Azure Security Center) |
| **CWPP** | Cloud Workload Protection Platform | Protects running workloads — VMs, containers, serverless functions — against active threats |
| **CIEM** | Cloud Infrastructure Entitlement Management | Identifies excessive permissions, detects unused access, recommends least-privilege IAM right-sizing |
| **CASB** | Cloud Access Security Broker | Provides visibility and control over cloud service use, including unauthorized SaaS and data movement |
| **SASE** | Secure Access Service Edge | Converges multiple network security functions (secure web gateways, zero-trust network access, cloud access security brokering) into a single cloud-delivered service |

---

### Recap

- The shared responsibility model puts OS, IAM, and app security squarely on the **customer** — provider failures are rare; customer misconfigs cause most breaches
- **Misconfigured storage** (public buckets), **leaked API keys**, and **excessive IAM permissions** are the top three cloud vulnerability classes
- **SSRF + metadata API** is one of the highest-impact cloud attack chains; **IMDSv2** is the primary countermeasure
- **IaC templates** can bake insecure configurations into infrastructure at scale if not audited
- **CSPM**, **CIEM**, and **CASB** are the three defensive tool categories most likely to appear on the exam

---

### Exam flags

- **Shared responsibility model** — expect a scenario asking which controls belong to the provider vs. the customer in IaaS vs. PaaS
- **SSRF → metadata service (169.254.169.254) → IAM credential theft** — know this attack chain and IMDSv2 as the defense
- **CSPM vs. CASB vs. CIEM** — expect a scenario matching a defensive need (misconfiguration scanning, unauthorized SaaS visibility, or IAM right-sizing) to the correct tool category
