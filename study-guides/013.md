## Encrypting Data

Encryption is the backbone of nearly every security control you've encountered — from HTTPS to BitLocker to PGP. This lesson maps every major algorithm, mode, and hardware mechanism the exam tests, so you know not just *what* each one is but *when and why* to choose it.

---

### Symmetric encryption: one key does both jobs

**Symmetric encryption** is a method where the *same key* is used to both encrypt and decrypt data. It's fast and efficient, making it the right choice for bulk data.

**DES** — the **Data Encryption Standard** — was the original federal symmetric standard, using a **56-bit key**. A 56-bit key allows ~72 quadrillion combinations, but modern hardware brute-forces that in hours. DES is **cryptographically broken** — never use it.

**3DES** (Triple DES) patched DES by running the DES algorithm three times per block (encrypt → decrypt → encrypt). Two-key 3DES reaches ~112-bit effective security; three-key reaches ~168 bits. But it's **3× slower** than single DES, and NIST has **deprecated** it — don't use it in new systems.

**AES** — the **Advanced Encryption Standard** — replaced DES in 2001 and is today's gold standard.

| Key Length | Use Case |
|---|---|
| AES-128 | Secure for general use; very fast |
| AES-192 | Intermediate; rarely chosen |
| AES-256 | High-security/government applications |

AES powers TLS session encryption, **BitLocker** (Windows full-disk encryption), **FileVault** (macOS full-disk encryption), and WPA3 wireless security.

> Think of DES as a padlock from 1975 — it looked strong then, but any locksmith today can crack it in an afternoon. AES-256 is a modern vault door.

### Modes of operation: how AES handles long messages

AES encrypts exactly 128 bits at a time. A **mode of operation** — a rule for how to handle data longer than one block — must be chosen for any real message.

**ECB** (**Electronic Code Book** mode): each 128-bit block is encrypted *independently* with the same key. Identical plaintext blocks → identical ciphertext blocks → patterns leak through. The "ECB penguin" demo shows an image of a penguin that, after AES-ECB encryption, still visibly looks like a penguin. **Never use ECB.**

**CBC** (**Cipher Block Chaining** mode): before encryption, each plaintext block is **XOR'd** — combined bit-by-bit — with the *previous ciphertext block*, so identical plaintext produces different ciphertext. Requires an **IV** (**initialization vector** — a random starting value for the first block). Encryption is sequential (each block depends on the last), but decryption can be partially parallelized.

**CTR** (**Counter mode**): encrypts a counter value (1, 2, 3…) and XORs the result with plaintext, turning AES into a **stream cipher** (one that produces a continuous keystream rather than fixed blocks). Fully parallelizable, no padding needed.

**GCM** (**Galois Counter Mode**): extends CTR by adding an **authentication tag** — a cryptographic checksum — over the ciphertext. This makes it an **AEAD** (**Authenticated Encryption with Associated Data**) scheme, providing *both* confidentiality and integrity in one pass. If even one bit is altered, the tag check fails and the data is rejected. GCM is used in **TLS 1.3**, SSH, and IPsec — the preferred mode for new applications.

| Mode | Parallelizable? | Integrity Check? | Use? |
|---|---|---|---|
| ECB | Yes | No | Never |
| CBC | Encrypt: No / Decrypt: Partial | No | Legacy only |
| CTR | Yes | No | OK |
| GCM | Yes | Yes (**AEAD**) | Preferred |

> GCM is like a sealed evidence bag: it encrypts the contents *and* adds a tamper-evident seal. If anyone opens it, the seal breaks and you know immediately.

### Stream ciphers

A **stream cipher** encrypts data one bit or byte at a time, rather than in fixed blocks. **RC4** was once used in **WEP** (Wired Equivalent Privacy — the original, now-broken Wi-Fi encryption protocol) and early TLS. Multiple cryptographic attacks have fully broken RC4; it is **forbidden by RFC 7465** (an IETF standard document explicitly banning it). Do not use RC4.

### Asymmetric encryption: key pairs

**Asymmetric encryption** uses a mathematically linked **key pair** — a public key (shared openly) and a private key (kept secret). Anything encrypted with the public key can only be decrypted with the private key, and vice versa.

**RSA** is the most widely deployed asymmetric algorithm. Its security rests on the **difficulty of factoring** the product of two very large prime numbers — a problem no classical computer can solve quickly for large enough numbers. RSA can encrypt data and create digital signatures, but it is **too slow for bulk data** — it's used to protect or exchange *keys*, not encrypt large files directly.

| RSA Key Length | Status |
|---|---|
| 2048-bit | Minimum acceptable today |
| 3072 or 4096-bit | Recommended for long-term security |

RSA key exchange (client encrypts a session key with the server's public key) was used in older TLS versions but **removed from TLS 1.3** because it lacks Perfect Forward Secrecy (explained below).

**ECC** (**Elliptic Curve Cryptography**) achieves equivalent security to RSA with much smaller keys, because its security is based on the **elliptic curve discrete logarithm problem** — a different mathematical hard problem that resists attacks more efficiently.

| ECC Key Size | Equivalent RSA Key Size |
|---|---|
| 256-bit | ~3072-bit RSA |

Smaller keys = faster computation + less memory, making ECC ideal for smartphones, IoT devices, and embedded systems. ECC is used in:
- **ECDH** (**Elliptic Curve Diffie-Hellman**) — key agreement
- **ECDSA** (**Elliptic Curve Digital Signature Algorithm**) — digital signatures
- **ECDHE** — the ephemeral variant used in TLS 1.3

> RSA is a massive combination lock — very secure but slow to dial. ECC is a compact biometric scanner — equally hard to defeat, but faster and smaller.

### Diffie-Hellman and Perfect Forward Secrecy

**Diffie-Hellman (DH)** is not an encryption algorithm — it is a **key agreement protocol**. Two parties each generate a public/private value pair, exchange only their public values, and independently compute the *same shared secret* without ever sending that secret across the network. An eavesdropper who intercepts the public values cannot derive the shared secret because of the **discrete logarithm problem** — there is no known efficient algorithm to reverse the math.

**Perfect Forward Secrecy (PFS)** is a property of a key exchange where **compromising the server's long-term private key does not expose past sessions**. PFS works by using **ephemeral** (temporary, one-time) key pairs: a fresh pair is generated per session, used to derive the session key, and then *discarded*. Without the discarded ephemeral private key, an attacker with the server's long-term key still cannot decrypt old traffic.

- **DHE** (**Diffie-Hellman Ephemeral**) — DH with per-session keys → PFS
- **ECDHE** (**Elliptic Curve Diffie-Hellman Ephemeral**) — ECC + ephemeral keys → PFS + efficiency
- Both are **mandatory in TLS 1.3**

Older TLS used RSA key exchange (no ephemeral keys), which means a future private key compromise could retroactively decrypt all recorded past sessions. TLS 1.3 eliminated RSA key exchange specifically to enforce PFS.

> DH without ephemeral keys is like having one master key that opens every door you've ever locked — steal it once, open everything forever. ECDHE generates a brand-new key for each door, then destroys it. Stealing the master changes nothing.

**DSA** (**Digital Signature Algorithm**) is a federal standard for **digital signatures only** — it cannot encrypt data. It's based on the discrete logarithm problem and has been largely replaced by ECDSA in modern systems.

### Hardware encryption devices

Software can always be attacked by malware or a compromised OS. Hardware encryption devices physically isolate keys so software cannot extract them.

**TPM** (**Trusted Platform Module**) is a dedicated security chip embedded on a computer's motherboard. It:
- Stores encryption keys in protected hardware storage
- Generates random numbers
- Provides **measured boot** — verifying system integrity at startup

BitLocker uses the TPM to store its disk encryption key; without passing the boot integrity check, the key never releases. **TPM 2.0** is required for Windows 11 and supports more algorithms than the older TPM 1.2.

> A TPM is a tamper-proof safe welded inside the motherboard: the key lives there and never comes out in the clear, even if the OS is compromised.

**HSM** (**Hardware Security Module**) is a dedicated, certified appliance for high-performance cryptographic operations at scale. Unlike a TPM (one chip, one machine), an HSM is an enterprise device that:
- Is validated to **FIPS 140-2 or FIPS 140-3** standards — federal benchmarks for cryptographic module security, with higher levels meaning greater physical tamper resistance
- Keeps private keys inside hardware — they are never exported
- Performs all crypto internally — keys never leave the device
- Handles many concurrent operations efficiently

PKI **Certificate Authority (CA)** private keys and payment-card processing keys are protected by HSMs.

> An HSM is a bank vault that also does the math for you: you slide a problem in, it hands you an answer, and the key never leaves the vault.

**Secure Enclave** is an isolated processor region physically separate from the main CPU, designed to protect the most sensitive security data on a device. Apple's **Secure Enclave Processor** stores **Touch ID/Face ID** biometric templates and device encryption keys — the main CPU and OS never see them. **Intel SGX** (**Software Guard Extensions**) creates encrypted memory regions called *enclaves* for confidential computing, where even the OS or hypervisor cannot read the data.

### Full disk and file-level encryption

**Full disk encryption (FDE)** encrypts an entire storage volume so that without the correct credentials at boot, the data is unreadable.

| Solution | Platform | Notes |
|---|---|---|
| **BitLocker** | Windows | Uses TPM; optional PIN or USB key |
| **FileVault** | macOS | Uses Secure Enclave or user password |
| **LUKS + dm-crypt** | Linux | **LUKS** = Linux Unified Key Setup; **dm-crypt** = Linux kernel disk encryption layer |
| **Self-encrypting drives (SEDs)** | Any | AES in drive firmware per the **Opal** standard; instant erasure by discarding the key |

At the file/folder level:
- **EFS** (**Encrypting File System**) — Windows per-file encryption within **NTFS** (Windows' default file system)
- **PGP/GPG** — encrypt individual files and email messages
