## Multifactor Authentication (MFA)

MFA is one of the most effective controls for stopping unauthorized access. This lesson covers every factor category, every implementation type, their security weaknesses, and the attacks that defeat each one — all of which are high-frequency exam territory.

---

### Authentication factor categories

Each factor is defined by *what it fundamentally represents*. True MFA requires two or more factors from **different** categories — two passwords are still just one category and do not qualify.

| Category | Also called | Examples |
|---|---|---|
| Something you **know** | Knowledge factor | Password, PIN, security question |
| Something you **have** | Possession factor | Hardware token, smart card, phone with authenticator app, USB security key |
| Something you **are** | Inherence factor | Fingerprint, face, iris, retina, voice |
| Somewhere you **are** | Location factor | GPS, IP geolocation, cell-tower triangulation |
| Something you **do** | Behavioral factor | Typing cadence, mouse movement, gait analysis |

**Location** is typically a supplementary risk signal, not a primary factor. **Behavioral** factors enable *continuous authentication* — passive identity verification throughout a session, not just at login.

---

### Why knowledge factors are the weakest

**Knowledge factors** — passwords and PINs — are the most widely used category but are vulnerable to brute force, password spraying (trying one common password across many accounts), phishing, keylogging, data breaches, and social engineering. Think of a password like a key duplicated a thousand times and handed to strangers — once it's out, you have no idea who has a copy.

---

### TOTP and HOTP

**TOTP** (Time-based One-Time Password), defined in **RFC 6238** — a numeric code generated by combining a shared secret with the current Unix time, rounded to 30-second windows, using **HMAC-SHA1** (a keyed cryptographic hash algorithm). The code changes every 30 seconds and the app and server stay in sync because they both know the secret and the time.

- Apps: Google Authenticator, Microsoft Authenticator, Authy
- **Critical weakness:** vulnerable to real-time phishing relay — an attacker who proxies your login can capture and replay your TOTP code *within the same 30-second window* before it expires

**HOTP** (HMAC-based One-Time Password), defined in **RFC 4226** — a counter-based variant where codes don't expire on a timer but are invalidated once used, as both sides increment a counter. TOTP is more common because it avoids counter-sync problems.

Think of TOTP like a parking meter: the code is valid for 30 seconds, then it's gone. A thief watching you enter your code can still use it — but only if they sprint.

---

### SMS OTP — the weakest MFA

**SMS OTP** sends a numeric code to the user's phone number via text. Widely supported but the weakest MFA form because:

- **SS7 vulnerabilities** — flaws in the global telephone signaling infrastructure (**SS7** — Signaling System No. 7, the protocol backbone of the phone network) allow sophisticated attackers to intercept SMS messages remotely
- **SIM swapping** — attacker social-engineers the mobile carrier's customer service into transferring the victim's number to an attacker-controlled SIM card, redirecting all texts
- **Number porting attacks** — a SIM-swap variant using the legitimate number-porting process

**NIST SP 800-63B** — the NIST (National Institute of Standards and Technology) digital identity guideline — deprecated SMS OTP for government systems because of these vulnerabilities.

---

### Push notification authentication

**Push authentication** (used by **Duo Security**, Microsoft Authenticator) sends a notification to an enrolled app when a login attempt occurs; the user taps approve or deny.

- More secure than SMS because it is cryptographically bound to a specific enrolled *device*, not just a phone number
- **MFA fatigue attack** (also called **MFA bombing**): attacker who has the victim's password floods them with push notifications until the victim accidentally approves one

**Defense:** **number matching** — the login screen displays a number and the push notification requires the user to type that same number, proving they are actively engaged with a specific, real login attempt. Think of it as a secret handshake you have to initiate — you can't just nod along passively.

---

### Hardware tokens

**Hardware tokens** are dedicated physical devices generating one-time passwords or performing cryptographic challenge-response. They are the most secure OTP option but cost more and require physical distribution.

- **RSA SecurID** — historically prominent token; generates time-based codes synchronized with an RSA server
- **FIDO hardware security keys** (e.g., **YubiKey**, **Google Titan Key**) — support multiple protocols; most phishing-resistant hardware token type

---

### FIDO2, WebAuthn, and passkeys

**FIDO2** is a phishing-resistant authentication standard combining two components:

- **CTAP2** (Client-to-Authenticator Protocol version 2) — the protocol that lets an external security key talk to the browser
- **WebAuthn** — the browser API that websites use to request FIDO2 authentication

**Origin binding** is FIDO2's core security property: the authenticator generates a unique key pair *per website origin* (scheme + hostname + port). The private key never leaves the device. During login, the authenticator signs a challenge that is *mathematically bound to the origin the browser reports*, so a phishing site at `amaz0n.com` cannot receive a valid FIDO2 response meant for `amazon.com`. This makes FIDO2 the **only common MFA mechanism that is truly phishing-resistant** — unlike TOTP, which can be relayed in real time because codes are just numbers with no site-binding.

**Passkeys** are **FIDO2-based discoverable credentials** — FIDO2 credentials stored on the user's own device (rather than an external key), unlocked by the device's biometric sensor or PIN, and optionally synced across devices via platform cloud storage (Apple iCloud Keychain, Google Password Manager, Microsoft Windows Hello). A passkey replaces *both* the password and the second factor with a single phishing-resistant gesture.

Think of FIDO2 like a lock that only responds to a key cut for *this specific door's address* — even a perfect copy of the key won't work on a door at a different address.

---

### Smart cards

A **smart card** stores an **X.509 certificate** — a digital identity credential in a standardized format — and its corresponding private key inside a secure chip. Authentication requires the card (something you have) plus a PIN (something you know) — inherently two-factor. The actual authentication uses **certificate-based mutual TLS** — a protocol where both client and server prove their identities using cryptographic certificates — so the private key never leaves the card.

- **PIV** (Personal Identity Verification) — the US government smart card standard
- **CAC** (Common Access Card) — the US military version of PIV

---

### Biometric authentication

**Biometric** systems implement the something-you-are factor. Key properties: cannot be forgotten, cannot be shared, cannot be changed if compromised.

| Modality | Key detail | Notable weakness |
|---|---|---|
| Fingerprint (Touch ID) | Stores a mathematical template, not the raw image | Latent fingerprint lifting |
| Facial recognition (Face ID) | IR depth-mapping for 3D liveness detection; ~1-in-1,000,000 false accept rate | Photograph defeated by 3D mapping |
| Retinal scan | Maps blood vessels in the retina; highly accurate | Expensive hardware, close proximity required |
| Iris scan | Random iris pattern; used in border control | High-security niche use |
| Voice recognition | Analyzes vocal characteristics | Vulnerable to recordings and **deepfake** audio — synthetic audio generated to mimic the user's voice |

**Liveness detection** (used in Face ID) defeats static-photo spoofing by requiring a genuine 3D depth response — a printed photo has no depth.

---

### Adaptive MFA

**Adaptive MFA** (also called **risk-based authentication**) uses contextual risk signals to decide *when* to demand extra factors. Low-risk context (known device, typical time, usual location) may allow single-factor access. High-risk signals trigger **step-up authentication** — a prompt for an additional factor mid-session.

Risk signals include: unrecognized device, unusual location, unusual time, and **impossible travel** — flagging logins from two geographically distant locations within a time window that makes physical travel impossible. Think of it as a bouncer who waves in regulars but asks strangers for ID.

---

### Recap

- **True MFA** requires factors from two or more *different* categories — two passwords are not MFA
- **TOTP** is phishable in real time; **FIDO2/WebAuthn** is the only common mechanism with cryptographic phishing resistance via origin binding
- **SMS OTP** is the weakest MFA form due to SS7 interception and SIM swapping; NIST 800-63B deprecated it for government use
- **MFA fatigue** exploits push authentication; **number matching** is the defense
- **Smart cards** (PIV/CAC) combine possession + knowledge and use mutual TLS — the private key never leaves the chip

---

### Exam flags

- **MFA category identification** — expect scenarios asking whether a given combination (e.g., two passwords, password + token) qualifies as true MFA and why
- **FIDO2 origin binding vs. TOTP relay attacks** — the exam distinguishes phishing-resistant mechanisms from those vulnerable to real-time relay; know *why* FIDO2 defeats phishing while TOTP does not
- **SMS OTP weaknesses** — SIM swapping, SS7 interception, and NIST 800-63B deprecation are all testable attack/policy details
