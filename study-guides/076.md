## Secure Baselines

Secure baselines define the minimum acceptable security configuration every system must meet before it goes live. This lesson covers what baselines are, where they come from, what they contain, and how organizations enforce and maintain them — all of which the Security+ exam tests directly.

---

### What a baseline actually is

A **secure baseline** is a documented minimum-security configuration standard that every system of a given type must satisfy before deployment or continued operation in production.

- It is a **mandatory floor**, not an aspirational target — the lowest security posture the organization will tolerate
- Every server, workstation image, network device, and cloud instance of a given type must meet it
- Without a baseline, each admin makes their own security decisions, creating a patchwork that is nearly impossible to audit or defend

**Why baselines matter:**
- **Consistency** — all systems of the same type share identical security settings regardless of who built them
- **Auditability** — a documented standard gives auditors something concrete to measure against
- **Efficiency** — automated tooling applies the baseline instantly, so deploying engineers don't make security decisions from scratch
- **Compliance** — frameworks like **PCI DSS** (payment card security standard) and **HIPAA** (healthcare data privacy law) explicitly require them

> Think of a baseline like a building code: every contractor must hit the same minimum standard, so inspectors know exactly what to check — no guessing.

---

### Authoritative baseline sources

| Source | What it is | Key detail |
|---|---|---|
| **CIS Benchmarks** | Free, consensus-developed config guides from the **Center for Internet Security** | Level 1 = practical, low-impact; Level 2 = restrictive, high-security environments |
| **STIGs** | **Security Technical Implementation Guides** from **DISA** (Defense Information Systems Agency) | Required for US government/DoD systems; more prescriptive than CIS |
| **SCAP** | **Security Content Automation Protocol** — a NIST-maintained framework for expressing and automating compliance checks | STIGs are distributed in SCAP format for tool-based scanning |
| **NIST SP 800-53** | Comprehensive security control catalog for federal systems | Defines Low/Moderate/High impact control baselines organizations tailor to their environment |
| Vendor guides | Microsoft Security Baselines, Apple Security Guide, Cisco/Palo Alto hardening guides | Product-specific; used alongside or instead of CIS/STIG |

> STIGs are like the federal building code for government facilities — stricter than the standard code, mandatory if you're building on federal ground.

### What a baseline actually configures

A typical OS baseline covers:
- **Disable unnecessary services and software** — reduces attack surface
- **Password policy** — complexity requirements, history (prevents reuse)
- **Account lockout policy** — slows credential-stuffing attacks
- **Audit logging** — logon events, privilege use, object access, policy changes
- **Disable/rename default accounts** — guest, built-in Administrator
- **Automatic security updates** enabled
- **Host-based firewall** — default-deny with explicit permit rules only
- **Screen lock timeout** after inactivity
- **Full-disk encryption** — protects data at rest from physical theft

### Deploying baselines at scale

Manual configuration doesn't scale. Organizations use:
- **Group Policy Objects (GPOs)** — enforce baseline settings on all Windows machines joined to **Active Directory** (a Windows directory service for centrally managing users and computers); reapplied at startup/login
- **Microsoft Endpoint Configuration Manager (formerly SCCM)** — extends GPO for patch management
- **Ansible, Chef, Puppet, SaltStack** — **configuration management tools** that express baseline settings as code for Linux, network devices, and cloud
- **MDM platforms** (e.g., **Microsoft Intune**, **Jamf Pro** — mobile device management systems) — push configuration profiles to mobile devices

---

### Hardening vs. baseline

These two terms are related but distinct:

- **Hardening** is the *active process* — removing software, disabling services, configuring settings
- The **baseline** is the *documented target state* the hardening aims to achieve
- A system is "hardened" when its configuration matches the baseline

> Hardening is the act of painting; the baseline is the spec sheet that says what color and how many coats.

---

### Configuration drift and continuous compliance

**Configuration drift** is the gradual divergence of a system from its baseline over time — caused by admin changes, application requirements, or patches altering defaults.

- Drift is inevitable without continuous enforcement
- **Compliance scanning tools** (e.g., **Tenable Nessus**, **Qualys VMDR** — vulnerability and compliance scanners; **CIS-CAT Pro Assessor** — CIS's own automated benchmark checker) compare live config against the baseline and report every deviation
- Findings feed into a **SIEM** (**Security Information and Event Management** platform — a tool that aggregates and correlates security event logs) for centralized alerting and audit trail
- Remediation options: **fix the deviation** or **formally accept it as an exception**

> Drift is like a ship slowly drifting off course — without continuous GPS checks and corrections, you don't notice until you're far from where you should be.

---

### Baseline exemptions

When a system legitimately cannot meet a control (e.g., a legacy app that breaks under strict settings), an **exemption** is required. The process must include:

1. Document the specific control that cannot be met and **why**
2. Identify **compensating controls** that partially mitigate the risk
3. Obtain formal **risk acceptance** from an authority (e.g., CISO)
4. Set a **review date** — exemptions are never permanent by default
5. Record the exemption in the **risk register** (the organization's official log of accepted risks)

---

### Recap

- A baseline is a **mandatory minimum** security configuration — the floor, not the ceiling
- **CIS Benchmarks** (Level 1/2) and **DISA STIGs** are the two primary third-party baseline sources; STIGs are required for government/DoD systems
- **Configuration drift** is the enemy of baselines — continuous compliance scanning detects it
- **Hardening** = the process; **baseline** = the documented target state
- Exemptions require documentation, compensating controls, management sign-off, and a review date

### Exam flags

- **CIS Level 1 vs. Level 2** — know that Level 1 is low-impact/practical and Level 2 is high-security/potentially disruptive
- **Configuration drift** — know the definition and that the remediation is either correcting the deviation or formally documenting an accepted exception
- **STIGs vs. CIS Benchmarks** — STIGs are mandatory for US government systems and distributed in SCAP format; CIS Benchmarks are vendor-neutral and broadly applicable
