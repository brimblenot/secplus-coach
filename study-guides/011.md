## Technical Change Management

Technical change management covers *how* approved changes are actually executed in a production environment — the tools, controls, and procedures IT staff use at implementation time. This is distinct from the governance layer (approvals, CAB review) and is heavily tested on Security+.

---

### Allow lists vs. deny lists

**Allow list** (formerly "whitelist") — a control that explicitly names every permitted item; anything not on the list is blocked by default.

- Only pre-approved applications can run; unknown code — even benign code — is automatically blocked
- Extremely effective against malware and ransomware because unknown malicious code has no path to execute
- Trade-off: high administrative burden — every new legitimate app must be evaluated and added before use
- Implemented via **EDR** (Endpoint Detection and Response — a security platform that monitors endpoints and can enforce execution policies), **AppLocker** / **Microsoft Defender Application Control**, and **MDM** (Mobile Device Management — a platform for centrally managing and enforcing policies on devices)

**Deny list** (formerly "blacklist/blocklist") — explicitly names what is prohibited; everything else is permitted by default.

- Antivirus is conceptually a giant deny list: it blocks code matching known malicious signatures, allows everything else
- Easier to administer in diverse environments — only bad items need listing, not every allowed item
- Inherently **reactive**: it cannot block unknown malware, zero-day exploits, or legitimate apps used maliciously, because those items haven't been identified and added yet

| Feature | Allow list | Deny list |
|---|---|---|
| Default stance | Block all, permit listed | Permit all, block listed |
| Blocks unknown threats? | ✅ Yes | ❌ No |
| Admin burden | High | Lower |
| Best for | High-security, controlled environments | Diverse, flexible environments |

> Think of an allow list as a nightclub with a guest list — you're not getting in unless your name is already there. A deny list is a "most-wanted" board at the door — anyone NOT on the board walks in freely.

### Restricted activities within a change window

A **change window** — the approved time slot during which a specific change may be made — authorizes only the exact scope documented in the **RFC** (Request for Change — the formal document describing a proposed change). A technician upgrading printer drivers is *not* authorized to modify firewall rules just because the window is open.

- Minor, directly necessary ancillary changes (e.g., a config file tweak the driver requires) may be made and documented in the change record
- Significant unexpected changes must be **escalated** to the change authority for expedited approval — not implemented unilaterally

---

### Downtime planning and blue-green deployment

Changes often require service interruptions (server reboots, database maintenance). Planned downtime must be communicated in advance via email, change calendar, and help desk notifications.

In **24×7 environments** where no downtime is acceptable, organizations use a **blue-green deployment** — a pattern where two identical environments (blue and green) are maintained; the change is applied to the inactive one while the other serves live traffic, then traffic switches once the updated environment is verified healthy.

- Switch can be automated to complete in seconds — invisible to users
- If the update fails validation, traffic never switches and rollback is instant

> Blue-green is like road construction with a detour already paved: traffic reroutes to the detour while workers fix the main road, then flips back when it's done.

### Version control

**Version control** — a system that records every change to files over time so changes can be tracked, audited, and reversed. **Git** is the dominant modern standard.

Each **commit** — a saved snapshot of changes — captures: the modified file content, the author's identity, a timestamp, and a description of why the change was made.

- Provides a full **audit trail** and supports forensic investigation of historical states
- Enables **rollback** — reverting files to any prior commit if a change causes problems
- **IaC** (Infrastructure as Code — the practice of defining servers, network devices, and cloud resources in version-controlled config files) extends these same traceability benefits to infrastructure, not just application code

---

### Dependency management

**Dependency management** — the practice of identifying and accounting for relationships between software components before making a change. Modern apps depend on third-party libraries, OS services, and external APIs.

- **Upstream dependencies** — services the *changed component relies on*
- **Downstream dependencies** — services that *rely on the changed component*
- An unaccounted dependency can cascade one "simple" change into multiple failures
- **SBOM** (Software Bill of Materials — a structured list of every component and library in a software system) makes dependency mapping systematic and helps identify which systems are affected when a vulnerability is found in a shared library

### Legacy application challenges

A **legacy application** is software that is no longer actively supported by its vendor, often runs on outdated OSes, uses deprecated or insecure protocols, and cannot easily be patched or modified without risking a break.

Because vendor patches no longer exist and direct modification is risky, legacy systems are managed through **compensating controls** — security measures that reduce risk without changing the system itself:

- Place behind an **application-layer firewall** — a firewall that inspects traffic at Layer 7, filtering by content and protocol, not just port numbers
- **Microsegment** the system — isolate it in a network zone where only specifically authorized systems and users can reach it
- Apply intensive monitoring
- Plan for eventual migration to a modern replacement

> A legacy system is like a load-bearing wall in an old building — you can't just knock it out, so you brace around it and start planning the renovation.

### Environment separation

Most organizations maintain four progressively stricter environments:

| Environment | Purpose | Control level |
|---|---|---|
| **Development** | Developers write and initially test code | Loose |
| **Testing / QA** (Quality Assurance) | Formal functional, integration, and performance testing | Moderate |
| **Staging / Pre-production** | Final validation in a near-identical replica of production | High |
| **Production** | Live system business operations depend on | Strictest |

Promotion between environments requires formal approval and testing gates — untested or experimental changes must never reach production directly.

**Sandbox environments** — isolated duplicates of production used to safely test patches, new software, or security tools without any risk to live systems. Also used in malware research: suspected malware is executed inside the sandbox so analysts can observe behavior without infecting production.

---

### CI/CD pipeline security

A **CI/CD pipeline** — where **CI** (Continuous Integration) means automatically building and testing every code commit, and **CD** (Continuous Deployment/Delivery) means automatically promoting passing builds to the next environment or to production — accelerates software delivery but creates risk if security checks are skipped.

Security tools integrated into the pipeline:

| Tool | What it does |
|---|---|
| **SAST** (Static Application Security Testing) | Scans source code for vulnerabilities *before* compilation |
| **DAST** (Dynamic Application Security Testing) | Simulates attacks against a *running* application to find vulnerabilities |
| **SCA** (Software Composition Analysis) | Scans third-party libraries and open-source components for known vulnerabilities |

---

### Configuration drift

**Configuration drift** — the gradual, often unintentional deviation of a system's actual configuration from its approved, documented baseline. It accumulates when small changes are made outside the formal change management process (e.g., a "temporary" exception that is never reversed, an automated tool that silently updates a setting).

- Drift creates undetected security gaps and makes systems hard to audit
- Managed by regularly comparing live configurations against the approved baseline and remediating differences

> Configuration drift is like a ship slowly drifting off course — no single moment looks alarming, but after enough small deviations you're headed somewhere you never intended.

---

### Recap

- **Allow lists** block everything by default (safest, most burden); **deny lists** permit everything by default (reactive, lower burden)
- A change window authorizes only the exact documented scope — unexpected significant changes must be escalated
- **Blue-green deployment** enables zero-downtime changes by switching live traffic between two identical environments
- **Version control** (Git) and **IaC** make every infrastructure and code change traceable and reversible
- **SAST**, **DAST**, and **SCA** are the three security testing tools that must be embedded in CI/CD pipelines

### Exam flags

- **Allow list vs. deny list** — know their default stances, which blocks unknown threats, and which is harder to administer
- **CI/CD security tools** — be able to distinguish SAST (static/source code), DAST (dynamic/running app), and SCA (third-party components)
- **Environment separation** — know the four environments in order and why untested changes must never go directly to production
