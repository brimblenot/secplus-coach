## Memory Injections

Malware has to run somewhere — and that somewhere is always RAM. This lesson covers how attackers hide malicious code inside legitimate processes, the specific techniques they use, and the defenses that catch them.

---

### Why injection beats running a standalone process

A normal malicious process has three big problems for the attacker:

- Security tools watch the **process list** for unknown or suspicious entries
- New process creation events land in **logs** that threat hunters review
- The process only gets the **privileges of whoever launched it**

**Process injection** solves all three: it places attacker-controlled code inside an already-running, already-trusted process. The injected code **inherits** that process's privilege level, access tokens, and permissions — and it blends in because it looks like the legitimate process from the outside.

> Think of it like a pickpocket slipping into a VIP's coat pocket — they're now being carried past the security checkpoints on the VIP's credentials.

---

### DLL injection — the most common technique

A **DLL** — *Dynamic Link Library* — is a shared executable file that multiple Windows processes can load simultaneously, containing reusable functions.

**DLL injection** forces a legitimate process to load a malicious DLL using a specific Windows API call sequence:

| API Call | What it does |
|---|---|
| **VirtualAllocEx** — allocates memory in a remote process | Carves out space inside the target process |
| **WriteProcessMemory** — writes data into another process's memory | Writes the malicious DLL's file path there |
| **CreateRemoteThread** — starts a new thread in another process | Calls `LoadLibrary` with that path, triggering Windows to load the DLL |

Once `LoadLibrary` runs, the DLL is fully mapped into the target process and runs with all its privileges.

> Imagine mailing a fake employee badge to a building, then calling the front desk and telling them to let that badge in — suddenly your proxy is inside with full access.

---

### Reflective DLL injection — no file required

Standard DLL injection needs the DLL file to exist on disk for `LoadLibrary` to find it. **Antivirus** — which scans files on the file system against known-bad signatures — can catch it there.

**Reflective DLL injection** removes that exposure entirely. The malicious DLL contains its **own loader code** that maps the DLL from raw bytes already in memory, bypassing the Windows loader. No file is ever written to disk; antivirus has nothing to scan. This technique is implemented in frameworks like **Cobalt Strike** and **Metasploit's Meterpreter** payload, so defenders must use **behavioral monitoring** rather than file scanning to detect it.

---

### Process hollowing — gutting a legitimate process

**Process hollowing** (also called *process replacement*) spawns a real, trusted Windows binary — like `svchost.exe` or `explorer.exe` — in a **suspended state** (created and allocated memory, but not yet running). The attacker then:

1. **Unmaps** the legitimate executable image from memory
2. **Writes malicious code** into the now-empty space
3. **Resumes** the process

The process list still shows a legitimate name and PID, but the code running inside is entirely the attacker's.

---

### Thread hijacking and APC injection

**Thread hijacking** targets an *existing* thread inside a legitimate process. The attacker suspends it, changes its **instruction pointer** — the CPU register holding the address of the next instruction to execute — to point to malicious code, then resumes it.

**APC injection** exploits Windows's **Asynchronous Procedure Call** mechanism, which queues a function to run inside a thread when that thread enters an *alertable wait state* (e.g., calling `SleepEx`). The attacker queues a malicious APC to a thread in a legitimate process; when the thread waits, the malicious function executes in its context.

---

### Process Doppelgänging — abusing NTFS transactions

**Process Doppelgänging** abuses **NTFS transactions** — a file-system feature designed to allow atomic, rollback-capable file operations:

1. Open a transaction; write a malicious executable inside it (file exists on disk within the transaction context)
2. Create a process from that transacted file
3. Roll back the transaction — the file disappears from disk
4. The process keeps running with the malicious code it was initialized from, but no on-disk file corresponds to it

Forensic recovery of the malicious executable is extremely difficult.

### Defenses

| Defense | What it is | What it stops |
|---|---|---|
| **DEP** (*Data Execution Prevention*) — hardware-enforced via the **NX bit** (*No-Execute bit*) in the CPU | Marks heap/stack pages as non-executable; processor raises an exception if code tries to run there | Simple shellcode injected into data buffers; bypassed by **ROP** (*Return-Oriented Programming* — chaining small sequences of already-present legitimate code instead of injecting new code) |
| **ASLR** (*Address Space Layout Randomization*) | Randomizes base addresses of the executable, stack, heap, and libraries on every launch | Hard-coded address exploitation; attacker needs an information-leak vulnerability first |
| **CFI** (*Control Flow Integrity*) | Validates at runtime that execution only follows control-flow paths the compiler deemed valid | ROP attacks (detects jumps to unexpected locations) |
| **EDR** (*Endpoint Detection and Response*) | Monitors API call sequences and scans process memory in real time | DLL injection API chains (`VirtualAllocEx → WriteProcessMemory → CreateRemoteThread`); injected code regions with no corresponding file on disk |
| **AMSI** (*Anti-Malware Scan Interface*) — a Windows API for inspecting code before execution | Lets security products inspect scripts (e.g., PowerShell) before they run | Malicious scripts that attempt to invoke injection techniques |

> DEP + ASLR together are like a bank vault in an unknown location: even if you could blow through the wall, you don't know which wall to hit — and CFI is the guard watching for anyone walking the wrong direction.

---

### Recap

- **Process injection** hides malicious code in a legitimate process to inherit its privileges and evade detection
- **DLL injection** uses `VirtualAllocEx → WriteProcessMemory → CreateRemoteThread`; **reflective DLL injection** removes the on-disk file requirement, defeating file-based AV
- **Process hollowing** swaps out a legitimate binary's code while keeping its visible identity
- **DEP** blocks shellcode execution in data pages; **ASLR** randomizes addresses; **CFI** blocks ROP; **EDR** catches API call patterns
- **AMSI** catches malicious scripts before they reach the injection stage

### Exam flags

- Know the **four-call DLL injection API sequence** and what each call does
- Know why **reflective DLL injection evades antivirus** (no file on disk, bypasses Windows loader) and how defenders must respond (behavioral monitoring/EDR)
- Know how **DEP, ASLR, and CFI** each mitigate different aspects of injection and why DEP alone is insufficient (bypassed by ROP)
