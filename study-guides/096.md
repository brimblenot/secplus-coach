## Identity and Access Management (IAM)

**IAM** — Identity and Access Management — is the set of policies, processes, and technologies that manage digital identities and control who can access what. This lesson covers the full IAM discipline: identity lifecycles, privileged access, single sign-on, federation standards, and directory services. Understanding IAM is critical because modern environments (cloud, remote work) have no clear network perimeter — identity *is* the perimeter.

---

### The identity lifecycle: joiner, mover, leaver

Every digital identity moves through three phases. The key security goal at every phase is granting exactly the right access — no more, no less.

**Provisioning (joiner)** — creating a new account with the correct access when someone joins or changes roles. Mature orgs trigger this automatically from the HR system based on role, department, and title.

**Access modification (mover)** — updating access when someone changes roles. Old role's access must be *removed*; new role's access is added. Failing to remove old access causes **privilege creep** — gradual accumulation of excess permissions over time.

**Deprovisioning (leaver)** — disabling accounts when someone leaves. Accounts should be pre-staged to disable on the last day. **Orphaned accounts** — active accounts belonging to departed users — are a serious risk: attackers can compromise those credentials with no one watching.

> Think of the lifecycle like a hotel keycard: provisioning cuts you a card for your room, the mover process upgrades or downgrades your room access when you switch floors, and deprovisioning deactivates the card at checkout. A key that still works after checkout is an orphaned account.

---

### Just-in-time provisioning

**JIT provisioning** — Just-in-Time provisioning — grants temporary, on-demand access to a resource and automatically revokes it when the task is done, rather than leaving standing (always-on) privileged access.

- A tech gets admin credentials to a production server for one maintenance window; they expire automatically afterward.
- Eliminating standing privilege limits the window of exposure if credentials are compromised.
- Enabled by automation integrated with HR triggers; standardized via **SCIM** — System for Cross-domain Identity Management — an HTTP-based protocol that automates account creation, updates, and deletion between identity providers and connected apps.

> Like a contractor badge that only unlocks the server room on Tuesday between 9–11 AM — it goes dead the moment the window closes.

---

### User identity governance

**Access recertification campaigns** (also: access reviews or certification campaigns) — periodic manager reviews where managers confirm each subordinate's current access is still appropriate. Uncertified access is revoked. Required by compliance frameworks like **SOX** — Sarbanes-Oxley, the U.S. law governing financial reporting controls.

**Separation of duties** — ensuring no single user holds a combination of permissions that enables fraud alone. Example: the person who enters payments cannot also approve payments.

**Toxic combination detection** — automated alerts when a user's permission set contains a dangerous pairing that violates separation of duties.

### Privileged Identity Management and Privileged Access Management

**PIM** — Privileged Identity Management — and **PAM** — Privileged Access Management — are specialized controls for admin accounts, which carry dramatically higher risk than standard user accounts.

| PAM Mechanism | What it does |
|---|---|
| **JIT privileged access** | No standing admin rights; elevation is requested, approved for a time window, then auto-revoked |
| **Session recording** | Full video and keystroke capture of every privileged session for audit and forensics |
| **Password vaulting** | Credentials stored in an encrypted vault; users never see the actual password; vault checks out creds on behalf of the user and rotates the password after each session |

Leading PAM vendors: **CyberArk**, **BeyondTrust**, **Delinea**.

> Password vaulting is like a bank cashier who hands you a pre-counted envelope — you never touch the vault, and the combination changes the moment you leave.

### Single sign-on

**SSO** — Single Sign-On — lets a user authenticate once to a central **identity provider (IdP)** and then access multiple applications using an authentication token, without logging in again at each app.

- **Security benefit:** revoking the SSO account immediately cuts access to *all* connected apps.
- **Security risk:** one compromised SSO credential opens *all* connected apps — making **MFA** — multi-factor authentication — on the IdP critical.
- **Operational benefit:** fewer passwords → fewer help desk resets.

> SSO is a park wristband: one scan at the gate and every ride lets you in — but if someone steals the wristband, they ride everything.

---

### Federation and its protocols

**Federation** extends SSO *across organizational boundaries*, letting users authenticate with their home org's IdP and access partner or cloud resources without separate accounts there.

**SAML 2.0** — Security Assertion Markup Language — is the dominant enterprise federation standard.

| Role | Definition |
|---|---|
| **IdP** (Identity Provider) | The authoritative source; performs authentication and issues signed assertions |
| **SP** (Service Provider) | The application the user wants; trusts the IdP's assertions |
| **SAML assertion** | A digitally signed XML statement from the IdP containing claims about the user's identity and attributes |

Flow: user hits SP → redirected to IdP → authenticates → IdP sends signed assertion → SP validates signature with IdP's public certificate → access granted.

---

**OAuth 2.0** — an *authorization* framework (what can a third party do?) — not an authentication protocol. Powers "Login with Google" buttons: the third-party app gets limited access to your Google data without ever receiving your password.

**OIDC** — OpenID Connect — adds an *authentication* layer on top of OAuth 2.0 by introducing the **ID token**, a cryptographically signed **JWT** — JSON Web Token — containing claims about who the user is.

| Protocol | Purpose | Token type |
|---|---|---|
| OAuth 2.0 | Authorization only | Access token |
| OIDC | Authentication + authorization | ID token (JWT) |
| SAML 2.0 | Enterprise federation (XML-based) | SAML assertion |

OAuth 2.0 + OIDC is the foundation of modern cloud/mobile federated identity; SAML 2.0 dominates legacy enterprise and SaaS SSO.

> OAuth is like a valet key — it lets someone park your car but not open the glove box. OIDC adds a nametag to that key so the valet also knows who handed it over.

### Directory services

**Active Directory (AD)** — Microsoft's on-premises **LDAP**-based (Lightweight Directory Access Protocol — a standard for querying directory databases) directory service for Windows domains. Stores users, groups, computers, and **Group Policy Objects** — policy containers that enforce configuration across domain machines. Serves as the Kerberos authentication authority on-premises.

**Azure Active Directory / Microsoft Entra ID** — Microsoft's cloud identity platform for Microsoft 365, Azure, and SaaS apps. Key features:

- **Conditional Access policies** — risk-based rules that require stronger authentication (e.g., MFA) when access comes from an untrusted location, unfamiliar device, or high-risk operation.
- **Azure AD PIM** — provides JIT elevation for Azure AD administrative roles, the cloud equivalent of on-premises PAM.

> AD is the master key registry for an office building; Azure AD / Entra ID is the same registry moved to a cloud-hosted security desk that also serves remote workers and contractors at partner sites.

---

### Recap

- **Joiner/Mover/Leaver** lifecycle: provision, modify (remove old + add new), deprovision — orphaned accounts are the main leaver-phase risk.
- **JIT provisioning** eliminates standing privilege by granting time-limited access on demand, automated via SCIM.
- **PAM** protects admin accounts with three core mechanisms: JIT elevation, session recording, and password vaulting.
- **SSO** centralizes auth (great for revocation, risky if credential is stolen — MFA is essential); **federation** extends SSO across org boundaries using SAML 2.0 (enterprise/XML) or OIDC on OAuth 2.0 (cloud/mobile).
- **Privilege creep** (movers) and **orphaned accounts** (leavers) are the two lifecycle failures most likely to appear on the exam.

---

### Exam flags

- **Privilege creep vs. orphaned accounts** — know which lifecycle phase each belongs to and why each is a risk.
- **SAML 2.0 vs. OAuth 2.0 vs. OIDC** — exam questions will test whether you can distinguish authentication from authorization and match the right protocol to the right scenario.
- **PAM mechanisms** — JIT access, session recording, and password vaulting are frequently tested as a set; know what each does and why password vaulting prevents credential reuse.
