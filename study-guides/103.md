## Digital Forensics

Digital forensics is the science of collecting, preserving, analyzing, and presenting digital evidence so it holds up in court — and it's just as critical in incident response as in law enforcement. This lesson covers the core procedures, tools, and concepts you must know for both real investigations and the exam.

---

### Legal hold and spoliation

A **legal hold** (also called a litigation hold or evidence preservation order) is a formal obligation to stop destroying any electronically stored information (**ESI** — any data stored digitally, such as emails, files, or logs) the moment an organization reasonably expects litigation or a regulatory investigation.

- IT must suspend automatic deletion, backup overwriting, and data-management jobs on affected systems.
- **Custodians** — employees (or former employees) likely to have relevant data — receive a formal notice to preserve everything and stop normal deletion.
- **Spoliation** — the failure to preserve relevant evidence — can result in sanctions, adverse inference instructions (the court assumes the missing evidence was bad for you), or outright dismissal of claims.

Think of a legal hold like pulling the plug on a shredder the moment your lawyer calls: every document in the queue must stay put, untouched, until the case is resolved.

---

### Chain of custody

**Chain of custody** is the documented, unbroken record of who possessed evidence, when, what they did with it, and to whom they transferred it.

- Evidence must be sealed, labeled, and stored to prevent unauthorized access or contamination.
- A gap in the chain raises doubt about tampering and can make evidence **inadmissible** in court.
- Physical evidence uses tamper-evident bags signed and dated by every handler.
- Digital evidence uses **cryptographic hashing** — computing an MD5 or SHA-256 hash at the moment of collection; any later modification produces a different hash, proving tampering mathematically.

Think of the hash like a wax seal on a medieval letter: if the seal is broken (hash doesn't match), you know someone opened it.

---

### Order of volatility

The **order of volatility** is the required collection sequence from most-to-least fragile data, so the most ephemeral evidence is captured before it disappears.

| Priority | Source | Why it matters |
|---|---|---|
| 1 | CPU registers & cache | Gone the instant power cuts |
| 2 | RAM | Lost on shutdown; may hold attacker tools, creds, decrypted data, live network connections |
| 3 | Swap / paging file | RAM overflow pages on disk — fragile but more persistent |
| 4 | Disk contents | Persistent; survives reboot but can be overwritten |
| 5 | Remote logs / monitoring | Stored off-system; relatively stable |
| 6 | Physical config (network diagrams, etc.) | Least volatile |

RAM is especially valuable: it can contain **running attacker processes never written to disk**, decrypted files, and active C2 connections.

### Forensic disk imaging and tools

**Forensic disk imaging** creates an exact bit-for-bit copy of storage media so analysts work on the copy, leaving the original untouched.

A **write blocker** is a hardware or software device that intercepts all write commands to the evidence drive, preventing accidental modification during imaging. Hardware write blockers are preferred because they operate below the OS and cannot be bypassed by software.

| Tool | Type | Key detail |
|---|---|---|
| **`dd`** | Linux CLI | Reads every block; `noerror` skips bad blocks, `sync` pads them with zeros |
| **`dcfldd`** | Linux CLI | Enhanced `dd` with built-in MD5/SHA hashing and progress output |
| **FTK Imager** | Windows GUI | Supports multiple formats; performs hash verification during imaging |
| **EnCase / E01 format** | Commercial | Proprietary format accepted in court; embeds metadata, hashes, and case info |

**Hash verification** — calculating MD5 and SHA-256 of both the original and the copy immediately after imaging — mathematically proves the copy is identical. A single flipped bit produces a completely different hash.

### Memory forensics

**Memory forensics** captures and analyzes RAM to recover volatile evidence before shutdown destroys it.

- **Live capture tools**: **WinPmem**, **Magnet RAM Capture**, **Belkasoft RAM Capturer** write RAM contents to a file while the system stays running.
- **Volatility Framework** — the standard open-source tool for analyzing memory captures — uses plugins to extract specific artifacts:

| Plugin | What it shows |
|---|---|
| `pslist` / `pstree` | Running processes and parent-child relationships |
| `netscan` | Active network connections (including C2) |
| `dlllist` | DLLs loaded per process (catches injected malicious DLLs) |
| `cmdscan` / `consoles` | Attacker command history |
| `hivelist` | Registry hives loaded in memory |
| `malfind` | Heuristically detects code injected into legitimate processes |

Think of a Volatility memory dump like an MRI of a running system: it shows everything happening inside at the moment of capture, including hidden processes the attacker hoped you'd never see.

### File system forensics

**File system forensics** recovers and analyzes data stored on disk.

**Deleted file recovery** works because most file systems only mark space as *available* on deletion — the actual data stays until overwritten. Tools like **Autopsy** (with the **Sleuth Kit** — an open-source library of forensic analysis tools) and **PhotoRec** (a file-carving tool that scans raw disk data for file signatures) can recover deleted files even after directory entries are gone.

**MAC times** — **M**odified, **A**ccessed, **C**hanged metadata timestamps on each file — let analysts reconstruct a timeline of file system activity.

**Windows-specific artifacts** are especially rich:

| Artifact | What it reveals |
|---|---|
| **Windows Registry** (hive files: `NTUSER.DAT`, `SAM`, `SYSTEM`, `SOFTWARE`, `SECURITY`) | Recently opened files/programs (MRU lists), typed URLs, connected USB devices, execution history (UserAssist key) |
| **Prefetch files** (`.pf` extension) | Program name, run count, last run time, file paths — proves execution even if the program was deleted |
| **Jump lists / LNK files** | Recent file access and application usage |

### Anti-forensics techniques

Attackers use **anti-forensics** to destroy or obscure evidence:

- **Secure deletion tools** (e.g., **BleachBit**) overwrite data before deletion, defeating file recovery.
- **Timestomping** modifies MAC timestamps to disguise when files were created or accessed.
- **Log clearing** — flagged by Windows **Event ID 1102** (Security log cleared) and **Event ID 1104** (other logs cleared) — removes the primary record of attacker activity.
- **Encrypted volumes** (e.g., **BitLocker**, **VeraCrypt** — full-disk encryption tools) make disk forensics impossible without the decryption key.
- **Living-off-the-land** attacks use only built-in system tools and stay memory-resident, leaving minimal file system traces — requiring memory forensics and behavioral telemetry to detect.

---

### E-discovery vs. forensics

**E-discovery** is the process of collecting, reviewing, and producing ESI in response to a legal proceeding. It differs from forensics in a critical way: e-discovery's goal is *complete and accurate collection of specified data*, not deep technical analysis. A forensic examiner may perform the actual collection to preserve integrity, but the legal team — not the forensic analyst — defines what must be produced.

---

### Recap

- **Legal hold** freezes ESI the moment litigation is anticipated; **spoliation** carries severe legal penalties.
- **Chain of custody** must be unbroken; cryptographic hashes serve as the digital equivalent of tamper-evident seals.
- Collect evidence in **order of volatility**: registers → RAM → swap → disk → remote logs → physical config.
- **Write blockers** prevent accidental writes during imaging; hash verification proves the copy is bit-for-bit identical.
- Anti-forensics techniques — timestomping, log clearing (Event IDs 1102/1104), secure deletion, encryption — are deliberate obstacles investigators must anticipate.

### Exam flags

- **Order of volatility sequence** — expect a scenario asking which source to collect first (always start with RAM/registers).
- **Chain of custody / hash verification** — expect questions linking admissibility to unbroken documentation and matching hash values.
- **Windows forensic artifacts** — Prefetch files and Event IDs 1102/1104 are favorite specific-detail targets.
