## Encryption Technologies

This lesson covers the hardware and software systems that implement cryptographic functions — TPM chips, HSMs, key management, and encryption at every layer from disk to cloud to network. Understanding *where* encryption happens and *how* keys are protected is what the exam tests here.

---

### Trusted Platform Module (TPM)

**TPM** — a standardized security chip embedded on a motherboard (or implemented as firmware, called **fTPM**) that performs cryptographic functions *bound to one specific device*.

- Generates random numbers and cryptographic keys; stores them in protected memory that nothing outside the chip can read
- **Measured boot** (also called trusted boot): during startup, each component (firmware → bootloader → OS kernel) is hashed; those hashes are stored in **PCRs — Platform Configuration Registers** inside the TPM, building a chain-of-trust record
- If any boot component is tampered with (e.g., a **bootkit** — malware that infects the bootloader), the PCR values won't match the baseline and the TPM can refuse to release keys
- **Attestation**: the TPM can generate a *signed quote* of its PCR values so a remote server can cryptographically verify the device's integrity before granting access
- **BitLocker** (Windows full-disk encryption) *seals* its disk encryption key to the TPM — the key is only released if boot measurements match; TPM 2.0 (required for Windows 11) adds SHA-256, ECC, and broader algorithm support vs. the older TPM 1.2

> Think of the TPM as a tamper-proof lockbox bolted inside the machine: it will only hand over the door key if it confirms the house hasn't been broken into since last boot.

### Hardware Security Module (HSM)

**HSM** — a dedicated hardware appliance built exclusively for cryptographic operations *at enterprise scale*, certified to **FIPS 140-2/140-3** — federal standards defining four tamper-resistance levels.

| FIPS Level | Requirement |
|---|---|
| 1 | Approved algorithms only |
| 2 | Tamper-evidence (physical seals) |
| 3 | Tamper-resistant enclosure + identity-based auth |
| 4 | Active tamper response — auto-destroys keys if breached |

**Where HSMs are used:**
- **Certificate Authorities (CAs)** protect root/intermediate private keys so they can't be extracted even if servers are breached
- **Payment processing** — PCI DSS (the **Payment Card Industry Data Security Standard**) requires HSMs for PIN encryption
- Cloud equivalents: AWS CloudHSM, Azure Dedicated HSM

> If a TPM is a personal safe, an HSM is Fort Knox — a hardened vault serving the whole organization, rated and certified to withstand physical attack.

### Secure Enclave and SGX

**Secure Enclave** — an isolated coprocessor *physically separate* from the main CPU, used on personal and mobile devices.

- Apple's **SEP (Secure Enclave Processor)** stores biometric templates (Touch ID/Face ID) and device encryption keys; performs all matching internally — the main OS never sees raw key material or biometric data
- Even a fully compromised OS cannot extract what's inside the Enclave

**Intel SGX (Software Guard Extensions)** — a CPU feature for x86 servers that lets an application create an **enclave** — an encrypted, hardware-protected memory region the OS, hypervisor, and BIOS cannot read or modify.
- Used for **confidential computing**: tenants get hardware-level assurance that even the cloud provider's admins cannot access their data during processing

> The Secure Enclave is like a bank vault inside a building — even if thieves take over the lobby (the OS), the vault stays sealed.

### Key Management Systems (KMS)

**KMS** — software or hardware that centrally manages the full lifecycle of cryptographic keys across an organization.

- Tracks creation date, expiration, rotation schedule, usage logs, and which services depend on each key
- Enforces **separation of duties**: key admins manage keys but can't access the protected data
- Available as on-premises, cloud (AWS KMS, Azure Key Vault, Google Cloud KMS)

**Cloud key trust models:**

| Model | Who Holds Keys | Cloud Provider Sees Plaintext? |
|---|---|---|
| Default (provider-managed) | Cloud provider | Yes |
| **BYOK** (Bring Your Own Key) | Customer generates; provider stores | Potentially |
| **HYOK** (Hold Your Own Key) | Customer keeps on-premises | No — data encrypted before upload |

> HYOK is like mailing only locked boxes to a warehouse — the warehouse staff can move your boxes but can never open them.

### Disk and File Encryption

**Full Disk Encryption (FDE)** encrypts the entire storage volume at the block level — every file, directory, and file system structure.

| Solution | Platform | Notes |
|---|---|---|
| **BitLocker** | Windows | TPM-only, TPM+PIN, TPM+USB, or USB alone; TPM+PIN strongest |
| **FileVault** | macOS | Login password or Secure Enclave on Apple Silicon |
| **LUKS** (Linux Unified Key Setup) | Linux | Works with **dm-crypt** kernel module; supports multiple key slots for passphrases/recovery keys |

**Self-Encrypting Drives (SEDs)** — drives that implement AES-256 encryption in their own firmware/controller, transparent to the OS; follow the **Opal standard** from the Trusted Computing Group. Key advantage: **cryptographic erasure** — discarding the internal **MEK (media encryption key)** instantly renders all data unrecoverable, far faster than overwriting.

**File-level encryption** protects individual files rather than whole volumes:
- **EFS (Encrypting File System)** — built into Windows NTFS; transparent to authorized users
- **PGP/GPG** — **Pretty Good Privacy / GNU Privacy Guard**; encrypts/signs individual files and emails using hybrid symmetric + asymmetric cryptography

---

### Database Encryption

**TDE (Transparent Data Encryption)** — encrypts database *files at the storage layer*; data appears unencrypted to authorized database connections. Available in SQL Server, Oracle, PostgreSQL.

**Column-level encryption** — encrypts only specific sensitive columns (e.g., SSNs, credit card numbers) while leaving other columns searchable in plaintext.

---

### Transport Encryption

**TLS (Transport Layer Security)** — application-layer protocol encrypting traffic for HTTPS, SMTP, and others; server authenticated via digital certificate; session key established via **ECDHE (Elliptic Curve Diffie-Hellman Ephemeral)**.

**IPsec** — network-layer encryption protecting *all IP traffic* between endpoints regardless of application.

**End-to-end encryption** (e.g., Signal, WhatsApp) — the service provider's servers only ever see ciphertext; they cannot read message content.

---

### Quantum Threats to Encryption

**Shor's algorithm** — a quantum algorithm that can factor large integers and solve elliptic curve discrete logarithm problems in polynomial time, breaking RSA and ECC entirely.

**Grover's algorithm** — provides a quadratic speedup for brute-force symmetric key search, effectively *halving* key strength (AES-128 becomes AES-64-equivalent against a quantum attacker).

---

### Recap

- **TPM** = single-device crypto chip; enables measured boot, PCR-based tamper detection, and disk-key sealing for BitLocker
- **HSM** = enterprise-grade appliance; FIPS 140-2/3 certified; used by CAs and payment systems for key protection at scale
- **Secure Enclave / SGX** = hardware-isolated regions where even a compromised OS cannot read key material
- **BYOK vs. HYOK**: BYOK gives you key generation control; HYOK keeps keys entirely off the cloud provider's infrastructure
- **SEDs** enable instant cryptographic erasure by discarding the MEK; quantum computing threatens RSA/ECC (Shor's) and halves symmetric strength (Grover's)

### Exam flags

- **TPM measured boot + BitLocker integration** — know what PCRs measure, what attestation proves, and why TPM+PIN is strongest
- **HSM FIPS 140-2 levels** — be able to match Level 1–4 to their physical security requirements
- **BYOK vs. HYOK** — know which model keeps the cloud provider from ever seeing plaintext keys
