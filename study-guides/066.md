## Firewall Types

Firewalls are the foundational tool for controlling traffic between network zones — but "firewall" covers a wide spectrum, from simple packet checkers to cloud-native inspection engines. This lesson breaks down each type, what it can and can't see, and where it belongs.

---

### Packet filtering firewalls

A **packet filtering firewall** is the simplest firewall type — it examines each packet in isolation, looking only at header fields, and either permits or denies it based on an **ACL** (Access Control List — a ruleset defining allowed/denied traffic combinations).

- Operates at **OSI Layers 3 and 4** (network and transport)
- Inspects: source/destination IP, source/destination port, protocol (TCP/UDP/ICMP)
- **Stateless** — every packet is judged alone, with zero memory of prior packets

**What stateless means in practice:**
- Cannot tell if an inbound `ACK` packet is a real reply or a crafted probe
- Cannot detect **IP fragmentation attacks** — malicious payloads split across multiple fragments
- Cannot detect session hijacking or connection-state manipulation

> 🔩 *Think of it like a bouncer who only checks your shirt color — no memory of who entered earlier, so a crafted outfit gets waved right through.*

---

### Stateful inspection firewalls

A **stateful inspection firewall** (also called a **circuit-level gateway** or **stateful packet inspection firewall**) tracks the state of active connections in a **state table** — a live record of established sessions including source/destination IPs, ports, and TCP sequence numbers.

- Operates at **Layers 3–4**, but uses session context
- Records the TCP **three-way handshake** (SYN → SYN-ACK → ACK) when a connection is opened
- Inbound packets are checked against the state table — no matching entry = blocked
- Handles complex protocols like **FTP** that open separate control and data connections

**Why this beats packet filtering:** An unsolicited inbound packet — regardless of port or address — is blocked automatically unless a rule explicitly allows it independent of state. A packet filter would need a permissive rule to allow any ACK-flagged packet, letting crafted packets through.

> 🗂️ *Like a coat-check that stamps your ticket on the way in — if you can't show the matching stub on the way out, you don't get your coat (or entry back in).*

This is the **baseline expectation** when someone says "firewall" without further qualification.

---

### Application-layer firewalls

An **application-layer firewall** (also called a **proxy-based firewall** or **application-aware firewall**) operates at **OSI Layer 7** — it fully parses application protocols like HTTP, FTP, SMTP, and DNS, and enforces policy based on actual content.

- Can block specific HTTP methods, enforce URL filtering, detect protocol anomalies
- Catches attacks invisible to stateful firewalls: FTP PORT command injection, DNS zone transfer abuse, SMTP relay abuse, HTTP command injection
- **Tradeoff:** significantly more processing overhead than stateful inspection, because every session must be fully parsed

> 🔍 *Like a customs agent who actually opens and reads your packages, not just checks the label — far more thorough, but the line moves slower.*

---

### Next-Generation Firewalls (NGFWs)

A **NGFW** (Next-Generation Firewall) is the current state of the art — it includes stateful inspection as a baseline and adds several layers of deeper capability.

| NGFW Capability | What It Does |
|---|---|
| **Deep packet inspection** | Reads and analyzes payload content across all traffic, not just headers |
| **App-ID** (Application Identification) | Identifies the actual application generating traffic by behavioral signatures, not just port number |
| **User-ID** (User Identity Awareness) | Links traffic flows to authenticated users via **Active Directory** (Microsoft's directory service for managing user accounts and group memberships) or other identity providers |
| **IPS integration** | Built-in **Intrusion Prevention System** — applies signature matching and behavioral analysis inline |
| **SSL/TLS inspection** | Decrypts HTTPS traffic, inspects content, re-encrypts before forwarding |
| **Threat intelligence feeds** | Blocks known malicious IPs, domains, and file hashes automatically |
| **Cloud sandboxing** | Suspicious files are executed in an isolated cloud environment to catch zero-day malware |

**Why App-ID matters:** Modern apps routinely use port 80 or 443 for everything. A stateful firewall sees only "allowed HTTPS traffic." An NGFW can distinguish Netflix streaming from corporate VPN from encrypted exfiltration — on the same port.

**Why SSL inspection matters:** Without it, roughly 90% of modern internet traffic is opaque to security tools. The NGFW acts as a **man-in-the-middle** — decrypting, inspecting, re-encrypting.

> 🛂 *An NGFW is like an airport security checkpoint that knows who you are (User-ID), X-rays your bag's contents (DPI), recognizes what brand of laptop you're carrying (App-ID), and sends suspicious items to a lab before you board (sandboxing).*

**Common NGFW platforms:** Palo Alto Networks, Fortinet FortiGate, Cisco Firepower.

### Web Application Firewalls (WAFs)

A **WAF** (Web Application Firewall) is purpose-built to protect web applications from HTTP/HTTPS-layer attacks. It is deployed as a **reverse proxy** — a device that sits in front of web servers and receives all inbound connections before they reach the backend.

**What WAFs block:**

| Attack | How It Works |
|---|---|
| **SQL injection** | Malicious SQL code inserted into parameters, targeting the database behind the app |
| **Cross-site scripting (XSS)** | Malicious client-side scripts injected into content, executed in other users' browsers |
| **Cross-site request forgery (CSRF)** | Tricks an authenticated user into unknowingly submitting a request to an app they're logged into |
| **Application-layer DoS** | High volumes of valid HTTP requests that overwhelm web servers — network-layer defenses don't stop this |

**Two WAF security models:**

| Model | How It Works | Tradeoff |
|---|---|---|
| **Positive (allowlist)** | Defines what a valid request looks like — blocks anything that deviates | Strong against novel attacks; requires detailed app modeling |
| **Negative (blocklist/denylist)** | Maintains a database of known attack patterns, blocks matches | Easier to deploy; must be continuously updated |

**Compliance note:** **PCI DSS** (Payment Card Industry Data Security Standard — the compliance framework for handling payment card data) requirement 6.6 mandates either a WAF or a comprehensive code review for web apps handling card data.

**Common WAF platforms:** AWS WAF, Cloudflare WAF, **ModSecurity** (an open-source WAF engine) with the **OWASP Core Rule Set** (OWASP — Open Web Application Security Project, which publishes the widely-used rule set), Azure Application Gateway WAF.

> 🚪 *A WAF is a specialized doorman for your web app — the NGFW checks who's allowed into the building, but the WAF reads every letter before it reaches the web server's desk.*

---

### Unified Threat Management (UTM)

A **UTM** (Unified Threat Management) appliance bundles multiple security functions into a single device with one management interface.

**Typical UTM functions:** stateful firewall + IDS/IPS + VPN + antivirus + web content filtering + email anti-spam

- **Best fit:** smaller organizations without staff to operate multiple specialized products
- **Tradeoffs:**
  - Not best-of-breed in any single function
  - Performance degrades when multiple functions run simultaneously on high-traffic networks
  - Most UTMs operate only at Layer 4 — lacking the application-layer awareness of NGFWs

> 🧰 *A UTM is a Swiss Army knife — convenient for small jobs, but a chef still wants individual, purpose-built knives.*

**Common UTM vendors:** Fortinet FortiGate (small-business models), SonicWall, Sophos.

### Cloud firewall deployments

The transcript covers three distinct cloud firewall constructs:

**NGFW as a service** — Next-generation firewall capabilities delivered from cloud infrastructure, with no hardware to procure or manage. Traffic is redirected to cloud-hosted firewall instances for inspection. Relevant to **SASE** (Secure Access Service Edge — a cloud architecture that converges networking and security services) deployments.

**Security Groups** (AWS/Azure equivalents) — **Stateful** instance-level firewalls controlling which traffic reaches individual virtual machines or containers.
- Rules specify: source IP or security group, protocol, port
- Traffic not matching an allow rule is **implicitly denied**
- Return traffic for established connections is **automatically permitted** (stateful)

**Network ACLs** (AWS **VPC** — Virtual Private Cloud — subnet-level construct) — Apply at the **subnet** level, not the instance level. Unlike security groups, NACLs are **stateless**:
- Both inbound AND outbound rules must be explicitly defined
- Return traffic requires an explicit outbound rule
- Serve as a coarse additional filtering layer complementing security groups

| Construct | Level | Stateful? | Return Traffic |
|---|---|---|---|
| **Security Group** | Instance/container | ✅ Yes | Auto-permitted |
| **Network ACL** | Subnet | ❌ No | Must be explicitly allowed |

> ☁️ *Security groups are like per-apartment door locks in a building; NACLs are like a checkpoint at the building's entrance — less granular, but a useful extra layer, and you have to badge both ways.*

---

### Recap

- **Packet filtering** = fastest, stateless, weakest — can't detect crafted packets or fragmentation attacks
- **Stateful inspection** = baseline standard — blocks unsolicited inbound traffic by tracking the connection state table
- **NGFW** = stateful + DPI + App-ID + User-ID + IPS + SSL inspection + threat intel + sandboxing
- **WAF** = purpose-built for web app attacks (SQLi, XSS, CSRF); uses positive (allowlist) or negative (blocklist) models; required by PCI DSS 6.6
- **Cloud:** Security groups are stateful (instance-level); NACLs are stateless (subnet-level) — both rules must be explicit

---

### Exam flags

- **Stateful vs. stateless** distinctions — especially why packet filters can't block crafted ACK packets, and why AWS NACLs require explicit outbound rules while security groups do not
- **NGFW capabilities** — expect questions requiring you to match a requirement (e.g., "block traffic by user identity" or "inspect encrypted traffic") to the correct feature (User-ID, SSL inspection)
- **WAF vs. NGFW** — WAF protects web applications specifically (SQLi, XSS, CSRF); NGFW protects network segments broadly — know which fits which scenario
