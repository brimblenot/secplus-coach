## Hardware Vulnerabilities

Hardware vulnerabilities operate at or below the OS level, making them uniquely difficult to patch, detect, or remove. This lesson covers the major categories the Security+ exam tests: firmware risks, end-of-life hardware, hardware trojans, side-channel attacks, Spectre/Meltdown, and physical interface threats.

---

### Firmware vulnerabilities

**Firmware** is low-level software stored in non-volatile memory (memory that retains data without power) that initializes and controls hardware components before the OS loads. The **BIOS** (Basic Input/Output System) and its modern successor **UEFI** (Unified Extensible Firmware Interface) are the most common examples, but firmware also lives in NICs, storage controllers, routers, cameras, and IoT devices.

- Firmware runs *below* the OS — a **rootkit** (persistent malware that hides itself) or **bootkit** (malware that infects the boot process) embedded in UEFI survives even a full hard-drive wipe and OS reinstall, because the malicious code lives in the motherboard's flash memory.
- Firmware can disable **Secure Boot** (a UEFI feature that verifies bootloader integrity before launching it) or silently modify the boot process before the OS loads.
- Patch cadence is dramatically slower — one thermostat vendor took a full year to release its first firmware patch after notification.

> Think of firmware like the wiring inside your walls: you can renovate the whole interior of a house (reinstall the OS) and the faulty wiring is still there, hidden and untouched.

### End-of-life vs. end-of-service-life hardware

**End-of-life (EOL)** is a manufacturer's notice that a product will no longer be sold. Security patches may still arrive for some time after EOL.

**End-of-service-life (EOSL)** is the harder cutoff: the manufacturer explicitly stops releasing security updates. Any vulnerability discovered after EOSL will **never be officially patched**.

| Milestone | Sales continue? | Security patches continue? |
|---|---|---|
| End-of-life | No | Yes (for a limited period) |
| End-of-service-life | No | **No — permanently** |

- EOSL is especially risky in embedded systems, medical devices, and industrial/network equipment that may run for decades.

> An EOSL device is like a car whose manufacturer shut down: you can still drive it, but no recall notices or safety fixes will ever arrive.

---

### Legacy hardware

**Legacy hardware** is equipment designed before modern security requirements existed. It may lack hardware encryption, not support current security protocols, and have insecure behaviors hardwired into the silicon — things no software update can fix.

- Industrial control systems (**ICS**), **SCADA** (Supervisory Control and Data Acquisition) networks, and **OT** (Operational Technology) environments commonly run hardware with 20–30-year lifecycles.
- When replacement is infeasible, organizations use **compensating controls** — network segmentation, additional firewall rules, and intrusion prevention signatures — to reduce (not eliminate) risk.

### Hardware trojans

A **hardware trojan** is a malicious modification to a chip or circuit board introduced during manufacturing or somewhere in the supply chain before delivery.

- It is physically embedded — not software — so it cannot be removed with a patch.
- Capabilities include hardware backdoors for data exfiltration, kill switches that disable equipment on command, or covert communication channels.
- Detection without destructive testing or highly specialized lab equipment is essentially impossible for a typical organization.
- Considered a nation-state level threat, but complex multi-tier supply chains make it relevant to high-assurance environments.

> A hardware trojan is like a listening device soldered onto a circuit board at the factory — it arrives looking perfectly normal and no OS scan will ever find it.

### Side-channel attacks

A **side-channel attack** extracts secret information not by breaking a cryptographic algorithm directly, but by measuring physical characteristics produced as a *side effect* of the hardware's operation.

| Attack type | What it measures |
|---|---|
| **Timing attack** | How long cryptographic operations take (key bits can cause measurable time differences) |
| **Simple power analysis (SPA)** | Electrical power consumed during a single operation |
| **Differential power analysis (DPA)** | Statistical correlation across thousands of power measurements to extract key material |
| **Electromagnetic (EM) analysis** | RF emissions from chips — same information as power analysis, no physical contact needed |
| **Cache-timing attack** | CPU cache hit/miss latency differences — lets one process infer what data another process is accessing |

> A side-channel attack is like figuring out someone's ATM PIN by watching how long they pause between button presses — you never see the screen, but the timing tells you plenty.

### Spectre and Meltdown

Both vulnerabilities, disclosed in January 2018, exploit **speculative execution** — a CPU performance feature where the processor pre-executes instructions along a predicted path before knowing whether they're actually needed. If the prediction is wrong, results are discarded, but crucially, **effects on the CPU cache are not fully reversed**, creating an information leak exploitable by cache-timing.

| | **Meltdown** | **Spectre** |
|---|---|---|
| CVE | CVE-2017-5754 | CVE-2017-5753, CVE-2017-5715 |
| What it does | User-space process reads **kernel memory** | Manipulates branch prediction to leak data from *other processes* via shared cache |
| Processors affected | Primarily Intel | Intel, AMD, and ARM |
| Software mitigation | **KPTI** (Kernel Page-Table Isolation — separates kernel and user memory maps) — with a performance penalty | Microcode updates + compiler changes + browser mitigations; *not fully eliminated* |

- **Kernel memory** is the protected memory space used by the OS; user-space processes should never be able to read it.
- **Microcode** is firmware embedded inside the CPU itself that controls how instructions execute.

> Spectre and Meltdown are like a bank teller who briefly glances at a restricted file while preparing your transaction — they put it away immediately, but you can infer what was in it from how long they hesitated.

### JTAG and physical interface attacks

The **JTAG interface** (standardized by the Joint Test Action Group) is a hardware debugging port built into most modern chips, originally designed for manufacturing testing.

- Provides direct access to processor registers, memory, and peripherals — a complete bypass of all software security controls.
- An attacker with physical access to an enabled JTAG port can read/write arbitrary memory, extract encryption keys, and modify firmware.
- **Mitigation:** disable, password-protect, or physically destroy JTAG ports on production devices.

---

### DMA attacks and Rowhammer

**DMA (Direct Memory Access)** is a hardware feature that lets peripherals read and write system RAM directly, without CPU involvement, for high-bandwidth performance. Interfaces like Thunderbolt and PCIe use it.

- A malicious device plugged into a DMA-capable port can access kernel memory and install rootkits with no OS-level detection.
- **IOMMU** (Input-Output Memory Management Unit) mitigates this by restricting which physical memory regions each DMA device can access. It must be enabled in system firmware.

**Rowhammer** is a DRAM (Dynamic RAM) attack that exploits the physical layout of high-density memory chips.

- Rapidly and repeatedly reading specific DRAM rows causes electrical disturbance in adjacent rows, inducing **bit flips** (a 0 becomes a 1, or vice versa).
- Strategic bit flips in page tables or other security-critical data structures can achieve **privilege escalation** (gaining higher system permissions than authorized) with no software vulnerability.

> A DMA attack is like handing a delivery driver a master key to the warehouse so they can move boxes faster — convenient, but now that driver can open every room without asking.

### Defenses

- **Hardware inventory and lifecycle management** — track every device's firmware version and EOSL date.
- **Firmware update management** — apply vendor patches promptly.
- **Supply chain verification and TPM attestation** — **TPM** (Trusted Platform Module, a dedicated security chip) takes measurements of firmware at boot to detect tampering.
- **Secure Boot with TPM** — validates firmware integrity before the OS loads.
- **Disable unused physical interfaces** — JTAG, unused USB, serial ports.
- **Enable IOMMU** — restricts DMA device access to system RAM.
- **Physical security** — locked equipment rooms, tamper-evident seals, access logging.

---

### Recap

- Firmware vulnerabilities survive OS reinstallation because the malicious code lives in hardware flash memory, not on the drive.
- EOSL (not just EOL) is the critical milestone — after EOSL, vulnerabilities in that hardware will never receive an official patch.
- Spectre and Meltdown exploit speculative execution; both leak data via CPU cache-timing side channels.
- Side-channel attacks target physical signals (timing, power, EM) rather than the algorithm itself.
- IOMMU mitigates DMA attacks; disabling/destroying JTAG ports removes that physical attack vector.

---

### Exam flags

- **Spectre vs. Meltdown** — be ready to distinguish which affects which processor families, what each leaks (kernel memory vs. cross-process data), and that both exploit speculative execution via cache-timing.
- **End-of-service-life** — know that EOSL means *no future patches ever*, and that compensating controls (segmentation, IPS signatures) are the organizational response when replacement is infeasible.
- **Side-channel attack categories** — be able to identify timing, power analysis (SPA vs. DPA), electromagnetic, and cache-timing attacks by what physical characteristic each one measures.
