## Resiliency (Domain 3)

Resiliency is about keeping systems available when things go wrong — hardware fails, disasters strike, attackers disrupt services. This lesson covers the key technologies and designs that let organizations absorb failures and keep operating.

---

### RAID: disk-level redundancy

**RAID** — Redundant Array of Independent Disks — is a technology that combines multiple physical drives to achieve redundancy, better performance, or both. Different RAID *levels* make different trade-offs.

| Level | Name | Min Drives | Redundancy | Performance | Capacity Cost |
|---|---|---|---|---|---|
| **RAID 0** | Striping | 2 | ❌ None — one drive fails, all data lost | Best read/write | 0% overhead |
| **RAID 1** | Mirroring | 2 | ✅ Full copy on each drive | Better reads, same writes | 50% overhead |
| **RAID 5** | Striping + distributed parity | 3 | ✅ Survives 1 drive failure | Good balance | 1 drive lost to parity |
| **RAID 6** | Striping + double parity | 4 | ✅ Survives 2 simultaneous failures | Slower writes than RAID 5 | 2 drives lost to parity |
| **RAID 10** | Mirror + stripe (1+0) | 4 | ✅ Survives multiple failures (not both in a pair) | Best combined | 50% overhead |

**Key details:**
- **Parity** — mathematically derived redundancy data; lets the array reconstruct a missing drive's content without storing a full copy
- RAID 5's weakness: large drives take 12+ hours to rebuild; a second failure during that window destroys the array — RAID 6 solves this
- RAID 0 is *worse* than a single drive for reliability: any one of *N* drives can cause total loss

> 🔁 Think of RAID 1 as keeping two identical paper copies of a contract — if one burns, you still have everything. RAID 0 is shredding one contract across two folders for speed, but losing either folder loses the whole document.

**Hot spare** — a spare drive sitting idle inside the array that automatically starts rebuilding the moment a failure is detected, minimizing the window the array spends in a vulnerable, degraded state.

### Geographic dispersion and site models

**Geographic dispersion** means spreading infrastructure across physically separate locations so a regional disaster (hurricane, power outage) can't take everything offline at once. **Multi-region** deployments spread across regions within one cloud provider; **multi-cloud** deployments spread across different providers entirely.

Two operational models for dispersed sites:

| Model | Both sites active? | Failover speed | Resource cost |
|---|---|---|---|
| **Active-active** | ✅ Yes — both serve live traffic | Fastest (already warm) | Higher — full duplication |
| **Active-passive** | ❌ No — secondary is standby | Slower (must activate first) | Lower — secondary sits idle |

**Replication** keeps secondary sites current:

- **Synchronous replication** — write is confirmed at *both* sites before the app gets an acknowledgment; zero data loss, but adds latency
- **Asynchronous replication** — write is acknowledged at the primary immediately, then sent to the secondary; lower latency but a failure during the lag window can lose recent data

### Disaster recovery site types

**Disaster recovery sites** — physically separate facilities used when the primary site fails entirely.

| Site type | Hardware ready? | Data current? | Activation time | Cost |
|---|---|---|---|---|
| **Hot site** | ✅ Fully configured | ✅ Continuously synced | Minutes–hours | Highest |
| **Warm site** | ✅ Hardware present, partial config | ⚠️ May lag | Hours–days | Medium |
| **Cold site** | ❌ Just power/cooling/space | ❌ Must restore from backup | Days–weeks | Lowest |

> A hot site is like a rental car already running in the parking lot. A cold site is like being told "there's an empty lot across town — go find a car."

### High availability and load balancing

**High availability (HA) clustering** — multiple server *nodes* — individual server instances — act as one logical system. If one node fails, surviving nodes absorb its workload automatically. Most HA clusters use **shared storage** so any node always sees the same data.

**Load balancing** distributes incoming requests across multiple servers using algorithms like round-robin, least-connections, or weighted distribution. Load balancers run continuous **health checks**; a failing server is automatically removed from the pool and traffic reroutes — users notice nothing.

### Platform diversity and failover

**Platform diversity** — using different OSes, vendors, or technology stacks for different components. A vulnerability specific to Windows won't compromise the Linux servers running the same function. This limits **blast radius** — how far a single exploit can spread — at the cost of more complex management.

**Failover** — switching production from a failed primary to a backup:
- **Automatic failover** — triggered by health monitoring with no human needed; fastest, but needs careful design to avoid *false positives* (failing over a healthy system unnecessarily)
- **Manual failover** — a human evaluates and decides; more control, but slower

---

### Recap
- RAID 0 = performance, zero redundancy; RAID 1 = full mirror; RAID 5 = 1 parity drive equivalent; RAID 6 = 2 parity, survives rebuild failures; RAID 10 = best performance + redundancy, 50% capacity cost
- Hot/warm/cold sites trade cost for activation speed; hot = minutes, cold = days to weeks
- Active-active serves traffic at both sites simultaneously; active-passive keeps the secondary in standby
- Synchronous replication = zero data loss + latency; asynchronous = lower latency + possible data loss on failure
- Platform diversity limits blast radius by ensuring not all systems share the same vulnerabilities

### Exam flags
- **RAID level trade-offs** — expect scenario questions asking which RAID level is appropriate given redundancy, capacity, or performance requirements
- **Hot vs. warm vs. cold site** — know the activation time and cost differences; likely tested via scenario ("organization needs recovery within 2 hours — which site type?")
- **Active-active vs. active-passive** — know which provides faster failover and why (secondary is already handling traffic vs. must be activated first)
