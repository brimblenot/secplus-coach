## Replay Attacks

Replay attacks let an attacker reuse captured credentials — no cracking required. This lesson covers how replay attacks work, their most dangerous variants in Windows and Kerberos environments, and the mechanisms that stop them.

---

### What makes a replay attack unique

A **replay attack** occurs when an attacker captures valid authentication data — session tokens, password hashes, Kerberos tickets — transmitted over the network, then retransmits that data later to gain unauthorized access.

- The captured data is **cryptographically legitimate**; the attacker doesn't break encryption or forge anything
- The attacker doesn't need to be on the network path during the attack — capture once, replay from anywhere, anytime
- Common capture methods: **network tap** (physical wire intercept), **ARP poisoning** (redirecting traffic through the attacker's machine), or **malware** that grabs credentials before/after encryption

> Think of it like photocopying someone's signed check — you didn't forge their signature, you just re-use the real one.

---

### Pass-the-hash (Windows / NTLM)

**NTLM** — **NT LAN Manager**, Microsoft's legacy challenge-response authentication protocol used for network resource access — uses the user's **password hash** directly as the authentication credential. The hash is never sent in cleartext, but it doesn't need to be: knowing the hash is functionally identical to knowing the password.

**Pass-the-hash** is a replay attack where an attacker uses a stolen NTLM hash to authenticate without ever knowing the plaintext password.

- **LSASS** — **Local Security Authority Subsystem Service**, the Windows process that stores credential material in memory — is the extraction target
- **Mimikatz** — a widely used credential-dumping tool — reads NTLM hashes straight from LSASS memory
- **hashdump** in **Metasploit** (a penetration testing framework) provides similar extraction capability
- Enables **lateral movement** — authenticating to other workstations, servers, and services across the domain, expanding access progressively

> It's like finding a copy of a master keycard in someone's desk drawer — you never had to pick the lock; you just use the copy.

---

### Pass-the-ticket (Kerberos)

**Kerberos** is an authentication protocol that issues **tickets** — cryptographically signed tokens — instead of sending passwords. The **KDC** (**Key Distribution Center**) issues a **TGT** (**Ticket Granting Ticket**) after initial login; the client uses the TGT to request **service tickets** for specific resources without re-entering credentials.

**Pass-the-ticket** extracts a TGT or service ticket from a compromised machine's memory and imports it into the attacker's session to authenticate as that user.

| Variant | What's stolen | Scope of access |
|---|---|---|
| **Pass-the-ticket** | TGT or service ticket | Resources the original user could reach, until ticket expires |
| **Golden Ticket** | NTLM hash of the **KRBTGT** account (the special Kerberos account whose key signs all TGTs) | Forge TGTs for *any* user, including domain admins, arbitrary validity period |
| **Silver Ticket** | Service account's NTLM hash | Forge tickets for *one specific service*, no DC interaction needed |

- Golden Tickets are extremely hard to eliminate — the KRBTGT password must be **changed twice in succession** to invalidate forged tickets

> A Golden Ticket is like stealing the bank's master seal — you can stamp any document you like and it looks official.

---

### How Kerberos fights replay

Kerberos has built-in anti-replay controls:

- **Timestamps** — every request must fall within a **±5-minute clock skew window**; older replays are rejected
- **Authenticator tracking** — the KDC keeps a list of recently seen authenticators and rejects duplicates within the window

---

### Broader anti-replay mechanisms

| Mechanism | How it works |
|---|---|
| **Nonce** — a number used exactly once, generated fresh by the server each session | Client must embed the current nonce in its response; old captures lack the right nonce |
| **Timestamps** | Request must include a current time value within an acceptable window |
| **Sequence numbers** | Packets are numbered monotonically; duplicates or out-of-order packets are dropped |
| **Challenge-response** | Server issues a fresh random challenge each authentication; captured responses only match the challenge that produced them |
| **Short-lived tokens** | Expiration limits how long a stolen token is useful |

### Web tokens and TLS

**Bearer tokens** — named because *any bearer* of the token gets access, with no binding to the original client — are common replay targets in APIs and OAuth flows. Capturing one from an `Authorization` HTTP header lets an attacker call any endpoint that token permits.

- **Token binding** — cryptographically ties a token to a specific TLS connection so it can't be used from a different one
- **PKCE** (**Proof Key for Code Exchange**) — an OAuth extension that prevents authorization codes from being intercepted and replayed
- **JWT** (**JSON Web Token**) **algorithm confusion attack**: an attacker changes the signing algorithm field from `RS256` (asymmetric) to `HS256` (symmetric — HMAC-based) and uses the server's public key as the HMAC secret, forging tokens if the server blindly trusts the algorithm the token declares

**TLS 1.3** includes anti-replay protection for **zero-round-trip resumption** (session ticket reuse). **WPA2 TKIP** (**Temporal Key Integrity Protocol**, the early WEP replacement) had known replay vulnerabilities; **CCMP** (**Counter Mode with Cipher Block Chaining Message Authentication Code Protocol**, AES-based) replaced it with per-packet sequence numbers.

---

### Defenses

- **Credential Guard** — stores credentials inside an isolated **Hyper-V** (Microsoft's hypervisor) container inaccessible to the main OS kernel, blocking Mimikatz from reading LSASS memory
- **Protected Users** security group in Active Directory — disables NTLM entirely for member accounts and limits Kerberos ticket lifetimes
- **MFA** — even if an attacker replays a valid hash, they can't satisfy a physical token or biometric factor
- **EDR** (**Endpoint Detection and Response**) — monitors for anomalous LSASS memory access patterns consistent with Mimikatz
- **Network segmentation** — limits which systems an attacker can reach to replay stolen credentials
- Short-lived session tokens over HTTPS with `Secure` and `HttpOnly` cookie flags

---

### Recap

- Replay attacks reuse **legitimate captured data** — no cracking or forgery needed
- **Pass-the-hash** exploits NTLM: the hash *is* the credential; stolen via Mimikatz from LSASS memory
- **Golden Ticket** = own the KRBTGT hash = forge TGTs for anyone, indefinitely
- Anti-replay tools: **nonces**, **timestamps**, **sequence numbers**, **challenge-response**, **short-lived tokens**
- **Credential Guard** and **Protected Users** group are the primary Windows-specific mitigations

### Exam flags

- **Pass-the-hash vs. pass-the-ticket** — know which protocol each targets (NTLM vs. Kerberos) and what is extracted
- **Golden Ticket** — know what makes it severe (KRBTGT hash, arbitrary user/validity, must rotate KRBTGT twice to remediate)
- **Anti-replay mechanisms** — be able to match nonces, timestamps, and sequence numbers to what attack they prevent
