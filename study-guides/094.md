## Monitoring Data

Security monitoring is only as good as the data feeding it. This lesson covers every major source of monitoring data — network flows, packet captures, logs, endpoint telemetry, and metadata — and explains how each one is collected, what it reveals, and how defenders use it to detect real attacks.

---

### Network flow data

**NetFlow** is a Cisco-developed protocol that exports summary records of IP traffic from routers and switches. Each record captures: source/destination IP, source/destination port, protocol, bytes transferred, packet count, and start/end timestamps — but **no payload content**, only metadata about the flow.

**IPFIX** — *Internet Protocol Flow Information Export* — is the vendor-neutral standards-based equivalent of NetFlow; same flow data, no Cisco dependency.

**sFlow** — *sampled flow* — captures only 1 out of every N packets instead of every flow, trading some precision for dramatically lower overhead on high-throughput links.

| Flow type | Captures every flow? | Payload? | Best for |
|---|---|---|---|
| NetFlow | Yes | No | Cisco environments |
| IPFIX | Yes | No | Vendor-neutral deployments |
| sFlow | No (sampled) | No | Very high-speed links |

**What flow data reveals:**

- **Port scans** — one source IP → many destination ports/hosts
- **Data exfiltration** — unusually large outbound transfers to external IPs
- **C2 beaconing** — regular, periodic outbound connections to the same external IP
- **Lateral movement** — a workstation making many SMB connections to internal servers

Flow data also enables **baselining** — learning what normal traffic patterns look like so deviations stand out.

> Think of NetFlow like your phone bill: it shows who you called, when, and for how long — but not what you said.

### Full packet capture

**Full packet capture** records every packet in its entirety — headers *and* payload — giving a complete forensic record of all communications. It allows session reconstruction, file extraction, and credential recovery if unencrypted protocols are in use. The tradeoff: enormous storage requirements.

- **Wireshark** — GUI tool for capturing and analyzing packets on a local interface
- **tcpdump** / **tshark** — command-line capture and filtering tools
- **NetWitness, ExtraHop, Arkime** (formerly Moloch) — enterprise platforms that index full captures so analysts can search them with queries rather than reading raw files

> Full packet capture is the security equivalent of a dashcam with audio — you get everything, but the storage bill is real.

---

### Deep packet inspection (DPI)

**DPI** — *deep packet inspection* — is the technique of reading packet **payload content**, not just headers. Used by next-generation firewalls, **IPS** (*intrusion prevention systems* — devices that detect and actively block malicious traffic), and web proxies.

- Identifies applications even on non-standard ports
- Detects malware signatures inside file transfers
- Enables granular content-policy enforcement
- Raises privacy concerns because it exposes user content

### Log data: network devices

**Syslog** is the standard logging protocol for network devices (routers, switches, firewalls, wireless controllers).

- Transport: UDP or TCP on **port 514**; encrypted via **TLS** — *Transport Layer Security, the protocol that encrypts data in transit* — on **port 6514**
- Severity levels 0–7 (0 = most severe):

| Level | Name |
|---|---|
| 0 | Emergency |
| 1 | Alert |
| 2 | Critical |
| 3 | Error |
| 4 | Warning |
| 5 | Notice |
| 6 | Informational |
| 7 | Debug |

### Log data: Windows Event Logs

Windows records security activity in three logs: **Security**, **System**, and **Application**. Key **Event IDs** to memorize:

| Event ID | Meaning |
|---|---|
| 4624 | Successful logon |
| 4625 | Failed logon |
| 4648 | Logon using explicit credentials |
| 4672 | Special privileges assigned to logon |
| 4688 | New process created |
| 4698 | Scheduled task created |
| 4720 | User account created |
| 4732 | User added to security group |

---

### Log data: Linux logs

Linux logging lives in **/var/log**:

- **auth.log / secure** — SSH logins, sudo/su use, PAM authentication
- **syslog / messages** — general system events
- **kern.log** — kernel events
- **audit/audit.log** — detailed kernel-level events when **auditd** (the Linux kernel audit daemon) is configured

---

### Application and cloud logs

**Web server logs** (Apache/nginx) use **Combined Log Format** — recording client IP, timestamp, HTTP method, URL, response code, bytes, Referer header, and User-Agent string. This lets analysts reconstruct every request and spot scanning or exploitation.

**Database query logs** record which queries ran, by which user, when, and against which tables. Required by **PCI DSS** — *Payment Card Industry Data Security Standard, the compliance framework for environments that handle cardholder data* — and essential for detecting SQL injection.

**AWS CloudTrail** — logs every API call to AWS services: caller identity, time, source IP, resource affected. **Azure Activity Log** and **GCP Cloud Audit Logs** provide equivalent coverage on their platforms.

### Security-specific telemetry

**EDR** — *Endpoint Detection and Response* — agents installed on every endpoint produce continuous telemetry: process creation trees, file system operations, network connections per process, and registry modifications.

Traditional **antivirus** only matches files against known malicious signatures at the moment of execution and keeps no ongoing record of activity — so it cannot look back at what happened. EDR records everything continuously, enabling **threat hunting**: querying historical endpoint data across the entire fleet (e.g., "show all systems where PowerShell spawned a network connection in the last 30 days").

**DNS query logs** record every domain resolved by every client. Valuable because nearly all malware communicates via DNS — detects **DGA** (*domain generation algorithm* — malware technique that auto-generates many random-looking domains to find its C2 server), connections to known-malicious domains, and DNS tunneling.

**Web proxy logs** capture full URLs (including query parameters) for HTTP and hostnames for HTTPS — revealing malware downloads, shadow IT, and web-based exfiltration.

### SIEM aggregation and log storage

A **SIEM** — *Security Information and Event Management system* — ingests all these sources, normalizes them into a common schema, and enables cross-source correlation.

**CEF** — *Common Event Format* — and **LEEF** — *Log Event Extended Format* — are standardized schemas that security products use so a SIEM can parse events consistently regardless of source.

Log retention tiers:

| Tier | Access speed | Typical window | Use |
|---|---|---|---|
| Hot storage | Immediate | 30–90 days | Active SIEM queries |
| Warm storage | Slower | 6–12 months | Compliance, investigations |
| Cold storage | Slowest | Years | Regulatory archival |

---

### Metadata analysis

**Metadata** — information *about* communications (who, when, how long, how often, how much data) rather than the content itself — can be as revealing as the content. A user who accesses a file server at 3 AM and then sends a large outbound transfer to an unknown IP reveals suspicious behavior through metadata alone, even if every packet is encrypted.

> Your envelope reveals your secret even if your letter is sealed: the address, the timing, and the weight tell the story.

### Sensor placement

Where a sensor sits determines what it can see:

**SPAN port** (also called a *mirror port*) — a managed-switch feature that copies traffic from specified interfaces to a monitoring port. The sensor sees traffic passively without being in the forwarding path. Can be accidentally disabled by switch misconfiguration and adds processing load to the switch.

**Network tap** — a passive hardware device that physically splits the signal on a link, sending a copy to the sensor while original traffic flows unimpeded. Preferred over SPAN ports for critical monitoring because it cannot be disabled by switch config errors and imposes zero switch overhead.

**Inline sensor** — sits directly in the network path; all traffic must pass through it. Required for blocking (as in an IPS), but introduces latency and is a potential single point of failure if it malfunctions.

| Placement | Can block traffic? | Fails safe? | Switch overhead? |
|---|---|---|---|
| SPAN port | No | Yes | Yes |
| Network tap | No | Yes | No |
| Inline sensor | Yes | No (single point of failure) | No |

---

### Recap

- **NetFlow/IPFIX** capture flow metadata (no payload); **sFlow** samples for high-speed links; full packet capture gets everything but costs storage
- **Syslog** uses port 514 (unencrypted) or 6514 (TLS); severity 0 = most severe, 7 = Debug
- Windows Event IDs 4624/4625 (logon success/fail), 4688 (process creation), and 4720/4732 (account/group changes) are the most security-critical
- **EDR** telemetry enables historical threat hunting that antivirus cannot, because antivirus only checks at execution time with no ongoing record
- Network taps are preferred over SPAN ports for critical monitoring because they are hardware-passive and cannot be disabled by switch config errors

### Exam flags

- **Syslog port numbers and severity levels** — expect questions pairing a scenario (e.g., "encrypted syslog transport") with the correct port (6514) or severity number
- **Windows Event IDs** — questions give a scenario (e.g., attacker created a new admin account) and ask which Event ID would appear; know the full list above
- **NetFlow vs. full packet capture vs. DPI** — questions distinguish what each captures (metadata only vs. full payload) and in which scenario each is the right tool
