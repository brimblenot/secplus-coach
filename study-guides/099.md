## Password Security

Password policies and storage mechanisms are two sides of the same coin: a strong policy means nothing if a database breach hands attackers a list of crackable hashes, and strong storage means nothing if users pick "Password1!" every 90 days. This lesson covers both sides end-to-end.

---

### Password policy: length over complexity

**Password policy** is the set of rules an organization enforces on how passwords must be constructed.

- **Length** is the single most important factor — longer passwords grow entropy exponentially, making brute-force search impractical.
- **NIST SP 800-63B** — NIST Special Publication 800-63B, the authoritative federal guidance on digital identity — recommends a minimum of 8 characters and allowing up to at least 64.
- Sensitive systems should target 15+ characters in practice.
- **Passphrases** — sequences of multiple random words (e.g., "correct-horse-battery-staple") — achieve length and memorability simultaneously.

> Think of a passphrase like a combination lock with five tumblers instead of three: every extra word multiplies the search space, not just adds to it.

---

### Why complexity requirements backfire

**Complexity requirements** mandate mixtures of uppercase, lowercase, numbers, and special characters. Research (and NIST 800-63B) now recommends *against* rigid complexity rules because they produce predictable user behavior.

- Users respond to complexity mandates with patterns: capitalize first letter, append a number, add "!" at the end → **Password1!**
- Once an attacker models that pattern, complexity provides almost no protection.
- NIST prefers: require *length*, prohibit *commonly used or compromised passwords*.

**Prohibiting compromised passwords** is one of the most effective controls available. The **HaveIBeenPwned (HIBP)** database — maintained by security researcher Troy Hunt and containing billions of credentials from historical breaches — can be queried at account creation to reject any password already in attackers' wordlists, regardless of how "complex" it looks.

> Complexity requirements are like telling people their locker combination must contain a capital letter — they all just put it first.

---

### Password expiration: stop the 90-day treadmill

**Password expiration policy** sets how often users must change their passwords. Traditional 90-day rotation is now considered counterproductive.

- Forced rotation causes *minimal changes*: users increment a trailing number or cycle through a small set.
- Users also write passwords down to cope.
- **NIST 800-63B recommendation:** do NOT force periodic expiration — only require immediate change when compromise is *known or suspected*.

---

### Account lockout: slowing online attacks

**Account lockout policy** limits consecutive failed login attempts to block **online brute-force** (trying many passwords rapidly against one account) and **password spraying** (trying one common password across many accounts).

| Parameter | What it controls | Typical value |
|---|---|---|
| **Lockout threshold** | Consecutive failures before lockout | 3–10 attempts |
| **Observation window** | Time period failures are counted within | 10–30 minutes |
| **Lockout duration** | How long the account stays locked | 15–30 min (auto) or admin-reset |

- **Auto-unlock** after a timer reduces admin overhead but creates a DoS risk if an attacker deliberately locks accounts.
- **Password history** stores hashes of the last 10–24 passwords and rejects reuse.
- **Minimum password age** prevents users from cycling through history immediately to get back to their old password.

---

### Password managers: the practical fix for humans

**Password managers** solve the core human problem: people can't memorize dozens of long, unique passwords, so they reuse — enabling **credential stuffing attacks** (using one breached credential to log into other sites).

- Generates long, cryptographically random, unique passwords per site.
- Stores them in an encrypted vault (typically **AES-256** — 256-bit Advanced Encryption Standard, the symmetric cipher used by the vault).
- User accesses the vault with one **master password** or biometric.
- **Anti-phishing benefit:** the autofill function checks the actual domain and will not fill credentials on a lookalike phishing page with a different domain.
- Enterprise options: **1Password Teams, Bitwarden Business, Keeper Business, LastPass Business** — add audit logging and policy enforcement.
- **KeePass** — open-source, offline password manager for users who don't want a cloud-hosted vault.

> A password manager is like a bank vault for keys: you remember one combination, and it holds every other key securely inside.

---

### Password hashing and storage

**Password hashing** is the process of running a password through a one-way cryptographic function before storage so the plaintext is never saved. If the database is breached, attackers get hashes, not passwords.

**Why fast hashes fail:**

- **MD5** and **SHA-1** — general-purpose hash functions designed for *speed* — let attackers test billions of guesses per second with GPU hardware.
- **Rainbow table attacks** precompute hashes for millions of common passwords; an attacker just looks up the hash to find the password instantly.

**Salting** defeats rainbow tables. A **salt** is a unique random value added to each user's password *before* hashing. The salt is stored alongside the hash. Because each user's salt differs, identical passwords produce different hashes, and precomputed tables are useless.

**Purpose-built password hashing algorithms** are *deliberately slow*, making brute force expensive even with salting in place:

| Algorithm | Key property |
|---|---|
| **Bcrypt** | Based on Blowfish cipher; auto-salts; configurable **work factor** (cost parameter) that doubles computation time per increase |
| **Scrypt** | **Memory-hard** — requires large RAM per attempt, limiting GPU parallelism because GPUs have little per-core memory |
| **Argon2id** | Winner of the 2015 Password Hashing Competition; combines GPU resistance and side-channel resistance; recommended for new systems; tunable iteration count, memory, and parallelism |

- **Argon2i** — optimized against **side-channel attacks** (attacks that infer secrets from timing or power consumption rather than cracking the hash directly)
- **Argon2d** — optimized for GPU resistance
- **Argon2id** — combines both; recommended for general use

> Bcrypt is like a vault door with a deliberate time-delay lock: even with perfect tools, you can only try so many combinations per hour.

---

### Passwordless and privileged account management

**Passwordless authentication** eliminates the password from the login flow entirely.

- **FIDO2 passkeys** — store a cryptographic key pair on the user's device; authenticate via device biometric or PIN; are phishing-resistant because the key is bound to the legitimate domain.
- **Magic links** — single-use tokens delivered via email; expire quickly; security depends on the user's email account.

**PAM (Privileged Access Management)** solutions vault passwords for shared admin accounts in enterprise environments.

- Rotates passwords **automatically after each use** — no individual ever knows the current credential.
- Admins work through a **session proxy** — they use the account without seeing the actual password.
- Prevents reuse of harvested privileged credentials.

---

### Recap

- **Length beats complexity** — NIST recommends minimum 8 characters, discourages mandatory complexity rules.
- **Compromised-password screening** (HIBP) is more effective than complexity mandates.
- **Do not force periodic expiration** — change only on known/suspected compromise.
- **Fast hashes (MD5, SHA-1) + no salt = catastrophic breach**; use Argon2id, Bcrypt, or Scrypt with salting.
- **Password managers** fix credential reuse and provide domain-aware anti-phishing autofill.

### Exam flags

- NIST 800-63B positions: length over complexity, no mandatory expiration, screen against breached-password lists.
- The difference between MD5/SHA-1 (fast, unsuitable) and Bcrypt/Scrypt/Argon2id (slow, memory-hard, suitable) for password storage.
- How salting defeats rainbow table attacks and why it alone isn't enough against GPU brute force.
