## Secure Protocols (Domain 4)

Every protocol on a network either protects data in transit or exposes it. This lesson maps the insecure-vs-secure protocol pairs you must know for Security+: what each protocol does, what it protects (or doesn't), and the port numbers that tie it all together.

---

### Web protocols: HTTP vs. HTTPS

**HTTP** — HyperText Transfer Protocol — is the protocol web browsers use to request and receive web pages. It operates on **port 80** and sends everything in plaintext: URLs, form submissions, cookies, and response bodies are all readable by anyone capturing traffic on the network path.

- Enables passive eavesdropping, session hijacking via cookie theft, and in-transit content manipulation.

**HTTPS** — HTTP transported over **TLS** (Transport Layer Security, the encryption layer that wraps the connection) — runs on **port 443**.

- Encrypts all request and response content so network observers see only ciphertext.
- Authenticates the server via a **certificate** (a signed digital credential) validated against the client's trusted **certificate authority** (CA) store — proving the server is who it claims to be, blocking impersonation.

> Think of HTTP as sending a postcard anyone can read; HTTPS seals it in an envelope that only the recipient can open, with a verified return address.

---

### File transfer protocols: FTP, SFTP, FTPS

**FTP** — File Transfer Protocol — uses **ports 20 and 21** and sends credentials and file content in cleartext. Any captured traffic exposes usernames, passwords, and every file transferred.

**SFTP** — SSH File Transfer Protocol — runs on **port 22** as a subsystem of SSH (Secure Shell, an encrypted remote-access protocol). Despite the similar name, SFTP is a completely different protocol from FTP — it uses the SSH protocol family, not FTP commands.

- Encrypts all data inside the SSH tunnel; supports public key authentication.

**FTPS** — FTP over TLS — is actual FTP protected by a TLS layer. It is a different protocol from SFTP even though the names look similar.

| Mode | Port | How TLS starts |
|---|---|---|
| Explicit (STARTTLS) | 21 | Begins unencrypted; client issues STARTTLS command to upgrade |
| Implicit | 990 | TLS assumed from the first byte of the connection |

> FTP is like mailing documents on a transparent conveyor belt. SFTP is a locked armored courier. FTPS is the same conveyor belt with an added sealed container bolted on.

### Remote access: Telnet vs. SSH

**Telnet** — a protocol for remote command-line access to another machine — operates on **port 23** and transmits everything in plaintext: commands, output, and credentials. An attacker capturing Telnet traffic can reconstruct the full session and harvest passwords.

**SSH** — Secure Shell — runs on **port 22** and provides an encrypted, authenticated remote administration channel.

- Supports **public key authentication**: the client holds a private key; the server holds the matching public key. No password crosses the wire, and breaking an asymmetric key pair is computationally infeasible at appropriate key lengths.
- Also enables **SCP** (Secure Copy Protocol — encrypted file copy), **SFTP**, and **port forwarding** (tunneling other protocols through the encrypted SSH channel).

> Telnet is a conversation shouted across an open room. SSH is the same conversation in a soundproofed booth with ID verification at the door.

### Email protocols

Email has three stages — submission, server-to-server transfer, and client retrieval — each with insecure and secure versions.

**SMTP** — Simple Mail Transfer Protocol — handles mail transfer between servers.

| Port | Role | Encryption |
|---|---|---|
| 25 | Server-to-server transfer | STARTTLS (opportunistic, not guaranteed) |
| 587 | Client mail submission | STARTTLS required |
| 465 | SMTPS — SMTP over TLS | TLS from connection start |

**IMAP** — Internet Message Access Protocol — lets clients access and manage messages stored on a mail server.

- Port **143**: plaintext. Port **993** (**IMAPS**, IMAP over TLS): always use this instead.

**POP3** — Post Office Protocol version 3 — downloads messages from server to client (simpler than IMAP).

- Port **110**: plaintext. Port **995** (**POP3S**, POP3 over TLS).

> Running email on unencrypted ports is like leaving every letter unsealed on a shared mail cart — anyone walking by can read it.

### Directory services: LDAP vs. LDAPS

**LDAP** — Lightweight Directory Access Protocol — queries and updates directory databases such as **Active Directory** (Microsoft's identity and authentication service). Standard LDAP runs on **port 389** in plaintext, meaning authentication credentials (including passwords in **bind operations** — the LDAP term for login requests) travel unprotected.

**LDAPS** — LDAP over TLS — runs on **port 636** and encrypts all directory traffic including authentication. Some environments use STARTTLS on port 389 as an alternative. Either way, plaintext LDAP must be prohibited, especially for authentication traffic.

> Querying an LDAP directory in plaintext is like shouting your Active Directory password across the office to log in.

### Network management: SNMP versions

**SNMP** — Simple Network Management Protocol — is used to monitor and manage network devices (routers, switches, etc.).

- **SNMPv1 and v2c**: authenticate using a **community string** (effectively a shared password) transmitted in plaintext with every message. Any attacker capturing traffic can harvest the community string and query or modify managed devices.
- **SNMPv3**: adds real authentication and encryption.

| SNMPv3 option | What it provides |
|---|---|
| Authentication | HMAC with MD5 or SHA verifies message origin |
| Privacy | DES or AES encrypts the message payload |
| **authPriv** mode | Both authentication AND privacy — the only mode permitted in secure environments |

> SNMPv1/v2c is like giving every network device the same master key and then printing that key on every request you send.

### Time synchronization: NTP and NTPsec

**NTP** — Network Time Protocol — synchronizes clocks across network devices on **port 123**. Accurate time matters for two reasons:

1. **Kerberos authentication** (the protocol Active Directory uses to verify user identities) requires clocks between client and server to be within **five minutes** of each other — clock skew beyond this threshold causes authentication failures.
2. **Log correlation**: if clocks drift across systems, reconstructing an attack timeline from multiple log sources becomes unreliable.

**NTPsec** — a security-hardened NTP implementation — supports authenticated NTP to prevent **clock manipulation attacks** (where an attacker feeds a system false time, potentially breaking authentication or corrupting audit logs). Internal NTP hierarchies (internal servers sync from a trusted external source; clients sync from internal servers) reduce exposure to external time-source manipulation.

> NTP is the shared clock on the wall every device trusts. If an attacker can move those clock hands, Kerberos locks everyone out and your logs become useless.

### VoIP protocols: SIP, RTP, and SRTP

**SIP** — Session Initiation Protocol — sets up and tears down voice/video calls. Unencrypted SIP uses **port 5060**; **SIPS** (SIP with TLS) uses **port 5061**.

**RTP** — Real-time Transport Protocol — carries the actual audio/video media stream. RTP itself is unencrypted.

**SRTP** — Secure Real-time Transport Protocol — encrypts and authenticates the media stream, protecting voice and video content from eavesdropping.

**DTLS** — Datagram Transport Layer Security — TLS adapted for UDP (a connectionless transport protocol). Used in **WebRTC** (the browser framework for real-time communication) to secure media streams without dedicated signaling infrastructure.

> SIP is the phone call setup; RTP is the actual voice. SIPS+SRTP means the setup AND the conversation are both sealed — using only SIPS with plain RTP is like locking the front door but leaving a window open.

### DNS security: DNSSEC, DoH, DoT

**DNS** — Domain Name System — translates domain names to IP addresses. Standard DNS runs on **port 53** (UDP for queries, TCP for large responses) in plaintext. Anyone monitoring traffic sees every domain a client resolves — revealing browsing and application activity. Plaintext DNS is also vulnerable to **cache poisoning**, where an attacker injects forged records into a resolver's cache to redirect clients to malicious systems.

**DNSSEC** — DNS Security Extensions — adds cryptographic signatures to DNS responses. Each DNS zone signs its records with a private key; resolvers verify signatures using the published public key, creating a chain of trust from the DNS root downward.

- Prevents cache poisoning by making forged signed records impossible.
- **Does NOT encrypt queries** — it provides integrity, not confidentiality.

**DoH** — DNS over HTTPS — sends DNS queries as HTTPS traffic on **port 443**, encrypting query content and making it indistinguishable from normal web traffic. Protects query privacy but makes DNS traffic invisible to network administrators.

**DoT** — DNS over TLS — sends DNS queries over TLS on **port 853**. Provides query confidentiality while remaining identifiable as DNS traffic, allowing network-level monitoring.

| Protocol | Port | Confidentiality | Integrity | Admin-visible |
|---|---|---|---|---|
| DNS (plain) | 53 | ✗ | ✗ | ✓ |
| DNSSEC | 53 | ✗ | ✓ | ✓ |
| DoH | 443 | ✓ | ✓ | ✗ |
| DoT | 853 | ✓ | ✓ | ✓ |

> Plain DNS is like asking a public librarian for a book title out loud — everyone nearby hears what you looked up. DNSSEC verifies the librarian isn't lying about which shelf it's on, but still doesn't whisper. DoH and DoT both whisper; only DoT uses a private room that security staff can still identify as the library.

### IPsec: IP-layer security

**IPsec** — Internet Protocol Security — adds security directly at the IP layer, below the application layer, making it work with any protocol running above it.

Two components handle different jobs:

| Component | Protocol # | Provides |
|---|---|---|
| **ESP** (Encapsulating Security Payload) | 50 | Encryption + authentication |
| **AH** (Authentication Header) | 51 | Authentication + integrity only (no encryption) |

**IKE** — Internet Key Exchange — negotiates security associations (the agreed-upon encryption parameters and keys for a session) on **UDP ports 500 and 4500**.

Two operating modes:

| Mode | What's encrypted | Use case |
|---|---|---|
| **Tunnel mode** | Entire original packet (payload + headers) wrapped in a new encrypted packet | VPN connections between networks |
| **Transport mode** | Payload only; original IP headers remain visible | Host-to-host security |

IPsec underlies many enterprise VPN solutions, including **L2TP/IPsec** (L2TP is Layer 2 Tunneling Protocol, which creates VPN tunnels but has no encryption of its own — it pairs with IPsec for security).

> IPsec in tunnel mode is like putting your entire original envelope — address label and all — inside a second sealed envelope.
