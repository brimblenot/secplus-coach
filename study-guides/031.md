## SQL Injection (SQLi)

**SQL injection** — abbreviated **SQLi** — is an attack where malicious SQL code is slipped into an input field, tricking the database into running commands the developer never intended. It's one of the most common and damaging web application vulnerabilities, and understanding it matters for both the exam and real-world defense.

---

### How SQLi works at its core

A normal login query looks like:
`SELECT * FROM users WHERE name = '[user input]'`

If a developer builds that string by **concatenating** — directly stitching — raw user input into the SQL text, an attacker can break out of the string early and inject new logic.

- Classic payload: input `' OR 1=1 --` makes the WHERE clause always true
- Result: the database returns every row — no valid credentials needed

> Think of it like a form that asks for your last name and you write: *"' OR 1=1 --"* — you've just talked the database into giving you the whole guest list.

---

### The three SQLi families

| Family | How results come back | Key variants |
|---|---|---|
| **In-band** | Same HTTP channel as the attack | Error-based; Union-based |
| **Blind** | No direct output — inferred indirectly | Boolean-based; Time-based |
| **Out-of-band** | Database opens a *separate* outbound connection | DNS/HTTP to attacker server |

**In-band SQLi** is the most straightforward because results travel directly back to the attacker over the same connection used to send the attack.

- **Error-based** — forces the database to emit a verbose error message (e.g., a divide-by-zero) that reveals database type, version, and table names
- **Union-based** — appends a `UNION SELECT` statement to the original query, piggybacking extra data from other tables; requires matching column count and data types

**Blind SQLi** is used when the application shows no database output at all.

- **Boolean-based** — sends true vs. false conditions and watches for behavioral differences (page loads vs. blank page); reconstructs data character by character
- **Time-based** — injects a delay function (`SLEEP` in MySQL, `WAITFOR DELAY` in MS SQL Server, pipe-receive-message in Oracle); a pause means the condition was true; timing is the side channel

**Out-of-band SQLi** — the database server initiates its own DNS lookup or HTTP request to an attacker-controlled server to exfiltrate data; used when in-band is blocked or unreliable.

---

### Authentication bypass

**Authentication bypass** is an immediately impactful SQLi technique where login is granted with no valid password.

- Attacker submits username: `admin --`
- The `--` is a **SQL comment delimiter** — it tells the database engine to ignore everything after it
- The `AND password = '...'` portion of the WHERE clause is commented out entirely
- The database authenticates on username alone

> Like crossing a bouncer who checks your name on the list but, thanks to a loophole you injected into his checklist, ignores the "must show ID" line.

---

### Beyond reading data

SQLi isn't just for reading — it can modify, delete, and even execute OS commands.

- **`xp_cmdshell`** — a stored procedure (a pre-compiled set of SQL commands) in Microsoft SQL Server that, when enabled, runs arbitrary shell commands under the database's service account
- **`LOAD FILE` / `INTO OUTFILE`** — MySQL syntax for reading and writing files on the server filesystem
- **SQLmap** — a widely available open-source tool that auto-detects injection points, fingerprints the database, and extracts data; it supports all SQLi types and automates privilege escalation

**Second-order (stored) SQLi** — malicious input is safely stored in the database on first insertion, then later pulled out and used in a *different* query without sanitization at that point of reuse; the attack fires on retrieval, not insertion.

---

### Defenses

**Parameterized queries** — also called **prepared statements** — are the primary and most reliable defense. The SQL structure is compiled by the database driver *before* user input is ever considered; input is bound as a separate data parameter, not interpreted as SQL syntax.

- **Why input sanitization alone isn't enough:** sanitization tries to scrub dangerous characters, but edge cases and encoding tricks can bypass it; parameterized queries structurally prevent user data from ever becoming executable SQL
- **Stored procedures** — pre-compiled SQL routines stored in the database — provide equivalent protection *when* they avoid building dynamic SQL strings internally
- **ORM frameworks** — **Object-Relational Mapping** tools like SQLAlchemy, Hibernate, and Entity Framework use parameterized queries by default, reducing developer error

Additional layered defenses:

- **Input validation / allowlisting** — reject values that don't match expected formats (e.g., non-numeric input in an integer field)
- **WAF** — **Web Application Firewall**, a filter that inspects HTTP requests and blocks SQL injection patterns before they reach the app
- **Least privilege** — application database accounts should have only the SELECT rights they need; no DDL (**Data Definition Language** — commands like `CREATE`, `DROP`, `ALTER` that modify database structure), no `xp_cmdshell`
- **Suppress verbose errors** in production to block error-based enumeration

---

### Recap

- SQLi injects malicious SQL into input fields; the `OR 1=1` pattern and `--` comment bypass are the signature tells
- Three families: **in-band** (error-based, union-based), **blind** (boolean, time-based), **out-of-band**
- Authentication bypass uses `--` to comment out the password check entirely
- **Parameterized queries** are the #1 defense; sanitization alone is insufficient
- Defense-in-depth = parameterized queries + least privilege + WAF + suppressed errors

### Exam flags

- **Parameterized queries vs. input sanitization** — know *why* parameterized queries are superior (structural separation of code and data vs. pattern-scrubbing that can be bypassed)
- **Identifying SQLi technique by payload** — `OR 1=1` (in-band), `admin --` (auth bypass), `UNION SELECT` (union-based), time-delay functions (time-based blind)
- **Second-order SQLi** — malicious input stored safely, executes later in a different query context
