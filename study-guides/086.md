## Vulnerability Remediation

Vulnerability remediation is the full lifecycle of handling a confirmed security weakness — from discovery through verified fix. This lesson matters because patching is just one tool; the exam tests whether you know the entire process, all the alternatives, and how to prioritize under real-world constraints.

---

### Remediation is more than patching

**Vulnerability remediation** is the complete process of responding to identified security vulnerabilities, covering every type of response available — not just installing a patch.

The main response options:

| Response | What it means |
|---|---|
| **Patching** | Vendor-supplied code fix applied to the vulnerable software |
| **Configuration change** | Fixing insecure settings (e.g., default credentials, open ports) |
| **Compensating control** | Reduces exploitability without fixing the root vulnerability |
| **Exception** | Temporary, approved deviation from the remediation deadline |
| **Exemption** | Long-term or permanent acceptance that the vuln won't be patched |
| **Risk acceptance** | Formal decision to tolerate the vulnerability with no additional controls |

---

### Patch delivery by platform

**Patching** — applying a vendor-supplied update that modifies vulnerable code — is the primary and preferred fix for most known software vulnerabilities.

- **Windows:** **Windows Update** for individual machines; **WSUS** (Windows Server Update Services — a Microsoft tool for distributing patches to fleets of Windows machines) or **MECM/SCCM** (Microsoft Endpoint Configuration Manager — enterprise patch deployment and inventory) at scale
- **Linux:** Package managers **yum**, **dnf**, or **apt**; managed at scale with **Ansible**, **Puppet**, or **Chef** (configuration management tools — they automate applying consistent settings and updates across many servers)
- **Applications:** Browser auto-updates, office suite built-in update checks, server apps via vendor docs
- **Firmware:** Embedded software in network devices and hardware — applied manually through the device management interface

### The seven-step patch management process

1. **Identify** — monitor vendor advisories, **NVD** (National Vulnerability Database — NIST's public catalog of CVEs with scores and details), **CISA KEV catalog** (see below), and scanner reports
2. **Assess** — determine applicability, rate urgency via **CVSS score** (Common Vulnerability Scoring System — a 0–10 numeric rating of vulnerability severity), exploitability, and asset criticality
3. **Test** — non-production environment first; urgency scales test time (Critical/actively exploited → hours; Medium/non-critical → two weeks)
4. **Schedule** — coordinate maintenance windows; Critical/actively exploited patches are **fast-tracked** outside normal windows
5. **Deploy** — use automated tooling
6. **Verify** — rescan affected systems; confirm vulnerability is gone
7. **Document** — update change management system and vulnerability tracking records

Think of this like a surgery checklist: skipping "verify" is like a surgeon skipping the post-op X-ray to confirm no sponges were left behind.

### Remediation SLAs by severity

**SLA** (Service Level Agreement — a defined maximum time allowed between confirming a vulnerability and completing remediation):

| Severity | SLA Target |
|---|---|
| Critical + actively exploited | 24–48 hours |
| Critical, no active exploitation | 7 days |
| High | 14–30 days |
| Medium | 30–60 days |
| Low | Next quarterly patch cycle |

High-target industries (financial services, healthcare) typically use tighter timelines.

---

### Compensating controls when patching isn't possible

A **compensating control** reduces the risk of a vulnerability without actually fixing it — it makes exploitation harder or limits damage.

- **Virtual patching** — deploying a **WAF** (Web Application Firewall — a device/service that inspects and filters HTTP traffic) or **IPS** (Intrusion Prevention System — a network device that detects and blocks attack traffic in real time) rule that blocks known exploit traffic targeting the vulnerability, without touching the vulnerable app itself
- **Network isolation** — moving the vulnerable system to a subnet reachable only by authorized admins
- **Disable the vulnerable feature** — if the feature isn't needed for business operations, remove or disable it, eliminating that attack surface
- **Enhanced monitoring** — deploy **IDS** (Intrusion Detection System — monitors traffic and alerts on suspicious patterns) signatures for the known exploit technique to shrink attacker dwell time

Virtual patching is like putting a security guard at the door of a building with a broken lock — the lock isn't fixed, but an attacker still can't walk in unchallenged.

### Exceptions, exemptions, and risk acceptance

**Exception** — a *temporary* approved deviation from the remediation SLA, with a documented plan and future remediation date.

**Exemption** — a *longer-term or potentially permanent* acceptance that a specific vulnerability won't be patched, requiring documented compensating controls and explicit management sign-off.

Both require:
- Written justification (incompatible patch, no patch available, business continuity risk)
- Identified compensating controls
- Signed risk acceptance from appropriate authority (e.g., **CISO** — Chief Information Security Officer)
- A review date
- Entry in the **risk register** (an organizational document tracking known risks, their owners, and accepted levels)

**Risk acceptance** — a formal management decision to tolerate an unmitigated vulnerability with *no* additional compensating controls. Appropriate when remediation cost exceeds expected loss, exploitation is extremely unlikely in the specific environment, or the system is being decommissioned. Must be documented, signed, time-limited, and revisited.

Exemptions are never truly permanent — they must be reviewed and closed when the underlying constraint is resolved.

### Prioritization tools: KEV and EPSS

**CISA KEV catalog** (Known Exploited Vulnerabilities — a CISA-maintained list of CVEs confirmed to have real-world exploitation): treat KEV items as highest priority regardless of CVSS score, because attackers are *already* using them. Federal agencies must remediate KEV items within specified timeframes (typically 2 weeks for Critical/High, 6 months for others).

**EPSS** (Exploit Prediction Scoring System — a machine-learning model that outputs a 0–1 probability that a specific CVE will be exploited within the next 30 days): complements CVSS by differentiating between vulnerabilities that share the same severity rating. Two CVEs both scored CVSS 7.5 but with EPSS 0.02 vs. 0.85 should be prioritized very differently. Risk-based vulnerability management combines CVSS + EPSS + asset criticality + exposure for a full picture.

### Configuration remediation

Not all vulnerabilities come from unpatched software. **Configuration remediation** fixes insecure settings:
- Changing default credentials
- Closing unnecessary open ports
- Removing unnecessary services
- Disabling unencrypted management protocols
- Applying security headers

Configuration vulnerabilities are identified by scanning against **CIS Benchmarks** (Center for Internet Security — consensus security configuration standards) or **DISA STIGs** (Defense Information Systems Agency Security Technical Implementation Guides — DoD configuration hardening standards), then verified by rescan.

---

### Verification and metrics

**Remediation verification** — re-scanning the patched or reconfigured system with an authenticated scanner to confirm the vulnerability no longer appears. Retain scan results as audit evidence.

Key **vulnerability management metrics**:
- **Mean time to remediate** (per severity level) — are SLAs being met?
- **% Critical/High remediated within SLA** — compliance with top-priority requirements
- **Open vulnerability count by severity over time** — is posture improving?
- **Patch compliance %** — fraction of systems fully patched
- **Exception/exemption count** — flags resource constraints or legacy system problems

---

### Recap

- Remediation spans patching, configuration changes, compensating controls, exceptions, exemptions, and risk acceptance — not just patching
- Patch management follows a seven-step process: identify → assess → test → schedule → deploy → verify → document
- SLAs scale with severity: Critical/active exploitation = 24–48 hours; Low = quarterly
- CISA KEV = confirmed real-world exploitation → highest priority regardless of CVSS; EPSS = predicted probability of exploitation within 30 days
- Exceptions are temporary; exemptions are long-term; risk acceptance has no compensating controls — all three require signed documentation and periodic review

### Exam flags

- **Remediation SLA timelines** — know the severity-to-timeframe mapping, especially Critical actively exploited (24–48 hours)
- **CVSS vs. EPSS vs. KEV** — know what each measures and when to use each for prioritization
- **Exception vs. exemption vs. risk acceptance** — know what distinguishes them (temporary/long-term, with/without compensating controls)
