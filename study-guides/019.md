## Certificates (Domain 1)

Digital certificates are how public-key cryptography gets tied to real-world identities — servers, people, software. Without them, you can't know whether the public key you received actually belongs to who you think it does, opening the door to man-in-the-middle attacks.

---

### The X.509 certificate format

**X.509** is the international standard format for digital certificates — every TLS/SSL certificate on the internet follows it. Think of it as a structured data file with defined fields, all covered by a CA's digital signature.

Key fields:

| Field | What it holds |
|---|---|
| **Subject** | Identity of the cert owner (domain name, org name, etc.) |
| **Issuer** | The **CA** — Certificate Authority — that signed it |
| **Serial Number** | Unique ID assigned by the CA; used in revocation lists |
| **Validity Period** | "Not Before" and "Not After" dates |
| **Public Key** | The certified public key + algorithm |
| **Extensions** | SANs, Key Usage, CRL Distribution Points, etc. |
| **CA Signature** | Covers all fields; verifiable with the CA's public key |

> Think of an X.509 cert like a government-issued passport: your photo (public key), your name (Subject), the issuing country (Issuer), and an expiry date — all stamped with an unforgeable seal (CA signature).

---

### Certificate validation levels

**Validation level** describes how thoroughly the CA verified the applicant's identity before issuing the cert.

| Level | What CA Verifies | Speed | Use Case |
|---|---|---|---|
| **DV** (Domain Validated) | Domain control only (email, URL token, or DNS record) | Minutes | Any HTTPS site |
| **OV** (Organization Validated) | Legal org name, address, requester authority | Days | Business/B2B sites |
| **EV** (Extended Validation) | Full legal, physical, and operational existence per CA/Browser Forum rules | Longest | Banks, government |

- DV is free/cheap and automated — enables widespread HTTPS, but shows no org info.
- OV shows the org's verified name in cert details.
- EV used to trigger a green bar in browsers (now removed from most), but still carries the strongest identity assurance.

> DV is like a gym keycard — proves you paid for access, says nothing about who you are. EV is like a notarized ID check before entering a secure facility.

---

### Wildcard and SAN certificates

**Wildcard certificates** use an asterisk (`*`) in the leftmost domain position (e.g., `*.example.com`) to cover any single-level subdomain — `www.example.com`, `mail.example.com`, etc.

- Does **not** cover the apex domain (`example.com`) unless explicitly listed as a SAN.
- Does **not** cover deeper levels (`sub.sub.example.com`).
- **Risk:** one compromised private key exposes every subdomain.

**SAN** — Subject Alternative Name — certificates list multiple fully qualified domain names, IPs, or email addresses in one cert. Modern TLS uses the SAN field for hostname verification; the Common Name field is deprecated for this purpose.

- A single SAN cert can cover dozens or hundreds of domains.
- Can mix wildcards and specific hostnames.

> A wildcard cert is like a master key that opens every door on one floor. A SAN cert is like a keyring with individually cut keys for many different buildings.

---

### Specialized certificate types

**Code signing certificates** are issued to developers/orgs to digitally sign executables and packages. The OS verifies the signature at install time — Windows shows the org name instead of "Unknown Publisher." Kernel-mode drivers on 64-bit Windows 10+ must use **EV code signing certs** submitted through Microsoft's Hardware Dev Center.

**S/MIME** — Secure/Multipurpose Internet Mail Extensions — certificates bind a user's email address to their public key, enabling two things in email clients like Outlook or Apple Mail:
- **Digital signing** → authentication + non-repudiation
- **Encryption** → confidentiality using the recipient's public key

**Client certificates** authenticate users or devices to servers (the reverse of the usual flow). Used in enterprise VPNs, mutual TLS, and smart card/PIV deployments. The private key never leaves the device and cannot be phished — stronger than passwords.

**Server certificates** authenticate servers to clients during the TLS handshake — the browser checks CA trust, domain match, and validity period.

---

### Certificate hierarchy: root, intermediate, and CSR

**Root certificates** are self-signed — the issuer and subject are the same entity, signed by its own private key. They're trusted because they're pre-installed in OS/browser trust stores by the vendor. Root CAs stay **offline** to protect their keys; compromise of a root CA would allow fraudulent certs for any domain.

**Intermediate certificates** sit between the root CA and end-entity certs (server, code signing, etc.). Intermediate CAs do the day-to-day signing, keeping the root CA offline. If an intermediate CA is compromised, only that CA's cert needs revocation — the root and other intermediates are unaffected.

**CSR** — Certificate Signing Request — is how an applicant asks a CA for a cert:
1. Generate a public/private key pair.
2. Create a CSR containing the public key and identity info, signed with your private key.
3. Submit to the CA — **the private key is never sent**.
4. CA verifies identity, signs the CSR → finished certificate.

> The CSR process is like mailing a locked padlock (your public key) to a notary (the CA). They stamp it and send it back — they never needed your key to the lock.

---

### Recap

- **X.509** is the standard cert format; key fields include Subject, Issuer, Serial Number, Validity, Public Key, and CA Signature.
- Validation levels DV → OV → EV represent increasing identity assurance; DV verifies domain control only.
- Wildcard certs cover one subdomain level only; SAN certs cover multiple explicit domains; both have specific scope limits.
- The root CA stays offline; intermediate CAs do live signing to limit root key exposure.
- The private key is **never** submitted in a CSR — the CA certifies the public key only.

### Exam flags

- **Wildcard scope rules** — what `*.example.com` does and does not cover (apex domain, deeper subdomains).
- **DV vs. OV vs. EV** — what each level verifies and how long it takes.
- **Root vs. intermediate CA roles** — why root CAs stay offline and what happens if an intermediate is compromised.
