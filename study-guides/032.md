## Cross-site Scripting (XSS)

XSS is one of the most common web vulnerabilities — and one of the most misunderstood. This lesson covers how injected JavaScript reaches victims, why the browser can't stop it on its own, and what actually fixes it.

---

### Why the browser can't tell good scripts from bad

**XSS (Cross-site Scripting)** — abbreviated XSS, not CSS, to avoid confusion with Cascading Style Sheets — is an attack where malicious JavaScript is injected into a trusted website and then executed by other users' browsers.

The key reason it works: the **same-origin policy** — the browser rule that prevents scripts on one domain from accessing resources on another — provides **no protection here**. The injected script is already *inside* the trusted domain. The browser sees it as legitimate.

> Think of it like a forger who sneaks counterfeit bills into a bank vault. When you later withdraw money, you get the fake — the bank handed it to you, so you trust it.

---

### The three XSS types

Each type differs in *where the script lives* and *how it reaches the victim*.

#### Reflected XSS (non-persistent)
**Reflected XSS** occurs when user-supplied input is included directly in the server's HTTP response without being stored. The script is "reflected" back to whoever clicked the crafted link.

- Attacker puts malicious script in a URL parameter (e.g., a search query)
- Victim clicks the link (delivered via phishing email, SMS, social media)
- Server echoes the script back; victim's browser executes it
- Transient — only hits users who follow the specific link

#### Stored XSS (persistent)
**Stored XSS** occurs when the malicious script is saved permanently on the server — in a database, log, or CMS — and served to every user who loads that page.

- Common injection points: forum comments, product reviews, profile fields
- No individual targeting needed — every visitor is a victim
- On viral platforms, a self-reposting payload can spread across the entire user base
- Considered the **most dangerous** variant

#### DOM-based XSS
**DOM-based XSS** — where DOM (**Document Object Model**) refers to the browser's in-memory representation of the page — occurs entirely in client-side JavaScript. The server never sees the malicious input.

- A client-side script reads from a browser-controlled source (e.g., URL fragment) and writes unsanitized data directly into the DOM
- Server-side filtering **cannot catch it** — the server isn't involved
- Requires auditing all client-side code that reads browser inputs and writes to the page

| Type | Script stored on server? | Server processes input? | Who's affected? |
|---|---|---|---|
| Reflected | No | Yes | Only users who click the crafted link |
| Stored | Yes | Yes | Every visitor to the page |
| DOM-based | No | No | Users who load the manipulated URL |

---

### What attackers do once the script runs

- **Session hijacking** — script reads `document.cookie` to steal the session token, replays it to impersonate the victim
- **Credential harvesting** — injects a fake login form that forwards credentials to the attacker
- **Keylogging** — captures every keystroke on the page
- **Drive-by download** — redirects the browser to a malware-serving site
- **BeEF** (**Browser Exploitation Framework**) — a tool that lets attackers maintain persistent control over a "hooked" browser, issuing commands long after the initial compromise

**Real-world example:** A researcher found a reflected XSS flaw on Subaru's vehicle management site. Auth tokens never expired, so stealing one via XSS granted permanent access to a victim's vehicle and account. Subaru fixed it before public disclosure.

---

### Defenses

**Output encoding** (also called output escaping) is the **primary defense**. Every time user-supplied data is written into an HTML page, special characters (`< > & " '`) must be converted to their safe HTML entity equivalents before rendering. The encoding rules differ by context (HTML body vs. attribute vs. JavaScript vs. URL), so encoding must happen at the exact point of output.

- PHP: `htmlspecialchars()`
- .NET: `HtmlEncoder.Encode()`
- JavaScript: **DOMPurify** — a library for sanitizing HTML fragments

**Content Security Policy (CSP)** — an HTTP response header that tells the browser which script sources are permitted — blocks inline scripts and scripts from unauthorized domains even if injection occurs. Valuable safety net when encoding is imperfect.

**Input validation** rejects input that doesn't match expected patterns before storage. Useful, but *not sufficient alone* — context varies and rules are hard to make exhaustive. It supplements, never replaces, output encoding.

**HttpOnly cookie flag** — a cookie attribute that makes session cookies inaccessible to JavaScript — directly neutralizes the most common XSS goal (session theft via `document.cookie`).

**SameSite cookie attribute** — a cookie setting that restricts cookies from being sent in cross-site requests — reduces related cross-site risk.

---

### Recap
- XSS injects JavaScript into trusted pages; the same-origin policy **does not** stop it because the script is already inside the trusted origin
- Three types: **reflected** (link-triggered), **stored** (server-saved, hits everyone), **DOM-based** (client-side only, server can't filter it)
- Stored XSS is the most dangerous; DOM-based XSS bypasses server-side filters
- **Output encoding** is the primary fix; **HttpOnly** blocks cookie theft; **CSP** blocks unauthorized script sources

### Exam flags
- Be ready to distinguish all three XSS types and explain why DOM-based bypasses server-side filtering
- Know that the **same-origin policy does not prevent XSS** and why (script is already inside the trusted origin)
- Identify **output encoding** as the primary control, with HttpOnly and CSP as key supplementary defenses
